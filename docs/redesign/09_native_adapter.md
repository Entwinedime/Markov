# 后续可选阶段 原生控制器适配

状态：未来扩展，不进入首轮实现与验收。前提是[统一接口](03_control_interface.md)与轻量控制器闭环已经稳定；是否开展取决于实际收益和维护成本。

本章是可选的“复用原生控制器”能力，不是接入另一个框架的常规步骤，也不属于当前模板生产中间层。默认跨框架路线仅调整子图获取与模板化，由共同轻量控制器消费统一模板。只有用户明确需要原生调度行为、且收益与边界已经确认时，才另行开展本章；不能以本章为理由把框架私有调度或 KV 状态机混入当前模板接口。

## 1. 为什么保留这条路线

原生代码能够复用框架已有的动态调度逻辑，但直接运行它并不能自动得到正确模拟时间。真实设备执行、返回对象、CPU 时延、timer 和后台线程都可能与控制逻辑耦合。

因此先用轻量实现验证共同接口；以后由 NativeControllerAdapter 替代控制器实现，复用既有模板、成本模型和执行核。它不是再增加一套正式预测产品，也不是让首轮以适配原生运行时为前提。

共同基础先按[统一流程](01_system_framework.md)和[语义插桩合同](04_collection_templates.md)建立：原生框架提供真实工作与模板来源，轻量控制器先在给定节点耗时下验证动态展开，节点模型随后接入。未来原生适配消费相同动作、端口、模板与状态合同，不另建一套采集语义或依赖原生代码来完成当前结构阶段。

## 2. 适配职责

| 原生行为 | 接口映射 | 需要验证的条件 |
| --- | --- | --- |
| 提交 prefill/decode/传输等工作 | invoke_step | 参数可取得，真实执行被可靠截获 |
| 检查/等待完成 | 完成事件或只读状态视图 | 不依赖真实设备 event 或忙轮询 |
| 读取时间、设置 deadline | 统一模拟时钟与 timer | 原生墙钟不会偷偷影响决策 |
| 更新请求、batch、缓存 | 原生控制器私有状态 | 不与执行核重复维护业务状态 |
| 需要执行返回值 | 声明的结果元数据 | 不虚构会影响路由的张量内容 |
| 后台 worker 推进 | 明确唤醒与执行边界 | 原生线程不会绕过模拟时间独立推进 |

适配器保留框架专属对象，核心只接收统一动作和事件。输入/输出处理、组批和提交等 CPU 工作仍绑定性能单元；原生函数在宿主机上的耗时不能未经说明直接作为目标 CPU 成本。

## 3. 开展顺序

1. 对一个框架选择一条简单路径，列出所需拦截点与状态依赖。
2. 仅接通统一接口已表达的步骤，验证设备替换、完成回传和时间一致性。
3. 与轻量控制器在共同支持范围下比较决策序列，差异说明来源，不要求所有近似都一致。
4. 检查第二框架是否可复用相同接口，记录必须新增的适配点与原因。
5. 若需要大量复制框架内部状态、改核心或接管 OS 线程，重新评估收益，不以“原生”名义隐藏成本。

## 4. 完成条件

通过同一用户入口选择控制器，模板与性能数据可复用，框架对象不泄漏到核心；没有真实 target workload 或 target 实测进入预测。决策与时间准确性分别验收。

无法隔离的路径报告不支持。适配范围与具体框架实现绑定，不宣称一次接入即可覆盖所有版本和机制。首轮轻量控制器继续可用，不因这项可选扩展而延期交付。
