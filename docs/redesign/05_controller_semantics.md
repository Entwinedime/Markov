# 阶段五 轻量控制器、模板变换与支持判断

当前实现状态与退出条件统一见[实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)。本文定义轻量控制、资源身份、有限变换和结构支持合同；S3/S4 未验收前不进入节点成本建模。


统一流程内的模板及其必要交互是唯一建模对象；模板外服务排除，不以原生进程全事件一致作为验收目标。支持条件属于模板及有限变换规则，静态筛选与实际实例化共用依据，不维护样本黑名单。调度器不解释模板来源；外围装配也须遵循公共适配接口。完整推进纪律见[工程约束](engineering_constraints.md#14-建模范围与开发粒度)，当前任务只在实施计划维护。

## 2026-10-10 目标展开与支持判定

每个 configuration × request workload 组合独立维护控制与执行状态，共享只读模板和适用成本。目标配置决定实现与有限变换，request 序列和完成事件决定调用顺序、次数及参数。源配置提供依据，不决定目标控制路径。

到达/组批/迭代变化由控制器组织；结构保持的参数或身份变化由映射处理；实现分支、通信或拓扑变化由明确结构规则或另一变体处理。规则写明前提、修改节点/边、端口和资源映射及不支持域，不因成本可查询就假定结构成立。内部语义区域承担局部变换，五类流程 block 保持稳定控制合同。

候选按来源、请求人数、完成/释放分支、shape 参数域及结构规则逐步资格化，通信在同批全部 rank 完成局部资格后检查。所有候选失败时，报告实际走得最远的阶段及其拒绝原因；不按错误字符串或观测/规则类别猜测优先级。已有完成分支但缺少长度变换属于规则缺口，不能被较早的不同完成分支候选改报为缺采。诊断排序不放宽候选条件，也不重试已写入执行图的装配失败。

Prefill/Decode 的局部变换以具体模型结构中的语义区域为定位依据，例如某层的 attention 或 MLP，再映射到其实际执行子图。模型模块层级不保证 kernel 边界一致；融合跨界、共享工作及异步端口需要保留，不能按模块名称机械拆图。重复层复用定义时仍生成独立目标层实例与依赖。

跨批 host 等待已按同步对象与目标前沿修复：历史目标图的 24 条缺失关系，在当前非 overlap 主线对照中全部补齐。独立核对匹配 180 次同步，并沿实际 completion_join 汇合边确认全部 168 条前沿关系；新增的其余关系也有同 stream、先提交后同步的原生依据。此案例已用于修正，属于开发证据，不作为未见 workload 泛化验收；源时钟、完整结构与其他变换资格仍待完成。

## 空调度决定与等待请求

Idle 表示一次真实的空调度决定，不是零耗时占位，也不等于整个服务进入空闲。当前容量清理路径的顺序为：上一请求 Published 释放逻辑槽位/页 → Schedule 先看到仍关闭的准入入口 → update 过滤掉已经结束的 running 成员 → 清除容量标志 → 空返回的 Selected 完成 → 下一轮 Schedule 才能接纳等待请求。不得提前清除标志、跳过这次决定，或重复释放已归还资源。

空决定只有 Schedule/Selected，不产生 Prepare、模型计算和 Publish。Selected 锚定该次原生 Schedule 的返回；没有 Prepare 时不能沿用“子 Prepare 开始”的选择端口。源 batch_id/phase 保持 null，内部用 Idle，跨调用按已有 schedule 顺序和实际依赖衔接，不编造批号。

生产端还记录 transition_resets_latch：pending 过滤删除任一成员时，原生前缀在准入前无条件清除旧容量标志。因此过滤成员、运行/待合并人数和 merge 完全相同时，旧标志差异不要求另一份前缀；保留所有设备过滤节点与依赖。该判断只投影匹配输入，不修改目标状态，也不放宽过滤成员差异。

待区分的两个清理入口是 pending prefill 在 transition 中被清空，以及 running decode 在 update 中被清空。前者可能继续准入并选出新 Prefill，不能看到空过滤就直接判为 Idle；后者在本轮准入已经结束后返回空结果。update 清空路径在内存检查与比例衰减之前返回，不可复制普通非回退 Decode 的完整 update 工作。

有等待请求时，原生 on_idle 的 is_fully_idle 检查立即返回，不重置准入比例。只有系统真正无等待/活跃工作时才进入空闲维护；该维护不属于 get_next_batch_to_run 模板，不能把它并入一次容量清理。当前 modeled 范围不能据此宣称已预测整段后台维护或轮询开销。

生产端按实际 update 区域识别更新调用，而不由 Decode phase 推断。普通 Decode 必须有一次更新过滤；Idle 可以没有 update，也可以有一次结果清空的更新。后者仅在单线程纯 CPU 区域下授予 running_update_region，目标同样必须清空非空输入；不允许用此参数域删除更新调用或替换为非空 Decode，节点和依赖全部保留。

复用资格必须同时覆盖空返回、过滤归属、入口/退出状态、CPU/等待、端口和外部依赖。历史 Idle 记录可作为机制与端口证据；缺失的准入、区域或 worker 事实保持未知，不能补默认值后当作当前合格模板。当前证据与待办见实施计划，不为此添加旧格式兼容执行路径。

## 目标请求池槽位

轻量控制器在现有 Progress 中保存请求槽位，空闲逻辑槽采用 FIFO，初始化为 1..capacity，0 保留为 padding。普通 prefill 在形成动作时预留槽位，decode 复用同一槽位；RequestSlice 把该身份传给同批四个动作，诊断中的 pool_slot 是目标身份，不从源请求复制。

预留是非 overlap 控制下的资源承诺，不能被另一批复用；设备上的写表/数据可见性仍由 Prepared、DeviceDone 等执行依赖决定，不把控制器调用时刻当成 NPU 写入完成。请求仅在 Published 完成且达到输出长度时归还槽位到空闲队尾。完成前到达的请求保持 Waiting，不能提前拿到尚未释放的身份。

槽位所有者仍只有控制器 Progress，BatchInput 是本次动作快照；没有新增状态服务、第二套时钟或全局映射。请求槽位、KV 页和页表已有参数交接，完整操作数、数据流和跨请求泛化仍需逐项资格化。

## 目标 KV 页身份

主线冷缓存、无共享前缀、无 overlap、非分离部署使用逻辑页身份：页 0 为 padding，空闲页初始为 1..floor(max_total_tokens/page_size)。Progress 持有每个请求的页列表；每次动作预留 ceil((context+input)/page_size) 所需的新增页，已有半页继续使用。准入使用生产端提供的完成次序预算，旧的完整输出预约已删除。预算与实际页所有权分开；进入动作前核对真实新增页需求，不足时返回 kv_retraction_not_implemented。机制和未验证范围见[准入策略](sglang_template_relations.md#准入策略与内存压力)。

非分块 Prefill 的输入预算在接纳请求后扣除，按页对齐计量；达到或越过预算后停止加入后续请求。它是结束组批的阈值，不是当前请求的硬长度上限。KV 容量判断独立进行，正向原生准入等价仍待真实策略资产验收。

准入关闭状态由控制器唯一维护。人数或 KV 准入失败后保持关闭，后续 Schedule 发现 pending Prefill 成员减少、接管非空新 Prefill，或过滤运行批次造成成员减少时才重新开放；非空批次合并保留原状态。Published 释放逻辑资源不直接重新开放准入，防止提前改变原生“先准入、后过滤”的决策顺序。KV 失败谓词现使用有效策略预算；这些状态和公式已编码，尚未独立验证完整原生准入一致。

RequestSlice.kv_pages 是本次计算结束前所需页的动作快照，BatchInput.free_kv_pages 是本次准备前的空闲页数。空闲队列为该数量的唯一来源，删除按已发布 token 再推算已用页的并行逻辑。预留期间不会再调度第二批，设备写入完成仍依赖实际端口，不把页身份预留当作 KV 数据已经就绪。

Published 完成且请求结束时，将其逻辑页归还统一 FIFO 队尾；分配从队首取出。控制器不复制原生 Prefill/Decode 的排序、分组和前插顺序，无共享前缀保证页所有权不重叠。原生 free/group/concat/unique 等工作及依赖仍保留在模板中，不能因控制状态简化而删除或改成零耗时。

逻辑页只在请求存活期间保持身份：不同活跃请求不别名，同一请求原有页不变，新增页数和空闲容量由长度决定。allocation、page table、attention/cache-write 与 release 统一使用同一动作快照。与原生验证对齐时按请求生命周期核对页身份双射和页内偏移，不要求全运行页号逐字相等；物理空闲队列顺序及地址敏感成本不由此建模。当前 need_sort=false、无共享/迁移的分支条件以页数和容量为依据；地址相关布局选择、分离部署延迟合并、共享缓存与异步回收仍不支持。

这里的归还是控制器可见的逻辑状态更新，不把 Published 当作设备 free_pages 张量已经计算完成。原生 free 可以提交页拼接后返回，后续分配仍须依赖该设备结果；目标图保留这种依赖，不能把逻辑页可预约误解为所有消费者可立即执行，也不为等待设备归还而人为推迟业务发布。

现有分组释放资产已核对这一区别：4 个最终归还节点都没有到 Published 的依赖路径；前一次归还到后续复用页的 6 个分配结果节点均有路径。目标 kv_release 描述与完成请求的槽位、页集合及空闲页计数一致。证据在 data/redesign/s3-grouped-release/release_audit.json。这只验证当前调用序列中的关系，不替代跨请求重组后的依赖资格；不能假设所有新组合天然保留该路径。

当前主线s4-runtime-wait-main已补充核对：两配置10/12个释放结果节点的页集合匹配完成请求；有后续新页分配的8/10个节点均有到下一分配kernel开始的路径，均不要求释放完成先于自身Published。新来源末次发布后的Cast/Concat尾部属于这一异步释放，不能因它们不在Published的前驱闭包中就补同步。证据见release_dependency_verification.json；范围仍限于这组开发请求与配置。

这里产生的是模拟目标的页身份，不要求等于预热后源运行的具体分配顺序。当前快照已用于 attention/cache-write 的有效页、prefix 末槽和连续写入范围，仍未覆盖所有准备/请求表 kernel 的 block table、last_loc 与 out_cache_loc，跨页扩展和释放后再利用仍需正式输入证据；不能据此声称完整地址语义通过。

## 1. 轻量控制器负责什么

按标准流程消费到达、完成和 timer 事件，维护请求、批次和已支持缓存状态，决定调用哪些模板。初期实现一套简单、明确的准入与组批规则，再按真实需要增加机制。具体规则必须和所声明的框架运行方式对应，不能用一个泛化名字声称精确复现两个框架。

流程动作具有输入、工作职责、完成端口、状态效果、参数和适用条件。控制器选择动作及参数，模板产生内部节点/依赖，执行核负责资源与唯一时钟，端口完成后由唯一业务状态维护者提交效果。控制器不直接修改图，不把 CostProvider 查询结果当成是否执行合法工作的决策。

复用 base 的流程骨架、步骤关系和模板；按目标状态重新决定批次成员、循环次数、工作量及已支持分支。base 的调度顺序、命中结果和等待时长不直接复制到 target。

能力按机制定义：批次上限、prefill 分块、KV 预算、缓存命中、预取 deadline 等逐项加入；不用配置 id、实验名称或固定矩阵格数分支。涉及框架特有规则的实现独立于共享事件核。

### 首个闭环的规则与近似

S1 已选择 SGLang 的 FCFS、无缓存/分块/overlap 的首条路径；下表固定轻量规则。入口快照、保守 KV 预约和同刻顺序作为明确近似，仍须 S3/S4 实机比较，不宣称就是两个框架的默认 scheduler。KTransformers 的原生差异与取证要求见[框架路径](framework_paths.md)。

| 决策 | 首个闭环方案 |
| --- | --- |
| 请求次序 | 按到达顺序进入队列，同刻使用 workload 声明顺序 |
| 准入 | 在目标的请求/token/KV 预算内准入，容量不足等待完成释放 |
| 批次 | prefill 与 decode 分开；每次在明确调度边界按预算形成批次 |
| 选择 | 有可准入 prefill 时优先处理；满批 decode 中部分请求完成后，先按原生压缩顺序推进一次剩余 decode，再检查新准入 |
| 并发 | 每副本先限制一个在途模型批次；模板内部保留 CPU/NPU 异步和必要重叠 |
| 结束 | 完成用户指定生成步数并经过已计时的完成处理后释放占用 |
| 未覆盖机制 | 初期不自动支持混合批次、抢占、投机执行、未采集缓存分支 |

只有真实配置对应这套规则，或结果明确声明并验证了该控制近似，才可报告对应范围的预测。若框架无法提供可比较部署，就调整首条流程或实现相应规则，不能靠修改目标实测条件掩盖差异。

当前实现已核对原生先准入、再 filter_batch 的顺序，某次三请求 base 的 phase/成员/context 与原生一致；另一真实 base 出现首次合批差异，控制资格尚未收口。TemplateBank 保留 source_call 与子调用树，生成新的模块身份、参数和端口；相同 token 条件使用对应源布局；未匹配时返回 internal_shape_transform_not_implemented，不再只改模块输入 shape。模型、TP、后端和 dtype 固定。当前缺成本时保留四步模块工作并返回 needs_data；改变到达计划会生成不同批次。这些是局部证据，不证明内部节点、kernel 布局、异步依赖或所有规则正确。

成员变化使用同一组 BatchFilter/BatchMerge 值合同。控制器在过滤 pending_prefill 后、追加到 running_members 前记录合并左右人数，再执行最终 running 过滤；合并人数不从最终计算请求数反推。空侧直接接管不会产生合并操作。该快照随批次动作传递，设备成员变换只在 Schedule 实例中应用；当前来源与参数资格见[批次合并设计](04_collection_templates.md#批次合并的左右成员与布局)，不把局部 Concat 关系当成任意合并路径已经支持。

## 2. 模板合同与语义变换

| 模板内容 | 合同 |
| --- | --- |
| 步骤及来源 | 对应标准步骤、原生实现、base 子图实例与上下文 |
| 入口/出口 | 每条跨模板依赖的含义，不只保留整个子图起止点 |
| 参数 | shape、token/KV、批次、页/字节、rank 等值的来源和单位 |
| 结构与效果 | 节点、依赖、资源需求及在各出口触发的业务效果 |
| 允许变换 | 可修改项、条件、重建依赖的方法和不支持项 |
| 节点时延入口 | 执行节点可接收给定耗时；性能单元及成本类型映射在结构资格后确定 |
| 范围 | 覆盖步骤、排除时间及控制近似 |

实例化产生独立工作身份，不修改源 DAG。变换作为一个原子操作完成工作量、依赖和端口调整；成本查询在合法结构生成后进行。

请求、batch、指针和绝对时间属于源实例，不固化为模板调度结果。参数映射明确区分模型固定量、用户输入、批次聚合、状态和实现布局，并落实到具体节点属性；更新模块的 BatchInput 不等于内部节点已变换。模板只在已声明实现与结构域内复用，必要变体必须有真实来源或明确改写依据。

### 有限规则如何定义

| 变化类别 | 负责方与规则 | 需要保留的依据 |
| --- | --- | --- |
| 调用顺序、次数、成员变化 | 控制器按目标状态选择和调用模板 | 准入/组批/终止规则、动作参数和完成反馈 |
| 结构保持的参数变化 | 模板将参数重绑定到节点 shape、布局和工作量 | 参数来源及映射、结构成立的范围、端口和资源不变量 |
| 结构变化 | 选择已观测变体，或显式增删/复制节点并重建依赖 | 原生实现分支或已定义规则、变化节点/边、rank/资源和端口处理 |

每条规则写清前提、修改对象、参数关系、依赖/端口的处理和不支持范围。插入通信时明确位置、collective、rank 与拓扑；这些是后续 TP 能力条件，当前固定 TP 不提前实现。规则数量按主线真实需求增加，不建通用图改写语言或任意子图生成器。

batch 或 context 改变时先判断执行结构是否保持。若原生 shape 分支切换实现，则选择合法变体或已有改写；缺变体为观测缺口，缺机制为未支持。不能只改 shape 字段就沿用旧结构，也不能从单次 trace 推断未出现路径。

| 变化例子 | 可以支持的前提 | 不能假设 |
| --- | --- | --- |
| 批次/token 数变化 | 参数来源明确，模板分支与实现仍适用 | 仅乘比例即可处理任意 batch |
| KV 长度变化 | attention 工作量及布局可构造 | base 测得的一次 attention 通用 |
| TP 变化 | 分片维度、rank 布局、collective 类型/位置及拓扑均有规则 | 所有 shape 除以 TP、成本同比缩小 |
| 缓存容量变化 | 控制器能表达命中/淘汰，所有可达动作有模板 | base 无淘汰则 target 也无淘汰 |
| 新后端、量化或卸载路径 | 新模板或已定义变换、对应成本和控制规则 | 仅换一个配置字段即可泛化 |

这些是能力条件示例，不是当前已实现列表。

### 资源工作撤销与区域替换

资源端口描述目标工作对线程、设备流和完成事件的要求。来源 lane 和时间戳只提供证据，不能决定目标是否仍在该资源上提交工作。

| 资源变化 | 依赖与状态合同 |
| --- | --- |
| 两边都使用 | 按已资格化资源角色映射入口/出口，替换内部工作，保留区域外工作及依赖 |
| 目标不再使用 | 删除该区域的实际服务及提交关系；保留资源的先前提交前沿，不能把“无新工作”改成“资源没有历史” |
| 目标新增使用 | 必须有工作来源及该资源的目标入口/出口关系；没有前序提交、完成消费者或依赖依据时拒绝 |

撤销工作不能仅删除 kernel、把旧耗时设为零，或保留一个伪设备任务。串行资源可在端口资格成立时用纯顺序边连接原先的外部前驱与后继；这条边不计服务成本，也不表示新提交。其他资源上的 CPU 调用、外围区间和业务完成效果需分别保留。

外部消费者分开处理：资源顺序依赖接回仍存在的前序工作；设备完成消费者必须改接到仍实际需要的目标完成集合；显式 wait 若保留，仍等待此前的真实提交。不能把所有完成依赖统一改成 CPU 返回，不能因撤掉本区域的设备工作而删除整个 serving 步骤的完成端口。外部依赖指向未暴露的内部事件时拒绝变换。

图装配仅以保留节点、插入节点及资格化导出更新资源前沿，没有新导出的资源保留原前沿。来源模板中存在某条 lane 不构成更新依据。该项已落实到 TemplateAssembly。整区域规划器现允许 donor 资源为来源资源的子集：共同资源映射端口，撤掉的资源仅添加 entry→exit 的线程/设备流顺序边，不插入服务。前提是两边切口已通过资源端口资格，跨区域只存在已配对的顺序边；跨模板的 thread_order/stream_order 使用生产端已识别资源参与同一端口配对，原连接保留；对向外导出的 native_host_wait，仅在它引用该设备流的唯一终止工作，且完成点与流出口相同或通过唯一 completion_join 相连时接受；向内导入的完成接口及未暴露内部端点仍拒绝。撤掉设备工作时保留这些边界身份，用顺序边和已证明的汇合关系重接，不产生设备服务。保留设备资源的双方须具有匹配的完成接口。新增资源现使用实例局部 lane、入口/出口及既有资源前沿装配：仅接受接收实例在切口之外没有同资源工作的情况，同一实例的独立切口不能重复引入同一资源。已资格化的非 overlap 调用序列决定跨步骤顺序，并连接后续实际工作和等待，不使用 donor 时间戳。后续同资源工作只连接既有依赖图中最早的不可比较入口，其他节点经已有路径继承约束；前序完成和显式等待继续保留。入口与出口复用同一可达前沿裁剪，不按时间选择。完整目标与后续等待语义仍须独立验收。

已观测末批次可能没有后继顺序边。资源缺少显式出口时，从该区域的实际服务/等待完成点中删除因果上早于其他完成点的候选；只有剩下唯一候选才作为出口，并继续检查入口到各项工作、各项工作到出口的可达性。没有工作或存在多个不可比较的终止点时拒绝；不按观测时间挑选，不追加请求制造后继边。该规则仅描述当前记录的图，不能替代采集完整性验收。

等待记录与执行图采用同一目标成员集合：完成拓扑改写后，保留节点提供原有 stream wait，插入节点携带 donor 的等待事实及目标局部完成边界；装配、执行和报告均消费该集合。插入时同步已映射的物理资源，未参与局部映射的外部资源保留同部署身份。删除等待节点不再留下来源等待记录；此机制不自动删除其他跨模板连接，外部完成接口仍须单独资格化。

Schedule 的过滤重复/省略与合并变化是另一项资格：目标控制状态先确定调用序列，每次调用有独立目标身份，生产端提供对应区域与状态效果；区域间通过目标依赖连接。撤掉一次过滤还必须处理其外围 CPU 工作和数据消费者，不能只修改 filter_index 或删除 Index 节点。该序列变换尚待实现，不新增第二个控制器或通用图改写语言。

存在条件必须进入实际候选资格或有限子图变换，不能只写在诊断 describe 中。页表除法由生产端将完整原生调用绑定为连续、单列跨行或多列跨步三种已观测布局；目标请求数、最大序列长度和页大小选择布局。布局改变时复用整个操作子图替换，包含 CPU、worker、cast、divide 和必要的物化工作，不能只删 AsStrided 或修改 shape。Prefill/Decode 仅在生产端已绑定为同一页表操作语义时共享变体；其他操作保持阶段约束。替换必须满足原有设备流入口/出口、完成消费者、worker 映射及 serving 端口切口条件，缺合法变体或接口时报告缺口。实际结构与独立验收状态见[整体审查](../redesign-workflow/2026-10-10_architecture_review.md)。

### 重复区域与批次共享工作

以下为待实现的序列变换合同，适用于逐请求发布和有序过滤调用；单区域替换通过不代表此合同已实现。复用现有语义区域、参数映射和原子拓扑改写，不增加另一种图或控制器。

- **序列由目标状态产生**：Publish 以本次目标 batch 的请求顺序及结束状态确定迭代；Schedule 以已确定的过滤/合并操作确定调用顺序。来源调用次数和原始 request ID 不决定目标次数。
- **每次迭代有完整边界**：生产端提供区域入口/出口、父步骤、请求或调用身份、分支及数据依赖。请求区域覆盖完整原生循环体，正常返回、continue 和异常均恢复父 scope；仅标记内部释放函数不足以定义一次发布。
- **共享与重复部分分别资格化**：循环体外的输入转换、迭代推进、输出及统计不能自动判为常量。生产端明确哪些工作依赖请求数、哪些跨迭代传递状态；缺少解释时整段变换拒绝，不能按人数平均切 CPU 节点。
- **目标身份独立**：重复使用同一 donor 时分配独立节点和完成身份，参数绑定到目标请求/槽位。请求对应的状态效果由现有控制状态维护，观测区域不再维护一份 KV 或请求状态。
- **组合一起提交**：先资格化所有重复区域、共享工作、资源前沿和外部消费者，再提交整个步骤。删除迭代须删除其 CPU/设备工作并重接依赖；插入迭代须有真实工作来源。不得依次修改实际图后在中途缺口处留下半个 Publish。

CPU 观测仍走 read_cpu_scopes → observe_cpu_control：显式 scope 边界切分原有服务候选、排除等待，注解不额外计费。结构验收继续使用显式给定耗时；循环体外成本或观测开销不能通过墙钟差补入预测。生产端的实际观测位置及证据见 [Decode 分支](sglang_template_relations.md#decode-首批复用的结构分支)。

冷请求、固定输出长度和非流式周期输出的参数由 PeriodicOutputPolicy 表达：生产端提供有观测来源的正周期 P；输入 g 为本次动作前已发布的生成数，完成本次动作后为 g+1。结束请求或 (g+1) 为 P 的整数倍时输出；此前周期已输出数量为 floor(g/P)×P，本次增量为 g+1 减此前数量，首次输出表示此前数量为零。未输出请求的增量为零，不表示 batch 无发送工作。此合同不覆盖流式、重试、恢复中途输出或数据相关停止。

PublicationParameterLayout 从目标请求生成有序成员工作，输出策略和载荷必须满足已有绑定及参数域；首次完成输出与普通非流式周期输出已有开发证据，不能推广到任意可选载荷。Decode 的逐请求纯 CPU 区域可在同一来源循环内复用已观测完成/继续分支，共享输出和设备释放保留在循环外，详见实施计划的当前验证范围。不能把输出条件相同当作整个 Publish 等价的证明。核心不读取框架环境变量，不维护另一份已发送进度。

成员 CPU 服务必须绑定目标槽位和目标 PublicationMemberWork。保留区域使用原位置对应的目标成员，替换区域在规划时携带接收槽位，不能沿 donor 的 request_slot 推导目标请求。执行节点引用实例持有的同一份输出工作，来源 span 仅用于追溯和显式给定耗时；物理图分别输出 publication_member_work 与共享 publication_work。该交接不授予 CPU 成本资格，也不把共享输出工作重复计入每个成员节点。

## 3. 语义粒度与性能粒度

一个 prefill 语义模板可以包含多个 CPU 准备、attention、MLP、传输和通信性能单元。语义模板负责业务边界；性能单元负责成本边界。性能单元可以随可测量性调整，语义合同保持稳定。

合并性能单元不能隐藏中间可被外部消费的端口或重要重叠；有这些交互就保留分段。节点与包含它的父模块不能重复计费。成本模型不足时改变测量粒度需要重新说明映射，不能改变业务工作来回避缺失。

9/8、10/9 是同批请求的上下文长度组合，部分参数可以影响 attention 等节点工作量；它们不定义整个 decode 的成本类别。目标内部结构和参数映射先确定，成本单元及其特征再依据实际工作确定。

### 给定节点耗时的动态展开

```text
加载流程合同、目标配置和 base 模板，建立唯一控制/资源状态
加入开放请求到达事件
循环处理下一组到达、端口完成或 timer：
    消费完成事实，在合同边界提交状态效果
    轻量控制器选择动作、请求集合和参数
    选择合法模板/变体，生成新节点身份并应用有限规则
    连接内部与跨模板依赖，为实际服务节点取得给定耗时
    执行核按依赖、资源和唯一时钟推进，产生下一批端口事件
达到声明终止条件后输出目标执行结构和条件化时序
```

给定耗时必须有明确来源、单位和假设，可作为适用实测输入或显式条件；不实现耗时预测算法，不调用性能补采，不读取目标真值。缺少值不默认零，纯逻辑 marker 除外。CPU 服务也经过完成边界，等待由依赖和资源生成，控制器宿主运行时间不计入。

给定时延仍影响后续可见请求和决策，目标结构逐步生长，不能提前复制 base batch 顺序。内部设备依赖其 launch，提交返回、设备完成和发布分别推进；模板端口不会人为形成全局同步。后续模型耗时接入同一展开和执行机制，不再实现另一套模拟器。

先检查同配置与准入 2→1 的节点、工作量、batch、shape、关键依赖、rank/资源、状态可见性、KV 和终止；再检查耗时变化影响下一轮的因果链。只有模块节点数相符或窗口耗时接近不足以通过。独立结构核对可在成本模型前进行，原生验证观测不进入目标生成器。

## 4. 判断模板资产能否预测目标组合

支持判断是关系：base 事实和模板、target 差异、workload、流程范围、控制器能力、成本与资源条件共同决定结果，不是给一个 target 参数组合贴永久标签。

按顺序回答：

1. **差异是否可解释？** 目标改变了哪些控制参数、模板参数、实现和部署条件？
2. **控制路径是否覆盖？** 已支持规则能否表达目标可能触发的决策和状态变化？
3. **所需步骤是否有模板？** 来自显式代表性结构采集的已观测子图或已有有限变换；未执行分支不能推定存在。
4. **模板能否变换？** 参数来源、shape、依赖、端口和效果是否仍明确？
5. **执行能否模拟？** 资源、异步、取消和发布时间机制是否已支持？
6. **成本是否可用？** 性能单元是否可绑定，能直接迁移、独立查询或预算内补采？

前五项形成结构可展开条件，必须先在给定节点耗时下验证；第六项是随后正式性能预测的成本资格，两者单列结论。第二至五项缺实现一般为 unsupported，机制已实现、仅缺合法观测或测量为 needs_data；必须说明获取路径。补测性能不能弥补语义缺失，给定耗时结构完成也不等于预测性能完成。

当前 TemplateBank 以类型区分缺观测与缺规则。已有 dense module 定义但缺某个 step/phase/rank 的源实例时，返回 observation/native_step_not_observed，候选为 needs_data，报告触发的步骤、阶段、rank 和模拟时刻。源实例未声明所需变换为 implementation/native_transform_rule_missing；模型模块规则未实现为 implementation/native_module_rule_not_implemented，二者为 unsupported。当前缺显式节点耗时由 NodeDurations 路径报告，节点成本模型尚未实现，不能用性能资产填补语义来源。

例如 base 没发生写回，而 target 可能触发写回：已有写回定义但本任务缺必要模板事实，可报告需要新 base 覆盖；连写回规则和模板定义都没有，则需要开发。不能拿目标实际写回 trace 作为预测输入。

## 5. 静态与动态判断

plan 检查声明的变换与能力，不假装穷举所有实际执行状态。已知可达分支缺规则/模板时提前报告；仅能在执行时确定的参数域或成本需求，随每次模板调用再次按其适用合同判断。

动态展开中遇到未覆盖分支或不可变换模板，停止该候选并给出触发状态，不能退回 base 顺序。结构阶段缺给定耗时定位相应节点和输入；正式性能阶段成本缺口才交给工作流补采，两者都不能通过删工作继续。

报告完整关系和原因，例如“base A → target B：TP 分片规则具备，但 collective 成本缺失”，而不是笼统的“B 不支持”。通过判断与精度达标是两个结果。

## 6. 实施任务与完成条件

1. 依据真实动作合同复核最小准入、组批、prefill/decode、发布和终止，声明并验证策略近似。
2. 实例化完整内部节点与依赖，为准入变化定义实际需要的参数规则/模板变体及明确不支持域。
3. 接通显式给定节点耗时、必要资源和统一事件核，先完成同配置、目标变化和时间反馈的结构验证。
4. 单列结构支持、模板/规则缺口与后续成本需求；节点模型在本阶段完成条件满足后开展。

交付是轻量控制器、有限模板规则、接受给定耗时的统一执行能力及结构报告。完成条件：同配置与允许目标变化的每个子图、节点和关键依赖都有来源与规则，状态只在约定边界生效，时延能通过事件链改变后续决策，未知分支明确停止；结构验证不依赖整批成本查表或性能补采。该条件是进入节点成本建模的前置条件。


### 当前源实例选择

TemplateBank 保留每个 step/phase/rank 下的来源候选。当前先检查有序请求的数量及 input/context tokens、同批锚点、publication 完成成员和 Schedule filter/merge；形状门槛尚未放开，没有相同 token 条件仍返回 internal_shape_transform_not_implemented。

运行时一次交接当前控制批次的全部 InvokeStep。TemplateBank 从 rank 0 的候选枚举来源 batch，再对该 batch 的全部步骤、全部 rank 联合检查。各实例由 instantiate_source 检查拓扑改写、通信工作量、保留 kernel 和插入参数；全部通过才返回。任一步骤或 rank 不适用则丢弃整组、尝试下一来源，不允许各 rank 分别选中不同批次。全部失败时报告推进最远步骤的具体缺口，避免后续候选的早期形状不匹配掩盖已找到的规则问题。

整组选择失败不向图装配或资源前沿提交实例；成功后仍需执行原有跨模板连接与执行图检查。该过程只资格化当前已实现的参数/改写域，不证明未映射工作、跨 rank 连接或新形状已经合格，也未允许任意混合不同来源步骤。

输入布局继续来自只读定义；source_call/source_subtree 用于来源追溯，不能把源决策复制为目标调度。后续扩大支持域必须同时落实参数、拓扑、外部连接和状态分支，不能通过删除入口比较获得成功状态。

源定义与调用实例在核心代码中分开。TemplateDefinition 由 TemplateBank 持有，保存源请求条件、布局、调用树、span、内部边、外部边界及标准端口；TemplateInstance 保存目标 WorkId、只读定义引用、实例拓扑和目标连接集合（连接记录及其绑定）。模板库在运行期间保持不变并长于调用实例，不为每次调用复制整份子图引用，也不修改源定义来改变目标参数。

TemplateTopology 持有实例当前的节点/源依赖索引、重接边及共享位置数据依赖，初始化为源定义的完整成员。ExecutionGraph 与 TemplateAssembly 的服务完成导出、前驱路径统一读取这一份拓扑；来源边界和标准端口保持稳定。外部连接由实例独立持有，装配、前驱路径、执行图和诊断共同消费；从源连接初始化，通信组联合改写可在图装配前替换任务及通知端点，失败丢弃完整候选。有限操作移除先在副本上合并所有删除和重绑定，检查数据端点仍是保留节点后一次提交；失败不改变原实例或源定义，不直接从多个消费者分别删节点。

正式instantiate在完成来源批次、人数和状态资格后，通过私有plan_materializations生成区域改写，再进行节点参数化和装配。跨人数的single_request_topology曾绕过完整资格，相关预览与专属logits view替换现已删除；原证据data/redesign/s3-logits-view-replacement/replacement_audit.json仅保留为历史局部诊断。当前控制器通过已有同人数模板动态组批，尚未实现任意批人数的整图变换。请求循环、共享工作、模型视图/物化与端口需要一起闭合，见[批人数变换整体边界](sglang_template_relations.md#批人数变换的整体边界)。

模板选择先检查输入相同或生产端已声明的候选长度域，再检查发布、成员和各参数/通信条件；接通消费者本身不能证明改变 B/T 的整批目标已通过。诊断预览只改变局部输入用于检查同一规划器，仍明确为 diagnostic_copy_only；完整目标验收需同时解决其余 serving 工作、分支和跨动作连接。

公开诊断中的 source_span_count/source_internal_edge_count 及输入/输出边界数用于核对定义交接，其中 span 包括观测注解，不能当作目标服务节点数。这些来源引用已进入目标节点、内部依赖、跨实例连接及已实现的有限变换；端口时刻由给定节点耗时和实际依赖计算，仍不能以模板定义已读入替代完整结构验收。


模板定义现在从 manifest 明确引用的 source_dag 读取实际拓扑：boundaries 保存源边界/资源 lane 的溯源，nodes 保存种类及局部起止边界，dependencies 保存关系种类及局部端点。标准端口和输入/输出边界统一映射为该定义内的局部索引，调用中的身份由 WorkId、rank 与局部索引共同限定。源 observed_time_ns 保留用于源 CPU 顺序投影，不作为目标时刻或节点服务时间。

局部化保留 CPU/通信注解等源记录，目标执行区分服务、等待与注解，并消费已解析的跨实例连接；非匹配 shape 必须有已实现的有限规则，否则报告缺口。local_ports/local_boundary_count 只是局部拓扑交接证据，不能替代实际目标图和来源资格的核对。


TemplateNode::role 将 CPU control、计算、DMA 和物理 device marker 归为需要耗时的服务候选，将 host/device wait 归为等待，将 CPU/通信观测包络归为注解。物理事件记录不是纯逻辑完成点，不能因名称含 marker 就默认零耗时。等待依赖生产者和进入条件；其观测墙钟不能再次计为服务。注解保留溯源与关系，不能在对应工作之外再收费。此分类不证明服务耗时已知；当前服务耗时由显式节点输入提供，旧模块成本路径已删除。

每个定义保留局部 lanes，含原图 lane 索引及其 domain/rank/native_id；边界引用局部 lane。这里的 CPU thread、device stream、通信注解及逻辑汇合是不同语义，源线程号/stream 号仅用于溯源，stream 的顺序也不能冒充设备算力或带宽容量。公开 source_node_roles/local_lane_count 可检查交接，目标资源绑定与容量规则仍需实际实现。

### 跨模板连接的读取

TemplateDefinition.connections 保留源跨模板边的关系类型、方向、本地边界，以及远端源边界和全部远端调用身份。本地端点与内部边/端口使用同一局部编号；远端身份仍属于来源证据，不能直接把源调用编号作为目标依赖。同一目标批次内的装配现在将其解析为 WorkId、rank、局部边界三元组；跨迭代资源关系按下文的前沿规则处理，未覆盖关系仍保持未解析。远端调用集合为空表示另一端尚无观测归属，不能当作依赖已满足。共同拥有两端的实例使用已有内部边，不再次添加外部连接。

公开实例诊断的 source_connections 可用于追溯这些关系。同一控制批次的全部动作和 rank 共同选择一个源 batch，避免相同 shape 从不同源迭代独立取模板。缺同批动作报告 native_batch_step_not_observed，沿用 base 缺口路径。装配只连接同时具有相同源边界和真实 owner 的已选实例；未选中或未归属的对端保留空 target_peers，不代表依赖已满足。执行核已消费解析后的连接计算节点与端口时间；未解析关系会停止候选，跨配置装配的完整资格仍待独立核对。


### 模板外 CPU 观测之间的顺序投影

同批内未直接匹配的 thread_order 连接，可以沿源图已经建立的同线程顺序路径连接相邻的已选模板边界。源 CPU 边界时间仅用于定位该既有顺序，不能用来指定目标时延；不同线程、stream 或同步关系不能使用此规则。模板外的中间观测不因此被归入某个 block，也不把它的墙钟间隔补成服务成本。

每条目标连接通过 binding_rule 区分 native_boundary、cpu_thread_projection 和 unresolved。投影所需前驱或后继不在当批时交给资源前沿规则，缺少适用依据仍为 unresolved；CPU 投影本身不解决跨迭代资源前沿。后续节点执行需要保留投影的先后约束，模板外工作的 scope 假设和源依赖缺口仍需报告。


### 每候选独立的资源前沿

原生 stream 同步现在独立记录等待对象：SourceGraph.stream_waits 将 HostWait span、原生 stream 身份和具有明确物理归属的设备 lanes 关联，即使源运行当时没有前驱边也保留。TemplateDefinition 将其完成点重绑定为本地边界；TemplateAssembly 在发布当批出口前读取已有目标前沿，ExecutionGraph 用 native_host_wait 边连接这些端点。原有批内观测依赖继续保留，不把当前批次的未来出口连回等待点，也不新增等待服务耗时。

这项前沿绑定限定于当前固定部署、非 overlap 的控制路径：进入下一批前，先前批次已提交其工作。原生 stream 与图中 lane 的归属必须明确；未知 stream、失败同步或未知资源出口使目标等待未解析，不能当作空 stream。该规则不证明 overlap 下任意跨线程提交的等待截面，后续支持此类路径时需要实际提交事件语义。当前实现已在已有真实资产上补齐已知 24 条差异，证据见执行日志和 data/redesign/s4-stream-wait-semantics/native_host_wait_completion_audit.json。任务完成汇合点是合法前沿，核对时须沿实际 completion_join 展开物理生产者，不能要求每条依赖都直接落在单个物理节点上。

TemplateAssembly 随 SimulationRuntime 创建，保存本候选已经装配的 CPU/stream 出口；TemplateBank 仍只保存不可变源定义。装配先解析当批内部连接，再读取已有目标前沿，最后发布当批出口，避免等待连接到自己刚提交的未来工作。资源键限定为当前固定部署中的原生 rank/thread 或 rank/physical-stream；更换线程布局、stream 生命周期或部署不在此规则的资格范围。

源跨批次的 thread_order、stream_order 和 native_host_wait 只有在关系类型、资源身份及源前后批次方向明确时才使用前沿规则。目标前驱引用 WorkId/rank/局部边界；源 batch 仅判断该规则是否适用。没有先前建模工作的资源标为 initial_resource，沿用当前 modeled 仿真从无在途请求/工作的状态开始这一假设；已使用但出口缺失的资源保持 unresolved。resource_export 表示为后续工作保存端点，不表示有一个尚未发生的后继已经完成。 模板内服务/等待的实际完成端点也参与资源出口，因此源采集末尾仍可被后续目标工作复用。根据当批已知依赖路径删除被同一资源其他完成端点覆盖的出口；没有路径证明的并行端点全部保留，不能按源时间取最大值。只有引用而没有已知工作完成端点的资源仍保留未知出口。 native_host_wait 的跨批出边同样导出其设备完成端点，资源键取源设备 stream；入边按该 stream 引用此前目标前沿。不能把等待方 CPU lane 当作此同步的设备资源，也不能因为后继尚未实例化就把已知出边视为本批缺失前驱。

诊断另报告 resource_predecessor、initial_resource 和 resource_export。多个出口不按最大观测时间擅自丢弃，后续节点执行应保持全部必要前驱。该装配状态不维护时钟或完成标志；节点执行仍应由唯一执行核负责，当前节点执行消费这些依赖；完整来源与变换资格尚未通过，不能据此宣布 S4 完成。


公开结果的 structure 字段独立报告结构资格与连接规则计数，即使 diagnostics=false 也保留。当前报告条件执行状态和 pending_source_and_transform_validation 资格说明；complete 只表示给定耗时下该次循环完成，不能解释为正式性能预测已验收。


执行核的单次运行边界不依赖整个Project或base/target角色。SimulationRuntime只借用本次workload的请求序列、控制器、模板和节点耗时，并持有可选诊断图路径；运行参数是ServingLimits。配置选择、组合身份与文件命名归PredictionWorkflow。每个组合新建运行实例，事件队列、模拟时钟、KV/控制状态及图不在组合间复用；请求与模板等只读输入须覆盖该次运行的生命周期。当前公开输入已使用配置与workload集合，工作流逐组合消费同一执行核；完整支持域和代表性建库资格仍待验收。

### 目标图装配

ExecutionGraph 在正式 SimulationRuntime 内接受已装配的批次。一个源边界在同批多个 block 中被引用时只生成一个目标边界；下一批复用同一源模板时创建新的目标身份。内部节点、关系、标准端口和已经解析的跨 block/资源连接进入同一张目标图；同批共享 span 不重复生成节点，同一目标约束去重。未解析的连接单列，不能用无环结果掩盖缺边。

每次追加后检查整张目标图的拓扑，发现环返回 target_dependency_cycle，停止候选。structure.graph 给出节点角色计数、边界/边数、目标端口与源端口映射，以及未解析连接。节点图已接入显式服务耗时、入口/出口门控和端口完成事件反馈；未解析连接或缺值时停止。原模块时钟已删除，结果属于给定条件下的执行，来源与变换资格仍待完成。

独立结构核对需要区分直接边与依赖可达性。同步前沿压缩或控制端口门控可能用一条已有路径承载原生直接等待关系；直接边数量不同本身不证明漏依赖，也不证明两图等价。对于每个差异，先以唯一工作/节点身份定位实际目标端点，再证明原生必要的先后关系在实际目标图中可达；同时检查新增路径是否引入原生不要求的串行约束。不能根据条件完成时间相同、节点无环或部分差异可达就判定整类依赖已通过。

### 结构缺口的可操作报告

来源报告的 observed_step_phase_rank_groups 统计非空的步骤/phase/rank 分组，source_instances 统计来源调用数；二者都不表示已归并的模板族数。observations 保留逐调用条件，不能将列表条数当成结构变体数。

模板实例化失败时，公开 gaps.requests 保留目标当步的请求身份及 input_tokens/context_tokens；provenance.source.observations 列出已观测步骤、phase、rank、source_batch/source_call 及有序 token 条件。该列表只声明实际样本，不将两个 context 之间的范围推定为支持，不触发整批性能补采。相同 token 条件仍不代表发布分支或内部算子已经取得完整资格。

候选失败优先保留推进到较后步骤的缺口；同一步内，较早来源的 shape 不匹配不应掩盖其他来源给出的具体规则或分支缺口。已知过滤/合并关系与目标不同归类为 implementation/unsupported，分别说明过滤序列、成员关系或合并分支尚未改写；不能将规则未实现报告为 observation/needs_data。这个选择只影响拒绝报告，不放宽任何模板资格。

早期 base 的单请求 decode 仅观测到 context 11/12，目标准入 1 首次需要 context 8；后续同配置覆盖采集已取得 8–14，发布分支仍分别核对。读取真实 kernel 元数据发现 context 11→12 时，计算节点数均为 743，但 Slice/Index 输出长度 12→13；不能只改请求描述或 input_layout 就声称内部结构已变换。有限规则需明确这些内部节点的形状与参数来源；缺少该规则或合法观测变体时继续拒绝。

### 发布分支也是模板条件

相同 input_tokens/context_tokens 不保证发布阶段走同一条原生路径。建库装配按 rank/batch 汇集实际 source_state.published_requests，SGLangTemplateBindings 将原生请求身份解释为 publication_finishes：按来源请求槽排列的可缺失布尔值。原生身份索引仅在建库期间存在；模板选择按槽与目标 RequestSlice.finishes 对齐，KV 释放生产绑定复用同一条件。四个步骤仍必须共同选择匹配该状态的源 batch。匹配形状但缺少发布分支时返回 observation/native_publication_branch_not_observed，不能借用另一条路径继续发布。observations 的 finishes 只来自实际观测，缺失为 null；gaps.requests 列出目标所需值。

该缺口目前不会自动触发重复原 workload 的采集，需明确 base 覆盖配方后再补充观测。结束状态匹配是必要条件，尚不证明所有 CPU 分支、KV 物理映射及内部参数均相同。

### 准入变化同时改变请求索引表布局

原生 ReqToTokenPool 按已解析的最大请求数加一个 padding 行分配 req_to_token，ModelRunner 的池配置受 max_running_requests 影响。当前固定主线 base 准入 2 的实际表为 3×40964，目标准入 1 需要 2 行；不能把该配置差异只交给轻量控制器。真实 kernel 描述显示写表 Triton、Slice、Index 和 IndexPut 均涉及该表或它的派生视图。

RequestPoolLayout 已接入固定 Ascend dense 路径的请求池缩容规则。它从原生 write_req_to_token_pool_triton 的输出确认表尺寸，要求实际行数等于 base 准入上限加一且所有观测一致；仅支持容量不变或减少。缺少一致观测返回 request_pool_source_layout_unresolved，增加容量返回 request_pool_capacity_increase_not_supported。

规则按具体算子和 operand 修改：写表 kernel 的输出；Slice 的表输入和序列宽度视图输出；Index 的表/视图输入；IndexPut 的表输入与输出。仅改行数为目标容量加一，保留列数、其他 operand、dtype、格式、节点及依赖。视图宽度必须等于该步最大 context_tokens+input_tokens，相关 operand 为 INT32；无法解释的形状或 dtype 分别返回 request_pool_operand_layout_unmapped / request_pool_operand_dtype_unmapped，不做全局数字替换。任意 context/batch 变化仍须先选择合法观测变体。

源 SourceKernel 不可变，TemplateInstance.kernel_overrides 保存目标参数，ExecutionGraph 节点使用实例的实际 kernel 描述。逐工作明细提供 observed_kernels、transformed_kernels，实际物理图节点的 kernel 字段提供执行参数；主报告通过文件路径引用，避免重复保存整图 kernel_parameters 数组，仍可核对规则是否真正进入执行结构。源模板的 request_identity 声明描述其固有实例化条件；额外请求池规则由核心按当前 kernel 观测和上述条件单独检查，并在报告中明确标记。

这条规则描述有限的 operand 布局变换，尚不证明底层 CANN 选择的 kernel/tiling 在缩容后完全相同，也未解决源图的全部同步缺口。必须继续独立验证结构与支持范围；给定耗时仅是分析条件，不从目标成绩反推规则或成本。


### 当前有限变换的独立验证缺口

2026-10-09 准入 2→1 的独立目标观测已完成。有效阶段序列和发布条件吻合，但完整内部结构未通过：FutureMap 的一维 INT64 状态表随请求池容量变化，alloc_extend 的 free_pages 长度依赖当前 KV 分配状态，部分 base 单请求变体还携带前批压缩的 Index 工作。这些条件尚未被当前模板参数和变体选择完整表达。二维请求表改写只是已实现规则的一部分，不能据此声明整个配置变化受支持或开始成本精度验收。后续规则须来自原生实现和 base 观测，目标事实只提供独立反证；不得按目标差异数量删节点或修正成本。详细证据见执行记录。


FutureMap 容量映射已补入同一 RequestPoolLayout：非 overlap dense 路径仍通过 output_tokens_buf 在执行阶段读写 token；该缓冲区长度为请求池容量加 padding 行。一维 INT64 的 Index/IndexPut 分别核对原生 operand 槽位、当前 batch 大小与输出形状，只改 pool operand 的长度（IndexPut 同时改输出），不改变索引/值、节点或依赖；未知 dtype/layout 返回缺口。该实现不解决 KV 空闲页和前批压缩的变体选择问题。


PagedKvLayout 将当前动作的 free_kv_pages 映射到 alloc_extend_kernel 第四个输入 operand。前三个 operand 分别为 prefix/sequence lengths 与 last location，均须为当前 batch 大小的一维 INT64；输出长度须等于本批输入 token 总数。规则只改空闲页列表长度，保留其余 shape、类型、kernel 和依赖；同配置复用模板也执行此状态映射。当前只支持已有真实观测的 extend 分配，遇到独立 alloc_decode_kernel 明确报告未支持，不假定所有分页路径已覆盖。KernelShapes 的厂商槽位解析由请求池与分页布局规则共享，没有增加通用变换注册机制。


### 过滤序列选择与空调度

当前 Schedule 模板选择还必须匹配 BatchInput.filters 的完整有序序列：每项包含 input_count 与 retained_indices，不使用源请求 ID 作为目标条件。四个有批次动作继续共享同一 source_batch，不能独立挑选相互不兼容的阶段。过滤条件无合法变体时返回 observation/native_batch_filter_not_observed，并报告要求的槽位；缺空调度阶段时返回 native_step_not_observed/phase=idle。

轻量控制器保留原生 running 与待合并 prefill 的成员语义，不只根据当前活跃请求数量组批。无批次的清理通过同一执行核产生 Schedule/Selected 事件；没有模板或给定节点耗时时停止，不删掉清理工作。实际推理 batch_invocations 不计空调度，图中的装配组则包含这些独立调度动作。该修复仍需真实 idle 模板及独立结构验证，不能仅以同配置条件执行结束宣告资格。


### 实际目标图的导出与核对

ExecutionGraph 在 diagnostics 开启时流式写出实际 boundaries/nodes/edges/ports，不通过模板重新拼接诊断图。source_boundary/source_span 关联到选用的 base，work_id/rank 和目标数组身份区分重复实例。有唯一成功原生关联的 DMA 节点同时输出 transfer（字节数、方向、API 来源）；它仍使用显式给定的节点耗时，不从源 DMA 墙钟生成成本，也不把观测字节数直接当成变形后的工作量。源关系名称与 SourceGraph 共用一个序列化实现；控制器新增的依赖用 null relation 明示。图文件先写临时文件再替换，预测轮次只在图文件完成后发布结果。该能力为完整目标依赖核对提供依据，不能用文件存在或边数一致替代语义正确性。


### 插入子图的目标边界身份

操作移植保留 donor 的节点与边界来源用于追溯，来源身份不决定新增目标事件是否共享。已存在的 source boundary 仍按原生共享关系装配；新内部点由实例拥有，以 work/rank/local boundary 区分。联合应用多个替换计划时分别重定位内部点编号，执行图为这些点分配独立目标事件，资源前沿与新增依赖使用同一身份规则。内部 lane 必须由规则显式映射到 recipient 资源，不沿用 donor 的线程号猜测目标关系。
