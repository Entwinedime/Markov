# Markov redesign：设计总览与实施路线

阅读入口：日常开发先读[工程约束](engineering_constraints.md)和[当前实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)，再按任务读取一份设计合同。涉及原生参数或分支时查[SGLang 关系参考](sglang_template_relations.md)；追溯历史时才查[执行记录](../redesign-workflow/2026-10-08_redesign_execution_log.md)。当前进度统一维护在实施计划，本目录各阶段的实现说明只解释局部能力，不作为独立进度表。


本目录维护长期设计。开发主线为 **SGLang + Qwen3-32B**，KTransformers 与原生控制器在主线稳定后扩展。阶段状态只读[当前实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)，可运行入口读[构建与运行](development.md)，不从历史日志或设计中的局部实现说明推导整体完成度。

自有代码实施与审阅遵守[代码与工程约束](engineering_constraints.md)：仿真核心使用面向类的现代 C++23，在 modeling Docker 中构建运行；最少必要校验，不维护独立 test 工程、多版本实现或向后兼容，弃用功能沿职责链完整删除。

## 1. 我们要做什么

用户提供一个固定模型、多个配置和多个 request workload，系统探索配置与请求序列的笛卡尔积。代表配置和采集 request 由系统选择，用户不指定 base。总体机制是代表性采集建立参数化模板，轻量控制器按各组合状态动态调用模板，经依赖和资源计算完成事件并反馈调度。当前按以下开发顺序实现：

**定义统一流程 + 按流程采集 base 子图模板 + 目标配置 + 轻量控制器 + 给定的节点耗时 → 动态展开目标执行结构。**

统一流程约束采集与控制：阶段具有输入、工作职责、完成端口、状态效果和参数；统一插桩为真实工作提供阶段归属；模板保留节点、依赖和可重绑定参数。执行核用给定耗时推进时间与完成事件，控制器据此组织后续模板。先验证目标结构与动态机制，再实现节点/局部子图的 cost model。

首要目标是用户友好、容易扩展维护和控制项目规模。首轮不追求完整复现任意框架、任意配置和每一段 CPU 执行；支持范围必须具体到模板来源对目标组合的适用条件、允许变换及预测范围。

## 2. 已确定的方向

| 讨论结论 | 对设计的约束 |
| --- | --- |
| 先统一接口，再轻量控制器，最后可接原生代码 | 首轮预测不执行原生 scheduler；未来适配器使用同一控制接口 |
| 标准流程定义语义边界 | 模板来自有边界、有上下文、有依赖关联的真实采集，不靠事件名猜语义 |
| 统一插桩记录，框架适配选择位置 | 阶段范围、工作关联和端口事件共用合同，保留异步身份，不增加 serving 同步 |
| block 定义、wrapper、子图提取强关联并模板化 | C++ 维护唯一语义合同，Python 消费合同采集事实；公共流程复用，框架差异通过绑定与浅层继承实现 |
| 动态展开子图 | 控制器决定调用什么模板；完成时延可以影响下一次决策 |
| 结构先行，cost model 后置 | 先在给定节点耗时下验收流程、模板和控制；成本补采不替代结构资格 |
| 语义与性能粒度不同 | 一个语义子图可以绑定多个性能单元；粒度调整不得丢依赖或重复计费 |
| 性能采样按四项约束选型 | 对象一致、适配简洁、跨框架共同途径、易构造特征范围；原生状态由框架管理，语义/性能插桩独立但共享工作描述，详见[采样合同](04_collection_templates.md#独立性能采样合同) |
| 配置集驱动采集与资产复用 | 参考 Dooly 增量发现配置结构、复用等价操作；不要求一个万能 base，一次代表采集不构成覆盖承诺 |
| 五个顶层 block 内部可有语义子区域 | attention、KV、通信等按独立变换/复用/外部事件需求标记；不为每个区域新增类 |
| 有限变换、渐进扩展 | shape 修改、已定义 TP 通信插入等需逐项支持；复杂变化靠后续模板与规则扩展 |
| 只处理统一流程子图 | 模板外服务默认排除，保留子图间必要依赖、端口和状态；不追求原生全事件完整性 |
| 先 SGLang + Qwen3-32B，再扩展 KTransformers | 先在一条真实路线完成闭环与验收；后续复用产品入口和核心合同，按实际差异增加适配 |

“原生框架与我们的核心代码两层”用于理清来源与职责，不是强制的软件分层。采集、语义、性能是功能视角，也不要求机械拆成三套系统。

### 2026-10-10 重点与项目贡献

代表采集与增量复用参考 [Dooly 调研](../../reference/README.md)，作为基础工作流，不单列为核心研究难题。重点依次是：统一语义获取、模板参数化、合法有限变换、动态依赖拼接、结构合格后的成本建模。五类顶层 block 基本足够表达当前 serving 流程，但不足以充当唯一变换粒度。

潜在贡献在于显式表达 CPU/设备/通信/等待及多种完成端口，解释结构变化如何影响后续调度；尚未证明优于 Dooly。需比较操作耗时汇总与依赖图执行的收益，不把 C++、Ascend 支持或代码量当作方法优势。当前无 overlap 范围不能证明重叠预测收益。

### 有边界的建库先于泛化验收

本轮讨论确定的路线是：**固定模型与探索集合 → 声明支持域 → 有预算的代表性建库 → 固定资产动态展开未见请求 → 结构合格后建立成本模型 → 输出探索结果**。用户不指定 base；代表 request 可以与目标 request 不同，目标调度仍由轻量控制器根据到达、资源状态和完成事件生成。

有限模板的复用依据分为模型内部同构复用、同一实现分支的参数化，以及有原生条件的有限分支选择，见[采集设计](04_collection_templates.md#模板数量有限的依据)。代表 request 负责取得这些关系的证据，轻量控制器负责生成目标控制路径，成本模型负责估计性能单元耗时；单次短运行不构成全范围覆盖证明。

轻量不是先做一个 demo 再不断补齐案例，而是在实现前解释有限模板的复用依据，用最小证据建立这些关系。轻量要求同时约束采集开销、模板定义和变换规则。prefill/decode 内部按模型结构划分，成本粒度另行确定。同一支持域内增加目标请求，应复用定义并增加展开实例；真实机制变化才可能需要新的结构族。预算耗尽或机制不明时停止并保留缺口，不承诺补采直到所有组合成功。

先定义模板参数、结构分支和目标依赖规则，再安排少量代表请求取得证据。结构覆盖以分支为单位，不以请求组合为单位。固定已建资产与规则验证未见请求；失败先诊断抽象、实现、缺分支或范围外问题，不能以反复补采让 demo 逐个通过。修正后使用新的未见输入重新验收，成本采样仍独立进行。具体纪律见[工程约束](engineering_constraints.md#13-不以补采和特例替代参数化设计)。


### 跨框架扩展边界

换框架主要调整子图获取与模板化，以及对应的性能样本生产；共同核心消费统一模板和工作描述，生产过程复用公共观测与提取能力。适配范围不扩大为每框架一套控制器、KV 管理器或执行核。统一合同不要求内部拓扑相同，也不保证共同轻量策略等价于所有原生调度。外围配置解释、模板选择和控制器装配也应通过统一适配接口，公共 workflow 不保留框架专属业务分支。完整职责见[框架边界](01_system_framework.md#框架差异收敛在模板生产端)和[模板生产抽象](04_collection_templates.md#统一生产流程与统一模板产物)；实际交付状态统一见实施计划，不能据文档或接口存在宣称已支持 KT 预测。

### 开发粒度与推进方式

按完整能力交付推进。先判断问题是否位于统一流程内，再看是否改变结构、控制状态或成本；不要求逐细节消融，不把每个原生差异变成实现任务。变换区域、接口和状态是验证重点，已有未变换内容沿用既有证据。支持条件来自模板和变换规则，不另建逐案例拒绝清单。具体纪律统一见[工程约束 §1.4](engineering_constraints.md#14-建模范围与开发粒度)。

## 4. 持续保持的边界

- 预测读取明确的建库资产、合法输入与独立测量。允许在探索配置上用代表 request 建库；完整目标 request 序列的验证观测只进入评价，不能回填模板、拟合或误差补偿。
- source DAG 来自一个或多个显式代表性结构采集，逐模板保留来源；目标 DAG 是各组合的动态展开结果。独立性能采样不能冒充语义覆盖。
- profile_manifest.json 是采集与 modeling 的正式交接点；不扫描目录猜输入。
- 当前 base 仅为对应且未变化的工作提供直接成本，不在线拟合共享模型；变化工作使用独立测量与既定模型。
- 缺失不记零；服务、等待、CPU residual 与观测开销分别说明。模板外时间的排除是范围定义，不是缺失值处理。
- 真实采集串行，显式允许且有累计预算，失败、预热与重试计入预算。
- 官方 third_party 工作树保持干净；自有插桩优先 wrapper/hook。轻量源码插桩方案必须明确隔离方式，不能恢复历史业务 fork。
- 不修改原仓库、清理旧资产或恢复独立测试工程；不引入本地 checksum、内部版本握手和冻结副本。
