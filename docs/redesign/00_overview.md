## 2. 项目机制

用户提供**一个固定模型、多个配置、多个 request workload**，系统预测配置与请求集合的各个组合。系统选择代表配置及采集请求，用户不指定 base。

完整机制是：声明支持域 → 有界代表采集 → 从统一流程中取得原生子图并模板化 → 按目标配置和请求重绑定参数、应用有限变换 → 轻量控制器根据状态调用模板 → 执行核按节点耗时推进依赖和资源 → 完成事件反馈控制器 → 输出探索结果，另做独立评价。

开发顺序仍是结构先行、成本后置：先验证“统一流程 + base 模板 + 目标配置 + 轻量控制器 + 给定节点耗时”能否动态展开正确结构，再建立真实成本模型。语义 block 可以包含多个性能单元，两者粒度不必相同。

框架提供原生运行事实，适配端解释插桩位置、模型结构、子图绑定和采样配方；共同核心消费统一模板和工作特征。目标控制路径由轻量控制器生成，后续可通过同一控制接口接入原生控制器。Python 负责原生观测与任务交接，C++ 负责语义提取、模板变换、控制、执行及成本消费。详细职责见[整体框架](01_system_framework.md)，不把“原生框架与核心代码两层”的思考方式机械转成两层目录。

## 4. 必须保持的边界

- **用户友好和可维护优先。** 不以细节数量或代码量证明质量；只有影响目标工作、必要依赖、资源、端口或状态的结构细节才值得维护。
- **只处理统一流程。** 模板外服务默认排除，保留跨边界必要因果。当前代码仍省略 host CPU 服务，详细范围见[性能合同](06_performance_execution.md)；后续稳态 CPU 与分层模板目标见当前专项，不把计划当作已有能力。
- **有限泛化。** 模板数量有限的依据是同构复用、参数化和有原生依据的分支选择，不是一个万能 base。模型、TP、后端或实现分支变化是否需要新来源，由生产与变换合同判定；目标请求变化也不自动保证可复用。
- **适配在生产端。** 换框架主要调整子图获取、模板化及性能样本生产，不复制一套控制器、KV 管理器或执行核。框架差异不能以名称特例进入共同核心，外围装配也遵守此边界。
- **采样有界。** 先定义工作特征、支持域、需求和预算，再安排采样；原生状态由框架维护，语义与性能观测共享执行底层。未知结构不能靠逐案例补采或硬编码拒绝清单掩盖。
- **资产与评价隔离。** manifest 显式交接；验证只用于评价，不回填模板、拟合或误差补偿。给定耗时只证明其限定的结构行为；有成本命中不等于精度通过。
- **能力如实声明。** 工程闭环、结构资格和精度分别验收。KT 预测、跨模型/TP/backend 泛化及原生控制器不因接口存在而获得支持。

代表性采集参考 Dooly；潜在研究价值在于原生依赖、有限变换和动态反馈能否提供额外解释力，仍需独立证据。尚未证明优于 Dooly 或 LLMServingSim；C++、Ascend 支持、更细的 CPU 建模或更多代码都不是方法优势。当前无 overlap 范围也不能证明重叠预测收益。
