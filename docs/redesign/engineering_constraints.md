# Redesign 代码与工程约束

本文件约束 redesign 的自有代码、构建、配置和文档，作为实现与审阅依据。用户明确指令优先。必须/不得是硬性规则；优先是默认选择，偏离时说明实际理由。

目标是简洁、有序、容易理解与维护，以最少的必要机制完成声明范围内的功能。约束从新增代码和被修改的职责链落实，不开展无关的全仓格式化或清理。

## 1. 简洁有序的代码风格

- 主流程应自上而下表达业务步骤，同一方法内保持同一抽象层次，编排与底层操作分别组织。
- 优先显式变量、普通循环、提前返回和简单分支，减少深层嵌套、隐式状态和跨层跳转。
- 命名表达业务含义，时间、字节、页等字段写清单位；数值规则使用有依据的常量或配置。
- 紧密相关语句成组，不同逻辑步骤之间留空行。不得通过多语句压行、复杂三元表达式或删除空行控制规模。
- 仅为独立职责、复杂逻辑或真实复用提取方法和类；不为几行代码增加转发层，不创建无明确边界的 utils/common 业务集合。
- 方法和文件围绕职责组织，不设机械的行数目标。规模控制来自删除重复与弃用逻辑，而不是拆文件或压缩格式。
- 注释说明单位、所有权、不变量、生命周期和取舍，不复述代码；不保留注释掉的实现或无归属 TODO。

C++ 和 Python 均须在同一个代码块内部按逻辑分段，不能把整个函数、循环体或条件分支中的多步处理连续挤在一起：

- 紧密相关的赋值与操作保持成组；输入解释、准备数据、执行操作、更新状态、生成结果等步骤切换处适当留一个空行。提前返回的校验与后续主流程之间也应适当分隔。
- 重要且不直观的位置补充简短注释，解释身份映射、依赖顺序、资源生命周期、时间或计费边界等关键约定及原因；注释放在所说明的逻辑组之前。
- 不机械地每行留空、不要求每个分支都写注释，也不对连续字段初始化或简单映射强行分段。空行和注释服务于阅读，不以增加行数为目的。
- 修改现有 C++、Python 方法时一并整理其内部逻辑分组。格式工具只负责基础排版，不能替代对分段和重要注释的人工审阅；不得借此改变业务行为或扩张功能。

### 1.1 控制规模，不用代码量换质量

- 不盲目扩张功能、支持范围、类层次、配置项或依赖；每项扩展必须对应当前实际需求和明确消费者。
- 持续关注整体逻辑复杂性与对应代码复杂性，不等运行失败或周期审查才处理冗杂。发现重复职责、同一事实多处维护、跨层耦合或局部分支不断增加时，及时修正职责、数据流与复用，并删除被替代的实现；不能继续添加分支、包装、检查和特例掩盖设计问题。
- 不为假想需求预建通用框架、插件系统、注册中心、复杂策略层或多套后端。未来方向可以写计划，代码只落实当前需要。
- 新增代码的价值以行为正确、可解释、可复用和易维护衡量，不以代码量、类/文件数量、检查数量或功能数量衡量。
- 性能模型精度不足时，先核对观测、语义、依赖、成本边界与模型适用域；不默认通过增加代码或细分特例提高分数。
- 复杂度确有必要时，在现有设计或计划说明解决的问题、证据和影响范围；不能以“更健壮”“更完整”作为无边界扩张的理由。
- 代码规模是观察指标，不是可读性的替代。不得为减少行数压缩表达，也不得为看似完整保留无用实现。

### 1.2 禁止硬编码拟合与结果补偿

- 不将手调的拟合系数、耗时常数、分段阈值、经验倍率或补偿表写进业务代码来凑实验结果；移到配置也不能改变这一约束。
- 不按 base/target 身份、workload 名、实验格、配置标签或目标评分分支，逐项指定成本、修正残差或调整预测结果。
- 成本必须来自适用的直接测量、独立采集及明确模型。拟合参数由规定的数据和算法产生，记录实际来源、特征、单位与适用域。
- 合理的模型公式和真实实现分支可以编码；常量与阈值必须有物理、协议或原生实现依据，不能以它们伪装人工调参。
- 不用 target E2E、调度、命中或误差反推预测参数；不通过拟合吸收错误结构、重复计费、未知 CPU gap 或观测开销。
- 数据缺失或模型域外时返回缺口、限制或不支持，不添加无关常数兜底。固定范围内的查表/插值必须对应真实测量，不能是按目标成绩编造的答案表。
- 改进先建立可解释机制，再用独立数据验证泛化；不能以当前实验分数上升代替模型正确性与维护性。

### 1.3 不以补采和特例替代参数化设计

实施顺序固定为：**原生机制与支持域 → 模板/参数/有限变换合同 → 最小证据和有界建库 → 固定资产的动态展开验收 → 成本建模**。不采用“先跑 demo，缺什么补什么，直到案例通过”的开发路线。

- **先解释复用，再采集**：按模型区域与 serving 机制定义模板，说明固定结构、动态参数、原生分支条件、端口和依赖。结构采集覆盖机制，不枚举 request 长度、批次组合或请求身份。
- **采集必须回答明确问题**：先查原生实现并复用、重提取已有事实；只有仍缺必要证据时才规划观测。每项观测写清缺什么、如何触发、取得什么即结束；未知分支条件不能靠不断试采证明。
- **三种规模同时受约束**：累计采集/后处理/存储开销、模板定义规模、规则规模分别说明。换配置、request、重试或恢复不重置预算；开销到限停止本次尝试。用户已授权后续采集额度由执行者自主制定，无须逐次请求确认；新增额度须先说明必要性、复用收益和有界停止条件，并追加累计记录，不因单个缺口盲目扩大上限。具体数值随任务填写，不硬编码通用轮数。压缩保留量、导出前体积和临时峰值分开记录；压缩后达标不能证明采集期间全程空间达标。
- **新输入不等于新定义**：同一支持域、同一实现分支的新请求应增加实例与目标展开工作。若必须逐长度新增模板或逐案例增加规则，先修正参数化设计，不能以更多成功案例宣称泛化。真实分支差异才构成新增变体或规则的理由。
- **缺口不直接触发采集**：模板消费者只返回结果或明确缺口；抽象/规则缺陷修公共实现，观测缺失先修记录合同，范围外明确拒绝。结构合格后的成本缺口由 S5 按性能单元处理，不重采整段 serving 结构。
- **同类缺口反复出现时收敛设计**：暂停增加局部映射、wrapper、子类与特例，检查共同边界、参数来源和依赖表达。修正应解决一类问题，完整删除被替代的实现；将特例移入配置也不算收敛。
- **新增工作须带来明确覆盖收益**：每项采集或规则变更关联已有覆盖表中的关系或缺失事实，说明解决哪一类输入，并记录被替代、删除的特例。仅增加同类样本、已映射节点数或成功案例，不作为继续扩张及阶段完成的依据；必要的局部实现仍须服务整体结构验收。
- **固定资产独立验收**：验收期间不追加模板和规则。验证输入一旦用于修正或补证据，就成为开发证据；修正后换未参与修改的输入验收。不增加内部版本、摘要或冻结副本机制。
- **停止与完成分开**：覆盖表内承诺的关系和证据齐备才算建库完成；预算耗尽、观测失败或抽象缺陷只结束本次尝试，保留未完成项。补采不是保证所有探索组合最终成功的兜底机制。

上述要求复用现有计划、覆盖表和执行记录，不新增规划平台、规则治理服务或独立 test 工程。具体执行依据见[采集设计](04_collection_templates.md#建库方案与结束条件)，联合验收见[验收合同](08_acceptance_delivery.md#固定资产下的泛化与规模验收)。

### 1.4 建模范围与开发粒度

只模拟项目统一流程定义的子图，以及子图之间必要的依赖、完成端口和状态变化。原生观测可以更广，但看到一个事件不构成把它纳入仿真的理由。模板外服务默认排除，不以完整 CPU 后台活动、HTTP 时延或清空未归属诊断作为阶段门槛。

2026-10-16 交付的性能闭环采用[CPU 排除范围](06_performance_execution.md)，历史结果保持原口径。2026-10-17 后续工作按[稳态、分层模板与 CPU 计划](../redesign-workflow/2026-10-17_steady_state_template_cpu_plan.md)重新定义必要 CPU 工作及独立成本：先明确行为、边界和结构，再采样建模。不得恢复逐函数/逐 API 补齐路线，也不把完整 CPU 残余、内部时钟或后台活动还原作为门槛；禁止整段 run_batch 墙钟叠加设备成本。真实等待由依赖计算，同步 host 复制仍归传输。沿现有成本链扩展，不预建可选 CPU 后端、不以未知填零、不维护旧兼容计费链；当前代码事实与目标能力分别说明。

- 先判范围，再判影响。范围外工作若确实影响范围内必要因果，优先以边界输入、初始状态或端口关系表达；有具体证据表明现有合同不足时才提出范围调整，不沿原生执行无限补实现。
- 语义模板与成本粒度独立。内部区域在独立复用、参数变换、对外执行/控制行为或计时边界需要时细化；不为每个性能节点建立语义类，不要求逐指令/逐 API 还原。范围内 CPU 循环量优先参数化，原生包装函数变化不自动成为新模板或新成本类型。
- 对未变换的模板内容沿用已建立的合同和证据；重点验证变换区域、外部连接和状态效果。相关实现改变或出现具体反证时才扩大检查，不能以原生全事件逐项一致代替约定范围的正确性。
- 分析前说清可能影响哪个结果、当前抽象哪里不足、什么证据足以停止。优先代码语义、现有观测及必要的耗时上界；不要求每个细节做消融，也不因影响未知自动启动采集。
- 每轮围绕一个完整能力缺口推进，先明确职责和完成条件。新发现分为当前阻塞、范围外限制、后续能力或待验证风险；不自动把所有发现加入当前门槛。收紧范围不掩盖已有承诺，复杂度真实必要时继续完成，不急于求成。
- 支持与拒绝由模板合同及实际变换规则的适用条件产生。静态筛选与实例化复用同一依据，不按失败样本堆积黑名单，不把配置标签、采集编号或某次节点数当成支持条件。动态才能确定的条件在实际应用时返回原因，不预建重复验证器。

这些是推进原则，直接约束工作方式；不因此新增“范围检查器”“粒度评分器”、覆盖平台或逐项代码任务。进度以交付能力和退出条件表示，不以检查、事件或采集数量换算百分比。

### 1.5 性能采样的适配边界

- 采样方案同时满足对象与子图一致、适配简洁、跨框架有共同实现途径、容易构造有界特征范围四项要求，详细合同只维护在[独立性能采样](04_collection_templates.md#独立性能采样合同)。
- 原生采样中的请求、批次、KV、执行更新与回收由框架管理；不为采样自行编排或复制这套状态机。此约束不禁止采集窗口/进程生命周期管理，也不取消仿真核心按合同维护目标状态的职责。
- 性能插桩与语义插桩职责及生命周期分开，共享工作描述、必要归属和底层观测能力；不复制整套语义提取流程，不为了命中特征篡改原生调度、输入状态或目标配置。
- 框架专有 benchmark 或底层 forward 仅是候选执行载体，其存在不证明满足本项目采样需求。公共抽象不得依赖某框架的 batch 类型或默认所有框架有同类入口；不预建逐算子重放平台和复杂反向求解器。
- 特征覆盖以实际工作为准，区分独立特征点与重复测量；未知或不可达条件保留限制，不用更多记录数、逐节点请求特例或无限补采替代覆盖与泛化证据。
- 性能需求推导、覆盖分析及采样交接是正式产品流程，不能由开发者查看 trace、一次性脚本或逐个补齐案例长期代替。性能对象按具体名称、计时边界和必要特征定义；需求分析与拟合/查询共用合同，不另建覆盖规则。机制见[性能需求推导与覆盖分析](06_performance_execution.md#性能需求推导与覆盖分析)。

## 2. 面向类组织核心，避免函数式架构

仿真核心使用面向对象设计。控制器、模板处理、成本提供者和模拟执行等实际职责由类表达，状态和操作在明确对象中封装。

- 类必须有实际职责或数据合同。固定结构的值对象可以用 struct，不为每组字段制造空壳管理类。
- 业务流程使用清晰的成员方法调用和显式状态推进，不使用闭包链、函数组合、回调管道或传递函数来承载完整流程。
- 不使用高阶函数/策略函数替代控制器、成本提供者等主要业务对象，不把状态藏在捕获列表或模块全局变量中。
- 简单局部比较器、标准库算法所需短 lambda 可以使用；它们不承载业务生命周期，不超出引用对象的生命周期。
- 优先组合，继承只用于确有替换实现的接口。类层次保持浅，不给每个类增加抽象基类、工厂或转发包装。
- 统一控制合同以类接口表达，轻量控制器和未来原生适配器围绕同一合同实现；接口不暴露具体框架对象或可任意修改的内部图。
- 状态只维护一份；同一事实不同时保存在 controller、runtime 和额外 manager 中。读取使用明确的只读视图。
- 不用万能单例、服务定位器、全局 registry 或庞大的上下文对象隐藏依赖；通过构造和必要方法参数明确依赖关系。
- 无状态、局部的数值转换等辅助操作可以是普通函数；核心业务对象与流程仍按类组织。

面向类不意味着所有字段都需要 getter/setter，也不意味着每几行逻辑都要拆成一个对象。核心流程的可读性优先于形式化设计模式。

## 3. 最少必要的校验与错误处理

- 外部配置、文件、采集数据与适配器输入在进入系统时校验一次；内部使用已建立类型与不变量，不逐层重复解析和检查。
- 不因为某个错误“理论上可能发生”就增加 assert、throw、raise、空值检查、存在性检查、默认兜底或重试。
- 标准库能够清楚报错时直接调用；不先判断存在再打开，不捕获后原样重抛，不多层包装同一错误。
- 仅在能够恢复、释放资源或确实需要补充位置上下文时处理异常。不得吞错、输出伪造成功或默认空产物。
- 可预期的业务结果用明确返回类型表达，例如成本可用、缺数据、不支持；缺失不得转换为 0。
- 保留真实输入约束、资源和内存安全、预测/评价隔离、DAG mutation 及关键时间不变量所需校验。精简不能掩盖已知错误。
- 优先通过所有权、合适类型和单一数据流消除非法状态，不增加一致性账本或一组重复标志。
- 不新增 SHA256/checksum/digest、文件指纹、重复读回比对、内部 schema/版本握手或冻结副本来证明本地产物有效。

每项新增检查在审阅时应能说明其对应的真实边界或业务条件；不需要另建校验清单或检查记录系统。

## 4. Modern C++23 规范

### 4.1 工具链与布局

- 仿真核心采用 C++23，CMake 3.20 及以上；明确设置标准、要求标准可用、关闭编译器语言扩展。
- 新源文件加入所属正式 target，公共头文件与实现分开，引用路径从 include 根开始。具体新目录在职责明确后确定，不继承旧目录作为兼容要求。
- 头文件使用 pragma once，直接包含所用声明，不依赖偶然的传递包含；头文件不得使用 using namespace。
- 类型使用 PascalCase，方法、函数和变量使用 snake_case，私有成员后缀为下划线。不要开展与任务无关的批量更名。
- 格式采用 4 空格、无 Tab、LF，C++ 行宽 160 列。落实到项目 clang-format 配置，只格式化本次修改文件，不用个人默认样式覆盖。

C++ 文件必须按抽象职责分目录，`src/markov/include/markov` 与 `src/markov/src` 使用对应的子目录。具体职责见[当前目录布局](development.md#c-目录与职责)。新增实现归入已有职责，只有独立职责确实成立时才增加目录；不把框架专属规则放入通用目录，也不为目录分层增加空类、转发头文件或兼容路径。移动文件同步更新 CMake、include 与文档引用。

分层同时约束依赖：`contracts`/`graph` 和统一模板消费者不依赖具体适配实现。公共 `production` 只保留绑定接口、共同调用记录和子图提取；原生框架解释归入 `adapters/frameworks/<框架>`，框架中的模型模块声明归入 `models`；profiler、SDK、硬件事件及通信实现解释归入 `adapters/runtimes/<环境>`。框架适配器可组合 runtime，runtime 不反向依赖框架。`controller`、`execution` 与 `performance` 不新增框架专属判断；`workflow` 装配，`cli` 只承担入口。CMake 依赖固定向内：workflow → adapters → core，不以文件移动代替依赖隔离。 依赖检查包含头文件的传递包含：具体框架配置属于 adapters，集合 Project 属于 workflow；core 只使用 Request、Environment、ServingLimits 等公共值，不经公共头文件间接依赖具体框架类型。

Python 采集代码同样分为 workflow、instrumentation、artifacts 和 adapters；公共 wrapper、标量记录与产物合同不得导入具体框架或 runtime。通过实际需要的浅层类接口注入 profiler 能力；不为每个 block 或未来环境创建空类。框架版本影响插桩位置，env 影响导出及解析，这两类变化不得散落到公共采集流程。原生版本是部署条件，不增加内部 v1/v2 或向后兼容入口。移动模块必须同步 import、Python 插件入口、子进程 `-m` 路径、源码根目录定位、CMake、Docker COPY 和当前使用文档。

框架、模型、并行策略和环境的支持资格按实际组合判定，不由目录存在、单独安装成功或某个组件的版本号推导。环境相关 patch、原生观察头文件、依赖固定与适用说明随适配器维护；Dockerfile 负责组合、复制和直接调用适配器，不增加无行为的转发安装层。框架专属环境修正放在 `adapters/frameworks/<框架>/<环境>`，公共 runtime 修正放在 `adapters/runtimes/<环境>/<组件>`。迁移同时更新构建来源元数据和运行时 import，不修改历史采集的原始来源记录。

### 4.2 所有权与生命周期

- 使用 RAII 管理文件、进程、锁、设备句柄和其他资源；正常返回与失败都有明确释放路径。
- 优先值语义、标准容器和 unique_ptr；shared_ptr 仅用于真实共享所有权，不作为默认依赖传递方式。
- 不以裸 new/delete 管理业务资源。裸指针、引用、span、string_view 仅表达有明确生命周期的非拥有访问。
- 只读对象使用 const，只读大对象使用常量引用或合适视图；跨对象保存视图时必须明确原对象生命周期。
- 注意容器扩容、删除和异步任务对引用/迭代器的影响；不在延迟动作中捕获即将销毁的局部对象。
- 没有特殊资源语义时使用编译器生成的特殊成员；不可复制资源明确禁止复制，不为普通值对象手写复制/析构。

### 4.3 类型与语言设施

- 使用 enum class 表达有限类别，不用散落字符串或整数代表核心状态。
- optional 表达真正可缺失值，variant 或 expected 等表达确有需要的结果；不为简单值增加多层包装。
- 非预期失败与可恢复业务缺口分开，错误类型和返回含义在接口处说明。
- 显式转换整数符号、范围和单位，不以无符号下溢表达负时间/缺失；溢出控制集中于真实输入与数值边界。
- auto 在类型由表达式清楚可见时使用；关键合同、所有权或单位不清楚时写明类型。使用明确构造，必要的单参数构造标为 explicit。
- 使用标准库和简单算法，默认选择显式循环。不要以现代 C++ 为理由堆叠 ranges 管道、模板元编程、宏生成或难读的泛型抽象。
- 不要求为了使用 C++23 而使用每个新设施。工具链缺少实际需要的设施时修正 modeling 环境，不维护旧标准的回退实现。
- 不随意加 noexcept、nodiscard、assert 或自定义属性；仅在合同和用途明确时采用。

### 4.4 封装与执行语义

- 通过明确对象方法更新 DAG、资源和状态，模板变换作为原子 mutation，不旁路修改内部存储。
- 控制器决定业务动作，执行核维护资源和唯一模拟时钟；不在多个类中重复维护同一时钟或完成状态。
- CPU 步骤、设备完成、发布和等待分别表达；模拟器宿主机执行时间不作为目标服务成本。
- 先落实统一流程、语义插桩、base 模板及给定节点耗时下的动态结构，再实现节点成本模型；扩大整批长度组合采样域不替代结构完成条件。
- 给定耗时是有来源、单位和假设的显式执行输入，复用正式控制与执行核；不造第二套测试后端、不填未知为零、不把条件化时序当成性能预测或生产拟合参数。
- 语义模板与性能单元粒度分别确定；内部节点/依赖和外部端口保留，有限变换明确前提、参数映射、节点/边改动及不支持域，不推定任意 shape 都保持执行结构。
- 模板、执行和性能共用目标工作值合同。执行层解析批次/成员上下文后再查询成本；模型不接收完整控制动作或模板参数化对象。给定耗时的来源键与实测成本特征分开传递，诊断上下文由拥有它的执行层输出。
- 诊断代码通过明确开关隔离；Release 正确性不能依赖 Debug 分支。正式产品错误不靠仅 Debug 有效的断言发现。

## 8. 不用的功能完整删除

确认某功能弃用后，围绕整个职责链删除，不只隐藏用户入口或加 disabled 标志：

1. 删除实现、无消费者类型/方法和只为它存在的适配层。
2. 删除 CLI 参数、配置字段、解析、分发、注册与调用方。
3. 删除专属构建 target、依赖、容器步骤和无消费者产物生成。
4. 更新当前示例与文档，删除指向旧入口的说明。
5. 审查引用和 diff，确认没有死分支、兼容包装或注释掉的实现。

声明为后续扩展的功能，例如原生控制器，可以保留具体计划；不提前写占位实现、空壳类、永远不启用的分支或重复后端。仍有实际用户的可选诊断功能不因默认关闭而当作死代码。

删除功能不等于清理用户数据。历史 profile、独立测量、目标评价和对照资产先确认来源与用途，不作为临时文件随意删除；不改原仓库或回滚用户已有改动。

## 9. Python、Shell、配置与副作用

- Python 用于确有需要的采集、适配和编排，兼容 3.10；业务职责按对象组织，不把核心仿真算法复制到 Python 入口。
- Python 使用 4 空格、双引号、LF、120 列，明确类型与固定结构对象；JSON 只在外部边界是原始字典。
- 不为复用旧辅助函数而导入 deprecated；需要的通用能力在新职责下实现或有依据地迁移。
- Shell 使用 Bash、set -euo pipefail、正确引用和参数数组，只做容器/构建薄封装；不使用 eval 或拼接外部输入为命令。
- CLI 负责输入、调用与呈现，不承载模板变换、调度或成本公式。导入模块不启动容器、服务、采集或写产物。
- 默认值来自明确语义，必填字段不通过连续 get/default 隐藏缺失。新增字段同步全部实际消费者和例子。
- 优先标准库与现有依赖，不为格式、重试或插件发现引入大型框架。
- 日志记录必要的进度、缺口和定位；不输出临时调试内容，不在配置或日志里写密钥。

### 9.1 探索合同与模板扩展约束

最终输入使用固定模型、配置集合与 request workload 集合，用户不指定 base。实现迁移时同步替换解析、编排、恢复、报告和示例，不维护旧单 base 合同兼容层。当前运行文档可明确记录尚未迁移的实现，不能将设计字段写成已支持命令。

采集规划参考 Dooly 的代表 request、增量发现及共有资产复用，不预建最优 base 搜索框架。五类顶层 block 保持控制职责，内部区域仅在独立变换、复用或外部事件需要时引入，不为每个区域强制创建类。结构先行、成本后置；多来源模板不能混入独立目标验证资产，缺数据不能填零。

### 9.2 框架差异只通过模板生产端接入

- 外围装配也须解耦：`workflow` 通过统一适配接口取得规范化配置、模板来源选择结果及控制器装配所需的公共参数，不直接解析具体框架配置或按框架名称选择业务路径。框架选择只在入口组合处绑定具体适配实现；共同控制器的创建使用公共合同，不向模板注入私有控制器。适配差异集中在模板生成与有限变换规则的生产、绑定，调度器不关心模板采集方式与来源。
- 支持条件由模板合同与实际变换规则共同提供，外围装配不另建一套重复的拒绝规则。接口按现有职责提取，不为未来框架预建插件平台、空壳实现或逐案例检查分支。
- 在已有公共能力范围内，新增框架的业务改动集中于入口绑定、事实提取、语义解释及模板化；共同控制器、展开器、执行核和成本调用不增加框架名称分支。
- wrapper、事件关联、子图装配和参数关系处理复用公共流程。仅为真实差异提供浅层继承或组合扩展，不复制整条链路，不建立万能适配器。
- 模板统一表达参数、节点/依赖、资源、状态效果、端口、有限变换与性能单元；不携带 Python 对象、原生函数回调或私有控制器。来源名称仅用于追溯。
- 公共状态只有一个维护者，模板声明读写及生效条件；框架专属来源解释不能渗透为核心 KV/调度特例。
- 新通用能力确实缺失时统一修改合同与实现，并保留范围外结论。禁止通过更名、搬目录或框架专属策略回调伪装核心已解耦。
- 接入验收检查改动落点和实际模板消费，不以相同 JSON 字段名或类型可解析作为跨框架成立的证明。此要求不授权当前提前实现 KT 或原生控制适配。

## 10. 周期性整体审查

持续开发不能只审查本轮 diff。默认每完成五个有实质代码修改的工作批次，或进入下一阶段前，对活动代码做一次整体审查；出现同类缺口反复补丁、重复支持判断、跨层增加框架特例或公开结果与声明不一致时，提前触发。不按工具调用数计数，不为计数新增程序、状态文件或定时任务，沿用执行记录。

周期审查以代码层次、代码风格、逻辑整理和代码收紧为主体：检查目录与类的职责、依赖方向、命名与逻辑分段、状态所有权，并删除重复实现、多余包装、防御性代码和临时特例。不能以功能缺口清单或阶段进度报告代替代码整体检查；功能资格与阶段验收单独记录。

- 从公开入口贯穿输入、模板生产、控制、变换、执行和结果，审阅 C++、Python 与构建的实际职责和调用链，酌情直接整改并验证行为；不能只检查格式、文件大小和编译成功。
- 检查职责和依赖是否符合抽象边界，同一事实、状态和支持规则是否只有一个维护者；是否存在无消费者抽象、重复实现、防御性包装、兼容分支或应删除的功能。
- 检查有限变换在正式路径上是否可达，以及范围、来源、参数、拓扑、端口和状态是否共同成立；区分已编码、诊断预览、同输入保持和独立目标验证。
- 检查硬编码的依据。原生符号和真实分支常量可存在于生产适配端；针对样本身份、长度组合或结果的特例不能冒充通用机制。检查规则增长是否带来可解释的支持域收益。
- 检查采集累计预算、缺口处理和验证资产用途，不能用补采或成本拟合掩盖结构问题。没有必要证据不新增设备任务。
- 记录有代码位置的发现、影响、优先级、最小整改与关闭证据；区分确认缺陷、架构债务和待验证风险。不用扫描命中或代码行数直接判定违规，不宣称静态审查证明运行正确。

审查使用现有计划和执行记录，必要时在 docs/redesign-workflow 下形成日期加 purpose 的报告，不建设审查平台或独立 test 工程。影响结构正确性或阻断当前目标的发现先整改，再扩展相关能力；其他项进入有边界的后续任务。整改以消除问题和通过必要公开入口验证收口，不以搬目录、增加接口或减少行数收口。

**记录方式。** 执行日志以一个里程碑或重要决策为单位，记录“日期与目的、实际结果、证据位置、适用范围/未证明部分”四项，必要时补累计资源变化。同一能力的连续小修合并到同一条；无实质结果的进度答复、常规构建和格式检查不单独成章。不要机械要求每次工具调用留文档。

**任务分类。** 当前计划明确区分“必须实现的交付”“持续遵守的约定”“范围外/后续能力”和“待验证风险”。约定不勾选为代码任务，风险没有具体影响证据时不自动成为门槛。源码已接入、开发回归、独立验证和真实性能精度分别表述；报告字段或拒绝路径通过不代表能力完成。

**状态维护。** 全局能力只在主计划维护，专项任务只在对应计划维护。用户限定“只做计划”时，仅修改文档并作必要只读盘点；保留已有代码事实，不能依据旧目标继续实施。历史状态须带日期，旧授权等待不能冒充当前审批要求。证据用于修正后，在其主记录改为开发用途，并撤销其他文档中仍称独立的表述。

**历史证据。** 审查报告是带日期的实现快照；新的整体审查先复核旧发现，不复制旧待办。数据删除后同步撤下活动文档中的失效资产入口，必要历史路径标为不可复核。保留关键限制、失败和取舍，不再要求从已删除数据恢复，也不复制旧文档全文归档。

逐文件源码审阅清单可作为同一审查记录的机器可读附件保存在 `docs/redesign-workflow/evidence/`；它记录内容身份和审阅归属，不保存运行数据或代替运行验证。采集、预测与构建证据仍放在对应 data 运行根下。

**目录与收口。** `docs/redesign/` 保存设计合同、开发说明和按需技术参考；设计编号用于导航，标题按职责命名，不再把主题编号写成执行阶段。`docs/redesign-workflow/` 保留主计划、里程碑及当前专项的计划/审查正文。已结束或被替代的专项记录移动到 `history/`，不复制备份；同步修改所有本地引用。一个专项使用同一份计划和审查记录，不能每轮新增同主题文档。历史文件不继续追加当前任务，活动文档通过链接引用其结论。

**提案与事实。** 未实现的目录、命令和清理规则只写在专项计划并标为拟实施。审查状态至少区分“待核对”“已确认待改”“源码已改待验证”“已在限定范围验证”；关闭要给出证据及边界。开发说明只陈述已有行为，局部验证不升级为全量审查、完整恢复或端到端交付。

**变更与证据对齐。** 先读主计划、专项及相关合同，再对照当前源码和证据。已有实现不写成“尚未实现”，新改动不自动继承旧运行的通过结论；初始基线、当前盘点与目标目录分别标注。未验证部分进入同一审查记录，不能重复建功能或提前勾选完成。

**压缩与检查。** 合并重复流水，更新原结论，保留机制前提、支持边界及必要证据。开发说明维护操作，设计维护合同，计划维护实施顺序；不要让三处各有一份待办。大文档先按流程整理章节和导航，不以删依据、挤长段或硬拆文件降低行数。整理后检查职责、链接/锚点、状态冲突与实际 diff，文档核对和代码审查分别报告。纯文档变更不触发构建、采集、数据清理或任务恢复；交付只记录本轮实际修改。

## 11. 适用与交付

实现前检查工作区，阅读当前设计合同及本文件；发现旧文档与当前约束冲突时按用户最新取舍统一文档，不静默沿用旧合同。

交付需说明具体修改、行为与范围影响、实际检查及结果。构建与仿真检查在 modeling 容器内完成；纯文档修改无需构建。

本文件定义约束，不预先建立一套审批、合规或检查平台。实际格式配置、正式 target 和入口随实现落地；文档中的规则不能被误报为工具链或程序已经实现。

### Git 提交格式

提交标题统一采用 `type(scope): summary`，使用英文、祈使语气，简洁说明本次实际改变；不以阶段编号或“完成全部”代替具体内容。

- `type` 使用 `feat`（功能）、`fix`（缺陷）、`refactor`（结构调整）、`perf`（性能优化）、`build`（依赖与构建）、`docs`（文档）、`style`（纯排版）、`chore`（其他维护）。
- `scope` 对应职责，例如 `collection`、`templates`、`controller`、`execution`、`performance`、`adapters`、`docker`、`deps`、`redesign`、`archive`；跨层改动选择共同职责，不强行拆开紧密耦合的接口与消费者。
- 一个提交表达一个可审阅的变更目的。大量存量改动可按依赖、历史归档、实现、文档分层提交；归档不等于阶段功能完成。
- 非平凡改动在正文说明原因、主要行为、实际验证及尚未验证的边界。不得把给定节点耗时下的结构验证描述成成本预测精度验证。
- 构建产物、采集数据、凭据及本地环境不提交。推送当前开发分支，不直接更新主分支，不使用强制推送覆盖远端历史。

示例：`refactor(collection): separate framework hooks from runtime observation`。
