# Redesign 代码与工程约束

本文件约束 redesign 的自有代码、构建、配置和文档，作为实现与审阅依据。用户明确指令优先。必须/不得是硬性规则；优先是默认选择，偏离时说明实际理由。

目标是简洁、有序、容易理解与维护，以最少的必要机制完成声明范围内的功能。约束从新增代码和被修改的职责链落实，不开展无关的全仓格式化或清理。

## 1. 简洁有序的代码风格

- 主流程应自上而下表达业务步骤，同一方法内保持同一抽象层次，编排与底层操作分别组织。
- 优先显式变量、普通循环、提前返回和简单分支，减少深层嵌套、隐式状态和跨层跳转。
- 命名表达业务含义，时间、字节、页等字段写清单位；数值规则使用有依据的常量或配置。
- 紧密相关语句成组，不同逻辑步骤之间留空行。不得通过多语句压行、复杂三元表达式或删除空行控制规模。
- 仅为独立职责、复杂逻辑或真实复用提取方法和类；不为几行代码增加转发层，不创建无明确边界的 utils/common 业务集合。
- 方法和文件围绕职责组织，不设机械的行数目标。规模控制来自删除重复与弃用逻辑，而不是拆文件或压缩格式。
- 注释说明单位、所有权、不变量、生命周期和取舍，不复述代码；不保留注释掉的实现或无归属 TODO。

C++ 和 Python 均须在同一个代码块内部按逻辑分段，不能把整个函数、循环体或条件分支中的多步处理连续挤在一起：

- 紧密相关的赋值与操作保持成组；输入解释、准备数据、执行操作、更新状态、生成结果等步骤切换处适当留一个空行。提前返回的校验与后续主流程之间也应适当分隔。
- 重要且不直观的位置补充简短注释，解释身份映射、依赖顺序、资源生命周期、时间或计费边界等关键约定及原因；注释放在所说明的逻辑组之前。
- 不机械地每行留空、不要求每个分支都写注释，也不对连续字段初始化或简单映射强行分段。空行和注释服务于阅读，不以增加行数为目的。
- 修改现有 C++、Python 方法时一并整理其内部逻辑分组。格式工具只负责基础排版，不能替代对分段和重要注释的人工审阅；不得借此改变业务行为或扩张功能。

### 1.1 控制规模，不用代码量换质量

- 不盲目扩张功能、支持范围、类层次、配置项或依赖；每项扩展必须对应当前实际需求和明确消费者。
- 优先修正职责、数据流、机制与复用，消除重复；不能靠不断添加分支、包装、检查和特例掩盖设计问题。
- 不为假想需求预建通用框架、插件系统、注册中心、复杂策略层或多套后端。未来方向可以写计划，代码只落实当前需要。
- 新增代码的价值以行为正确、可解释、可复用和易维护衡量，不以代码量、类/文件数量、检查数量或功能数量衡量。
- 性能模型精度不足时，先核对观测、语义、依赖、成本边界与模型适用域；不默认通过增加代码或细分特例提高分数。
- 复杂度确有必要时，在现有设计或计划说明解决的问题、证据和影响范围；不能以“更健壮”“更完整”作为无边界扩张的理由。
- 代码规模是观察指标，不是可读性的替代。不得为减少行数压缩表达，也不得为看似完整保留无用实现。

### 1.2 禁止硬编码拟合与结果补偿

- 不将手调的拟合系数、耗时常数、分段阈值、经验倍率或补偿表写进业务代码来凑实验结果；移到配置也不能改变这一约束。
- 不按 base/target 身份、workload 名、实验格、配置标签或目标评分分支，逐项指定成本、修正残差或调整预测结果。
- 成本必须来自适用的直接测量、独立采集及明确模型。拟合参数由规定的数据和算法产生，记录实际来源、特征、单位与适用域。
- 合理的模型公式和真实实现分支可以编码；常量与阈值必须有物理、协议或原生实现依据，不能以它们伪装人工调参。
- 不用 target E2E、调度、命中或误差反推预测参数；不通过拟合吸收错误结构、重复计费、未知 CPU gap 或观测开销。
- 数据缺失或模型域外时返回缺口、限制或不支持，不添加无关常数兜底。固定范围内的查表/插值必须对应真实测量，不能是按目标成绩编造的答案表。
- 改进先建立可解释机制，再用独立数据验证泛化；不能以当前实验分数上升代替模型正确性与维护性。

### 1.3 不以补采和特例替代参数化设计

实施顺序固定为：**原生机制与支持域 → 模板/参数/有限变换合同 → 最小证据和有界建库 → 固定资产的动态展开验收 → 成本建模**。不采用“先跑 demo，缺什么补什么，直到案例通过”的开发路线。

- **先解释复用，再采集**：按模型区域与 serving 机制定义模板，说明固定结构、动态参数、原生分支条件、端口和依赖。结构采集覆盖机制，不枚举 request 长度、批次组合或请求身份。
- **采集必须回答明确问题**：先查原生实现并复用、重提取已有事实；只有仍缺必要证据时才规划观测。每项观测写清缺什么、如何触发、取得什么即结束；未知分支条件不能靠不断试采证明。
- **三种规模同时受约束**：累计采集/后处理/存储开销、模板定义规模、规则规模分别说明。换配置、request、重试或恢复不重置预算；开销到限停止本次尝试。用户已授权后续采集额度由执行者自主制定，无须逐次请求确认；新增额度须先说明必要性、复用收益和有界停止条件，并追加累计记录，不因单个缺口盲目扩大上限。具体数值随任务填写，不硬编码通用轮数。
- **新输入不等于新定义**：同一支持域、同一实现分支的新请求应增加实例与目标展开工作。若必须逐长度新增模板或逐案例增加规则，先修正参数化设计，不能以更多成功案例宣称泛化。真实分支差异才构成新增变体或规则的理由。
- **缺口不直接触发采集**：模板消费者只返回结果或明确缺口；抽象/规则缺陷修公共实现，观测缺失先修记录合同，范围外明确拒绝。结构合格后的成本缺口由 S5 按性能单元处理，不重采整段 serving 结构。
- **同类缺口反复出现时收敛设计**：暂停增加局部映射、wrapper、子类与特例，检查共同边界、参数来源和依赖表达。修正应解决一类问题，完整删除被替代的实现；将特例移入配置也不算收敛。
- **新增工作须带来明确覆盖收益**：每项采集或规则变更关联已有覆盖表中的关系或缺失事实，说明解决哪一类输入，并记录被替代、删除的特例。仅增加同类样本、已映射节点数或成功案例，不作为继续扩张及阶段完成的依据；必要的局部实现仍须服务整体结构验收。
- **固定资产独立验收**：验收期间不追加模板和规则。验证输入一旦用于修正或补证据，就成为开发证据；修正后换未参与修改的输入验收。不增加内部版本、摘要或冻结副本机制。
- **停止与完成分开**：覆盖表内承诺的关系和证据齐备才算建库完成；预算耗尽、观测失败或抽象缺陷只结束本次尝试，保留未完成项。补采不是保证所有探索组合最终成功的兜底机制。

上述要求复用现有计划、覆盖表和执行记录，不新增规划平台、规则治理服务或独立 test 工程。具体执行依据见[采集设计](04_collection_templates.md#建库方案与结束条件)，联合验收见[实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md#轻量与泛化的联合验收)。

## 2. 面向类组织核心，避免函数式架构

仿真核心使用面向对象设计。控制器、模板处理、成本提供者和模拟执行等实际职责由类表达，状态和操作在明确对象中封装。

- 类必须有实际职责或数据合同。固定结构的值对象可以用 struct，不为每组字段制造空壳管理类。
- 业务流程使用清晰的成员方法调用和显式状态推进，不使用闭包链、函数组合、回调管道或传递函数来承载完整流程。
- 不使用高阶函数/策略函数替代控制器、成本提供者等主要业务对象，不把状态藏在捕获列表或模块全局变量中。
- 简单局部比较器、标准库算法所需短 lambda 可以使用；它们不承载业务生命周期，不超出引用对象的生命周期。
- 优先组合，继承只用于确有替换实现的接口。类层次保持浅，不给每个类增加抽象基类、工厂或转发包装。
- 统一控制合同以类接口表达，轻量控制器和未来原生适配器围绕同一合同实现；接口不暴露具体框架对象或可任意修改的内部图。
- 状态只维护一份；同一事实不同时保存在 controller、runtime 和额外 manager 中。读取使用明确的只读视图。
- 不用万能单例、服务定位器、全局 registry 或庞大的上下文对象隐藏依赖；通过构造和必要方法参数明确依赖关系。
- 无状态、局部的数值转换等辅助操作可以是普通函数；核心业务对象与流程仍按类组织。

面向类不意味着所有字段都需要 getter/setter，也不意味着每几行逻辑都要拆成一个对象。核心流程的可读性优先于形式化设计模式。

## 3. 最少必要的校验与错误处理

- 外部配置、文件、采集数据与适配器输入在进入系统时校验一次；内部使用已建立类型与不变量，不逐层重复解析和检查。
- 不因为某个错误“理论上可能发生”就增加 assert、throw、raise、空值检查、存在性检查、默认兜底或重试。
- 标准库能够清楚报错时直接调用；不先判断存在再打开，不捕获后原样重抛，不多层包装同一错误。
- 仅在能够恢复、释放资源或确实需要补充位置上下文时处理异常。不得吞错、输出伪造成功或默认空产物。
- 可预期的业务结果用明确返回类型表达，例如成本可用、缺数据、不支持；缺失不得转换为 0。
- 保留真实输入约束、资源和内存安全、预测/评价隔离、DAG mutation 及关键时间不变量所需校验。精简不能掩盖已知错误。
- 优先通过所有权、合适类型和单一数据流消除非法状态，不增加一致性账本或一组重复标志。
- 不新增 SHA256/checksum/digest、文件指纹、重复读回比对、内部 schema/版本握手或冻结副本来证明本地产物有效。

每项新增检查在审阅时应能说明其对应的真实边界或业务条件；不需要另建校验清单或检查记录系统。

## 4. Modern C++23 规范

### 4.1 工具链与布局

- 仿真核心采用 C++23，CMake 3.20 及以上；明确设置标准、要求标准可用、关闭编译器语言扩展。
- 新源文件加入所属正式 target，公共头文件与实现分开，引用路径从 include 根开始。具体新目录在职责明确后确定，不继承旧目录作为兼容要求。
- 头文件使用 pragma once，直接包含所用声明，不依赖偶然的传递包含；头文件不得使用 using namespace。
- 类型使用 PascalCase，方法、函数和变量使用 snake_case，私有成员后缀为下划线。不要开展与任务无关的批量更名。
- 格式采用 4 空格、无 Tab、LF，C++ 行宽 160 列。落实到项目 clang-format 配置，只格式化本次修改文件，不用个人默认样式覆盖。

C++ 文件必须按抽象职责分目录，`src/markov/include/markov` 与 `src/markov/src` 使用对应的子目录。具体职责见[当前目录布局](development.md#c-目录与职责)。新增实现归入已有职责，只有独立职责确实成立时才增加目录；不把框架专属规则放入通用目录，也不为目录分层增加空类、转发头文件或兼容路径。移动文件同步更新 CMake、include 与文档引用。

分层同时约束依赖：`contracts`/`graph` 和统一模板消费者不依赖具体适配实现。公共 `production` 只保留绑定接口、共同调用记录和子图提取；原生框架解释归入 `adapters/frameworks/<框架>`，框架中的模型模块声明归入 `models`；profiler、SDK、硬件事件及通信实现解释归入 `adapters/runtimes/<环境>`。框架适配器可组合 runtime，runtime 不反向依赖框架。`controller`、`execution` 与 `performance` 不新增框架专属判断；`workflow` 装配，`cli` 只承担入口。CMake 依赖固定向内：workflow → adapters → core，不以文件移动代替依赖隔离。

Python 采集代码同样分为 workflow、instrumentation、artifacts 和 adapters；公共 wrapper、标量记录与产物合同不得导入具体框架或 runtime。通过实际需要的浅层类接口注入 profiler 能力；不为每个 block 或未来环境创建空类。框架版本影响插桩位置，env 影响导出及解析，这两类变化不得散落到公共采集流程。原生版本是部署条件，不增加内部 v1/v2 或向后兼容入口。移动模块必须同步 import、Python 插件入口、子进程 `-m` 路径、源码根目录定位、CMake、Docker COPY 和当前使用文档。

框架、模型、并行策略和环境的支持资格按实际组合判定，不由目录存在、单独安装成功或某个组件的版本号推导。环境相关 patch、原生观察头文件、依赖固定与适用说明随适配器维护；`docker/install` 只承担调用，Dockerfile 负责组合与复制。框架专属环境修正放在 `adapters/frameworks/<框架>/<环境>`，公共 runtime 修正放在 `adapters/runtimes/<环境>/<组件>`。迁移同时更新构建来源元数据和运行时 import，不修改历史采集的原始来源记录。

### 4.2 所有权与生命周期

- 使用 RAII 管理文件、进程、锁、设备句柄和其他资源；正常返回与失败都有明确释放路径。
- 优先值语义、标准容器和 unique_ptr；shared_ptr 仅用于真实共享所有权，不作为默认依赖传递方式。
- 不以裸 new/delete 管理业务资源。裸指针、引用、span、string_view 仅表达有明确生命周期的非拥有访问。
- 只读对象使用 const，只读大对象使用常量引用或合适视图；跨对象保存视图时必须明确原对象生命周期。
- 注意容器扩容、删除和异步任务对引用/迭代器的影响；不在延迟动作中捕获即将销毁的局部对象。
- 没有特殊资源语义时使用编译器生成的特殊成员；不可复制资源明确禁止复制，不为普通值对象手写复制/析构。

### 4.3 类型与语言设施

- 使用 enum class 表达有限类别，不用散落字符串或整数代表核心状态。
- optional 表达真正可缺失值，variant 或 expected 等表达确有需要的结果；不为简单值增加多层包装。
- 非预期失败与可恢复业务缺口分开，错误类型和返回含义在接口处说明。
- 显式转换整数符号、范围和单位，不以无符号下溢表达负时间/缺失；溢出控制集中于真实输入与数值边界。
- auto 在类型由表达式清楚可见时使用；关键合同、所有权或单位不清楚时写明类型。使用明确构造，必要的单参数构造标为 explicit。
- 使用标准库和简单算法，默认选择显式循环。不要以现代 C++ 为理由堆叠 ranges 管道、模板元编程、宏生成或难读的泛型抽象。
- 不要求为了使用 C++23 而使用每个新设施。工具链缺少实际需要的设施时修正 modeling 环境，不维护旧标准的回退实现。
- 不随意加 noexcept、nodiscard、assert 或自定义属性；仅在合同和用途明确时采用。

### 4.4 封装与执行语义

- 通过明确对象方法更新 DAG、资源和状态，模板变换作为原子 mutation，不旁路修改内部存储。
- 控制器决定业务动作，执行核维护资源和唯一模拟时钟；不在多个类中重复维护同一时钟或完成状态。
- CPU 步骤、设备完成、发布和等待分别表达；模拟器宿主机执行时间不作为目标服务成本。
- 先落实统一流程、语义插桩、base 模板及给定节点耗时下的动态结构，再实现节点成本模型；扩大整批长度组合采样域不替代结构完成条件。
- 给定耗时是有来源、单位和假设的显式执行输入，复用正式控制与执行核；不造第二套测试后端、不填未知为零、不把条件化时序当成性能预测或生产拟合参数。
- 语义模板与性能单元粒度分别确定；内部节点/依赖和外部端口保留，有限变换明确前提、参数映射、节点/边改动及不支持域，不推定任意 shape 都保持执行结构。
- 诊断代码通过明确开关隔离；Release 正确性不能依赖 Debug 分支。正式产品错误不靠仅 Debug 有效的断言发现。

## 5. 仿真必须在 Docker 内构建和运行

C++ 仿真代码的配置、编译、静态工具检查和正式执行使用 modeling 容器。宿主机负责代码编辑、Git 和容器调度，不作为仿真工具链或运行结果的验收环境。

现有 modeling 服务定义在 [inference.yml](../../docker/compose/inference.yml)，环境定义在 [Dockerfile](../../docker/images/modeling/Dockerfile)。当前进入环境的命令是：

```bash
docker compose -f docker/compose/inference.yml run --rm --no-deps modeling bash
```

### Git 提交格式

提交标题统一采用 `type(scope): summary`，使用英文、祈使语气，简洁说明本次实际改变；不以阶段编号或“完成全部”代替具体内容。

- `type` 使用 `feat`（功能）、`fix`（缺陷）、`refactor`（结构调整）、`perf`（性能优化）、`build`（依赖与构建）、`docs`（文档）、`style`（纯排版）、`chore`（其他维护）。
- `scope` 对应职责，例如 `collection`、`templates`、`controller`、`execution`、`performance`、`adapters`、`docker`、`deps`、`redesign`、`archive`；跨层改动选择共同职责，不强行拆开紧密耦合的接口与消费者。
- 一个提交表达一个可审阅的变更目的。大量存量改动可按依赖、历史归档、实现、文档分层提交；归档不等于阶段功能完成。
- 非平凡改动在正文说明原因、主要行为、实际验证及尚未验证的边界。不得把给定节点耗时下的结构验证描述成成本预测精度验证。
- 构建产物、采集数据、凭据及本地环境不提交。推送当前开发分支，不直接更新主分支，不使用强制推送覆盖远端历史。

示例：`refactor(collection): separate framework hooks from runtime observation`。
