# 集合闭环、动态反馈与恢复

本文维护集合闭环与恢复合同，当前状态统一见[实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)。主线为 SGLang + Qwen3-32B，结构验收先于节点成本；KT 与原生控制器后续扩展。工程闭环和最终性能精度分别验收，本文不重复阶段进度。

首个性能闭环沿用原生子图、有限变换和轻量控制动态展开，按[性能合同](06_performance_execution.md)排除 host 控制类 CPU 服务耗时；控制、请求/KV 状态以及提交、等待、发布依赖仍保留。设备计算、通信、搬运和设备命令计时，同步 host 复制仍归传输。当前成本入口不再接受旧CPU候选或采样类型，历史产物不自动重分类；实现与验收状态统一见[实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)。

## 配置集 × request workload 集的产品工作流

正式输入为固定模型与两个非空集合，按配置×workload输出独立组合。产品闭环包含代表性建库、模板复用、正式性能需求分析、共享采样建模及受影响组合重算；各项实现状态以[实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)为准，不从单项入口存在推导全部验收完成。

解析输入 → 声明支持域并分析原生机制 → 复用资产、列出最小证据与累计预算 → 有边界的代表性建库 → 核对模板与变换覆盖 → 给定耗时下逐组合动态展开与 S4 结构验收 → S5 性能需求推导与覆盖分析 → 共享的有界采样、建模及成本绑定 → 成本驱动的动态展开与需求细化 → 探索结果矩阵及独立评价。

采集规划参考 Dooly，作为基础编排，不建设最优 base 搜索系统。用户不提供 base 或采集 request；一个代表配置足够则只采一次，多来源采集必须对应建库方案中明确的证据需求。“增量”表示按已知机制复用并补充必要证据，不表示预测失败后持续追加采集。逐模板记录来源与合法重绑定条件。成本采样需求可跨组合共享，可变执行图和状态不能共享。

恢复按组合记录状态及共享资产依赖，失败/不支持组合不阻塞其他组合。预算和已完成采集保留；模板或成本补充后从初始状态重算受影响组合，无新信息不反复重跑。完整目标 request 验证与建库隔离，不用评价误差驱动拟合或调参。

## 1. 首条闭环的完整交互

先在主线冷缓存、明确 token 输入及固定输出长度下，用统一流程采集的 base 模板和给定节点耗时完成以下结构路径；节点模型就绪后复用同一交互做性能预测：

| 时点/步骤 | 控制器行为 | 模板与执行行为 | 后续事件 |
| --- | --- | --- | --- |
| 请求到达 | 加入待处理集合，启动支持的调度步骤 | 实例化调度模板，保留必要工作与依赖，不追加 CPU 服务时间 | 调度步骤出口完成 |
| 准入与组批生效 | 提交已形成的批次计划 | 准备与提交模板，连接前置依赖 | submitted 端口完成 |
| prefill 执行 | 等待相关结果，可处理其他合法事件 | 按依赖推进设备计算、通信和传输，保留提交逻辑 | device_done 端口完成 |
| 完成处理 | 提交处理步骤，随后更新 token 进度 | 保留结果处理逻辑，等待必要物化、传输及发布出口 | 对应状态发布 |
| decode 迭代 | 为下一轮选择请求并调用模板 | 按当前 batch/KV 实例化 decode 工作 | 逐轮完成事件 |
| 请求终止 | 达到长度条件后声明逻辑完成 | 记录 scope 内边界，释放相应占用 | 新一轮调度或任务结束 |

每项动作都能回答：使用什么 base 模板/变体、参数怎样映射到内部节点、依赖和端口是什么、耗时来自哪里、谁在何时更新状态。先修复流程与结构，再增加性能能力。结构闭环不要求独立性能补采。

## 2. 统一运行循环

```text
加载流程合同、已校验任务、base 模板与明确的时延来源
结构验证使用显式给定耗时；性能阶段使用声明域内成本模型并保留资格说明
为目标建立控制器私有状态、资源状态和模拟事件队列
加入 workload 到达事件
循环：
    推进到下一个模拟事件
    执行核完成必要端口、释放执行资源
    控制器消费事件与只读状态，返回动作
    实例化被调用模板，应用允许变换并连接依赖
    为计时范围内工作取得时延，保留 CPU 控制及因果，登记完成事件
请求达到声明终止条件后生成结构/条件化时序或正式性能结果
```

纯 CPU 逻辑可以在同一模拟时刻完成，随后继续消费端口和状态；不能因此增加全局串行屏障或删除等待。没有未来事件、仍有未完成请求时报告具体未满足依赖或机制错误。不能把无法推进解释为正常完成；也不通过固定步长忙轮询推进时间掩盖缺失唤醒。

执行范围内仍有影响请求完成的工作时不能提前终止。响应完成后的后台尾部若在 scope 外，记录未完成尾部和资源状态；它不能影响另一个候选，因为每个候选从独立初始状态开始。

## 3. 时延如何改变目标结构

当前首先验证批次完成时间如何影响下一次组批的可见请求：给定节点耗时改变发布时刻，已有到达计划中的请求可能在下一次决定前进入等待集合，因而调用次数、成员、shape 和依赖发生变化。变化由统一事件核产生，不能复制 base 等待轮数或读取真实 target 调度。

这项因果验证先于成本模型，不需要找一份性能资产恰好触发指定分支。给定耗时的来源和条件必须显式报告，不能用手调常量拟合原生成绩。以后已具备预取/deadline 与双方模板时再验证其他分支，不提前扩展当前支持范围。

### 建库、预测与验收的缺口处理

| 缺口 | 处理 |
| --- | --- |
| 已支持语义不能表达，或合法参数变化无法实例化 | 修正公共抽象、参数映射或实现；不默认补采 |
| 已定义的必要结构分支缺原生证据 | 返回具体结构需求；在授权内回到有边界的建库步骤，核对覆盖后再预测 |
| 未声明支持的机制或无合法变换规则 | unsupported，不现场增加目标特例 |
| 结构成立，计时范围内成本测量不足 | 按独立单元/域/预算补采，不新增语义模板；CPU 服务排除不构成补采缺口 |
| 独立泛化验收暴露问题 | 停止该项验收，修正后重新选择未参与修正的输入；不自动采集该验证序列补答案 |

预算是硬上限，不是采集必要性的证明。上述分类复用现有 gaps、action 和来源报告，不新建另一套运行后端或审批系统。

每次结构采集前按[建库方案与结束条件](04_collection_templates.md#建库方案与结束条件)明确预期证据；完成后核对实际取得的证据再决定覆盖结论。缺口未消除时保留具体原因，不能将换配置、换请求或增加预算当作自动继续的理由。结构建库结束后才进入固定资产验收；正式预测发现新的结构需求时报告并结束受影响组合，其他有资格的组合继续执行。

## 4. 缺口与补采

缺口先按流程/结构资格判断。给定耗时阶段缺值时说明所需节点输入，不触发模型性能采样；以下性能补采合同只适用于已通过结构资格、且属于首个闭环计时范围的工作；不为排除的 CPU 服务补建测量边界或模型。

- 缺规则或不允许的模板变换：该候选 unsupported，说明需要开发的能力。
- 已有定义但缺结构事实/模板：needs_data；结束受影响组合，记录缺少的事实并回到建库方案。先检查原始资产能否重提取，再决定是否安排预算内的代表采集；不在预测重试循环中自动补模板，不运行完整目标 request 序列来取得预测答案。
- 模板可生成但缺性能数据：由[正式需求分析](06_performance_execution.md#性能需求推导与覆盖分析)推导对象、计费边界及特征范围，核对已有模型/数据并跨组合合并。运行时细化同一份需求，不依赖人工打开诊断图，也不按来源节点或目标请求各建一项采样任务。边界/特征合同不足与数据不足分别处理。
- 可用独立资产则导入；否则按[性能采样合同](04_collection_templates.md#独立性能采样合同)先声明请求构造、实际覆盖目标和停止条件，仅在允许且预算充足时串行采样。一次原生执行可服务多个适用需求，多个候选共享样本；客户端请求数不直接作为实际批次特征。

补采后从相同初始状态重新执行受影响候选。首轮不持久化任意模拟中间状态，减少恢复复杂度。已完成真实采集和预算不会重置；新成本若改变其他候选已经使用的绑定，必须明确重算受影响结果。

运行前的需求推导与运行时的特征细化共同构成正式流程；动态性不能成为省略前者、逐个发现成本缺口的理由。补采仅在已声明性能单元、测量域和累计预算内进行，合并同类需求；无新可用证据时停止。结构缺口不能进入自动“运行—补模板—再运行”循环。即使每轮换了 request，只要缺口仍来自同一未解决抽象，也应停止采集并修正设计。

建库与性能补采各有独立入口：只有缺兼容来源且 base 允许时，才按代表配置组作一次有界建库；资产损坏、缺规则及成本不足不授权替代采 base。可执行的代表组优先；缺来源或失败组合保留原因，已有模板的组合继续性能流程。已观察域仍缺对象或配方已尝试而无新触发时停止，不因重新分组重复采样。预算包括失败，不能由恢复重置。

独立测量先交给拟合进程，成功候选通过正式资产与收据交接；显式候选保持优先，空候选保留缺口。预测不取得原始测量，也不从缺口中自动扩展测量域。结构资产补充须重新核对建库覆盖，成本资产补充则在原性能域和累计预算内继续。两者都不改变原生控制或目标语义。

自动取得新资产后，按适配器给出的复用域重算受影响配置组的全部 workload；匹配与分组共用依据。结果按配置/workload 身份合并，其他组合及其资产/诊断引用保持。没有新资产时只更新失败或选择状态，不增加预测轮次。用户显式替换资产且影响范围不明确时完整重算；改变模型、配置集合或请求则新建任务。

## 5. 产品恢复与物理隔离

任务持久化保留复现输入、完成的采集资产、累计用量、候选状态和结果来源。默认只输出摘要和必要合同，完整 DAG 和细粒度诊断按开关输出。恢复继续当前任务，不用文件存在或摘要替代实际适用条件。输入快照、运行账本、处理收据和资产 manifest 各有一个写入者：分别表达输入、任务状态、阶段完成和资产发布，不能复制成多套可变状态。 输入修订须与旧结果失效共同登记，未完成输入发布先恢复交接，再启动计算；不能在新输入下返回旧的已完成结果。短暂交接内容在确认后撤下，不演变成多版本输入库。

| 情况 | 正式处理原则 |
| --- | --- |
| 宿主中断、容器仍活动 | 依据真实进程状态接回现有任务，不创建替代容器或重复计量；活动期间的资产/预算修订不生效 |
| 原生完成、后处理未交接 | 先消费已有结果或继续原处理；不能将原生成功当作模板/样本发布完成 |
| 后处理确定失败 | 由处理进程的失败收据确认并隔离；保留来源与原因，恢复不自动重采或重试确定失败 |
| 显式修正后处理或替换资产 | 先完成已登记任务的交接，再应用修订；修订不得被旧交接覆盖，预算继续累计 |
| 部分组合成功 | 保留成功结果及仍被引用的资产；整个任务仍反映未完成组合 |
| 全部阶段完成后恢复 | 读取正式结果，必要时完成已确认的清理，不重复采集、拟合或预测 |

清理必须发生在正式发布与消费确认之后，只删除本任务拥有且无活动写入者的内容；失败和未交接数据保留。共享目录、未重算组合和诊断引用必须独立于已消费工作目录。单根及原始导出释放已在当前短示例验收，具体行为与保留例外见[专项审查](../redesign-workflow/history/2026-10-16_code_cleanup_review.md)，不由本合同推定已经通过。

预测进程仅获得 base 与独立性能资产，不能访问 target profile/score。独立观测使用 validation 角色和预算，不生成模板或成本资产。整次探索在所有组合预测完成后固定资产再验证；预测缺数据时保持可修订，不运行验证补答案。独立评价只读固定结果与 validation 事实，对齐模型、配置、请求、起止/发布端口和时钟；不启动拟合、补采或回写控制规则。评价保持单独路径和最小数据挂载，不新增通用评价框架。

SGLang新采集在既有`native_environment.json.request_timing`保存负载驱动器的`perf_counter_ns`原点与实际时钟实现，普通请求的计划到达为原点加输入offset；代表组仍按真实提交减原点记录到达。该原点不是进入统一流程的时刻，不消除前端排队、模板外时间或观测扰动。只有端口与时钟已关联，才能报告对应原生间隔；profiler端口不能未经关联直接与该原点相减，历史或异常缺失的原点不回填。

同一请求与起止端口可关联时，可直接比较理想化 CPU 预测和原生实际间隔，并报告偏差。原生间隔仍包含被有意省略的 CPU 服务、范围外工作及观测影响；该比较不是纯设备同范围真值或精度已合格的证明。无需先逐段还原/扣除这些时间，不用残差补偿。端口、原点或时钟缺证据时仅保留不可比较原因。具体评价范围见[验收合同](08_acceptance_delivery.md)。

公开 `predict/status/resume` 已有持久任务。C++ Planner 生成复现输入；Python 编排资产、容器和恢复，模拟算法仍在 C++。现有锁、原子发布、原生监控及累计预算继续复用，不为目录整理新建任务平台。追加预算表示新的总额度，保留已用量及实际超出量。

模拟容器只读挂载必要程序、输入和明示资产，按职责授予工作目录、共享对象目录及显式诊断目录的写权限；不开放网络或设备，不挂载目标验证。独立评价保持单独角色。当前命令、示例及故障定位集中在[开发说明](development.md)，具体实现与验证状态由主计划及专项审查维护。

## 6. 交付边界

产品闭环须从公开输入得到组合结果，模板/性能需求、覆盖与采样共用同一工作合同，失败和恢复不重置预算、不丢失已完成结果。固定预测资产后独立评价，报告范围、缺口与省略的 CPU 时间，不将验证用于补齐成本。

结构、成本资格和精度分别验收，详见[验收合同](08_acceptance_delivery.md)。当前任务只在[主计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)及其专项维护；运行成功不等于精度通过。
