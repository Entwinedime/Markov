# 阶段七 最小闭环、动态反馈与恢复

本文维护集合闭环与恢复合同，当前状态统一见[实施计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)。主线为 SGLang + Qwen3-32B，结构验收先于节点成本；KT 与原生控制器后续扩展。已有显式采集/导入、集合执行或恢复入口，不代表自动建库及真实成本闭环已完成。

## 配置集 × request workload 集的产品工作流

正式输入已切换为固定模型与两个非空集合，按配置×workload输出独立组合；代表性建库、多来源语义覆盖选择、受影响组合重算和节点成本仍为待完成设计，不能将已有集合执行称为最终闭环。

解析输入 → 声明支持域并分析原生机制 → 复用资产、列出最小证据与累计预算 → 有边界的代表性建库 → 核对模板与变换覆盖 → 固定资产逐组合动态展开 → S4 结构验收 → S5 成本绑定与独立测量 → 探索结果矩阵。

采集规划参考 Dooly，作为基础编排，不建设最优 base 搜索系统。用户不提供 base 或采集 request；一个代表配置足够则只采一次，多来源采集必须对应建库方案中明确的证据需求。“增量”表示按已知机制复用并补充必要证据，不表示预测失败后持续追加采集。逐模板记录来源与合法重绑定条件。成本采样需求可跨组合共享，可变执行图和状态不能共享。

恢复按组合记录状态及共享资产依赖，失败/不支持组合不阻塞其他组合。预算和已完成采集保留；模板或成本补充后从初始状态重算受影响组合，无新信息不反复重跑。完整目标 request 验证与建库隔离，不用评价误差驱动拟合或调参。

## 1. 首条闭环的完整交互

先在主线冷缓存、明确 token 输入及固定输出长度下，用统一流程采集的 base 模板和给定节点耗时完成以下结构路径；节点模型就绪后复用同一交互做性能预测：

| 时点/步骤 | 控制器行为 | 模板与执行行为 | 后续事件 |
| --- | --- | --- | --- |
| 请求到达 | 加入待处理集合，启动支持的调度步骤 | 实例化 CPU 调度工作，或按 scope 声明纯逻辑步骤 | 调度步骤出口完成 |
| 准入与组批生效 | 提交已形成的批次计划 | 准备与提交模板，连接前置依赖 | submitted 端口完成 |
| prefill 执行 | 等待相关结果，可处理其他合法事件 | 执行内部 CPU/NPU/通信/拷贝工作 | device_done 端口完成 |
| 完成处理 | 提交处理步骤，随后更新 token 进度 | CPU 结果处理节点与发布出口 | 对应状态发布 |
| decode 迭代 | 为下一轮选择请求并调用模板 | 按当前 batch/KV 实例化 decode 工作 | 逐轮完成事件 |
| 请求终止 | 达到长度条件后声明逻辑完成 | 记录 scope 内边界，释放相应占用 | 新一轮调度或任务结束 |

每项动作都能回答：使用什么 base 模板/变体、参数怎样映射到内部节点、依赖和端口是什么、耗时来自哪里、谁在何时更新状态。先修复流程与结构，再增加性能能力。结构闭环不要求独立性能补采。

## 2. 统一运行循环

```text
加载流程合同、已校验任务、base 模板与明确的时延来源
结构阶段使用给定节点耗时；正式性能阶段使用已资格化成本模型
为目标建立控制器私有状态、资源状态和模拟事件队列
加入 workload 到达事件
循环：
    推进到下一个模拟事件
    执行核完成必要端口、释放执行资源
    控制器消费事件与只读状态，返回动作
    实例化被调用模板，应用允许变换并连接依赖
    取得节点服务时延，调度就绪工作，登记完成事件与 timer
请求达到声明终止条件后生成结构/条件化时序或正式性能结果
```

没有未来事件、仍有未完成请求时报告具体未满足依赖或机制错误。不能把无法推进解释为正常完成；也不通过固定步长忙轮询推进时间掩盖缺失唤醒。

执行范围内仍有影响请求完成的工作时不能提前终止。响应完成后的后台尾部若在 scope 外，记录未完成尾部和资源状态；它不能影响另一个候选，因为每个候选从独立初始状态开始。

## 3. 时延如何改变目标结构

当前首先验证批次完成时间如何影响下一次组批的可见请求：给定节点耗时改变发布时刻，已有到达计划中的请求可能在下一次决定前进入等待集合，因而调用次数、成员、shape 和依赖发生变化。变化由统一事件核产生，不能复制 base 等待轮数或读取真实 target 调度。

这项因果验证先于成本模型，不需要找一份性能资产恰好触发指定分支。给定耗时的来源和条件必须显式报告，不能用手调常量拟合原生成绩。以后已具备预取/deadline 与双方模板时再验证其他分支，不提前扩展当前支持范围。

### 建库、预测与验收的缺口处理

| 缺口 | 处理 |
| --- | --- |
| 已支持语义不能表达，或合法参数变化无法实例化 | 修正公共抽象、参数映射或实现；不默认补采 |
| 已定义的必要结构分支缺原生证据 | 返回具体结构需求；在授权内回到有边界的建库步骤，核对覆盖后再预测 |
| 未声明支持的机制或无合法变换规则 | unsupported，不现场增加目标特例 |
| 结构成立，成本测量不足 | 按独立单元/域/预算补采，不新增语义模板 |
| 独立泛化验收暴露问题 | 停止该项验收，修正后重新选择未参与修正的输入；不自动采集该验证序列补答案 |

预算是硬上限，不是采集必要性的证明。上述分类复用现有 gaps、action 和来源报告，不新建另一套运行后端或审批系统。

每次结构采集前按[建库方案与结束条件](04_collection_templates.md#建库方案与结束条件)明确预期证据；完成后核对实际取得的证据再决定覆盖结论。缺口未消除时保留具体原因，不能将换配置、换请求或增加预算当作自动继续的理由。结构建库结束后才进入固定资产验收；正式预测发现新的结构需求时报告并结束受影响组合，其他有资格的组合继续执行。

## 4. 缺口与补采

缺口先按流程/结构资格判断。给定耗时阶段缺值时说明所需节点输入，不触发模型性能采样；以下性能补采合同只适用于 S4 结构资格和 S5 单元定义完成后的正式预测。

- 缺规则或不允许的模板变换：该候选 unsupported，说明需要开发的能力。
- 已有定义但缺结构事实/模板：needs_data；结束受影响组合，记录缺少的事实并回到建库方案。先检查原始资产能否重提取，再决定是否安排预算内的代表采集；不在预测重试循环中自动补模板，不运行完整目标 request 序列来取得预测答案。
- 模板可生成但缺性能数据：按公共工作描述汇总实现、shape/工作量和部署条件，交给工作流；同类需求形成特征范围，不按来源节点或目标请求各建一项采样任务。
- 可用独立资产则导入；否则按[性能采样合同](04_collection_templates.md#独立性能采样合同)先声明请求构造、实际覆盖目标和停止条件，仅在允许且预算充足时串行采样。一次原生执行可服务多个适用需求，多个候选共享样本；客户端请求数不直接作为实际批次特征。

补采后从相同初始状态重新执行受影响候选。首轮不持久化任意模拟中间状态，减少恢复复杂度。已完成真实采集和预算不会重置；新成本若改变其他候选已经使用的绑定，必须明确重算受影响结果。

动态执行可能发现成本需求，但补采仅在已声明性能单元、测量域和累计预算内进行，合并同类需求；无新可用证据时停止。结构缺口不能进入自动“运行—补模板—再运行”循环。即使每轮换了 request，只要缺口仍来自同一未解决抽象，也应停止采集并修正设计。

已删除的联合批次路径曾按 phase/input/context/prompt/finished-count 汇总需求；当前显式节点耗时路径不生成这些整批需求。C++ Planner 生成独立请求配方，用真实 token 反馈形成不同 decode 进度，不重放业务到达序列。它是已有机制，后续须按节点/局部子图成本合同复核；不以穷举上下文组合替代节点模型，也不以配方声明证明实际域已经到达。

合法成本资产导入后，受影响候选从初始状态重算；新的成本工作域仅在已声明测量域和原 performance 累计预算内安排采样。结构资产补充须先重新完成建库覆盖核对，不沿用成本补采循环。已经完成采样的相同需求仍缺成本时返回 independent_measurement_domain_not_reached，不重复无新增信息的配方；用户也可用 resume 显式替换合法独立资产。工作流不因补成本改变原生控制或目标语义。

当前predict先消费已声明资产，只有compatible_template_missing且base允许时才按代表配置组进行一次有界建库。已声明资产加载/编译失败先修复，不以重新采集掩盖；规则、节点成本及其他结构缺口不启动采集。每组仅一次尝试，失败不自动重试，预算在组间累计；配方或已终止采集的失败原因按组记录，其他组继续选择，发布时只关联受影响配置；生成manifest导入持久输入后重新预测，仍缺成本就保留缺口。失败未导入资产时只更新组结果，复用原预测继续选组；selecting阶段持久记录这一恢复位置，不为未改变的输入新增预测轮次。后处理由持有锁的处理进程在异常时写出processing_failure.json，宿主命令报错本身不等于确定失败；编排只隔离有该记录的失败，将详情保留在原attempt并给所属组标记base_processing_failed。中断/状态不明仍向外报告并保留active_representative。恢复先消费已有成功结果或确定失败，不自动再次后处理失败组。采集attempt与后处理恢复复用CollectionWorkflow，active_representative记录尚未交接的组；resume先回收原attempt并完成交接，不新建替代采集。自动建库成功后按生产适配器给出的配置组重算该组全部workload；来源匹配与分组必须共用复用域，不能漏掉其他潜在消费者。原轮结果保留实际执行子集，任务结果按配置/workload身份替换对应条目并合并source_coverage，其他组的结果及诊断路径保持。显式替换模板或性能资产时影响范围尚不明确，仍完整重算。正式成本闭环尚未完成。

## 5. 产品恢复与物理隔离

任务持久化保留复现输入、完成的采集资产、累计用量、候选状态和结果来源。默认 compact；完整 DAG 和细粒度诊断按开关输出。resume 对当前任务继续未完成工作；修改输入另建任务，不用文件是否存在或摘要替代实际适用条件。

预测进程仅获得 base 与独立资产，不能导入评价模块或访问 target profile/score；评分在独立路径运行。observe-target 使用独立 validation 角色、显式候选和累计预算采集目标事实，不生成 base 模板或成本资产。evaluate 读取已有结果与 validation 观测，不启动新采集或回写控制规则和成本。实际隔离需要在参数、模块依赖和运行时挂载三处落实。

公开 predict/status/resume 已实现持久任务。C++ Planner 生成实际复现输入，Python 只编排资产、容器和恢复；模拟算法仍在 C++。采集复用原 container monitor、串行锁和预算。CPU 轮次保存实际项目输入，由容器持有 processing.lock 并原子发布结果；恢复复用 live 容器或同轮已发布结果，禁止重复创建同名执行。宿主命令中断不等于容器停止：保存当前处理阶段，以Docker实际状态报告prediction_live；活跃预测期间的resume只报告状态，资产/预算修改返回requested_changes_applied=false。容器结束后恢复接收同轮结果，不能因宿主中断新开轮次。完成任务的重复 resume 不增加 round。预算追加使用新的总额度，保留超时停止的实际超出量。

实际模拟 Docker 容器只读挂载必要的程序、复现输入和明示资产文件，只有该轮结果目录可写，网络和设备均未开放。已有真实 Docker Mounts、宿主 SIGKILL、暂停/恢复 CPU 容器和并发 resume 的证据；评价程序尚未接入，完整预测/评价双向隔离验收仍待完成。

## 6. 实施与完成条件

1. 先在 S4 用给定耗时完成同配置、准入 2→1 和时间反馈的结构闭环，独立核对节点、依赖、端口及状态。
2. S5 节点成本资格满足后，用同一执行机制完成正式性能预测，单列成本域和关系支持依据。
3. 将已有恢复/预算设施按正式单元合同复核，覆盖缺模板、缺成本、禁采、预算耗尽和中断。
4. 完成预测与独立结构/性能评价的隔离；给定耗时报告不冒充预测或最终精度。
5. 提供 S7 所需完整证据，保留当前未实现能力；本次文档修订不新增可运行命令。

交付是可供普通用户运行的最小产品闭环。完成条件是从输入到结果无需拼内部脚本、实际范围与报告一致；运行成功不等于精度验收通过。
