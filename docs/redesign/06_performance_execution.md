# 阶段六 性能模型与执行引擎

状态：`NodeCosts` 为现有执行核提供统一查询，`NodeDurations` 保留显式给定值，`CpuCostModel` 消费准入/worker 经验候选。`ExecutionGraph` 根据依赖推进，`SimulationRuntime` 反馈控制器。当前显式候选消费仍是有测量限制的条件运行；正式成本覆盖、适用性与精度交付见实施计划。消费[模板工作](05_controller_semantics.md)，遵守[控制接口](03_control_interface.md)。

成本提供者与执行引擎按[代码与工程约束](engineering_constraints.md)作为职责明确的 C++23 类实现；正式仿真在 modeling Docker 内构建和运行。

## 1. 两个职责

成本提供者回答一项明确工作在声明条件下需要多少服务；执行引擎根据依赖、资源和并发关系决定何时开始、何时完成。控制器收到完成事件后生成新工作。性能层不能修改业务策略，也不能用低成本替代缺失语义。

执行引擎的依赖、资源、时钟和端口反馈先在 S4 用给定节点耗时完成；本阶段为同一执行机制提供预测耗时。开发顺序是结构先行，运行时耗时仍参与动态展开，不是先生成一张固定目标图后统一填总时长。给定耗时输入标明来源与假设，不作为训练样本、拟合常量或预测精度证明。

DAG 包含预测范围内的 CPU、NPU、通信、传输和必要标记。它不是仅由 NPU 算子组成的图；也不要求收录原生进程的所有 CPU 事件。

### 参数化模板与成本资产

借鉴 Dooly 的动态参数来源与等价测量复用；性能粒度按工作描述、可测边界和外部依赖选择，可以是节点或局部子图，不由五类 block 或整个 decode 长度决定，也不要求每个单元独立执行。合并模块保留外部依赖，不能重复计算已吸收的子项。采样方法统一遵守[四项约束与采样合同](04_collection_templates.md#独立性能采样合同)，优先验证原生请求执行中的采样，不照搬逐算子重放体系。

成本身份包含必要实现、模型固定参数、dtype/layout、硬件及适用条件；token/request/KV 等为动态查询特征。跨配置共享需要这些条件适用或有明确迁移规则，相同名称、hash 或节点数不证明等价。不照搬 Dooly 的宿主 CPU 计时、缺失常数回退或签名摘要机制。

结构覆盖和成本覆盖分别报告。先在 S4 用给定节点耗时验证未参与建库的请求序列，再用模型替换耗时来源，复用同一执行核；结构不足不能用性能采样补齐。

成本查询消费目标节点的工作描述；来源 span 和来源请求槽只解释观测出处。已资格化的 Decode 发布成员绑定见[成员工作交接](05_controller_semantics.md)，逐成员 CPU 服务和共享输出属于不同计费边界，不因引用同一份有序成员数据而重复计算整段输出成本。

CPU服务内部的同步原语不必各自成为性能单元。当前已核对的直接aclrtMemcpy保留为annotation，并由单一CPU服务包围；S4的给定耗时覆盖该服务，不能再给内部复制加一份耗时。S5可选择测量整个服务，或在证据允许时拆出复制及其余CPU工作；后者必须明确方向、字节、内部等待和互斥计费范围。CPU缓存、workspace/tiling等实现差异先检查是否改变外部端点；只影响服务开销的差异作为成本适用条件，不能反过来要求S3逐缓存状态增加语义模板。

## 2. 预定义成本类型

| 类型 | 查询特征 | 数据来源与限制 |
| --- | --- | --- |
| 矩阵等计算节点/局部子图 | 操作与实现、shape、dtype、layout、部署 | 独立样本与适用模型，CPU/NPU 实现不能互换 |
| attention 工作 | 实现、输入 token 数、各序列 context、head/布局、dtype、部署 | 长度是该工作单元的特征，不定义整个 decode 的成本类型 |
| CPU 控制阶段 | 阶段、请求数、token/页数、调用量、线程与框架条件 | 分阶段实测；不默认只依赖 batch size |
| 搬运/存储 | 方向、字节、介质、页粒度、并发条件 | 对应服务测量，执行量与可见量分开 |
| 通信 | collective/物理任务、字节量、rank 数和拓扑 | 原生推理或适用的独立通信测量，明确计费层次与等待 |
| 设备事件/通知命令 | 物理命令种类、runtime、设备/通信描述与资源 | 保持模板的物理服务角色；不能等同于逻辑注释 |
| 纯逻辑标记 | 明确语义边界 | 可以零服务，等待由依赖产生 |

成本类别先保持少量且职责明确，实现算法可先用精确匹配、查表、简单插值或有依据的公式。节点身份、workload 名和实验标签不参与拟合。新增算法无需改控制器。

类别与特征从已确定的性能单元出发。一个 forward 模板可以包含矩阵、attention、通信、拷贝及 CPU 服务等多个单元；同一语义阶段不只对应一个模型。9/8、10/9 描述批次上下文，必要时进入某个 attention 工作的特征，不能作为整批 decode 的唯一成本键。精确查表可以用于有真实样本的具体单元，不能靠枚举所有批次状态替代可维护的节点模型。

遵守工程约束中的禁止硬编码拟合规则：参数由明确的独立数据与算法产生，不用手调倍率、目标特例、补偿阈值或残差表凑精度；把这些值移到配置也不允许。误差改进先检查语义、计费边界、数据和适用域，不默认扩张模型实现。

## 3. 成本来源与映射

未变化的对应工作可以直接迁移 base 服务成本，前提是实现、工作量、部署和测量边界适用。变化或新增工作使用独立性能数据，当前 base 不自动用于在线拟合。

每个性能单元声明所覆盖的节点、入口/出口、资源和成本来源。合并单元必须能保持外部依赖与重叠；不能既计父模块又计内部节点。base 中的墙钟包络若包含等待，不能直接当成可迁移服务。

### 性能样本与子图工作的对应

模板展开后的工作与采样结果共享公共工作描述；采样适配端解释原生事件，成本模型只按实际工作和必要运行条件拟合/查询。来源 span、请求身份和采样序号用于追溯，不是跨运行匹配键。语义和性能插桩独立，但实现身份、输入特征、覆盖节点和计费边界必须对应；相同入口、kernel 名或 shape 不能单独证明等价。部分子图的有效样本不授予整条 serving 流程成本资格。

| 工作 | 测量来源与边界 |
| --- | --- |
| 模型计算及相关 CPU 提交 | 在原生实际 forward 及运行时调用上观测节点或局部子图；模型前向耗时不能分摊给内部节点，也不覆盖外部调度/发布 |
| CPU 控制与 worker | 通过原生请求路径触发接纳、准备、提交和完成处理，按线程与服务区间测量；CPU 实际处理、设备等待、排队及插桩开销分开，不跨线程相减或重复填写阶段总时长 |
| I/O 与搬运 | 记录模板范围内的操作、字节量、方向、内存类型与同步条件；CPU 发起、传输、后续消费保留各自边界。磁盘/网络只在统一流程明确包含时纳入，模型加载和预热不计入预测窗口 |
| 通信及物理设备命令 | 原生推理可采到真实多 rank 工作；已有独立通信采样须核对实现和部署。到达错峰及同步等待由目标依赖处理，实测区间中尚未解释的内部停顿不自动视为可迁移服务 |

采用整体 collective 模型时必须明确吸收的内部工作并保持外部端口；采用物理任务模型时按对应任务计费，父包络不再收费。当前物理图不能未经转换直接套用整体通信耗时。传输与 CPU 包围区间同样不能重复计费。不同测量载体的外围流程可以不同，但只能把证据用于实现、状态及计费边界对应的性能单元。

统一预热不等于所有状态相同；KV、workspace 和并发条件仅记录、解释所需适用性，不因此建立我们自己的原生状态管理器。硬件任务耗时也可能含竞争，CPU 墙钟也可能含等待；均不能用经验常数剥离或由端到端残差补偿。性能模型与执行引擎分别承担服务估计和目标依赖/资源等待，未建模的竞争保留限制。

```text
CostProvider::estimate(unit_descriptor, deployment) ->
    available(service_ns, resource_demand, provenance, applicability)
    | needs_data(measurement_request)
    | unsupported(reason)
```

外推必须有明确方法和适用假设；未知返回 needs_data，不返回零或无关默认值。输入边界校验后内部信任合同，避免每次查询重复解析字典和增加兜底。

### 经验候选的生产

`CostFittingWorkflow`读取显式独立CPU单元资产，在输入边界校验并转为`AdmissionCostSample`；`AdmissionCostFitter`只接受公共类型，按成员工作规模分组取中位数，不依赖框架或文件路径。该候选用于已确认接纳且完整遍历的准入调用，初始化由已有工作描述推导；长度与rank不作为拟合键，其可迁移性需要独立证据。

候选还从来源声明读取`observed_context`，包含模型、框架版本、配置、部署、runtime以及各worker的CPU亲和性与runtime，不复制请求token或进程ID。它是观测来源条件，不是跨部署匹配结论；框架版本、CPU数量或亲和性相同均不能单独证明实现和硬件等价。

候选保留样本数、原始范围、来源manifest、测量缺口及假设；不移除高值，不吸收嵌套等待，不自动校正时钟或提升资格。偶数样本中位数按整数ns向下取整。源数据、部署与独立验证仍是适用性依据，不能只凭中位数相同合并实现。拟合与消费分开；显式 `assets.cost_models` 导入后，执行核通过同一目标工作查询使用候选，不改变给定表或自动提升测量资格。`CpuCostModel` 共享评价和消费的特征读入与查找，避免两份匹配规则。

同一workflow提供固定候选评价，共享已校验的单元读取结果。性能层按候选的工作键精确匹配，输出分组与总体绝对/相对误差；未命中的工作单列，不外推或填零。评价路径不调用fit，样本文件不能与候选记录的拟合来源直接重叠；数据用途仍以独立采样记录为依据，不以文件名不同证明独立。观测上下文一致性仅报告，不将配置字段逐项相等偷换为已建立硬件迁移规则。评价不改变原测量缺口或声明精度通过。

物理计算候选由同一入口的 `--unit kernel` 生成。runtime 生产端将原始 kernel 描述转换为公共 `kernel_work`；`KernelCostFeatures`/`KernelCostFitter` 只处理 kernel、张量描述及实际启动规模，不解释 vendor 列名或框架方法。相同工作键取实测中位数，共享既有统计与固定候选评价；原始 trace 引用参与独立性检查。该基线尚未覆盖数据相关工作、缓存/并发状态、目标启动规模映射与 profiler 影响，不能因 shape 匹配就作为已资格化服务。`KernelCostModel` 已接入统一 `CostModel` 查询：完整张量描述必须命中且只对应一个观测启动变体，额外语义工作由其他模型处理。目标启动规模沿用该唯一变体是条件假设；多变体不平均或挑选，未命中不补零。正式启动映射、数据相关成本与迁移资格仍须完成，不能按每个目标请求补一张耗时表。

### 当前给定耗时执行与后续成本模型

NodeDurations 只接受显式 base 引用、ns 单位、假设说明和逐 source_span 的服务耗时；入口校验负数、重复身份及数值范围。 模板加载后由所属bank绑定来源manifest；执行节点按实际定义（包括donor）携带来源。耗时查询使用manifest与局部source_span，NodeDurations按manifest持有多份已校验耗时，逐来源加载失败不会发布部分数值；查询同时限定manifest与局部编号，不借用另一来源的同号记录。缺耗时报告source_manifest。实际图根sources表保存路径，节点source_asset引用该图内表项，避免逐节点复制路径；它不是内部版本或模型身份。一次探索共用只读耗时集合，资产报告分别保留文件、假设和条目数；跨来源模板组合已在记录范围内通过条件执行，实际来源集合由执行图报告；不以此代替S5成本资格。ExecutionGraph 将服务节点耗时加入 begin→end 约束，等待和注解仅保留依赖；不使用观测墙钟作为服务，不再查询整批 context 组合或联合延迟。

执行核向 `NodeCosts` 传递 `ServiceWork`，包含借用的来源身份、rank、实际node_kind和目标kernel/通信/复制/发布描述；不重读原采集shape。缺给定值时，缺口的`service_work`提供当前目标工作，已有来源字段继续用于追溯。成员发布描述仅覆盖被查询成员，整批发布另行表达。没有设备描述不代表CPU：查询先保留实际节点种类，只有CpuControl使用cpu_service分类；物理DeviceMarker保持设备命令身份，通信/复制的工作描述另行保留。诊断图也输出同一kind，不改变服务/等待/注释角色。CPU服务保留来源中已知的`control_part`，查询以`cpu_part`表达调度前缀、准备主体/后缀、执行、发布或提交；插入节点沿用实际供体的阶段。阶段是工作分类，不代表每个内部服务节点承担整阶段成本。调度前缀查询的`control_context`借用运行时已提交的目标InvokeStep，提供准入入口、候选/预算检查、队列整理及transition；该上下文不等于每个服务节点的独立工作量，不重复计费，也不把来源参数当作目标参数。目标控制/提交工作量和测量边界仍须交接，不能据此声明CPU模型可用。

当前统一查询按声明顺序匹配显式成本候选，再查剩余给定值；`CpuCostModel` 与 `KernelCostModel` 实现同一 `CostModel` 接口，分别按目标成员/提交工作或计算描述查找，来源 span 只供给定值及追溯。workflow 解析一次模型来源配置，通过 `TemplateAdapter::supports_cost_configuration` 判断实现路径；SGLang 复用已有控制路径与配置关系，只容许请求池容量、Prefill 预算变化。调度器及公共成本查询不读取这些框架字段，组批与 shape 差异仍由目标结构/工作表示。候选的模型/框架/部署必须匹配，runtime、硬件与 CPU 迁移仍未资格化；相同实现路径不等于成本特征完备，尤其不能隐藏 worker 基线省略 shape 的假设。匹配值和给定值分别计数，未知返回具体缺口。输入与报告约定见[经验成本合同](02_user_contract.md#显式经验成本输入)。

节点图计算端口完成时刻，由 SimulationRuntime 的唯一事件时钟按到达和完成事件推进控制器。每 rank 的入口门控及出口门控显式入图；跨 rank 的公开端口在各 rank 均完成时生效。published 才提交 token/KV 状态。未解析连接或缺给定值停止候选，不补零、不自动性能补采。

报告中的 `release_ns` 是工作提交到执行图的时刻，同批提交可以包含尚未满足的入口依赖。实际执行顺序以物理图边界的 `completion_ns` 和依赖边为准；不能用前驱端口晚于后继 `release_ns` 判定依赖违规。公开端口时间取各 rank 完成时间的最大值，逐 rank 的门控仍按对应 rank 连接。

原独立 CPU/设备/通信采样设施和历史资产保留。当前 CPU/设备采样仍只接受显式非空工作域，已删除按目标 workload 长度和批大小自动生成采样网格的入口；使用方式与范围见[开发说明](development.md#6-独立性能采样)。后续特征域规划从性能单元和模板参数关系出发，须经过实际覆盖评价，不恢复按目标请求逐项补采。旧联合模块 CostProvider、联合资源时钟、成本单元报告及其整批自动补采分支已经删除。S5 提供节点成本并复用当前执行核，不恢复另一套模块后端或把已有联合观测拆成未经测得的服务。

## 4. CPU 时间如何处理

| CPU 部分 | 处理方式 |
| --- | --- |
| 调度、KV 查找、准备、提交、完成处理等已纳入步骤 | 按阶段性能单元估计服务时间，必要时保留子节点 |
| 等设备、I/O、worker 或容量 | 用依赖和资源状态计算等待，不迁移 base 原等待总时长 |
| 模板外 CPU 时间 | scope 中明文排除，说明影响；不能称完整 HTTP |
| 模板内未解释 residual | 保留为独立问题，补依据或报告缺口，不让其他模型吸收 |
| 插桩/profiler 开销 | 有配对测量才能校正，不能随意从 gap 扣减 |

轻量控制器运行所耗的宿主 CPU 时间不进入预测。调度决策、提交和完成处理若计时，必须经过相应 CPU 工作完成边界才产生约定效果。初期不模拟每条指令和任意 OS 调度，但必须表达影响已支持行为的 CPU 阶段。

同一控制路径可以复用阶段成本模型，工作量随目标批次和配置变化。改变线程组织、实现路径或隐藏同步时不能沿用旧阶段成本；模型是否适用由条件判断。

算子准备工作还可能受executor/tiling缓存历史影响；冷KV不是这类缓存的初始状态声明。先在结构阶段核对准备分支及其外部提交/等待端口，再确定性能单元和必要状态特征。来源中的workspace调用不能无条件复制或删除，不能默认所有目标均已预热。当前独立观测差异及原生代码依据见[整体审查](../redesign-workflow/2026-10-10_architecture_review.md#独立原生对照事件依赖保留cpu执行缓存资格仍缺)，尚无该状态的完整实现资格。内部CPU注释数量变化不自动要求新增控制器状态或模板变体：若差异完全位于同一CPU服务单元内，且不改变外部提交、等待与状态端口，应由该单元的工作描述和后续成本处理；存在外部因果变化时才需要结构变换。不得把零服务计费的注释差异直接解释为缺失服务，也不得据此宣称其包围的CPU成本可直接迁移。

### CPU 测量与执行边界的交接

CPU阶段标签不是成本单元身份。现有结构提取先扣除显式等待，再按提交、语义作用域及必要因果边界切分服务；同一阶段可以有多个CPU服务节点。旧`CpuSamplingObserver`用调用线程的`thread_time_ns`测量阶段，原生等待计数也为thread-local，因此既不能给每个切分节点重复填阶段总值，也不能覆盖其他worker的`dispatch`。来源墙钟区间只证明边界，不作为独立CPU服务测量。

正式CPU成本接入按以下顺序实现，复用既有模板和事件核：

1. **先确定测量单元的入口、出口及线程。** 以已有语义区域/原生操作为候选，使用目标工作量作特征；同名阶段、来源span编号或原始持续时间不能单独作为成本身份。
2. **允许合并纯内部切分，但保留对外完成边界。** 同一线程、同一服务职责且内部没有对外提交、等待或状态生效端口时，可以测量并计费整个局部单元。不能将跨线程服务相加后塞进控制线程，也不能把跨设备提交的阶段总值放在阶段末尾；没有端口内部分布证据时，不按节点数或base时间比例分配。
3. **在确定的单元边界观测实际线程服务。** 控制线程与worker分别记录；只包围已纳入统一流程的工作。等待仍由依赖处理，嵌套区域只计一次，已有探针计数不能视为全部观测开销已校准。需要测量的边界由可复用单元决定，不为源图每个节点添加独立wrapper。
4. **明确覆盖后再采样与估计。** 首个单元须同时有目标特征、执行计费落点和对应测量方案。先用已有资料确认匹配关系，再安排有界独立测量；旧阶段样本只作边界和开销研究，不能先导入模型再逐项修补。独立留出验证不得反向补偿成本。

执行与提交单元复用现有`TemplateOperation`的host/worker窗口及设备关联，但不能把整个operation默认收缩为单一CPU成本。主线程窗口可能包含入队端点，worker窗口可能包含设备提交端点；计时至少保留这些端点前后的服务分段。无内部跨线程端点只是候选条件，还须保留同线程外部依赖、等待及状态边界。操作窗口之外的流程内执行工作仍须由所属语义区域表达，不能因未匹配operation而删除或填零。观测适配分工为框架层提供区域和目标工作，runtime层提供实际线程上的入队/执行/提交边界；公共性能层消费规范化单元，不识别框架方法或SDK名称。Ascend的`CpuSampling`封装原生计数器ABI和读取，SGLang采样器只选择业务边界并计算差值。新增队列观测将业务范围沿原生ID传到worker，保留各线程CPU时钟及已有等待/探针计数。代码已接入，并完成一次真实观测的队列配对和阶段归属核对；目标成本匹配及服务解释尚未完成。

当前Ascend队列的具体落点是：在`enCurrentNPUStream`已有correlation_id建立提交身份，在`ReadQueue`的`manager().Call`两侧观测worker执行，并在其中保留runtime提交端点。ID不依赖profiler开关，复制到队列槽后保持；`EXECUTE_OPAPI_V2`入队复制时转为`EXECUTE_OPAPI`，不能把原始类型相等作为关联条件。外层`Dequeue`含空队列轮询/休眠，不能整段计费；`manager().Release`位于现有worker区间之外，不能顺带并入该单元。相应queue补丁和native缓冲记录已实现，保留原生任务名称与类型，原生库与队列翻译单元编译通过；正式采集镜像已部署并完成单次有界观测。runtime拦截函数记录进入/退出点及线程CPU、等待、探针计数，已按现有trace及SDK声明加入主线kernel提交入口，已在本次prefill/decode观测中验证实际拦截；这不证明所有调用分支或目标成本资格。`cpu_workers`是原始观测资产，保留needs_data及缺口；不直接按来源编号拟合。同步直调路径不能伪造队列身份，仍由原有主线程边界表达。

独立CPU观测由runtime层的`CpuWorkerUnits`规范化为`cpu_worker_units.json`。框架只传入显式阶段/worker文件；归属先在入队线程选择唯一最内层阶段，再由pid/correlation_id传到worker。每个线程以入口、runtime进出、出口的相邻点形成不重叠测量段，嵌套API不能再叠加父调用总量；入队与worker不跨线程相减。阶段元数据共享保存，单元以scope索引和原始文件/行号追溯。线程CPU、已记录等待与探针计数分别保留，不自动相减或提升为纯服务成本；未配对、失败或无法唯一归属的记录保留缺口。该资产是测量交接格式，不是新增语义block或按每个切口创建一个模型。

提交端口的对应属于模板生产适配端的职责。profiler的高层launch入口与底层runtime提交入口不能仅因同属一个worker就视为同一边界。Ascend归一化先用原生HostToDevice flow及connection_id确定设备任务的生产调用，再在同线程、该调用区间内识别唯一的runtime提交入口；对应明确时将flow起点细化到该入口，并保留原profiler端点。调用入口表达提交的依赖边界，返回点只划分CPU服务，不制造设备必须等待API返回的屏障。没有唯一对应时保留原始flow及该单元的成本限制，不按时间最近选择、不增加公共核心中的SDK名称分支。一个worker只有一次观测到的runtime调用，也不自动证明该调用与结构端口等价；来源时间差只帮助定位，不可变成固定补偿或分摊比例。

目标侧的worker服务通过`SourceCpuWork`表达原生操作和提交前/调用内/提交后三种位置。生产适配端只标记已完整覆盖worker窗口、且中段与已确认runtime调用边界完全对应的现有CPU服务，不新增节点、不分摊总耗时；额外切口或等待继续保留原结构。模板按节点保存该描述。展开后，执行图通过实际目标提交端口连接设备工作；提交后段由目标返回端点找到对应调用，重复供体插入不能仅按来源span编号关联。`ServiceWork`取得目标提交根的kernel/传输等描述，故shape来自目标变换结果，来源提交编号不进入成本特征。根节点仍可能是通信逻辑包络；关联成功不等于已经取得完整通信成本特征或成本资格。

worker 候选以完整单次提交的 before/call/after 三段线程 CPU 观测为单位，按操作名称与位置取中位数。该初始假设省略 shape、rank 和阶段，适用性必须通过独立数据评价；目标工作仍保留实际 shape，不能把省略特征误写为不需要目标信息。含已观测等待的单元不参与该候选；对已有成对计数的探针开销，按段从线程 CPU 时间中扣除，保留原始观测与计数。runtime 记录点以同一线程的前后时钟测量计数/墙钟读取及向量写入开销，下一边界恰好接收该计数；边界时钟调用尾部等未测开销仍是限制，不使用固定补偿。候选与评价共用规范化测量合同，保留来源、缺口和观测上下文；评价不修改拟合值，不能依据目标误差加入补偿。公开入口见[开发文档](development.md#从独立单元样本拟合候选)。

首个具体单元采用已生产的准入预算成员区域，对应适配器绑定的完整原生预算方法。只有区域为单入口/出口且唯一CPU服务节点恰好覆盖这两个端口，才将其标记为一个完整成员单元；其他区域继续保留原有节点表达，不拒绝整个模板或分摊阶段总量。普通节点由来源成员顺序绑定，插入节点使用实际目标request_slot，不能把供体槽位当作目标槽位。C++成本查询通过`ServiceWork::admission_member()`取得类型化的`AdmissionServiceWork`，提供accepted_requests、running_requests、input_tokens和该成员horizon_checks；已支持的接纳路径以accepted_requests是否为零推导request_states_initialized，首次建立与后续插入不另存一份状态。诊断JSON由同一值对象输出，模型不需要解析报告或重复解释目标槽位。阶段总工作仍单列control_context。该表示复用已有区域和执行节点，不增加图合并、额外服务收费或模板格式。

CPU采样已按相同绑定接入无profiler的完整原生调用观测，单独输出cpu_units，保留首次req_states初始化/后续插入、入口工作参数、实际接纳与返回。对非SWA路径，只在确认接纳后由原生控制流推出完整horizon遍历数，拒绝情况仍为未知。线程CPU时间、runtime等待/探针和相邻时钟读取样本分开保存，不自动相减形成合格成本。外围阶段仍包含原生调用服务，只扣观测器内部测得的新增wrapper开销；外层HookRegistry进出不在此扣除区间，因此不能把阶段样本称为已完全去除插桩开销。阶段样本与单元样本不能重复收费。接下来核对实测边界、必要特征及独立验证；当前cpu_unit_readiness仍为needs_data。旧采集中的阶段耗时与带语义计数插桩的区域时长均不能直接作为此单元的合格成本；必要特征和独立测量资格仍待完成。原生预算方法首次调用建立并排序成员状态，后续调用有序插入，再执行预算遍历；首个模型先以初始化/插入分支和成员工作规模作为候选特征，不预先计数每次排序或插入比较；这是一项待独立验证的粒度选择，不是所有成员排列成本相同的保证。验证若表明同规模的排列差异影响精度，再补对应特征；不因原生代码存在内部循环就自动增加插桩和模板字段。避免按输入长度建立整段调用成本表；相邻时钟只提供观测量级，不代表全部wrapper开销。

以上是S5接入合同，尚未实现CPU局部单元合并和正式测量映射。它不要求重做S3/S4、不扩大统一流程范围，也不把所有源图切口自动升级为独立性能模型。

### 通信采样与节点工作的交接

独立通信采样保留collective包络和逐rank记录，同时输出`task_samples`。Ascend适配器以rank、stream/task/context原生身份连接通信明细与唯一物理任务，保留操作、字节、dtype、transport、源/目标rank和硬件起止时间，并携带采样域与原始证据引用。任务语义与已有SourceCommunicationTask一致；不按时间接近或包络比例分摊。

物理分类沿用归一化结果：数据任务、等待和标记分别保存。等待通过依赖处理；物理DeviceMarker是已有模板中的真实设备命令，不能和零服务的逻辑Annotation混淆。物理命令和数据任务的观测时长均须经测量解释，数据任务也可能含内部传输停顿，不直接升级为合格成本。已知setup才可排除，真实归属缺失或歧义保留为缺口。逐节点导出不自动解除profiler、内部停顿或部署资格问题，不能把父collective包络再重复计费。

## 5. 单一事件引擎

维护唯一模拟时钟、就绪工作、完成事件和资源状态。依赖满足且资源可用时启动工作，根据服务和竞争模型安排完成。请求到达、timer 与工作完成共享时间轴。

CPU lane/worker 队列表达顺序和容量；设备 stream 表达顺序，不等于设备全局串行；链路、存储等共享资源在实际需要时加入容量/带宽模型。不能给每个并发传输都无条件分配完整带宽。

排队由引擎生成，不在服务成本中重复计入。竞争若改变在途工作的服务速度，引擎负责更新完成安排，控制器只消费最终模拟事件。初期无法表达的竞争机制单列近似或不支持，不暗设全串行。

CPU 提交完成可以开放设备启动，CPU 返回段与设备重叠；设备完成与缓存发布分开。取消按已支持语义处理，已执行字节和最终可见字节分别保留。

## 6. 输出与误差

scope 内窗口时间由起止事件计算，不能直接相加全部节点成本。请求 TTFT、完成时延和吞吐只有对应边界存在时可报告；建模范围用 modeled 标记，不能伪装为包含排除段的真实 HTTP 指标。

成本误差、结构误差、控制近似和资源近似分别说明。不用 target 残差补 CPU 时间，不用组件正负误差抵消证明每项准确。NodeScale 保持可选且默认关闭，只作显式诊断变换，不能替代正式语义或成本模型。

## 7. 实施任务与完成条件

1. 确认 S4 在给定耗时下的内部结构、资源和完成反馈已经通过，再确定性能单元及特征。
2. 按[采样合同](04_collection_templates.md#独立性能采样合同)验证对象一致性、简洁适配、共同执行途径和有界特征覆盖，再按计算、attention、CPU 服务、通信和拷贝的实际需要复核样本、建立模型；不以扩大采样量替代合同收敛。
3. 核对父子覆盖、端口、服务/等待、观测开销和适用域，不以联合包络填未知节点。
4. 将模型耗时接入同一执行核，输出单元级缺口及来源；采集由工作流管理，成本函数不启动设备。

交付是节点/局部子图成本提供者、单元级独立测量映射与性能报告，复用已验收执行核。验收要求特征对应实际工作、来源和域明确、无重复计费、缺失明确、CPU 状态仍按端口生效；给定耗时的结构证据、模型留出误差和完整预测误差分别报告。
