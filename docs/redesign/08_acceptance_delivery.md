# 阶段八 验收与维护交付

状态：最终独立验收待实施。主线为 SGLang + Qwen3-32B；结构资格先在 S3/S4 用统一流程、语义插桩、真实模板和给定节点耗时验收，S5 再做节点模型，最终汇总性能闭环证据。KT 与原生控制器后续扩展，不作为主线门槛。依赖[闭环集成](07_integration_workflow.md)。

## 2026-10-10 新合同验收增量

- 用户只提交固定模型、多个配置、多个 request workload 及资产/采集条件，无须指定 base；输出覆盖笛卡尔积，逐组合报告状态、指标、来源和缺口。
- 用已建模板预测多组未参与建库的请求序列，包含合法新长度、批次和到达变化；无依据分支明确拒绝，不以逐长度补采冒充参数化。
- 核对五类顶层 block、内部语义区域、性能单元的不同职责及局部变换、异步端口、跨批依赖。
- 覆盖资产复用、代表配置补采、范围外拒绝、缺数据、预算耗尽、部分失败与恢复；不要求每次探索只能采一次。
- 在同范围、输入和成本来源下比较操作时延汇总与依赖图执行，证明额外结构解释了什么。尚无优于 Dooly 的结论，无 overlap 实现时不宣称重叠收益。

集合合同与结构泛化纳入 S3–S6 交付，完整独立精度及方法收益评价在 S7 汇总。

## 1. 范围先于精度

为 SGLang + Qwen3-32B 给出模型/部署、控制规则、模板、允许变换和预测 scope。首先检查每个目标组合及其模板来源/变换关系是否在声明范围内，再评价结构与时间。KT 现有采集成果和未支持能力单列说明，后续适配完成后按同一标准独立验收。

modeled 范围的结果应和对应可观测范围比较，完整 HTTP 真值另外报告；无法从目标观测分离相同范围时说明不可直接评分。不能从完整 HTTP 减掉任意 residual 来制造匹配。要求 http_e2e 时必须实际覆盖全部必要边界与时间。

精度指标和门槛在最终验证前确定，不根据成绩回调门槛。旧实验的 WAPE/P90 数值与固定格数不是新合同的自动门槛；未确认时报告实际指标，精度验收保持未完成。

## 2. 语义与动态性

这一部分是进入成本建模的前置验收，在 S3/S4 完成；S7 引用并复核证据，不能等性能模型完成后才判断结构是否正确。

先检查统一流程的输入、职责、端口、状态效果与参数是否对应原生工作；统一插桩是否通过阶段范围、工作关联和端口事件解释节点归属；模板是否保留内部依赖、跨模板端口、参数来源及合法变体。函数返回、CPU 提交结束、设备完成和业务发布必须区分，阶段划分不能增加原生同步。

分别检查步骤数、工作量、batch、shape、通信、页/字节、关键依赖、执行与发布差别。模板局部成本准确不能证明控制顺序正确，总耗时接近也不能证明结构准确。

至少覆盖：base 自身、一个允许参数变化、一个受支持的时间相关决策、一个缺模板/规则拒绝、一个缺成本恢复。控制近似和数据依赖假设单列，不能把未比较的动态行为计作精确复现。

结构阶段使用显式给定节点耗时，检查同配置、准入 2→1、时间反馈与缺规则/变体停止；报告节点、工作量、shape、关键依赖、资源、端口、请求/KV 状态和终止。对照原生行为时说明时延条件和控制近似，区分错误规则与不同耗时导致的合法调度差异。独立原生验证观测不进入生成器，不能通过目标成绩调整给定耗时。

有限规则还要说明成立条件、改变的节点/边、参数映射、端口处理及不支持范围。仅更新模块 batch/context、内部沿用旧 kernel，或整批长度组合样本齐全，都不能算节点结构验收通过。缺成本恢复在正式性能阶段另行验收。

### 固定资产下的泛化与规模验收

验收同时检查正确性和维护规模。对同一声明支持域，扩大目标 request 集合应只增加实例化与展开工作；不能要求同步增加结构采集、模板定义或案例规则。若出现增长，必须先定位到真实分支或设计缺陷，并记录其对本轮验收的影响。性能样本是否足够另按成本适用域判断，不与结构定义数量混算。

泛化验收开始前明确模板资产、规则和支持域；本轮期间不补语义模板、不修改规则。覆盖未参与建库的合法长度、批次和到达变化，并记录不支持输入的拒绝。若验证发现促成了规则修正或结构补采，该输入转为开发证据，不能仍记作独立泛化通过；使用新的未见输入重新验收。

同时报告建库累计成本（含初始化、预热、失败）、去重后的结构变体及规则增长原因。检查新增内容对应真实分支还是在枚举请求组合；不能只凭有限 demo 跑通、预算未耗尽或耗时接近宣告完成。不设未经证据支持的固定模板数、采集轮数阈值，也不允许因没有阈值而无限扩张。

核对建库是否按预先声明的证据目标结束，区分成功覆盖与因预算/缺陷停止。固定支持域下增加未见 request 序列时，目标实例数可以增长，模板定义和规则应保持不变；若必须增长，先解释是否为真实且此前未覆盖的实现分支。分别报告原始实例、结构族、变体、规则与成本样本数量，以及初始化、观测、后处理和存储开销。没有真实测量时，轻量采集仍是设计要求，不能宣称已经达到。


验收报告还需说明每次补采的缺口类别、预期事实、实际取得的证据和累计开销。检查失败是否触发了隐式重采或逐案例新增规则；出现这种行为时，本轮泛化验收不通过。成本缺口按性能单元另行处理，不能用增加结构模板来掩盖。该检查复用执行记录和已有报告，不新增测试工程或治理平台。

以下任一情况均不能据此宣告 S3/S4 收口：只有已采请求能够展开；同一已声明分支的新长度需要新增模板；规则依赖具体请求身份或案例组合；未知分支通过反复试采被当成已覆盖；只报告短观测窗口而遗漏初始化、后处理或失败成本。先修正对应设计或缩小明确声明的支持域，再开展固定资产验收。允许报告边界清楚的局部成果，不将缩小范围后的通过计作原计划全部完成。

轻量化验收逐项对照采集覆盖表：承诺的机制是否有证据、一次采集是否复用了共有部分、新增模板/规则是否各有机制依据、实际运行及后处理/存储是否在本次上限内。固定支持域下增加目标 request 集时，不新增结构定义和规则是必须检查的结果；若发现真实新分支，则返回建库并保留本轮未通过的结论。预算内结束只是开销合格，不能替代结构资格或泛化通过。

## 3. CPU 与性能

CPU 阶段必须能够解释工作量、服务与等待，不能用模拟器自身运行时间替代目标成本。成本留出误差、同成本结构/时序检查、完整目标预测误差分别报告。

成本单元允许比语义模板更细，也可在保留外部端口和重叠时合并；检查矩阵、attention、通信、拷贝和 CPU 服务的特征是否对应实际工作。9/8、10/9 等 context 组合可以是部分节点特征，不能替代整套节点模型。给定耗时输入与模型预测耗时的用途和结果明确区分，无父子或等待重复计费。

训练、开发验证与最终留出数据用途明确。预测完成后才独立读取 target 实测；评分不能触发拟合、补采或自动调参。报告总体、分组、尾部、缺口与失败覆盖，不只挑成功候选。

采样、I/O、CPU residual 和 probe overhead 分开，不能通过其他成本吸收误差。硬件或真实数据不足时，运行与精度条目保持未完成。

| 首次运行 | 用户只准备项目、模型、workload、配置和采集权限 |

| 独立评价 | 不修改预测、控制规则或成本 |

## 5. 规模与维护性

当前通过主线的配置变化、测量域扩展和必要行为规则修改检查维护成本：新增一个同语义配置主要改输入；新增测量域主要改采样和成本；新增行为修改有限控制规则与模板。KT 后续接入时仅补充子图获取与模板化差异，复用公共生产流程并交付统一模板；验收共同控制、图展开、执行和成本调用没有新增框架业务分支，并核对参数、状态效果及端口确实被同一消费者使用。本轮不为完成该检查提前实现 KT。只有新通用资源/事件机制确有需要时才扩展核心。

重点检查有没有重复状态、两套时钟、按实验标签的分支、逐配置实现、无边界工具文件和过早插件框架。行数作为观察指标，不以压缩格式、迁移统计范围或拆文件数量证明维护性。

新增功能、抽象和依赖须有实际需求与消费者，不用代码量换质量。检查成本参数是否有真实来源、有无硬编码或配置化的手调补偿；不能因特定实验分数变好就接受扩大特例代码的方案。质量以机制正确、独立验证、清晰职责及实际维护成本评价。

运行时不依赖 deprecated 的内部工作流；复用旧通用代码前确认职责与实际消费者。官方源码保持干净，采集适配不演变为业务 fork。

## 6. 采集收益、检查与交付

分别记录首次 base/性能获取开销与新增目标边际开销，包括启动、预热、失败和重试。已有资产的本次复用开销与原始获取成本分开。没有可比真实运行基线时不宣称节省比例。

实现按实际修改范围执行静态检查、正式构建和少量真实输入公开入口；C++ 核心采用 clean Release/validation 构建。不新增独立测试脚本、夹具或 CTest 工程。完整评价面板在规则和公式稳定后执行。

最终交付用户操作、当前能力表、范围与误差报告、模板/控制/成本扩展说明和资产来源。当前阶段文档是短期设计与计划，收口后将稳定合同合入正式文档，整理临时计划；实施记录保持历史性质。README 现阶段继续为空，正式入口文档后续按用户要求恢复。
