# 验收与维护交付

本文维护验收条件；实际交付状态只见[主计划](../redesign-workflow/2026-10-08_redesign_execution_plan.md)。主线为 SGLang + Qwen3-32B；结构资格先在 S3/S4 用统一流程、语义插桩、真实模板和给定节点耗时验收，首个性能闭环再覆盖设备计算、通信、搬运和设备命令，最终汇总独立评价证据。host 控制类 CPU 服务耗时有意排除，控制、状态和必要依赖保留；同步 host 复制仍归传输。工程闭环、结构支持和性能精度各自需要相应证据。KT 与原生控制器后续扩展，不作为主线门槛。依赖[闭环集成](07_integration_workflow.md)。

当前专项将稳态、分层归一化和必要 CPU 成本纳入后续联合验收，顺序及拟定指标见[专项计划](../redesign-workflow/2026-10-17_steady_state_template_cpu_plan.md#12-p7独立验收一键交付与整体收紧)。本文的首个闭环 CPU 排除结论仅适用于现行实现和历史结果，不能替代新目标的验收；P0 固定范围后同步本正文，历史成绩保持原样。

## 1. 范围先于精度

为 SGLang + Qwen3-32B 给出模型/部署、控制规则、模板、允许变换和预测 scope。首先检查每个目标组合及其模板来源/变换关系是否在声明范围内，再评价结构与时间。KT 现有采集成果和未支持能力单列说明，后续适配完成后按同一标准独立验收。

首个闭环报告理想化 CPU 的 modeled 结果，计时范围见[性能合同](06_performance_execution.md)。对齐同一请求、起止/发布端口及可关联时钟后，可直接报告预测与原生实际间隔的偏差；原生间隔包含有意省略的 CPU 服务、范围外工作和观测影响，不能称为纯设备同范围真值。无需先逐段分离全部 CPU 时间才能比较，也不能从完整原生/HTTP 测量任意减 residual 制造匹配。端口或原点无法对齐时，不给对应数值。完整原生/HTTP 指标单列，http_e2e 仍要求实际覆盖相应边界和时间。

精度指标和门槛在最终验证前确定，不根据成绩回调门槛。旧实验的 WAPE/P90 数值与固定格数不是新合同的自动门槛；未确认时报告实际指标，精度验收保持未完成。

## 2. 语义与动态性

这一部分是进入成本建模的前置验收，在 S3/S4 完成；S7 引用并复核证据，不能等性能模型完成后才判断结构是否正确。

先检查统一流程的输入、职责、端口、状态效果与参数是否对应原生工作；统一插桩是否通过阶段范围、工作关联和端口事件解释节点归属；模板是否保留内部依赖、跨模板端口、参数来源及合法变体。函数返回、CPU 提交结束、设备完成和业务发布必须区分，阶段划分不能增加原生同步。

分别检查步骤数、工作量、batch、shape、通信、页/字节、关键依赖、执行与发布差别。模板局部成本准确不能证明控制顺序正确，总耗时接近也不能证明结构准确。

至少覆盖：base 自身、一个允许参数变化、一个受支持的时间相关决策、一个缺模板/规则拒绝、一个缺成本恢复。控制近似和数据依赖假设单列，不能把未比较的动态行为计作精确复现。

结构阶段使用显式给定节点耗时，检查同配置、准入 2→1、时间反馈与缺规则/变体停止；报告节点、工作量、shape、关键依赖、资源、端口、请求/KV 状态和终止。对照原生行为时说明时延条件和控制近似，区分错误规则与不同耗时导致的合法调度差异。独立原生验证观测不进入生成器，不能通过目标成绩调整给定耗时。

有限规则还要说明成立条件、改变的节点/边、参数映射、端口处理及不支持范围。仅更新模块 batch/context、内部沿用旧 kernel，或整批长度组合样本齐全，都不能算节点结构验收通过。缺成本恢复在正式性能阶段另行验收。

### 固定资产下的泛化与规模验收

验收同时检查正确性和维护规模。对同一声明支持域，扩大目标 request 集合应只增加实例化与展开工作；不能要求同步增加结构采集、模板定义或案例规则。性能样本是否足够另按成本适用域判断，不与结构定义数量混算。

泛化验收开始前明确模板资产、规则和支持域；本轮期间不补语义模板、不修改规则。覆盖未参与建库的合法长度、批次和到达变化，并记录不支持输入的拒绝。若验证发现促成了规则修正或结构补采，该输入转为开发证据，不能仍记作独立泛化通过；使用新的未见输入重新验收。

验收报告逐项对照采集覆盖表，记录承诺机制的实际证据、共有部分的复用，以及原始实例、结构族、变体、规则和成本样本数量。开销包含初始化、预热、观测、后处理、失败和存储；每次补采说明缺口类别、预期事实与实际所得。复用现有执行记录，不新增测试工程或治理平台；没有真实测量时不宣称轻量采集已达标。

以下情况不能宣告 S3/S4 收口：只有已采请求可展开；同一已声明分支的新长度需要新增模板；规则依赖请求身份或案例组合；未知分支靠反复试采被当作覆盖；遗漏初始化、后处理或失败成本。若发现真实新分支或设计缺陷，返回建库并保留本轮未通过的结论；不能用结构补采掩盖成本缺口。缩小支持域后的局部成果也不等于原计划全部完成。

预算内停止与成功覆盖分别报告。不设无证据的固定模板数或采集轮数门槛，也不允许无界扩张；有限 demo 跑通、耗时接近或预算未耗尽，都不能替代结构资格和固定资产泛化证据。

## 3. 计时范围与独立评价

保留原生模板和目标动态展开，只为声明范围内的设备计算、通信、搬运和命令取得性能数据。检查工作特征、成本来源、必要依赖及无重复计费；同步 host 复制不能被归入排除的 CPU 服务。CPU 调度、提交和结果处理不追加服务时间，但仍执行逻辑和状态效果，不增加全局屏障或忽略数据搬运。不再要求 CPU gap、worker 前后段或纯 CPU 主体的测量覆盖作为首个闭环门槛。

固定模板、规则和成本资产后，预测未参与建库/拟合的请求输入，再从独立 validation 事实读取对应原生端口。先交付少量可解释的窗口和请求偏差、缺口及范围说明，不建设指标全集或自动调参平台；评价不回灌模型、不触发补采。

给定耗时可以用于结构或条件分析，未资格化成本候选也可报告条件数值比较；两者均不能冒充已通过真实性能精度。首个真实成本闭环要求计时范围内工作脱离 given，并单列模型适用性与独立观测限制。有意省略 CPU 时间产生的偏差不是必须补回的缺失节点，不以逐片段探针或父级残差修正来掩盖它。软硬件或真实观测不足时，相关验收结论保持未完成。

| 首次运行 | 用户只准备项目、模型、workload、配置和采集权限 |

| 独立评价 | 不修改预测、控制规则或成本 |

## 5. 规模与维护性

当前通过主线的配置变化、测量域扩展和必要行为规则修改检查维护成本：新增一个同语义配置主要改输入；新增测量域主要改采样和成本；新增行为修改有限控制规则与模板。KT 后续接入时仅补充子图获取与模板化差异，复用公共生产流程并交付统一模板；验收共同控制、图展开、执行和成本调用没有新增框架业务分支，并核对参数、状态效果及端口确实被同一消费者使用。本轮不为完成该检查提前实现 KT。只有新通用资源/事件机制确有需要时才扩展核心。

重点检查有没有重复状态、两套时钟、按实验标签的分支、逐配置实现、无边界工具文件和过早插件框架。行数作为观察指标，不以压缩格式、迁移统计范围或拆文件数量证明维护性。

新增功能、抽象和依赖须有实际需求与消费者，不用代码量换质量。检查成本参数是否有真实来源、有无硬编码或配置化的手调补偿；不能因特定实验分数变好就接受扩大特例代码的方案。质量以机制正确、独立验证、清晰职责及实际维护成本评价。

运行时不依赖 deprecated 的内部工作流；复用旧通用代码前确认职责与实际消费者。官方源码保持干净，采集适配不演变为业务 fork。

## 6. 采集收益、检查与交付

分别记录首次 base/性能获取开销与新增目标边际开销，包括启动、预热、失败和重试。已有资产的本次复用开销与原始获取成本分开。没有可比真实运行基线时不宣称节省比例。

实现按实际修改范围执行静态检查、正式构建和少量真实输入公开入口；C++ 核心采用 clean Release/validation 构建。不新增独立测试脚本、夹具或 CTest 工程。独立评价按声明范围复用已有结果和真实输入，不以新增测试工程或评价面板作为首个闭环前提。

最终交付用户操作、当前能力表、范围与误差报告、模板/控制/成本扩展说明和资产来源。当前阶段文档是短期设计与计划，收口后将稳定合同合入正式文档，整理临时计划；实施记录保持历史性质。README 现阶段继续为空，正式入口文档后续按用户要求恢复。

完成结论分别覆盖软件可运行、关系支持、语义、声明范围内性能、用户体验和维护性，不能以构建通过或历史成绩替代。首个闭环通过不代表完整原生 CPU/HTTP 性能、所有框架或全部 S6/S7 交付完成。
