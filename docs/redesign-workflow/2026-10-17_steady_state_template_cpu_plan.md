# Serving 稳态、分层模板与 CPU 建模工作计划

制定：2026-10-17。状态：**计划已制定，P0–P7 待执行**。本次只维护计划、入口和必要的范围说明，不修改代码、不启动采集、不把方案写成已有能力。

全局状态只在[主计划](2026-10-08_redesign_execution_plan.md)维护；本文件是本专项任务、实施顺序和退出条件的唯一正文。遵守[工程约束](../redesign/engineering_constraints.md)，延续已完成的[结构整理成果](history/2026-10-16_structure_cleanup_plan.md)。

## 1. 要解决的问题与最终结果

本专项把现有有限工程闭环推进为：**在声明配置域内，用少量分层、参数化的语义模板，结合可测的 CPU/设备成本，预测预热后 serving 统一流程的执行结构与性能。**

| 已确认的问题 | 本专项要求得到的结果 |
| --- | --- |
| 性能采样额外预热目标特征点，目标验证仍可能首次编译 | 结构采集、性能采样、独立验证使用相容的稳态协议，初始化和编译退出计时窗口 |
| 当前 host CPU 服务被排除，只有设备等成本 | 定义少量 CPU 工作及其计时边界、特征和独立样本；保留 CPU/设备重叠 |
| 五类阶段承担了过多内部细节 | 五类顶层流程保留，模型与 serving 内部按复用和变换需要分层 |
| 来源调用仍作为完整阶段定义保留 | 结构定义、参数绑定、来源观测、目标实例分开；相同结构共同引用定义 |
| CPU 函数分支、循环及优化配置可能放大模板数量 | 按稳定职责表达行为和工作量；必要实现差异形成有限变体，不枚举原生调用树 |
| 支持、结构、成本和精度容易混为一谈 | 配置变更分类，结构与成本覆盖分开，分层验证后再判断请求性能 |

最终交付仍走现有公开入口和一键示例。用户输入继续是固定模型、配置集合、request workload 集合，不指定 base、CPU 常数或模板来源。代表来源和采样需求由系统组织，目标验证不回流生成或拟合。

## 2. 当前基线与证据用途

以下是实施前事实，不是本专项完成项：

- 主线为 SGLang + Qwen3-32B / Ascend TP2。现有 FCFS、无 prefix cache、无 overlap、无 graph、非 mixed/chunked 路径已有完整工程流程。
- 当前库有 5 类顶层步骤、112 份阶段级来源定义，分入 18 个 step/phase/rank 桶；模型内部 3328 次区域引用共享 26 份结构。112、18、26 的对象不同，均不能直接称为完整归一化后的模板种类数。
- 当前已有 NPU 计算、通信、传输和设备命令样本，本次正式运行产生 10 份非空候选。缺的是 host CPU 成本链及更完整的适用域，不是所有性能数据都不存在。
- 当前预热仅执行一个 1-token 输入、2-token 输出请求；性能采样另对每个点预热。这种动作相同不足以保证目标执行状态相同。
- 同引擎重复双请求的开发观测为：首次约 11706 ms，后续约 266–277 ms，中位数约 269 ms；现有预测约 85 ms。已观察到首次 Triton 内核编译、host launcher 构建，以及热态显著 CPU 执行。CPU/设备重叠程度和同口径设备精度尚未独立量化。
- 把实测 CPU 时间代入简式得到约 267 ms，只是解释性计算，不是独立 CPU 预测，也不能当作接近 1% 精度的证明。
- 当前活动自有 C++/Python/Shell 为 211 文件、35211 物理行；此前 237 文件审查还包含构建、配置等内容。后续规模对比沿用同一计数范围，不以拆文件或删除空行作为瘦身。

正式基线入口为[已有运行摘要](../../data/20261016T154651.604935Z_sglang-qwen3-32b/results/summary.md)。归因、重复执行与成本敏感性记录见[已有精度分析](../../data/20261016T233213.460800Z_accuracy-analysis/results/analysis.json)。这些已用于本专项设计，属于**开发证据**，不能重复作为最终独立精度验收。原结果、资产和历史范围不回写。

## 3. 范围与工作分类

### 3.1 本专项的目标范围

- 固定当前模型、框架实现、dtype、TP、attention backend 和部署；以已有结构资格允许的请求长度、人数、到达和预算变化为起点，P0 写清条件及数值域。
- 默认起点为**引擎已预热且无在途业务请求**，逻辑 KV 清空；保留符合协议的编译缓存、分配缓存和 workspace 初态。暂不支持从繁忙服务中间截取带在途工作的窗口。
- 计时目标覆盖统一流程内的调度、准备、提交、设备计算、通信、实际搬运、必要完成处理和发布。CPU 加入后仍不等于 HTTP 端到端预测。
- 模型加载、运行时初始化、首次编译、预热、HTTP/tokenization 及合同外后台服务不计入预测。它们仍计入实际采集开销；窗口内合法的分配、扩容和同步由目标状态决定，不能统称初始化而删除。
- 树表达语义组合；实际执行仍是带资源、状态和异步端口的 DAG。五类顶层动作不因内部细分变成几十个并列控制器动作。

### 3.2 配置变化分类

| 变化类别 | 例子 | 处理原则 |
| --- | --- | --- |
| 参数与工作量变化 | 合法长度、批次成员、KV 页需求、传输字节 | 同一语义定义及允许变换产生新实例；成本覆盖单独判断 |
| 有限执行分支变化 | 原生已知 kernel/通信算法分支、融合/非融合实现 | 显式条件选择有限实现变体；先检查已有证据，不把每个 shape 当新模板 |
| 执行实现变化 | attention backend、TP、dtype、runtime 或编译实现改变 | 重新判断来源与成本适用性；必要时获取新来源，本专项不自动授予跨实现迁移 |
| 控制与状态机制变化 | chunked/mixed prefill、overlap、prefix cache、抢占 | 要求对应控制器、状态和端口能力；不能仅凭增加子图支持，当前保持范围外 |

优化开关按真实作用归入上述类别，不按开关名建立笼统复用规则。语义结构可共享，不表示具体 kernel 变体或成本一定可共享。

### 3.3 不同性质的工作

| 性质 | 本专项处理 |
| --- | --- |
| 必须实现 | 稳态协议、分层结构及归一化、目标组合、必要 CPU 成本与采样、联合预测及独立验收 |
| 持续遵守的约定 | 公共接口、唯一状态所有者、生产端适配、有界采样、代码收紧、文档单一正文；不逐条变成新平台或检查程序 |
| 范围外能力 | KT 预测、跨模型/TP/backend 泛化、复杂缓存/抢占、原生控制器、逐算子重放平台、复杂采集搜索、为使用随机森林而扩采 |
| 待验证风险 | profiler 扰动、CPU 可测边界、资源竞争、kernel 选择、跨区域融合和跨 rank 接口；先按影响与现有证据判断，不自动全部变成采集门槛 |

**结构先行、成本后置。** P0/P2 要先确定 CPU 行为与计时切口，避免 P5 重拆结构；在 P4 结构资格通过前，不开展 CPU 大规模性能采样或复杂拟合。P4 使用的显式给定耗时是条件分析输入，不能成为实测数据或调参常数。

每阶段关闭一个完整能力及其生产/消费链。实现与合同同次更新，旧路径从入口到产物完整删除，不长期维护两套模板或 CPU 后端。

## 5. P0：固定稳态范围、泛化空间和验收口径

### 实施内容

1. 盘点输入合同、框架配置、模板来源、现有变换及成本适用域，形成一张配置变更表；明确哪些是参数变化、有限实现分支、重新采集和控制能力扩展。
2. 固定当前主线的请求域、逻辑 KV/workspace 初态、无在途工作条件、CPU/设备资源假设，以及暂不支持的优化机制。已承诺但未验收的关系不能静默删掉后宣称完成。
3. 定义业务计时入口、首次/最终 Published 和采样服务边界。预测使用 workload 的逻辑到达；原生需有对应入口观测，报告计划到达与实际进入的差异。客户端计划时刻含前端开销时，原对照保留为更广窗口，不能靠减残差当作同范围真值。
4. 确定三条验证链：给定耗时的结构资格、同批次工作/成本核对、稳态请求指标。固定独立输入的选择方法与指标汇总，开发证据不再担任最终独立验证。
5. 更新现有设计合同中的旧 CPU 排除范围与预热假设，明确历史结果、当前实现和目标设计。只在原正文修改，不追加互相冲突的“最新合同”。

### 交付与退出

- 交付更新后的用户、采集/模板、语义、性能、集成与验收合同；P0 结果放回对应设计文档，不新增一套设计手册。
- 一项配置变化能够判断影响谁、如何复用、需要什么证据；CPU 行为、成本和等待各有归属。
- 计时起止、实际可观测边界、当前支持域与后续验收输入类别均可执行；缺少的入口观测进入 P1/P2。
- 本阶段先读代码和已有证据，不因表格未填满就采集。不能解释的配置机制保持范围外或待核对，不枚举试跑寻找答案。

## 6. P1：建立真正相容的稳态协议

### 实施内容

1. 对照原生配置和声明特征域，确定会触发编译/launcher 构建的有限执行条件。优先利用框架/runtime 已有的预热与缓存能力；补充请求由适配器构造，不能在核心识别 Triton/CANN 函数名。
2. 替换只保证“一次 Prefill、一次 Decode”的预热假设。用有界代表特征覆盖本阶段所需实现路径，不运行每条目标 request 生命周期作预演，也不保证预热任意 shape。
3. 语义采集、性能采样和独立验证复用同一协议及完成判据。性能点额外预热时，记录其覆盖关系，验证窗口须满足对应条件；不能只比较预热函数是否相同。
4. 原生框架负责请求结束、KV 清理及 worker idle 确认；观察编译缓存和 workspace 的保留条件，登记可迁移初态。不同配置不能无条件复制同一容量快照。
5. 分开记录初始化、编译/预热、业务观测和后处理。计时窗口若出现未覆盖的首次编译，标记本轮稳态证据无效或超出覆盖域；不得把秒级时间摊进 kernel/CPU 模型，也不得自动无限预热。

### 交付与退出

- 现有 session、capture、sampling 与 validation 使用同一稳态约定，环境事实中可核对实际执行和起点状态；不创建第二个预热管理平台。
- 在少量代表点与未用于设计的合法点上，证实计时窗口没有初始化编译污染，并记录正常重复波动。仅耗时下降不替代编译/执行状态依据。
- 业务窗口仍可发生真实分配、扩容与资源等待；预热耗时及失败均进入累计预算。
- 覆盖条件未知、原生清理不满足或预算到限时结束本批，保留原因；不能通过删高值、假填缓存或反复换请求掩盖问题。

## 7. P2：分层语义、统一插桩与子图接口

### 目标结构

以下是职责层次，不是要求每项创建新类，也不是把模型顺序强制当作全局串行屏障：

```text
Serving：Schedule / Prepare / Prefill / Decode / Publish
├── serving 内部动作：准入、成员过滤/合并、输入与 KV 准备、结果发布/释放
└── 模型执行
    ├── 模型输入处理
    ├── Decoder Layer × 实际层数
    │   ├── Attention 区域
    │   └── MLP 区域
    └── 模型输出处理
```

### 实施内容

1. 按 Qwen3 实际执行细化模型输入、重复层、Attention、MLP 与输出区域；归一化、残差、采样及通信等工作必须有明确归属，不能只覆盖两个大模块后漏掉中间工作。
2. 参考 [LLMServingSim 的 Qwen3 层次与 within](../../reference/llmservingsim/profiler/models/qwen3.yaml)，以模型/上下文解释原生模块；不能仅以函数同名或张量数值相等判定相同语义。保留真实物理节点、融合工作及异步依赖。
3. 每个可独立复用/变换的区域定义职责、参数、读写状态、输入输出端口、资源和外部依赖；没有独立复用/变换收益时保留为父区域的观测视图。
4. 将 CPU 稳定行为与原生函数调用树分离。候选职责包括准入/成员处理、输入元数据准备、模型任务提交和结果处理；循环量由目标请求/批次状态派生，不能复制 base 迭代数。
5. 在设备提交、数据可用、状态生效或外部消费者需要的地方保留切口。边界之间的 CPU 工作可以聚合；存在中间可见事件时不能合成一个全阶段总时长。
6. C++ 定义公共语义合同，prepare 将绑定交给 Python 通用 wrapper；框架/模型适配提供位置及参数来源，runtime 适配提供物理身份。复用现有插桩链，禁止两种语言各维护一套 block 名称与语义推断。
7. 为每项物理工作确定唯一归属。父子区域可以共同引用，收费只发生一次；跨区域融合节点按完整工作和联合接口表达，不为了树的整齐拆出虚假 kernel 或增加同步。

### 交付与退出

- 交付分层区域合同、原生绑定和可追溯子图切口；控制器继续使用五类顶层动作。
- 从任一模型/serving 区域能够定位内部工作、外部依赖、参数来源和状态效果；没有区域空洞、物理工作重复收费或树引入的全局屏障。
- 已有 26 份共享结构和模型 wrapper 优先复用；能重处理现有事实就不重新采集。缺少关键字段时先修观测合同，再安排最小补证据。
- 暂不为每个原生 CPU 函数或每个性能节点建立语义类；遇到跨层融合先选择合法联合边界，不立即增加通用切图语言。

## 8. P3：归一化定义、参数绑定与有限实现变体

### 实施内容

1. 分开四种对象：原生调用观测、可复用结构定义、定义的参数/来源绑定、目标执行实例。调用记录继续可追溯，但不能仅因多采了一次就增加一种定义。
2. 使用局部节点/边界与资源角色表达结构，把层号、调用 ID、原生时间、具体线程/stream 号等来源信息放入绑定；保留必要别名关系、相对 rank、状态效果、端口和外部约束。
3. 将已有资格的动态维度变成有来源的参数关系，分离请求长度、成员数、上下文与固定模型维度。相同 shape 不证明同工作；仅能改 shape 也不证明可以迁移完整实现。
4. 复用现有局部结构共享，按模块边界、稳定操作角色及显式依赖生成局部规范表示。定义比较包含语义/实现条件、固定模型属性、参数规则、资源别名、端口及规范拓扑；动态值放入绑定。来源中独立 stream 的偶然时间先后不能成为目标依赖。原生恰好相同的拓扑可以共享；不能用删除必要依赖、合并不同融合实现或忽略分支条件来减少数量。
5. 重复模型层共用定义，层身份、权重角色、参数和依赖各自绑定。定义共享不合并目标实际计算次数，也不把 TP 的物理 rank 或通信关系抹掉。
6. CPU 循环次数优先参数化，普通函数包装差异留在适配端。只有改变必要工作、对外状态、提交关系或可迁移成本条件的分支才形成有限变体；不能为每条原生调用路径存一张完整图。
7. 模板组合条件从生产绑定及实际变换共同取得，不新增平行的拒绝清单或支持验证器。结构选择不依赖来源 request ID、采集编号、目标标签或观测耗时。
8. 同步编译资产、选择、实例化、诊断和重建消费者，删除被替代的阶段重复结构/候选扫描链。保留事实与来源关系；格式调整不保留兼容版本，无法从旧事实重建时说明缺失，不能猜测补齐。

### 交付与退出

- 交付分层定义及绑定的正式资产，预测通过新职责链消费；统计在现有结果/目录与诊断中汇总，不再建独立模板管理平台。
- 分别报告语义种类、独立结构定义、实现变体、来源观测、绑定和目标实例数，设备与 CPU 分开；父定义引用子定义时说明计数层次，不能相加制造“总模板数”。
- 重复层、同结构调用和合法参数变化不会重复保存定义；固定实现域内增加 workload 只增加实例/绑定，不增加语义定义。
- 模板数量由实际职责与有限实现分支解释，不预设必须压成 5 或 26。阶段退出要逐项解释未合并结构的必要差异；单纯缺少归一化能力不能包装成真实变体。
- 若数量随请求长度组合或 CPU 调用路径持续增长，返回参数化/边界设计，不通过扩大结构采集填满组合。

## 9. P4：固定模板下的目标组合与动态结构验证

### 实施内容

1. 用分层定义和目标状态组织完整执行：模型重复层、合法参数变换、serving 动作与有限分支选择；模板来源不进入共同控制器决策。
2. 保持请求、逻辑 KV、workspace 和执行资源的唯一所有者。状态变更按对应端口生效，避免“CPU 返回了”被误解为“设备结果可用”。
3. 树形组合生成 DAG，明确跨层、跨模板、stream 和 rank 连接；保留提交与设备完成的区分，不把父区域耗时加到子图总和。
4. 将纳入范围的 CPU 动作接入公共可计时工作及依赖，先使用显式给定的 CPU/设备耗时完成结构验证，改变耗时检查到达与完成先后是否正确改变组批及工作量；不读取真实 target 调度决定目标图。此时不启动拟合或以给定值冒充模型，真实成本在 P5/P6 接入。
5. 固定模板和规则，覆盖合法长度、请求成员变化、排队/错峰到达、不同结束时刻，以及各自已有资格的页与容量变化。优先选择少量能区分机制的输入，不做全笛卡尔积穷举。
6. 先汇总潜在工作对象和参数关系，动态实例化再细化实际特征；缺成本时仍保留完整已展开前沿需求，不能退回每次只发现一个节点。

### 交付与退出

- 沿正式预测路径检查批次成员、shape/数据量、重复次数、端口、关键依赖可达性、KV/资源生命周期与结束条件；完整图仅在诊断时输出。
- 同一模板资产能够处理未参与建库的合法请求，定义不随目标序列增长；给定耗时改变后，控制反馈产生合理结构变化。
- 必要原生依赖保留，新增关系没有制造错误串行化。批次数、节点数或总时长相等不能单独作为通过依据。
- 合同/规则缺陷回到 P2/P3；真实新实现分支重新声明域和最小证据。结构缺口不能通过 CPU 拟合、额外时延或目标 workload 补采来关闭。

## 10. P5：CPU 工作定义与独立性能采样

### 实施内容

1. 在 P2 切口和 P4 目标工作上定义少量 CPU 性能对象。特征优先使用实际处理的请求数、输入 token/元数据量、存活/完成成员数、提交工作量及必要实现条件；先解释特征作用，再决定是否加入。
2. 区分 CPU 自身执行、等待设备/其他线程以及数据搬运。等待由依赖计算，已独立计时的传输不在 CPU 聚合中重复收费；线程 CPU 时间和墙钟一起用于验证测量边界，不能把任一指标直接当成完整可迁移成本。
3. 按线程/进程与资源角色保留必要串行关系。不同 TP rank 的 CPU 工作可以并行；CPU 与设备通过提交和完成端口重叠，不能相加两个 rank，也不能把整个 run_batch 墙钟当 CPU 后再加设备时间。
4. 框架适配选择稳定动作与参数来源，runtime 适配提供低扰动计时/关联；核心只消费公共 CPU 工作。性能插桩独立于重语义 profiler，共享实际批次身份和执行底层。
5. 继续通过原生请求生命周期生成样本，原生框架维护请求/KV/worker 状态。可以在同一常驻 Engine 内运行多个短采样点，不要求私有 batch 接口或自建原生状态机。
6. 请求构造是触发手段，覆盖依据是实际批次及 CPU 工作特征。不可控/不可达点说明原因；不能声明客户端 batch 数就认定测到了对应对象。
7. 比较轻量采样与未装成本插桩时的稳态行为和时间，识别观测扰动。重 profiler 里的 CPU 函数墙钟不直接进入模型，不用完整 serving 残差生成 CPU 标签。
8. 重复测量与独立验证按运行/请求组划分；同一次执行的重复模型层不能当作独立样本随机拆分。保留波动、环境与适用条件，不把异常值无依据地删除。

### 交付与退出

- 至少覆盖当前主线需要的调度/成员处理、准备、模型提交及发布 CPU 工作，成本模型能取得相同定义、相同边界的真实样本；具体对象按实际可测职责收敛，不预建逐函数模型库。
- CPU 样本与目标实例共享特征合同，并保留独立来源、部署、稳态和测量边界；异步等待、传输和父子包络不会重复进入服务量。
- 在少量固定批次的开发核对中，能够解释 CPU/设备重叠和主要时间来源。无法分离的重要区域先修切口；不立刻细化成每个 API 的成本类。
- 未覆盖的优化配置不自动导入本阶段，不能为“统一 CPU 模型”恢复已删除的微观采样与分类链。

## 11. P6：统一性能需求、采样覆盖与成本驱动执行

### 实施内容

1. 将 CPU 对象接入现有需求、样本、拟合与查询链。语义模板与性能粒度分开：一个区域可包含多个计时单元，多份语义模板可共享同一种成本对象。
2. 由归一化模板、参数关系和目标配置/request 范围先生成可能工作及特征域；复用已有数据，再由动态展开细化实际点。CPU 与设备需求均跨组合合并，未知时延不能填零继续正式预测。
3. 在声明域内安排少量代表点和必要边界点，记录实际覆盖、不可达点及停止原因。成本不足不重新采 serving 结构；只有新增可用证据才重算受影响组合。
4. 首先使用有依据的直接测量、参数化查表或简单插值。是否需要更复杂回归，取决于同范围独立误差和样本密度；不把随机森林、更多采样或更多特征预设为交付条件。
5. CPU 服务、设备计算、通信、传输和设备命令共用唯一模拟时钟，依赖/资源约束决定并发与等待。成本提供者只回答耗时，不修改控制策略或结构。
6. 新 CPU 时间会改变后续组批及特征点，按原初态重算受影响候选并细化同一份需求。配方已尝试却无新证据、域外或预算到限时停止，不增加新一套补采循环。
7. 压缩正式结构与成本产物，保留共同定义、绑定和有效样本；默认结果只保留必要摘要/引用，诊断仍按开关生成。沿现有 run 根、账本、恢复和清理，不引入新的任务平台。

### 交付与退出

- 公开预测实际消费测得的 CPU 与设备成本，目标结构、时间反馈和指标使用同一执行循环；正式结果无 given、无范围内缺成本、无目标残差修正。
- 从模板到需求、实际采样、成本查询与覆盖报告能够自动贯通，用户无需手工打开大图逐节点补数据。
- 同一支持域内添加请求不增加模板定义；性能样本是否增加由特征覆盖决定。缺口统计不能把“定义数”“对象种类”“特征点数”和“记录条数”混在一起。
- 缺样本、域外或未知机制保留明确状态；恢复不重置预算，不丢失已完成组合，也不恢复旧模板兼容路径。

## 12. P7：独立验收、一键交付与整体收紧

### 验收顺序

1. **结构。** 固定模板/规则，检查未参与实现的合法请求与配置组合，分别核对组批、工作量、关键依赖和资源/状态；排除给定耗时导致的合法调度差异，不能要求全部原生事件逐项相等。
2. **局部成本与重叠。** 选择固定实际批次，分别检查 CPU 工作、设备计算、通信/传输及必要端口，确认总耗时接近不是重复收费或错误串行化的抵消。
3. **请求性能。** 使用同稳态、同起止和可关联时钟的独立窗口，报告 TTFT、每请求平均输出间隔、请求完成时延、总窗口/吞吐；只有具备逐 token 观测时才报告逐 token ITL 分布。

### 目标与证据

- 工程精度目标建议先采用：同口径请求时延/TTFT/平均输出间隔的相对误差中位数不超过 20%、P90 不超过 30%，总窗口/吞吐相对误差不超过 20%。这是待 P0 固定的计划目标，不是用户已确认的既有指标，也不是当前精度承诺；不得看到最终成绩后回调门槛。
- 极短或近零间隔同时报告绝对误差；不同请求长度/并发分别汇总，不能只给总体平均掩盖一个子域失败。样本少时列出逐项结果，不能用不稳定的分位数代替证据。
- 验收输入、参数域和指标在修改前选定。用于纠错/补采的输入转为开发证据，随后使用新的未见输入；不因更换文件名或压缩形成独立性。
- 归一化后的定义数应由模型职责和有限实现分支解释；扩大验收 workload 集合时定义不增长。CPU 内部包装函数和循环次数变化不自动增加模板种类。

### 产品与代码交付

- 更新现有 `example/sglang_qwen3/`，一条命令从空资产完成稳态建库、独立成本采样、联合预测、固定结果和独立验证；全部产物仍进入一个时间相关 run 根。
- 检查共享定义/绑定加载、清理后重建、缺成本后继续及终态恢复。验证数据仍不挂入预测/拟合容器，不为了本专项新建故障注入或 test 工程。
- 完整审阅活动代码职责与关键生产/消费链，重点收紧 templates/production、Python 编排和新增 CPU 链；复用既有审查记录方式。删除旧重复阶段图、重复推断、无消费者观测/字段和被替代入口。
- 比较同口径代码规模、定义/绑定数量、原生启动次数、采集/后处理时间、默认保留量与临时峰值，解释必要新增和真实删除；不预先承诺总行数必然下降。
- 合同、示例和开发说明只陈述已实现行为；完成总结进入同一里程碑，专项结束后归档并同步链接。范围不足或指标未达标时保留未完成结论，不以流程返回 0 代替验收。

## 13. 代码职责与修改落点

| 现有位置 | 本专项应承担的修改 | 不应放入 |
| --- | --- | --- |
| C++ `contracts/` | 分层语义、CPU 工作、端口和状态等公共合同 | 原生函数名、框架 batch 类型 |

## 14. 采集、复杂度与停止纪律

- 实施批次开始前在同一执行记录写明：待回答问题、可复用事实、需要新增的证据、数值化的原生/后处理/存储预算、预期覆盖与结束条件。具体额度依据当时实验和已有账本确定，恢复、失败、换请求不清零；已授权自主采集，无须逐次确认。
- P0 以只读分析为主；P1 先验证协议；P2/P3 优先重处理现有事实；P4 固定结构；P5/P6 才取得 CPU/联合成本数据。不能为了省一次设计核对而完整重跑全部 serving。
- 原生生命周期、启动和预热成本与有效样本量分别报告；尽量在单次常驻运行中取得多个点。结构/成本/验证保持独立用途，复用资产不破坏独立性。
- 同一机制连续缺口且没有新增有效证据时，返回最早不成立的合同或参数关系，停止追加局部 wrapper/映射/拒绝条件。真实新分支先解释条件与收益，再决定是否纳入范围。
- 按现有约束进行周期整体审查；每阶段进入下一步前检查职责、状态所有权、代码分段、无用链路和定义/规则/样本规模。检查结果合并记录，不另建治理平台。
- 构建与仿真在 Docker 内进行，C++23、现代面向类风格；C++/Python 逻辑组留空行并给必要注释，不改 `.clang-format`，不维护兼容版本，不创建独立 test 工程，不写硬编码拟合。
