## 1. 目标、范围与边界

目标是把当前“能跑通”的有限主线整理成用户能操作、维护者能解释和修改的工程流程。本次交付四项结果：

1. **输出收敛：** 一次运行只有一个以开始时间命名的目录；每类文件有明确消费者、保留理由和清理条件，最终结果有固定入口。
2. **一键示例：** 在 `example/` 提供经过真实验收的薄脚本，从空运行资产完成建库、性能采样、预测、独立对照和摘要，无人工拼命令或搬文件。
3. **全量审查整改：** 覆盖全部活动自有代码及构建/安装资源，核对职责、依赖、状态、接口、正确性和恢复；确认问题依次解决。
4. **实质瘦身与总结：** 删除无消费者功能、重复状态/转换/报告和过度包装，交付实际流程、扩展位置、保留策略、规模对比及限制。

**精度分析延后，确认的结构问题在本专项解决。** 结构问题包括错误的工作量/依赖/端口、重复计费、状态双重推进、资产角色混用、错误恢复及悬空引用。单纯的耗时偏差、拟合方法升级和观察扰动归因不进入本次实现；若审查确认它们包含结构错误，只修已确认部分，并说明结果为何改变。

不扩展 KT 预测、跨模型/TP/backend 泛化、原生控制器或 CPU 微观模型。已有 KT 采集等仍有真实消费者的功能保留。不以删行比例、文件数量、目录搬迁或拆类数量代表完成，不压缩空行/注释，不新增兼容版本、通用任务/缓存平台或独立 test 工程。C++23、Docker 内构建运行、类职责和必要注释等约束持续有效，`.clang-format` 不改。

## 4. B：完整审查与产物盘点

### 4.1 审查范围和方式

审阅 `src/markov`、`src/collection` 全部活动源码与头文件，包含原生观察库、patch 和安装脚本；覆盖根 CMake、pyproject、`scripts`、`example`、`docker`、`configs` 及实际文档入口。`third_party`、`reference` 按需只读核对；`deprecated` 只检查活动依赖，不重构历史项目。保留工作区已有改动，不以重置或只看 diff 代替审阅。

先从公开入口追出实际调用、数据交接及状态所有者，再逐文件阅读直接生产者/消费者。搜索、依赖和代码规模辅助定位，编译通过不能证明未读模块已审完。同职责文件可归组写结论，但每个文件须能定位；“前序读过”“已搜索目录”不算本次覆盖。

| 范围 | 必查职责与风险 |
| --- | --- |
| CLI、Shell、示例 | 只负责参数和呈现；重复默认值、JSON 业务拼装、私有入口及隐藏旧路径 |
| Python workflow | 容器、任务、预算、锁、发布和恢复；父/子状态、跨类私有调用和共享字典的唯一写入者 |
| C++ workflow / contracts | 公共输入、适配装配、需求与结果；框架分支泄漏、重复支持判断、两侧重复业务状态 |
| instrumentation / 框架与模型适配 | block—wrapper—提取对应；原生符号、模型结构和采样配方在适配端，不自建原生 KV/组批状态 |
| runtime / native / 环境 | profiler、时钟、设备任务、队列与传输关联；不反向解释框架业务，patch、ABI 和安装消费者匹配 |
| graph / production | 来源身份、节点归属、依赖与端口；时间相邻不能替代因果，无消费者事实不默认转存 |

| performance | 需求、覆盖、样本、拟合和查询共用工作特征；缺数据与合同不足分开，费用不重叠，查询不启动采集 |

| 构建、配置和风格 | target/include/import 方向、失效选项和安装资源；空壳类、转发、防御性包装、命名、逻辑空行与重要注释 |

### 4.2 两张清单与整改次序

沿用[审查记录](2026-10-16_code_cleanup_review.md)，补齐两张清单，不新增治理平台：

- **代码覆盖/发现：** 文件或职责组、直接消费者、已读结论、问题性质与影响、最小整改、验证方式和状态。无问题的模块也记录检查范围；确认缺陷、维护债务、待验证风险分开。
- **产物清单：** 生产者、消费者、唯一信息、正式路径、发布完成标志、保留/清理条件、重建方式与成本。涵盖原始 trace/CSV/DB、语义记录、事实、来源图、实例、编译模板、样本、成本、目录、结果、收据和日志。

整改优先级：① 正确性和数据安全；② 职责、重复状态、默认输出和生命周期；③ 可读性与局部冗余。精度研究与范围外能力另记，不转成无限采集任务。没有消费者的输出优先停掉生产链；可共享则共享引用；诊断用途默认关闭；确有复现用途才保留。

第一工作批次只做底稿：完整文件清单、`explore → summary` 调用/状态图、所有产物的消费与保留表，复核审查记录 B10–B14 的交接风险与最新证据，再补齐其他层。此时不启动模型，不预定新类数量。B 退出时维护者应能沿任一默认文件找到生产者、消费者和清理条件，并知道全部未关闭问题及处理次序。

## 5. C：统一运行目录、输出内容与生命周期

### 5.1 最终目录合同

新运行在 `data/` 创建带 UTC 开始时间的根，例如 `20261016T100000.123456Z_sglang-qwen3-32b/`；`Z` 明确时区且符合原生 profiler 的字符限制。同刻冲突只增加必要后缀，恢复沿用原根。内部来源/样本/组合用稳定编号，用户名称保留为元数据，不直接作为路径片段。以下目录已在最终运行核对，按实际阶段创建：

```text
data/<开始时间>_sglang-qwen3-32b/
├── run.json                       # 状态、累计用量及引用入口
├── inputs/                        # 正式输入快照
├── captures/
│   ├── base/<来源>/                # manifest、必要来源事实
│   ├── performance/<采样>/        # manifest、独立样本
│   └── validation/<组合>/         # 独立端口观察
├── assets/
│   ├── templates/<来源>/          # 编译模板
│   ├── costs/<样本来源>/           # 实际非空候选
│   └── catalogs/                  # 有消费者的共享工作对象目录
├── results/
│   ├── prediction.json            # 最新合并预测
│   ├── comparison.json            # 有实际验证时才生成
│   ├── summary.md                 # 用户首先阅读
│   └── sampling-plan.json         # 仅未完成且需说明采样需求时保留
├── logs/                          # 每个任务一份必要日志
├── work/                          # 未确认交接或失败的必要中间物
└── diagnostics/                   # 显式启用的详细图与诊断
```

按实际阶段创建目录，不预建空壳。主任务及采集/拟合/验证子任务共用根目录，避免无业务含义的 `runs/run-*` 嵌套。模型权重、第三方源码、镜像和共享构建是显式外部依赖，不复制到运行目录；设备锁继续使用既有唯一协调设施。导入外部资产须明确引用，不扫描其他运行找“最新”文件。

### 5.2 每类文件留下什么

| 类别 | 默认保留与消费者 | 清理或重建条件 |
| --- | --- | --- |
| 输入与任务状态 | 一份正式输入；状态只存必要阶段、身份、用量及引用 | 子任务只存独有参数，不复制整份可变状态 |
| 原始导出 | 处理中保留；尚有独立消费者或不可替代事实的部分保留 | 规范化完成并确认交接后释放本任务拥有的可替代导出；原始重解释需要显式诊断保留 |
| 规范化事实 / 性能样本 | 每来源一份压缩正式数据，供重提取/拟合 | 保留当前合同下的重建依据；不承诺恢复未来未采到的字段 |
| 来源图 / 源实例 JSON | 默认是提取、编译中间物 | 成功发布编译资产并确认后清理；从事实重建，诊断模式可保留 |
| 编译模板 / 成本候选 | 每来源一份模板、每实际非空类别一份候选，供预测 | 多组合共享；空候选不落盘，缺口由正式结果表达 |
| 工作对象目录 | 同一来源和工作合同共享，供需求/成本与追溯 | 真正不同的合同不强行去重；不依赖人工硬链接 |
| 轮次结果 / 收据 | 未确认交接时保留 | 合并发布并保存未重算组合引用后清理旧全量结果和已消费收据 |
| 日志 / 失败资料 | 每任务一份日志和必要失败定位信息 | 不在 JSON 与文件中重复存整份日志，未交接失败数据不提前删除 |
| 完整图 / 详细报告 | 默认关闭；诊断时引用共享来源与实例变化 | 不逐工作复制不变定义；开关只影响诊断输出，不改变业务结果 |
| 独立验证 / 对照 | 独立角色与引用，仅评价使用 | 不进入模板、候选或预测容器，不反向修正结果 |

最终结果的内容也要精简：`prediction.json` 保存各组合的状态、已有指标、scope、缺口与资产引用；`comparison.json` 保存对齐依据、差值和不可比较原因；`summary.md` 保存输入概况、组合结果、累计用量、关键限制、结果及恢复入口。大图、逐条样本和重复来源不默认展开。失败/缺数据也生成可读摘要，无验证不伪造成功对照，未知值不填零。

增长约束比固定文件数更重要：来源事实/模板不随组合数复制，样本不随预测轮数复制；整次运行只保留一份最新合并结果和有效对照；终态恢复不增加采集、拟合、预测产物或重复日志。独立 rank、不同特征与失败证据不能为缩小体积被误删。

### 5.3 所有权、发布与恢复

| 责任 | 所有者与交接 |
| --- | --- |
| 运行根、输入、子任务登记、累计预算 | 现有 Python workflow / RunDirectory；CLI 和示例只传参数 |
| 原生进程、设备租约、实际用量 | NativeAttempt / CollectionWorkflow；父任务消费确认终态，不从日志猜测退出 |
| 观测与规范化资产 | 对应采集适配/normalizer 发布 manifest；消费者只读显式引用 |
| 编译、拟合与预测内容 | C++ 正式入口；Python 负责持久任务与合并发布，不复制算法 |
| 对照和摘要 | 正式 workflow 只读固定预测及独立验证，不再维护业务状态 |

这是责任分配，不要求再造一批类。`run.json`、manifest、处理收据分别表达任务、资产和交接，避免相互复制状态。生产者直接写正式职责目录，临时物写 `work/`，不由示例结束后 `mv/rsync` 整理。

改造顺序：统一路径解释和 Docker 挂载 → 核对 CBOR/manifest 内嵌身份 → 同步生产者/消费者 → 发布完整资产及权威引用 → 消费者确认 → 清理本任务无活动写入者的中间物。涉及输入修订时，结果失效与待发布输入须有可恢复的同一交接，不能让新输入对应旧成功结果。

必须保持未重算组合的有效引用；宿主中断不等于原生容器退出，恢复不得重复启动或计费。完成后的 `status/resume` 不能因为工作文件已清理而重做预测或拟合。目录内部引用完整是必达；整棵目录跨机器迁移仅在实际验证后声明，不为此增加迁移平台或兼容格式。

### 5.4 旧数据如何处理

文档阶段未清理数据。恢复实施时先保留基线和必要开发证据；23:04 核对发现 data 已被外部清空，因此旧数据不能重放，已撤下失效链接。其原规模与结果只作历史记录，不当作当前可复核基线。已从空资产取得最终运行证据，并按真实引用删除无消费者的开发副本；开发证据注明退役状态，保留小型记录和必要输入，不复制全部旧数据“备份”后宣称瘦身。

## 7. E：完整边界整改与实质瘦身

按 B 的问题顺序处理未被 C/D 解决的部分，保留完整审查覆盖。主要原则是删除重复职责和无消费者链，再决定是否拆类，不预先规定类数或新目录数。

| 贯穿链条 | 整改落点与结束标准 |
| --- | --- |
| block → wrapper → 事实 → 模板 | 共同语义可追溯；框架符号、模型结构和 runtime 观察归各自适配；删除旧探针时同步下游字段 |
| 模板 → 变换 → 控制 → 执行 | 来源共享，实例只携带变化；规则前提唯一，控制器不解释来源，状态/时钟不重复维护 |
| 需求 → 样本 → 拟合 → 查询 | 对象和单位一致，缺口分类准确，验证隔离，查询不补采；不引入新模型或人工补价 |

| 方法和类内部 | 同一抽象层次，按逻辑留空行，注释说明关键不变量；合并无行为包装，保留真正必要的外部输入和资源检查 |

重点复核：Python/C++ 不各持一份业务状态；runtime 不识别框架业务；核心没有按配置标签/样本身份的特例；CPU 不计时仍保留因果；逐批累计图重建先查无效重复和报告开销，仅有实际必要性才改算法。跨时钟若影响身份/选边/顺序，按结构问题解决；只涉及测量精度的未知限制留待后续，不重启 CPU 微观模型。

每批采用“审查结论 → 贯穿修改 → 必要验证 → 关闭记录”。删除说明旧消费者为何不再需要，新增说明替代了什么重复责任或补齐什么当前能力；无关的未变模块不反复跑验证。若继续出现相同局部补丁，先回到所有者和合同整理，不叠加包装或硬编码拒绝清单。

| --- | --- |
