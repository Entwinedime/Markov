## 1. 目标与执行顺序

最终输入为一个固定模型、配置集合、request workload 集合；系统选择代表配置和短采集请求，用户不指定 base。主线为 SGLang + Qwen3-32B，KT 和原生控制器后续扩展。

统一流程与插桩 → 有预算地建立参数化子图模板 → 目标配置与 request → 轻量控制器组织模板 → 有限变换、依赖拼接 → 给定节点耗时动态展开 → 结构验收 → 节点成本模型 → 配置 × workload 探索。

五类顶层 block 表达 serving 职责，Prefill/Decode 内部按模型结构划分。语义区域与性能单元粒度独立。换框架的业务差异应集中在模板获取与生产端，共同控制和执行消费统一合同；该边界尚未完整实现。详细合同与约束分别以设计文档、[工程约束](../redesign/engineering_constraints.md)为准，本计划不另抄一套。

plan/predict的candidate_recipe是生产端给出的机制候选，可以通过显式profile --representative执行，但尚不是完成覆盖判断的自动建库方案。P取真实worker的effective_server_args.page_size；prompt_page_offsets表示P加偏移，不能从探索request取长度或硬填本机128。当前双成员候选要求池容量至少2、P≥4、Prefill预算至少2P−1，并预留4P token容量容纳两个各跨一页的请求；4P是本配方的充足余量，不是原生最小容量公式。容量1明确报告配方未定义。

| 顺序 | 两请求输入长度 / 输出数 | 预期机制及理由 |
| --- | --- | --- |
| 1 | P−2、P−1 / 1、1 | 两成员准入与last_loc、冷Prefill立即完成、逐请求直接释放、共享输出 |
| 2 | P−1、P / 4、2 | 首次Decode中第二成员跨页并结束；后续第一成员跨页、继续、结束，覆盖部分过滤、单成员Decode、零/非零新增页、空/单成员释放组 |
| 3 | P−2、P−1 / 2、2 | 双成员Decode同时结束的拼接释放；入口同时核对上一组完成后的清理 |

三组共6请求、12输出token，与目标workload数量或长度无关。每组一起提交，等前组完成才提交下一组，不使用猜测的毫秒间隔；批次形成本身仍以原生记录为准。profile --representative已使用批量input_ids、逐请求sampling_params和真实返回屏障；普通workload采集保持原到达序列。页大小与配方预算在Engine初始化后从实际配置解析，批量返回时刻不作为逐请求完成时刻或节点成本。s3-representative-execution一次运行取得P=128下7个完整批次、两rank共58份实例（含2份Idle Schedule），仍须逐机制核对资格。组间等待客户端返回不保证原生running batch已经清理，后组过滤可能包含上一组已完成成员。

执行前先对照已有同配置资产删除已覆盖观测需求，再落实真实页大小、配置预算及公共采集生命周期。当前s3-representative-execution/mechanism_coverage.json已核对7个完整批次，两个rank均有分配页/无新增页、空/单/多成员释放及请求级绑定。此为事实与区域资格清点，不是完整建库证书；无需为这些已存在分支重采。各预期机制必须在全部rank上实际出现且模板参数/端口合格，否则停止并报告，不能换workload自动重试。当前候选明确未覆盖running合批、周期性非最终输出、准入预算停止、内存压力和域外后端变体；这些项需结合既有规则/事实确定复用或缺口，不能凭三组候选标记完整建库。未完成这项覆盖判定前，不把predict的缺模板转成自动profile。

计划保存任务和当前状态；设计保存合同；执行记录保存里程碑和证据索引；development 保存可运行命令。相同规则只维护一个正文来源，其他位置链接引用。审查时一并删除重复进展和失效的“下一步”，保留真实限制、决策理由及证据路径。
