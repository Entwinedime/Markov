# 架构与代码职责

Markov 从一个 base 配置的真实执行获得源 DAG，按 target 配置生成目标工作与依赖，再估计成本并执行，输出正式 HTTP 窗口耗时。它不是把每个 target 重新采集一遍，也不是用 target 的耗时反推参数。

```text
模型、平台、base 配置、workload、target 集合
    │
    ├─ base 采集 → profile_manifest → 原始 DAG ───────────┐
    │                                                  │
    └─ 独立性能采集 → 性能数据库 → 离线成本包 ──────┐    │
                                                  ↓    ↓
                           目标工作与依赖规则 ↔ 成本绑定与同钟执行
                                                  │
                                             HTTP E2E 结果
                                                  │
                                  实验时另读真值、独立评分
```

两条输入主线职责独立，不表示同时占用设备。已有适用成本包时，预测不读取数据库或在线训练。完整 HTTP 保留 gap、未归属成本和 Prefill/Decode；部分仍沿用 base 的近似必须随结果说明。

## 三个阶段的交接

| 阶段 | 输入和职责 | 交付与边界 |
| --- | --- | --- |
| 原始 DAG | 只读所选 base manifest；合并通道、统一时钟、建立调用归属、资源与依赖 | 源图、原始观测、请求和窗口上下文；不读取 target 真值 |
| 目标工作与依赖 | target 配置、workload、源语义和框架规则决定操作、工作量、资源及条件分支 | `OperationWork` 与结构修改；不携带成本系数，不因缺成本删合法工作 |
| 成本绑定与执行 | 未变工作迁移源成本，变化工作查询独立模型，沿依赖和资源执行 | 耗时、来源、覆盖与缺口；成本提供者不生成操作或改变策略 |

时间条件不能提前全部决定。例如预取能否在期限前完成取决于本次实际执行时间。结构侧先提供条件与后续规则，执行器到达相应时刻再触发；两者使用同一个时钟，没有另一份理想目标图供事后修补。

`CostMigration` 记录源节点是否可以迁移。被替换区域先移除，剩余工作只有已证明不变才能沿用成本；变化或新增工作缺规则就报结构缺口，缺模型就报成本缺口，不能用整段 Prefill/Decode 倍率兜底。

## 代码从哪里读

下表记录实际位置，路径前缀分别为 `scripts/internal/markov_internal/` 与 `src/modeling/trace_graph/`。

| 层 | Python | C++ |
| --- | --- | --- |
| 公开装配 | 根脚本 `profile/model/run/build.sh`；`applications/` | `src/cli/` |
| 输入准备 | `preparation/base.py`、`preparation/calibration/`、`preparation/performance.py` | 读取规范化后的输入，不管理设备采集 |
| 统一预测 | `modeling/`、`modeling/execution/` | `src/cli/prediction_batch.cpp`、`src/cli/workflow.cpp` |
| 源解释 | `modeling/source_dag/` | `src/io/`、`src/frontend/`、`src/source_dag/`、`src/adapters/` |
| 图与结构 | 传递输入，不复制 C++ 规则 | `src/core/`、`src/structure/`、`src/modules/hicache/model/` |
| 成本 | `modeling/cost/` 管理独立测量、训练和包 | `src/cost/` 查询响应、I/O 服务及迁移 |
| 执行与报告 | 应用层汇总，`applications/accuracy/` 独立评分 | `src/modules/hicache/runtime/`、`src/simulation/`、`src/reporting/` |

当前老项目的声明仍主要在 `include/markov/trace_graph/`，实现位于 `src/`。这是实际布局，不是今后的目录规范；将同职责头源归并时须连同引用和构建一起改，文档整理不等于已迁移源码。

读取源构图时，从 manifest 输入、事件关联、窗口与源索引进入；读取目标预测时，从批次入口、结构规则、成本查询和执行器进入。具体框架字段只在适配层解释，不让后续各层重复判断原生名字。

### 一次改动应覆盖哪里

| 修改 | 主要责任链 |
| --- | --- |
| trace 字段、调用名或时钟 | 采集生产者 → manifest/适配读取 → 源语义消费者 |
| HiCache 合法执行分支 | 状态规则 → 工作/依赖生成 → 执行触发；新增工作再声明成本需求 |
| 成本公式或变量 | 测量定义 → Python 离线训练 → 成本包 → C++ 查询；不改策略 |
| 图存储或粒度 | 原始图/修改接口 → 目标生成 → 执行与报告；核对外部依赖及计费 |
| 实验报告 | 已完成的领域结果 → 报告/独立评分；不回写预测或触发采集 |

同一批次内，相同 manifest 与 CPU 校正的 targets 共用一次源准备。源事件、观测表、CPU 区间、只读索引及框架操作观测由会话持有；用于成本迁移的源图视图也只建立一次。各目标在 fork 后持有自己的图修改、执行状态和查询统计，源事件只有实际修改时才复制。不同源组顺序处理，目标并发由预算限制；跨批次尚不能复用源准备。

执行器为有效工作分配紧凑状态，回调、请求锚点和原始证据仍使用稳定图编号，通过统一映射衔接。结构修改优先在已证明的拓扑顺序上验证受影响边；无法证明安全时仍完整检查环路，诊断构建继续独立核对修改后的图。这不表示源 trace 已变成小型预测输入。

目标程序只合并同资源、无外部消费者和状态作用的串行CPU步骤；连续K/V拷贝保留首末提交及设备完成，成本与残余间隔沿用原计算。异步任务的提交、worker释放、设备完成和可观察中间结果仍分别执行。调用描述在程序内共享，展开后的来源映射允许多个原CPU步骤对应一个串行片段。

仿真器拥有唯一的已执行状态。私有程序步骤照常参与成本、依赖、资源队列和同刻事件排序，但只在声明的状态、资源和外部端点触发HiCache规则；直接追加的控制和计时节点默认触发规则。NodeScale保持完整展开并逐节点作用。诊断使用同一个执行器独立回放最终图，不能通过另一个时钟修补结果。

## 源图的事实与边界

源图保留原始时间与仿真时间，通道在合并及裁剪前用同次采集的时钟锚点统一。调用归属来自同线程包含关系和唯一提交关联，不按最近时间、kernel 名或窗口重叠猜测。

正式窗口由客户端 workload 报告定义。窗口前信息只初始化状态或解释跨界工作；HTTP 结束前已经开始的操作保留必要因果尾部，但不把随后新轮询全部加入，也不延长 HTTP 端点。源静态回放在私有副本上运行，先于 CPU 校正和 target 变换，不写回预测输入。

源图中已有明确同步依赖的调用仍使用历史 10 微秒服务近似，原阻塞区间另存。它不是独立测量，不可导出成训练样本或再扣除一次采集开销。设备时钟矛盾也不会因回放 E2E 接近就消失。

## 目标工作如何产生

HiCache 状态模型决定命中、驻留、分配、释放、读写及取消；工作程序记录张量子操作、前驱、资源和执行方式。runtime 将其绑定到成本与时钟。设备消费者等待设备完成，CPU 消费者等待主机返回，异步提交不能提前阻塞 CPU。

| 操作族 | 工作依据 | 主要支持边界 |
| --- | --- | --- |
| Attention 与页表 | 上下文、目标 token 数、页宽、真实布局 | 已识别的单请求、非投机路径；MLA、滑窗和调度改变不自动支持 |
| 投影、激活、归一化、旋转 | M/N/K、dtype、stride、融合方式及模型角色 | 当前非量化 Qwen3/Ascend 规则；同名函数不代表同一几何 |
| Embedding、logits 与采样 | 词表分片、索引、末 token 投影、收集及输出处理 | 已识别的单请求贪心路径；logprob、LoRA、自定义采样需新规则 |
| 输入与 allocator | buffer 几何、sequence/prefix、页状态、分配/释放分支 | 已声明后端 ABI；编译、首次准备、失败重试分别处理 |
| Prefill 接纳 | 未命中输入、生成预留、目标可用页与写入确认 | 串行非分块路径；部分新增 CPU 接纳使用独立粗粒度区间 |
| 通信 | 参与者、载荷、提交、完成与等待 | 普通 HCCL all-reduce 和末 token 单行 all-gather |

常规队列检查仍迁移源窗口内的检查机会，再按目标时刻计算可确认量。它不是完整调度器：DMA 完成后可能没有后续检查来发布，不能强制“设备完成即缓存可见”。D2H 提交、设备完成、host/storage 发布和引用释放分别表达。

未被规则接管但工作变化的节点不能直接迁移。特殊布局、模型、并行方式及框架版本变化，需要适配解释、结构规则和成本域分别成立；并非更换路径后自然支持任意部署。

## 粒度、状态与成本

判断细粒度是否必要，要看该时刻能否改变外部依赖、资源竞争或后续分支。保留 CPU 提交、worker 接收、设备完成、跨 rank 同步、逐批发布、容量变化、超时与取消。无外部消费者、无资源切换及状态改变的内部串行工作才有合并空间。

状态可以按页范围或批次更新，服务可以按张量或逻辑操作估计；不能把提交、设备服务与返回简单相加，因为它们可能重叠。父成本拆成子成本后不能再收费，实际传输量与最终可见缓存量也不可混为一谈。

NodeScale 默认关闭，作用于最终绑定的耗时，包含新生成节点，不修改回归系数或原始源图。历史静态成本回放按现行规则保留，是有限诊断能力，不恢复旧执行规则，也不代替完整目标结构验证。

## 三类报告的用途

| 实验报告 | 回答的问题 | 不能据此推出 |
| --- | --- | --- |
| 原始 DAG 静态回放 | 源依赖和原始成本能否重现所选窗口 | CPU 开销校正准确、目标分支正确 |
| 目标结构比较 | 语义操作、工作量和已匹配端点间可达关系是否相符 | 未匹配操作、全部 CPU/control 或资源依赖已证明 |
| 独立性能评分 | 预测 HTTP 与正常 target HTTP 相差多少 | 误差小即结构完整、任意配置都能外推 |

应用默认只输出预测和限制，实验才启用额外报告并独立读取真值。结构比较使用稀疏依赖与可达关系，不要求原始边逐条相同；数量一致也不能证明语义一致。目标 trace 自身仍可能缺跨 rank CPU 关系，差异需要按实际路径解释。
