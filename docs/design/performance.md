# 性能边界、采样与成本模型

性能层回答**一项明确工作在给定特征与运行条件下需要多少服务时间**。执行层依据服务时间、资源和依赖计算开始/完成，控制器消费完成事件；性能层不改变图或组批策略。

本文件约定后续性能能力的边界。执行结构先使用给定耗时完成动态变换、展开及独立结构验收，再接入实测采样、成本需求和模型。给定值、来源 profiler 时长和请求运行成功都不代表性能层已经建立。

## 与执行结构的交接

正式耗时消费接口为 [NodeDurations](../../src/markov/execution/durations.hpp)：输入目标图及已有执行节点，返回整数 ns。`GivenDurations` 按执行种类读取显式假设，实际遇到的种类缺值即失败，不回退来源时长。假设改变后从初态重算，因为时延会改变后续组批。

未来实测提供者复用该边界；工作定义、参数和物理实现来自已生成的目标结构，不由性能层再推导一份模型语义。真实成本缺口需要表达覆盖状态，不能填零、偷偷使用 given 或换成更粗的父包络。

语义区域与性能单元分别定义。一个区域可以包含多项 CPU、设备和搬运工作；重复模型层共享同一工作模型，调用次数独立。父区域只计自身服务，不能重复计入子区域或设备成本。模型规模、TP、dtype、backend 和运行环境的变化分别审查成本适用性，不因结构可变换就授予成本外推资格。

## 工作特征与计费边界

| 工作 | 需要保留 | 独立测量对象 |
| --- | --- | --- |
| CPU 自身服务 | 稳定起止切口、线程/角色、阶段、实际成员及工作量 | 相同切口的本线程 CPU 服务 |
| 设备计算 | 实际操作/实现、shape、dtype、布局及影响算法的操作数 | 对应物理工作，不使用整个模型包络 |
| 同步传输 | 方向、字节、两端条件及明确 driver 边界 | 排除之前依赖等待的传输服务 |
| 异步 DMA | 实际设备工作、字节及资源 | 设备服务，CPU 发起单独处理 |
| 通信 | 操作、数据量、参与者、拓扑及 transport | 实际通信服务；与内部物理任务分解互斥 |
| 提交和运行时命令 | 对应调用、参数及资源 | 主机自身工作，不包含等待期间墙钟 |

attention 的 query/context、heads 和 cache 布局是特征，整段 Decode 长度不是一个成本类型。相同 shape 也可能有不同索引、页布局、分支或内容相关工作；缺少必要操作数时保留合同缺口，不能按 kernel 名加补偿分支。

等待、事件和逻辑标记首先表达因果，真实服务与等待分别处理。执行器从前驱和资源就绪计算等待，不迁移来源的 CPU gap，也不把 `run_batch` 墙钟减设备总时间当成 CPU 标签。

## CPU 的两个问题

**路径如何变化。** 按提交、入队、worker、等待、结果处理和输出端口保留稳定作用；成员循环和有限分支由模板组合表达。普通函数调用树和 observer 的碎片不自动变成新成本类别，不逐个原生 Python 函数建模。

**服务如何测量。** 性能观察使用结构已经确定的同名切口，取得自身 CPU 服务和必要工作量。父子嵌套只计自身部分，等待归依赖，复制另有边界。线程时钟读取及回调开销需独立校准并保留原始记录；低于分辨率或受首次编译影响的点不能成为有效标签。

校准不能消除全部 profiler、缓存、线程调度和 SDK 扰动。需要真正未安装对应观察器的对照，停写记录而仍执行回调不等于无插桩。若 SDK 把就绪等待与服务封装在不可分入口中，应明确局部近似和资格，不能用固定 gap、端到端残差或手调倍率掩盖。

## 采样的统一要求

1. **对象一致。** 性能与语义采集共享原生模型分片、backend 和底层执行，按真实工作与完整特征关联；同名、同 shape 或入口相同都不足以证明一致。
2. **适配简单。** 原生框架维护请求、KV、槽位和 worker；不为调用 ModelRunner 或 batch 入口复制状态机，也不假定每个框架都有 `bench_one_batch`。
3. **特征可构造。** 从目标需要的工作范围构造有限短请求或公共原语配方，再核对实际命中的成员、shape、context、实现和角色；发出请求不等于命中。
4. **开销有界。** 同一常驻原生会话运行多个点及重复观测，合并相同配方；初始化、预热、采样、后处理和保留量分别计账。相同配方没有新增证据时停止，不反复完整 serving 补点。

语义观察和性能观察分别控制生命周期，性能采样不要求携带重语义 profiler。两者共享必要的工作绑定和定位，不能各维护一套原生入口映射。辅助张量、传输替代和观察器工作不成为业务成本。

统一预热建立已加载、相关路径准备完成、逻辑 KV 清空的起点，保留明确允许的编译/分配缓存。新路径的首用开销仍须识别；不通过跑完整目标序列提前获取调度答案。

## 单卡 TP 与运行条件

单卡按原生角色执行目标 TP 的本地分片；请求长度不除以 TP，层、head、线性轴和通信接口由适配器解释。性能采样与结构来源必须使用相同分片底层，本地实测只授予实际发生的本地工作资格。

所有实际需求角色都必须能通过采样适配器到达，包括 TP4/TP8 的 rank 2 及以上。结构角色相符不自动证明服务时间相同；跨 rank 共享成本需要独立依据，不能复制普通角色样本或删除角色特征来掩盖缺口。

真实多 rank 通信、协调、争用和后台进度不能由单卡替代测得。逻辑 collective 的连接保持，成本需要真实通信数据；原生主机、worker、事件和布局工作与 transport 分开，不能叠加整体包络与内部任务。

测量记录 CPU、设备及 runtime 条件。卡号和模型路径用于定位，不证明环境等价；缺失条件保持未知。跨硬件、角色或后端共享必须有依据，dummy 数据不授予数据相关分支的泛化能力。

## 需求、模型与独立评价

完整性能流程应由目标工作自动产生需求，归并重复特征，查询已有候选，再把缺少的数据交给有限采样配方；不能依赖开发者逐节点查看 trace 补表。需求和实际查询使用一份工作合同，不从人读摘要反推机器需求。

动态调度下尚未展开的路径保持未确定，不能声称模板库已列出全部精确采样点。新模型发布后从初态重算；预算、已尝试配方和停止条件贯穿整个任务，不能形成无界“运行—发现缺口—补采”循环。

先建立有独立标签的简单基线，再按数据密度和误差来源选择插值、回归或其他模型，不预设随机森林或逐特征查表一定合适。模型参数来自数据与算法；禁止按 workload 标签、目标误差或手调阈值拟合。可查询、样本覆盖和精度通过分别报告。

结构来源、单元性能样本和独立目标验证分开。拟合/留出按运行或请求组隔离，同次运行的重复层不算独立样本。固定规则和模型后核对局部工作、CPU/设备重叠、关键端口及请求指标；整体时间接近不能代替边界正确。

评价按统一起点、同一请求及可关联时钟对齐真实输出，ResultProcessed 与 RequestOutput 分别核对。缺失端口和零分母不造比例；已用于修正规则或模型的目标转为开发数据。真实成本、独立证据及适用范围齐全后，才评价性能精度。

后续性能验收目标为独立留出上的 MAPE < 6%；具体指标、统计粒度和排除项须在该阶段启动时固定。此目标不作为当前给定耗时执行结构的验收结论。
