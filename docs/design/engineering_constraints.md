# 工程与文档维护约束

本文件约束自有代码、构建、配置及文档。用户最新明确指令优先；规则服务于简洁、有序、可维护的实现，不据此新增检查平台或审批流程。本文是静态规范，不记录实施进度。

## 代码表达与规模

- 主流程自上而下表达业务步骤，一个方法保持相近抽象层次。优先显式变量、普通循环、提前返回和简单分支，减少隐式状态与跨层跳转。
- C++ / Python 在同一 block 内按逻辑成组，不同步骤适当留空行；身份、依赖、单位、所有权、计费和生命周期等重要位置写简短注释。独立注释上方保留一行空行，与上方代码分开。不要机械每行空一行，也不把整段逻辑挤在一起。
- 命名表达业务含义，时间、字节、页等写清单位。不保留注释掉的实现、无归属 TODO 或宽泛的业务 utils 集合。
- 只为真实职责或复用提取方法、类和目录，不为几行代码增加转发层。规模来自整条冗余职责链的删除，不用拆文件、删必要注释、压行或迁出统计范围凑目标。
- 同一事实只由一个所有者维护。已有类型和结果直接交接，删除无业务作用的重复解析、规范化、转换、拷贝、序列化、读写、图遍历与进程启动；先修所有权，不急于添加缓存和管理层。
- 区分给人看的报告、流程消费的数据和可选验证明细。精简报告不能兼任完整机器交接；仅供验证的信息在生产端按开关记录，不能先完整生成再裁剪，也不能通过删减必需数据或压缩排版冒充精简。
- 新功能、字段、分支、依赖与抽象必须有当前消费者。不预建插件中心、万能规则语言、多套后端或未来占位功能，不用代码量换质量。
- 发现特例持续增长、相同规则多处修改或跨层判断时，立即回查职责，允许整文件或多文件删除重写，完整移除旧链路。

## 类、组合与特化

核心以类组织实际职责，状态与操作有明确归属；简单值合同用 struct。面向类不等于每个字段加 getter/setter，也不等于每个 block 一个子类。

| 差异 | 选择 |
| --- | --- |
| 参数值、绑定位置不同 | 值对象和参数，公共算法一份 |
| 不同部件协作 | 对象组合，分别持有自身状态 |
| 同职责的实际运行时替换，或固定流程中的少量差异 | 清晰接口或浅层继承，只替换差异步骤 |
| 同算法确实服务多个编译期类型 | 必要的 C++ 模板，类型要求明确 |
| 少量类型相关操作不同 | 普通重载或局部特化，不复制整个流程 |

不以闭包链、函数组合或回调管道承载业务生命周期，不将状态藏在全局变量或 lambda 捕获中。局部比较器、短标准算法 lambda 及无状态辅助函数可以使用。避免同时用虚分派、模板分派和条件分支表达同一差异。

语义子图模板是业务资产，C++ 模板是语言机制，两者没有一一对应要求。参数差异不能生成逐长度、逐 batch 或逐来源的类和特化。

## 抽象与目录边界

目录和类应对应原生观察、来源解释、子图生产、模板变换、控制决策、成本查询、事件执行及外围装配。高层表达协作，底层解释具体结构；不能只搬目录而保留跨层耦合。

- C++ 头文件和源文件按职责放在同一目录，例如 `src/markov/templates/template.hpp` 与 `src/markov/templates/template.cpp`；不再维护平行的 include/src 目录树。采集侧自有 C++ 代码同样遵循同目录规则。
- C++ 业务代码以 `src` 为 include 根，使用 `markov/<职责>/<文件>.hpp`；不保留旧路径转发头文件。普通实现放在 `.cpp`，头文件只保留必要声明和模板定义，不因同目录改成全部 header-only。实际交付的文件进入正式 CMake target，不预建空目录或占位类。
- 依赖向内为 `workflow → adapters → core`；core 不经直接或传递 include 取得具体框架配置或 workflow Project。
- 框架、模型、并行和环境差异留在相应 adapters。框架可组合 runtime，runtime 不反向依赖框架；controller/execution/performance 不按框架名、原生函数或 kernel 名增加业务分支。
- Python 分为 workflow、instrumentation、artifacts、adapters。公共 wrapper 与产物合同不导入具体框架或 runtime，能力通过必要接口传入。
- 环境补丁、依赖固定和原生观察资源随适配器维护；Dockerfile 负责选择组合、复制与直接调用，不增加无行为安装转发层。官方 third_party 工作树保持上游内容。
- 文件移动同步 include/import、子进程模块路径、源码根定位、CMake、Docker COPY、调用方与说明；跨语言合同同步生产者和消费者。

共享核心维护控制和资源的唯一状态，模板声明读写与端口，不注入框架私有状态机。新公共能力确有必要时修改共同合同及实现，不能把特化回调藏成第二套调度器。

## C++23 与 Python

- C++23、CMake≥3.20，要求标准可用并关闭编译器扩展。头文件 `#pragma once`，直接包含所用声明，不依赖偶然传递 include，不在头文件使用 `using namespace`。
- 类型 PascalCase；方法、函数、变量 snake_case；私有成员以下划线结尾。4 空格、LF，沿用仓库格式；**不修改 `.clang-format`**，不开展无关全仓更名或排版。
- 优先值语义、标准容器和 `unique_ptr`；仅真实共享所有权使用 `shared_ptr`。RAII 管理资源，非拥有指针/引用/span/string_view 必须有清楚生命周期。
- 默认使用编译器生成的特殊成员；普通值对象不手写析构或复制。关注扩容、异步动作和视图失效，不以裸 new/delete 管理业务资源。
- `enum class` 表达有限类别，`optional` 表达真正可缺失值，`variant/expected` 用于明确合同，不层层包裹简单数据。
- 单位、符号和范围在边界转换，不借无符号下溢表达缺失。auto 用于含义清楚的表达式，不堆叠 ranges、模板元编程或宏掩盖主逻辑。
- `noexcept`、`nodiscard`、assert 等仅在实际合同需要时使用，不批量添加。Release 正确性不依赖 Debug 分支。
- Python 使用实际推理环境支持的语法，现有环境基线为 3.10；新特性须先确认环境，不为形式现代化升级整个推理栈。避免模块级业务状态及重复 JSON/路径工具。
- Shell 明确处理参数和真实资源生命周期，进程参数用数组，不拼接不可信 shell 文本。路径和设备通过输入/部署声明，不硬编码本机实验位置。

## 校验、错误与删除

外部配置、文件和适配输入在边界校验一次；内部依赖已建立类型与不变量。不得为理论可能的错误堆叠空值检查、存在性检查、重试、默认值和异常包装。

标准库能清楚报错时直接使用；仅为恢复、释放资源或增加必要位置上下文捕获异常，不吞错或原样多层重抛。成本缺失、不支持等可预期结果使用明确状态，不能转为零或空成功。

保留真实输入、安全、独立评价隔离、原子 DAG 改写及关键时间不变量需要的检查。优先用所有权消除非法状态，不新增一致性账本、内部版本握手、checksum/指纹或重复读回机制。

只维护当前合同，不保留 v1/v2、旧字段别名、自动识别旧格式或旧标准 fallback。需要历史事实时显式重建或一次性转换，不长期维护双格式。真实上游版本与部署信息可记录，不能作为内部版本兼容理由。

弃用功能按完整链路删除：实现与类型、调用方、CLI/配置、注册分发、构建依赖、产物、示例和说明。不能只隐藏入口或加 disabled，也不能在活动代码中依赖 deprecated。

## 建模与采集纪律

先说明机制、范围和有限变换，再取最小证据，固定资产验证动态结构，最后建模。结构问题不能通过扩大长度组合、增加样本或修改成本掩盖。

验证矩阵、案例构造、给定耗时组合、留出安排、批量调用及跨运行汇总放在 `example`，复用并收紧已有示例，不因验证增加任务平台或业务输入语法。`src` 不导入示例；正式 workflow 维护单个任务的启动、设备、预算、恢复和产物，核心及适配器只实现正式能力与有实际消费者的通用诊断。窗口判据和一次性检查不进入业务状态机，示例也不复制 shape/KV/依赖规则或原生生命周期。阶段审查分别记录业务与示例代码净增减，新增业务路径须说明正式消费者，重复流程合并或删除。

只处理统一流程及必要因果。是否细分取决于复用、变换、外部行为或测量需要；不以还原全部 CPU 函数、后台事件或所有 gap 为门槛。CPU 服务、等待、传输和父子计费分开，不叠加 run_batch 墙钟与设备成本。

禁止以手调系数、倍率、阈值、补偿表、workload/配置标签或目标残差凑结果；挪到配置也不允许。公式和真实原生分支须有依据，拟合参数来自独立数据与算法。给定耗时注明来源、单位和假设，不作为实测覆盖或精度证明。

性能采样须对应模板工作、适配简单、可经共同原生生命周期实现，并可构造有界特征范围。真实请求/KV 状态由框架管理；需求、覆盖、采样交接是产品环节，不能长期依靠人工逐节点补录。

采集前说明问题、可复用事实、新证据、累计运行/后处理/存储预算与结束条件。用户已授权后续额度自主安排，无须逐次确认；新增额度仍须有明确收益和记录，失败、换请求和恢复不清零。初始化/预热、有效观测、后处理、导出量、保留量及峰值分别说明。

固定资产独立验收期间不补模板、不改规则。证据用于修正后转为开发用途；预算停止不等于覆盖完成，同类缺口无新事实时返回合同和抽象，不继续堆 wrapper、拒绝分支或采集。

## 构建、必要验证与持续审查

C++ 核心的配置、构建、静态工具和仿真使用 modeling Docker；宿主负责编辑、Git 与容器调度。直接加载原生 SDK、受其 C++/系统 ABI 约束的采集桥，在对应推理 Docker 内按 C++23 模式单独构建；其原生依赖不进入核心构建或纯预测。纯预测仅挂载程序、输入和明确资产，不需要设备、网络或目标验证数据。模型、缓存、数据和构建产物不提交，也不擅自清理他人资源。

不新增或恢复独立 test 工程、CTest、test 脚本、fixture、mock 或改名的内部自测入口，除非用户明确要求。使用静态推导、正式构建和必要真实输入公开入口；独立评价及有用户用途的诊断仍属产品能力。没有新修改、失败或未决问题时不反复扩大验证。

每次修改联查调用方、生产者、消费者与状态所有权。默认每五个实质代码批次或阶段交接前做整体审查；同类补丁反复、框架分支跨层或结果与声明不一致时提前。沿现有记录人工掌握节奏，不为计数写工具。

整体审查重点是层次、风格、逻辑和收紧：哪些职责应合并、混合职责应拆开、专属规则应归位、无用链路应整段删除。跨文件检查相同规则和真实消费者，不能用格式通过、行数下降或构建成功替代内容审阅。报告确认缺陷、修改及证据，静态未验证的风险单列。

## 文档的三层职责

文档只分三层，不另建导航层、审查档案库或按会话复制的备份目录。

| 层 | 位置与职责 | 更新方式 |
| --- | --- | --- |
| 静态设计与约束 | `design/`：整体路线、公共合同、工程规范与稳定操作说明 | 仅设计、接口、约束或操作发生真实变化时有意修订；不随每轮工作追加 |
| 项目主工作流 | docs 根目录的一份主文档：从项目开始至今的精简里程碑、当前整体判断和优先级 | 发生重要进展、窗口关闭或全局取舍变化时更新 |
| 窗口计划与日志 | `windows/YYYY-MM-DD_purpose/` 下的 `plan.md` 与 `log.md` | 同一功能/重构/修改持续更新原 pair，结束后汇总并撤下 |

**跨层不引用。** 不写跨层 Markdown 链接，也不写“见主计划”“按某设计文件第几节”或路径形式的内容依赖。每份文档独立说明读者需要的结论。可以链接源码、配置和实际证据；同层确有必要时可引用，但不建立密集互链。

**不复制正文。** 静态文档定义规则；主工作流记录项目级结果；窗口维护自身范围、任务和实施事实。主工作流对活动窗口只保留一句状态及项目影响，不复制其阶段表、逐条待办或实验数值。必要上下文可用一两句自足概括，不抄另一层的完整合同。

**一处维护一个问题。** 静态主题按职责合并，字段细节有源码/示例时不再复制巨量清单。跨文件规则只留一处权威正文；主工作流合并旧主计划与里程碑功能，窗口不另写总结、review、evidence 等平行正文。

### 窗口计划和日志

计划开头写开始日期、状态和一句目标，正文只需：范围与非目标、阶段及交付、完成/停止条件、关键风险及必要资源。计划维护任务与阶段状态，日志维护实际行动和证据，两者不复制正文。计划任务区分待做、源码已改待验证、限定范围验证和完成；约定不勾选为实现任务，未知风险不自动扩大门槛。

日志按日期正序记录实际发生的工作，每条使用以下格式；同日多条按发生次序排列，不补造具体时刻或另加流水号：

```markdown
## YYYY-MM-DD — <阶段或事项>：<本批主题>

**范围：** 对应的阶段/问题及本批边界，必要时注明基线。

**改动：** 实际修改、审查发现或已作决定，以及必要原因。

**验证：** 方法、输入/覆盖范围、实际结果和证据位置；没有执行验证时明确说明。

**结论与限制：** 本批已证明的结果、未验证部分及影响后续工作的缺口。
```

- 四个字段各司其职，通常各一至三句；多项独立验证可以在“验证”下列短列表。证据写必要路径、关键命令或结果数值，不粘贴完整输出、巨量 JSON、环境清单或重复配置。
- 一条对应一个有意义的工作批次。同一问题的连续修改和验证合并记录；有独立决策、重要失败或阶段交接时另起条目。标题写具体事项，不使用“最新进展”等无区分度名称。
- 区分源码检查、编译、条件运行、真实原生观察及独立验收。记录历史结果时注明是复核已有证据；未运行写“未运行”，不能将静态判断或给定耗时结果写成运行/精度通过。
- 计划独占任务清单及阶段当前状态；日志保留当时做了什么、证明了什么，不在文件开头维护第二份滚动状态，不复制后续步骤或每日重复待办。“结论与限制”只保留本批产生或改变的事项。
- 影响范围、预算或结论的失败与取舍必须保留。整理时可合并同一批次的条目、压缩重复叙述，但不能覆盖历史失败，也不能把后来通过改写成早先已通过；纠正旧记录须说明纠正了什么。

详细运行数据保存在 data，临时验证材料明确标为临时位置；日志只保留复核入口、必要计数和口径。采集条目须注明本批会话/尝试数、实际覆盖及累计额度变化；源码或文档条目不填无关资源字段。无新工作不追加空条目，不为日志格式新增生成器、账本或自动检查平台。

活动窗口允许覆盖多个会话，purpose 用稳定职责命名，不按每次对话新建。原则上只保留当前活动窗口；确有独立并行任务才增加 pair。篇幅增长时先替换过时结论、合并重复，不挤成长段或无限附加“最新情况”。

### 关闭与取消

1. 核对实际结果，将窗口状态明确标为完成、提前结束或取消；未实现内容不得写成完成。
2. 在主工作流写一条自足总结：日期/目标、主要修改与取舍、实际验证范围、结论与遗留项。保留影响后续判断的失败及证据，不复制完整日志。
3. 未完成事项明确为继续的具体目标、范围外能力或待验证限制，不能随目录删除消失；需要继续执行时才建立有明确边界的新窗口。
4. 汇总后删除整个窗口目录，不再维护关闭的 plan/log，也不另建历史归档。静态合同不会因窗口关闭自动改写；确需改变设计时作为明确修订处理。

活动计划若仍有未完成范围，不能为了整理目录擅自关闭或取消。主工作流只留其概要，实施细节继续由该窗口维护。

### 文档检查与历史证据

完成整理后检查职责、跨层引用、链接/锚点、状态矛盾及失效描述。证据被删除时取消可点击入口，必要历史结论注明不可复核；不重建旧账本或伪造当前验证。尚未实现的命令只出现在窗口计划，不写入操作说明。

纯文档任务只检查文档，不触发构建、采集、数据清理或恢复。交付说明本轮真实修改和检查，不把旧工作区 diff 全算成本轮成果。

## Git 与交付

提交标题采用英文祈使语气的 `type(scope): summary`。type 为 feat、fix、refactor、perf、build、docs、style、chore；scope 对应实际职责。

一个提交表达一个可审阅目的，大量改动可按依赖、实现、文档等分层，但不要拆散紧密耦合的生产者与消费者。正文说明原因、行为、实际验证和未验证边界。构建产物、采集数据、凭据、本地环境和 deprecated 参考目录保持忽略；曾跟踪的本地参考文件从 Git 索引移除，不删除本地内容。推送开发分支，不直接更新主分支或强推历史。
