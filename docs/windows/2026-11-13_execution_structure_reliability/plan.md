# 执行结构可信性、职责重组与独立泛化计划

开始日期：2026-11-13。

目标：厘清并完善执行结构的事实来源、工作语义、完成边界及变换规则，系统整理全流程职责和交互，再冻结实现开展独立泛化调查，收齐结果后深入分析根因。本窗口的最终验证用于取得真实结论，不要求结果全绿，不在验证期间返修。

## 1. 整体流程与范围

本窗口始终围绕同一条产品流程推进：

    固定模型、配置集合、请求集合
        → 自动规划有限代表来源
        → 原生运行及语义、资源、任务观察
        → 解释事实并构建来源粗图
        → 切分、参数化、归一化为模板
        → 原生控制提交目标动作
        → 模板变换、连接与核心执行
        → 资源/完成反馈推动下一动作
        → 请求输出与精简结果

独立目标原生执行另行提供对照事实。原生控制拥有请求逻辑和组批决定；核心唯一管理资源、就绪、在途工作和模拟时间。图中的事件是边界，工作是边界之间的活动；API调用、设备任务、粗图片段和模板定义分别解释。

本轮保留单机SGLang/Ascend、Dense/条件MoE、TP/PP/EP及合法组合、PD、chunked prefill、mixed和一级prefix cache的范围，重点是既有能力的依据与可维护性。模型、dtype、并行拓扑、backend和页布局变化按实际实现域取得来源；同域请求、成员、容量等变化检验有限变换能力。声明支持域是验证前固定的范围，不能根据通过结果倒推。

性能模型、性能精度验收、真实权重自然路由、数值计算正确性、多机实现、轻量控制器、overlap/speculative及多级缓存搬运不在本轮。结构验证需要的服务/完成测量属于本轮；不因此提前建设通用成本模型。原生不支持的配置如实记录，不patch上游强行支持。

## 3. 洞悉与完善执行结构

### S0：建立可以解释整体的工作合同

沿入口、原生观察、来源解释、粗图、模板、控制、资源执行和评价逐条追踪生产者与消费者，盘清现有保留、删除和待完善的职责。

按工作生成规则归类，至少覆盖CPU自身工作、设备计算、数据搬运、通信、等待与纯边界，以及API派生但缺独立设备任务的操作。每类说明：承接什么工作、实际资源、输入输出及状态效果、开始/返回/完成/可见性的含义、必要依赖、费用责任、原始来源和不确定性。按类型收集必要信息，不为每个实例增加全量字段或一套管理对象。

区分直接测量、原生元数据/接口推导、合理封装和缺依据四种情况。缺口按共同生成机制和影响归纳，分开记录确认缺失、解释待核实、验证未覆盖及范围外能力；不把每个未知端点变成独立补丁任务。

交付一张全流程概览、工作类别与证据表、跨层输入输出及所有权表，写入本窗口实际运行根的results，不另建文档层。明确哪些缺口会改变工作、依赖、资源或控制；单纯SDK内部细节不自动成为阻断项。

### S1：核实原生操作及其图中解释

先从既有原始记录和固定原生/runtime实现查明语义，再决定是否需要新观察。重点核实小拷贝等API派生工作：调用、提交、实际执行、CPU返回和结果可见分别是什么；必要时取得内存类型、方向、字节数、实际队列及完成依据。不得仅凭Async名称、非零字节数或没有SDK task推定独立异步设备工作。

一并审查观察标记、真实任务、同步、后台提交、CPU服务和封闭PD服务的分类与边界。保留真实工作，避免观察器开销成为业务工作；等待、CPU服务和设备活动不能重复计费。框架解释业务作用，runtime解释执行机制，核心消费已经解释清楚的共同事实。

修改完整观察—关联—解释—发布链；可删除重写错误抽象及整段旧路径。若API没有独立设备任务但完成语义可证明，按实际合同表达，不强造kernel；若原始记录确实缺少必要事实，先声明要判别的具体假设，再做最小有界采集。

退出条件：每类工作有执行和完成依据；必要事实未解释的类别不取得对应资格。同步/异步判断及跨层交接有具名代表证据，未知信息没有被零成本或无依据的工作替代。

### S2：闭合完成条件、时钟与旁路

逐条追踪CPU返回、命令接受、设备完成、数据就绪、Work消费、通知可见、等待恢复和资源可释放的关系。明确哪些边界能由已有事实推导，哪些必须直接观察，哪些内部点可由封闭区域承接。

保留原始时间、单位、时钟域及校准依据；CPU顺序坐标、设备序位与真实时间分开。已存在的时间不得在解释、规约或投影中丢失。不同设备分别维护实际校准；同一设备各点须共享可行的校准解释，不能只检验互不关联的逐点窗口。

完善统一耗时/完成条件接口及实际消费者，必要时调整CPU—设备—原生控制的交接。旁路只提供经身份和因果核对的服务、完成和输入条件，不提供组批、分配、查询答案或目标图体。

整轮观测窗口只能表达真实未知，不能作为关键完成点已对齐的证明。对会影响控制、数据可读或资源复用的未知边界，取得更强事实或证明其影响已被明确封装；不能只留下宽窗口后继续宣称该范围通过。允许有依据的测量精度范围，不追求每条底层记录的无限精确时间。

退出条件：决定性输入及完成条件有完整解释，实际宿主快慢不驱动模拟；共同校准、时间缺测和结构作用的资格分别检查。本阶段不要求拟合成本模型。

### S3：完善粗图和模板生成机制

从真实事实检查粗化前后的工作承接、端口、数据/状态读写、资源共享、提交/完成和跨区间依赖。封闭内部细节须解释中间消费者、异步尾部及费用责任；无SDK记录或难以配对不能成为删除理由。

统一梳理framework封闭区域、runtime区间规约与核心投影的职责：专属语义在adapter，通用切分、事件映射及图不变量在核心。定义与调用绑定分开，父子工作计费一次，跨兄弟/调用/rank作用有明确所有者。

检查参数公式、guard、分支选择、重复次数、局部组合和角色共享的原生依据，保留别名、版本、实际写入者与独立资源。等价worker在观察前选代表，必要协议参与者保持完整。模板类别由实际实现和接口条件决定，不随长度、请求数或来源路径机械增长。

退出条件：粗图和模板的各类生成/变换规则可独立解释；来源还原、局部变换、归一化及角色复用分别取得有限开发见证。重复问题回到共同生成规则，不增加目标标签或逐长度分支。

### S4：完善连接、资源与原生控制交互

沿张量生产/消费、stream提交/等待、跨rank通信、PD载荷/metadata/准入、KV/字段/缓存引用和请求输出追踪完整闭环。区分逻辑预约、物理绑定、内容就绪与最终释放，资源只有一个实际所有者。

对齐两侧的预热协议、逻辑reset、请求/路由和初始资源状态；加载、编译和预热排除在目标窗口外。新路径首用是否侵入窗口须实际核实，不能通过先运行完整目标序列预先取得控制答案；workspace热状态与KV/缓存逻辑初态分别说明。

补足对外作用所需的调用内资源生效和访问依据，以及原生传输期间必要的请求/页/字段关联。某项内部绑定如不影响保留合同，须说明为何可封装，不机械采齐所有私有变量。通知的产生、传递、可见与消费分别维护。

核对原生控制提交动作、模板返回布局、核心执行、资源结果和唤醒的统一接口；请求/PP轮转/PD准入决定仍由原生执行。未触发的Event.query、长在途归还及设备故障按可达性处理：支持域需要的路径取得有限见证，范围外能力明确保留，不靠延长请求盲采。

退出条件：全链具名代表能从原始事实解释到输出；来源、内容、连接、资源和控制证据分开。旧原生启动失败不自动归因于核心，也不以改变上游框架取得成功。

## 4. 整体职责重组与冻结

### S5：全链路职责、接口和目录重组

基于S0–S4已经核清的事实，从用户任务到最终输出重新设计实际维护边界。允许跨目录合并、拆分、迁移或重写，不要求保持当前文件树；设计和实现一起完成，避免先造接口框架再长期保留过渡路径。

| 职责 | 交付保证 |
| --- | --- |
| 任务与部署装配 | 只组织输入、有限来源、容器、额度、恢复和发布；框架/runtime选择有明确接入位置 |
| 共同原生切口 | 观察和无设备控制共享实际ABI、参数及生命周期定义，特化有单一来源 |
| 观察与事实解释 | 观察器提供事实，framework解释业务，runtime解释执行；推导的适用条件与缺口不丢失 |
| 粗图与模板生产 | 核心执行通用投影、切分、共享与求值；adapter声明专属几何、条件和绑定 |
| 原生控制交互 | 请求逻辑归原生；协议转换不生成第二套调度策略或资源账 |
| 资源与事件执行 | 核心唯一维护物理资源、就绪、依赖和时间；从共同动作/图接口消费信息 |
| 结果与独立评价 | 正式结果来自真实执行点；案例和评价在example，来源检查不借预测补真值 |

重点检查Python/C++交接、当前SGLang/Ascend装配依赖、跨文件重复规则、大类和零碎转发。按实际替换需求提取接口或组合，不为尚无消费者的第二框架、多机平台或万能插件中心预建抽象。

退出条件：每项状态、规则、产物及发布动作有唯一所有者；高层表达协作，底层解释差异。移动与删除同步更新include/import、CMake、Python入口、Docker安装/COPY、示例和实际操作说明。

### S6：全项目整理、评价就绪与冻结

关联阅读全部自有业务代码、共享适配、原生桥、独立工具、构建/安装及公开示例。整链删除过渡实现、无消费者字段、兼容分支和重复数据处理，按真实职责合并或拆解文件。规模分别统计src和example，优先删无用职责，不压行、不删必要空行和注释。

整理公开一键流程和中间产物：机器交接完整、人读结果精简、验证明细显式生成；生产成功、失败前缀、恢复和清理分开。以消费者判断数据保留，不按目录名或日期删除。静态设计仅随真实接口变化有意修订，历史结果不改判。

独立检查须分别覆盖原始事实到解释、解释到粗图、模板内部、跨图连接和原生控制。验证器不能调用生产投影/模板求值器制造真值；共享原生ABI不免除独立取证。使用真实案例副本的有限反例确认缺工作、错shape/版本/伙伴、漏等待、提前读取/复用和矛盾时间能被识别，不新增test/mock工程。

只对实际改动做必要统一构建、正式入口和开发回归。旧案例用于检验整理兼容性，不再计为独立泛化；语义或观察改变后核实原始事实是否仍足够，不能直接沿用旧资格，也不默认全量重采。

冻结前必须完成：

- 工作语义与关键完成依据闭合，尚未知的内部细节有明确封装及不影响声明结论的依据；关键缺陷不能以partial标签直接带入。
- 来源检查与比较器的输入、判据、错误分类及必要反例就绪；明确真实测量、条件运行和未验证范围。
- 已有开发案例、留出模型/输入范围、机制责任、抽样规则、资源额度与停止规则分开固定。
- 核心、adapter、观察器、原生/依赖、镜像、模板规则、来源规划策略、评价器和结果分类完成阶段交付；实际程序和环境身份记录清楚。

冻结的是实现及方法，不是禁止新任务正常生产来源。S7每组来源库在目标留出前固定；S8/S9允许冻结策略按新用户输入自动取得新来源，发布后不可根据目标结果补采或替换。

## 5. 独立泛化调查：三批执行，全程不返修

### 独立性与输入规则

在冻结交付后，按预先规定的合法范围及抽样方法生成目标，立即固定输入；不按Markov是否成功筛选。新输入不得只是历史目标改名。保留边界点、区间内未见取值和机制组合，数量不是覆盖证明。

两条泛化责任分别统计：

1. 同域固定库：主/辅助来源先固定，未见目标只通过参数、有限规则和原生控制生成，不人工补库。
2. 跨域自动流程：核心/adapter/规划器固定，新模型、拓扑或页布局按正常产品流程取得来源。来源规划可以读取目标配置和请求，不能读取独立目标trace或比较结果补答案。

结构调查可继续注入本例必要的真实时间条件，明确输入了哪些条件及其测量资格。局部检查给定真实动作/参数时，动作选择不取得资格；完整闭环的组批和资源结果必须由实现产生。独立目标只供评价和明确声明的时间条件提取，目标图体、内部shape答案和依赖不进入来源或预测。

### 三批初始覆盖责任

初始安排72个目标责任，S7/S8/S9各24个；一个目标指一组模型、配置、请求输入的原生对照及正式预测/评价，来源作业和资格探针另计。S6按机制可达性细化具名矩阵；确需调整数量时须在看到留出结果前说明原因并保留原覆盖责任。

| 批次 | 初始分配 | 主要覆盖 |
| --- | --- | --- |
| S7 固定库，24项 | 长度/页边界6、成员/并发6、容量/复用6、到达/输出差异6 | Dense及条件MoE；同域变化，包含不等长、部分完成、跨页、排队、突发和空闲后到达 |
| S8 自动新来源，24项 | 新Dense模型8、新MoE模型8、既有模型新实现域8 | 新模型几何、BF16/FP16代表、TP1/2/4/8、合法PP/EP及PD角色、未见合法页布局 |
| S9 组合与持续运行，24项 | TP×PP/角色复用6、EP×PP/PD6、调度/cache交互6、持续与资源压力6 | 合法单机组合、异构双池、chunk/mixed/prefix、淘汰及长短请求持续运行 |

两个新模型不参与S0–S6开发，最终身份按固定候选选择规则确定并记录版本/配置。优先公开常用、当前原生栈能运行、落在声明机制范围内的模型；只凭原生资格筛选，不凭Markov结果换模型。候选及备用规则在冻结前固定，目标执行记录在冻结后取得。保持dummy权重和显式EP路由的当前语义；无需为本轮下载真实权重，不能据此声称自然路由或数值正确性。

矩阵保留原有合法TP1/2/4/8、PP3/4、EP2/4/8、TP/EP×PP与PD组合的覆盖责任，按每池及总设备约束选点，不做全笛卡尔积。页大小包含1/16/64/128/256及至少一个此前未用、原生合法的取值；容量覆盖4096至65536，并选择合法的大池代表至262144；并发覆盖1至128，持续请求覆盖256及一个更长代表。长度围绕页、chunk和容量的真实分支取点，遵守模型上下文和显存。机制需要相应来源，不把机制切换伪装成同域参数变化。

### 执行、失败与不可变边界

- S7–S9期间固定业务、adapter、观察/解释、评价代码、镜像、规则和已发布来源；不返修、不热补丁、不人工补采、不按结果改标准。
- 自动有限来源规划是正式被测能力，按冻结策略预先产生作业并核对实际触发；发现缺口后人工追加来源属于调查失败，不在本轮执行。
- 原生资格失败、来源/变换不足、确认结构差异、测量不足、评价工具错误、超时和额度未执行分别记录；不把partial、blocked或未执行计为通过。
- 有依赖的下游按实际原因记录，无依赖案例继续；来源失败不阻止独立目标原生取证，预测缺来源与目标原生资格分别记录。工具报错也保留结果并继续其他任务，不在批次中修评价器；旧已知原生受阻配置不原样重试，也不拿来充当新的泛化覆盖。
- 每个真实目标原则上一采，后续比较复用事实；失败不自动重试。仅对已完成步骤恢复发布/处理不算重采，仍沿原所有者和费用继续。
- 三批之间只整理状态、结果、费用和引用，不修改冻结方法。发现严重问题照实记录；若安全或资源条件确实不允许继续，保留已执行/未执行责任，不能缩小分母宣布完成。

每批交付先给整体流程完成情况，再给原生资格、自动来源成功、预测完成和独立结构结论四个分母。另列人工干预需求、来源/模板增长、缺口影响的工作类别与接口，避免只堆节点级partial清单。工作出现次数、模板类别和独立案例数分开统计。

## 6. S10：完整报告与共同根因

确认全部预定责任都有终态或明确未执行原因，先整理整体能力图、有效支持范围和失败分布，再沿原始事实、构图规则、模板、控制和评价追踪共同原因。

分别判断逻辑覆盖不完整、设计/推进/验证方法问题、适配层差异和工具缺陷；多个表象可以属于同一根因，一个案例也可能存在多个原因。按证据区分已确认、强线索和待验证，不把最早报错或调用名称直接当根因。

本阶段只读分析源码和冻结资产，可做有界离线查询，不修改生产/评价代码、来源、正式结论或输入，不新跑原生和仿真验证猜想。输出建议修复的职责链、可能删除/重组范围、影响及所需最小新证据；实际修复属于之后另行安排的工作。

总报告包含：方法与独立性、两类泛化结果、整体流程与工作依据、完整案例清单、必要代表证据、资源费用、未知/失败范围、共同根因及优先级。报告可全部失败但仍完成调查交付；结果不理想不能成为在本轮返修的理由。

## 7. 资源、数据与交付纪律

计划制定本身不触发采集、重构、数据删除、镜像重建或提交推送。取得执行指令后，实施启动时建立一个新的UTC运行根，沿inputs、sources、assets、targets、results、logs、work和可选diagnostics组织；旧运行只作显式开发证据/回归输入，不能自动发现为新资产或计入新留出。

初始窗口额度如下，S0须结合实际环境细化到作业后才能采集：

| 部分 | 原生累计上限 | 尝试上限 | 后处理累计上限 |
| --- | --- | --- | --- |
| S0–S6 开发及冻结准备 | 10800秒 | 24次 | 10800秒 |
| S7–S9 独立调查 | 32400秒 | 136次 | 32400秒 |
| 窗口合计 | 43200秒 | 160次 | 43200秒 |

单原生任务初始期限900秒，单后处理/评价1200秒；协调器留出关闭时间，真实超时仍计费。新窗口保留额度768GiB，项目data合计初始上限1TiB；模型缓存、镜像和构建在根外的占用另记，不能以迁出统计充当精简。额度是上限，不是必须花完的任务量。失败、换输入和恢复均不清零；独立调查前按实际成本一次核对资源是否足以覆盖全部责任。必要扩额自主记录收益和变化，不因看到失败增加重试或改变调查输入。

原生次数按采集任务的实际尝试计，来源、目标、资格及故障探针全部占用同一额度，并另列实际Engine初始化次数。72个目标责任不等于72次原生尝试，也不把rank数当采集次数。

按实际消费者保留原始事实、当前资产、必要失败、报告与恢复/费用信息；清理已消费SDK导出和临时构建，引用需要的内容保留。原始证据不足时不能先删除再声称可复核，也不擅自清理旧基线、共享模型或他人资源。

代码按C++23/Python实际环境编写，头源同目录，逻辑块有空行和必要注释，注释上方留空行，不改.clang-format。优先类与组合、浅层接口和有消费者的特化；保留边界校验与关键不变量，删除冗余防御、兼容、转发和无人消费路径，不新增任务平台、版本系统或独立test工程。

开发先静态推导完整机制，完成整块修改后统一必要构建和运行；核心在modeling镜像构建，SDK桥在对应source镜像构建。验证编排留example，不把窗口矩阵写进src。每五个实质代码批次或发现系列问题时归纳共同根因，调整方法后再继续，不以运行—补缺循环代替开发。

每阶段开始核对上一阶段完整交付和现状；S0–S6可据此调整后续任务，保留原因和原责任。每阶段结束从Git起点检查全部修改及相关未改代码，整理文档、数据、构建及实际镜像，完成代码/文档/数据检查后按type(scope):英文祈使标题分层提交推送，核对远端再进入下一阶段。S7之后只交付调查记录与结果说明，不借维护边界修改冻结实现；提交集中于阶段收尾。

当前用户暂存、reference、.gitignore及其他独立工作保持原样，data、模型、构建和deprecated不提交。日志只记有意义批次的范围、改动、验证、结论与限制；status集中维护阶段、资格、基线和恢复起点，不能只报缺口而省略整体能力。

窗口完成条件：S0–S6工程交付闭合，S7–S9全部调查责任如实记录，S10报告及根因判断完成，维护交付与远端核对完成；不以未知配置全部通过或性能准确为条件。完成后将总体结果汇入主工作流并删除窗口目录，不另存文档归档。
