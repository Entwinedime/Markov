## 1. 计数、证据和场景选择

- **覆盖责任：** 第一阶段共F01–F56，表示必须解释和检查的行为/合同，不是56次采集或56个完整目标。一个真实案例可满足多项责任，不能将检查项相加宣传为独立场景数。
- **真实案例：** 一个确定的模型、配置、request/路由和初态组合及其原生事实。复用它重建图、模板或预测不新增原生案例；改变请求/配置后，需要自己的对应真值。
- **来源：** 正式规划器产生的有限主/辅助采集作业，不能按场景数机械增加；新实现域按实际需要取得来源，同一结构分支不按长度复制采集。
- **独立目标：** 第二阶段首批B1十六、B2十二、B3八、B4十二，共48个完整目标责任。来源、原生资格探针、错误输入检查及修正复核不混入这48个目标。
- **证据资格：** 静态机制推导、原始事实核对、局部自还原/给定动作展开、完整原生控制对照分别报告。静态推导和局部自洽不能替代独立真值；必要合同反例走既有公开入口，不新增test/mock工程。

第一阶段每组先将责任映射到具体输入、实际触发和证据：优先复用已采案例，对缺少的行为构造小而确定的输入，再组合真实耦合场景。已有案例能同时满足多个责任就合并，不为了填数量分别启动Engine；无法覆盖必要两侧边界时不能只换标签。

第二阶段的配置清单在A6前确定，具体请求在冻结后依照已声明方法生成并固定。与全部开发及历史输入核对关系，标明新输入、配置重放或模型留出；不按结果筛选，不因新seed、目录或重复采集自动获得独立资格。

### 2.2 有限配置空间与取点规则

| 维度 | 开发检查的代表范围 | 选点与重新采集原则 |
| --- | --- | --- |
| runtime/backend | 固定当前SGLang/Ascend及实际源码/镜像身份 | 不引入第二环境；同镜像标签不等于同身份，项目包变化也不自动要求全部重采 |
| dtype | BF16、FP16 | 原生合法的模型/配置代表；dtype变化取得相应来源，不虚构支持FP32/量化 |
| page_size | 1、16、32、64、128、256 | 模型/后端合法者，页布局变化新来源；无需每模型×每页值都采 |
| TP | 1、2、4、8 | TP1为真正无TP基线；新拓扑新来源，不统一除以TP假定结构相同 |
| EP | 原生合法1、2、4、8 | EP不额外乘物理卡数；均衡、集中及随token变化的路由按现合同展开 |
| PP | 1、2、3、4及合法微批 | 检查首中尾、微批尾部、层数不整除PP的合法代表；不默认为所有模型原生支持 |
| PD | 对称及1→2、2→1、2→4、4→2等合法拓扑 | 普通单stage先行，再含PP/EP组合；TP×PP两池之和≤8，两池页布局/dtype符合现合同 |
| KV容量/token | 4096、8192、32768、65536、131072、262144 | 选择原生显存可承载的模型/拓扑检查小中大池，保留真实不足，不给所有模型套最大值 |
| max_running_requests | 1、2、8、32、128 | 请求数取1、m、m+1及多波代表，m−1仅在正整数合法时使用 |
| max_prefill_tokens | 256、1024、2048 | 按原生软预算/准入语义检查，不自行重写控制策略 |
| chunk/mixed/cache | 关闭、单机制及真实耦合 | 机制启用须有相同机制来源；chunk上限128/256代表，mixed和prefix按实际原生支持组合 |

基准开发目标可用Qwen8、TP1/TP2、page16、KV8192、并发8、prefill预算2048；这是便于定位的目标配置，不要求用户选择这个base，来源仍由正式规划器决定。

### 2.3 请求与内容取点

设页大小p、chunk上限c、并发上限m。输入均为正长度，符合模型上下文与原生资源约束；无效输入只在边界检查中拒绝，不启动原生。

- prompt：最小1，p−1/p/p+1、2p−1/2p/2p+1；chunk场景c−1/c/c+1和2c±1，另选不同页内余数的内部点。不对所有整数长度采集。
- output：1、2、3、7、17、33的适当组合，确定性覆盖Prefill即结束、一次Decode、多轮Decode、部分退出和最后成员继续；不是每个案例都随机选一个值。
- 成员：单请求、等长批、不等长批、恰好准入、超准入、反复成员进出；相同batch数不同token总量及相同token总量不同成员数分别检查。
- 到达：同刻、密集短波、稀疏连续、前批释放附近以及排空后长间隔到达。具体时间按实际原生/旁路事实核对，不把声明到达直接当成组批答案。
- 内容：无共享、共享前缀在页内/页边界、部分匹配/完全匹配、同长度不同内容。全前缀命中仍需遵守原生logits/末token处理，不预设“模型工作为零”。
- MoE：均衡/集中/交替路由，普通token及实际padding尾部，PP全模型专家层和不同EP拓扑的共同逻辑token。共享token但专家条件不同的缓存身份单独检查。
- 持续：256和1024短请求代表，至少一个长短混合及一个资源压力/缓存代表；请求ID保持唯一，反复重用的是物理槽位、页、缓冲及局部调用身份。

## 4. 必须覆盖的相互作用

单机制见证完成后，按实际依赖选择组合。以下是必须说明的耦合，不是要求所有取值相乘：

| 相互作用 | 需要回答的问题 |
| --- | --- |
| 参数所有权×调用路径×guard | 同一种子调用从不同父路径进入时，是否保留同一输入合同及真实条件？ |
| 成员退出×释放分组×队列准入 | 早结束/晚结束是否只改变原生动作，不污染模板参数或提前重用资源？ |
| 容量×数组形状×真实算法分支 | 哪些可直接求值，哪些选择已有实现，哪些说明来源/表示不足？ |
| 到达×资源反馈×业务时钟 | 输入到达相同但完成边界不同时，原生如何推进；旁路只注入必要时间？ |
| EP×padding×角色/PP位置 | 逻辑token、实际补齐、专家分布、不同rank形状能否统一解释？ |
| PP×微批尾部×输出/返回 | 尾部成员和首中尾stage是否有明确边界及正确返回环？ |
| PD×异步完成×源释放 | 源已逻辑结束时数据是否仍被传输消费，目的何时可准入？ |
| PD×预约顺序×peer绑定 | 同一拓扑下远端迭代顺序变化时，调用输入、池/字节几何和串行服务是否一致交接；按端点辨认后再核对必要因果，不能以子调用位置代替身份？ |
| prefix×压力×请求结束 | 页驻留、引用、淘汰和复用是否正确，不能用终态相同掩盖中途错误？ |
| prefix×路由×全模型内容 | 同token不同expert与PP局部层能否保持共同缓存身份？ |
| chunk×mixed×prefix×并行 | 多机制实际同时触发后，控制、形状和资源/因果是否仍闭合？ |

每组若不能触发必需行为，先从原生代码确定原因并有界调整开发输入；无法触发但有真实不可达/封闭依据时说明资格，不凭开关或其他案例通过宣称覆盖。不得把本计划要求的可达机制静默移出范围。
