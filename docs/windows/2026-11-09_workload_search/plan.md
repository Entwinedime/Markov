# 三类负载的配置搜索与实测确认

开始日期：2026-11-09。

目标：在不超过 12 小时的执行窗口内，完成 ShareGPT、BurstGPT 和程序生成负载的配置搜索，用独立实测展示推荐配置的性能、资源占用及预测误差，形成可用于第三阶段汇报的结果。

## 1. 本轮要回答什么

给定一组请求和资源预算，预测器能否选出比默认配置更合适的 HiCache 配置？主要展示真实对话上的收益，用真实请求长度分布检验适用边界，再用可控复用负载解释容量、回载和重算的取舍。

希望至少一个缓存敏感场景取得不增加声明报价、实测耗时下降 10% 以上的结果。ShareGPT 是主要应用案例，人工负载是机制对照；如果只有人工负载受益，不能表述成真实负载优化成功。这个数值是期望收益，不是筛掉负面结果或反复换请求的依据。

本轮沿用现有预测器、共享成本和简单预算搜索，不比较复杂搜索算法，不重跑旧 315 格，不同时开展新平台、新模型、高并发、真实突发调度或完整长期稳态研究。三类负载都有自己的结果，低复用场景没有明显收益也保留。

## 2. 三类请求及真实性边界

| 负载 | 正式请求数 | 输入与顺序 | 每请求生成数量 | 本轮用途 |
| --- | ---: | --- | --- | --- |
| ShareGPT | 200 | 公开对话记录；保留会话内轮次和记录中的历史上下文，按固定规则交错会话 | 原回答经目标 tokenizer 计算的长度，上限 32 tokens | 真实多轮内容中的自然前缀复用与配置推荐 |
| BurstGPT | 200 | 公开 API 请求记录的连续合格片段；保留原记录顺序及输入/输出长度配对，用确定性的独立内容实现输入长度 | 原记录 Response tokens，上限 32 tokens | 真实长度分布驱动的串行回放与弱复用对照 |
| 程序生成 | 1,200 | 手工设计规则、通过代码生成前缀族和独立后缀，固定种子及访问顺序 | 固定 8 tokens | 大请求量下，局部复用、隔段回访和缓存容量压力 |

以上是正式请求数，不含每类额外 8 个准备请求、估时试跑和独立成本采样。正式输入共 1,600 个请求，其中一类超过 1,000；不得用累计重复次数代替单条 workload 的规模。

### 2.1 ShareGPT

- 使用已具备的公开语料与目标模型 tokenizer，固定随机种子 20261109；记录具体数据文件、公开来源及选中记录身份。优先排除上轮已使用的会话，不以预测耗时或实测收益挑选会话。
- 按数据身份和固定种子选取有至少两个可用用户轮次的会话，以会话内先后顺序、会话间轮转的方式形成 200 个正式请求；边界截取记录清楚。输入长度限定 256～2,048 tokens，超范围的轮次及被中断的后续历史单列，不能偷偷裁掉历史来制造命中。
- 使用数据中的实际历史文本，不把本次模型生成的回答当成下一轮记录的原答案。因此这是固定历史的离线回放，不是在线闭环对话或回答质量评测。
- 现有公开清洗版可能已经拆分过会话，只声称保留所选记录中的轮次，不声称恢复原始完整会话。会话交错是本实验设定，不能称为真实线上到达。
- 从输入 token 直接统计共同前缀、复用距离和输入长度；会话身份本身不作为缓存命中事实。不得额外复制请求以提高命中率。

公开来源：[ShareGPT 数据说明](https://huggingface.co/datasets/anon8231489123/ShareGPT_Vicuna_unfiltered)。

### 2.2 BurstGPT

- 固定公开文件和模型字段，选取 API log 中输入长度 256～2,048、输出长度大于零的记录；按固定起点取前 200 条合格记录。保留原行号、时间戳、被排除记录及筛选比例，不按模型预测或已有耗时挑片段。
- 公布文件提供请求统计，没有请求正文或可验证的 token 前缀。使用固定种子产生互相独立的合法 token 内容，长度与选中记录一致；公共协议前缀如存在则单列。不能依据相同 Session ID 编造可复用前缀。
- 原记录的 token 数来自原服务；本轮把该数量作为目标模型的长度代理，不声称还原相同文本在 Qwen tokenizer 下的真实长度。
- 原始时间戳保留在选择记录中，但本轮按串行发送，不复现原始到达间隔或并发；公开 Elapsed time 属于原服务，不作本平台的真值。
- 报告名称明确写为“BurstGPT 长度驱动的串行回放”。不声称验证其真实正文、缓存命中、突发调度、吞吐或 P99。

公开来源：[BurstGPT 数据字段与用法](https://github.com/HPMLL/BurstGPT)。

### 2.3 程序生成

这里的“代码生成”指用代码生成请求数据，不自动等同于真实线上代码补全业务。生成器属于实验例子，不进入预测核心。

- 固定种子 20261109，构造 32 个可复用前缀族及 180 个一次性前缀；共享前缀取 768/1,536 tokens，独立后缀取 64～256 tokens，每个完整请求的 token 内容可追溯。
- 1,200 个请求中，720 个按局部热点访问，300 个在相隔 16～64 个请求后回访，180 个使用新前缀。规则提前确定，共同前缀和独立后缀在实际编码后核对，输出生成内容不决定后续输入。
- 工作集横跨设备容量及部分主存容量，预期能看到命中、淘汰、回载和重算。预期不作为实际发生证明，最终以预测和正常 API 的工作记录分别报告。
- 采用 8-token 短输出控制大规模运行成本；与两个真实来源的 32-token 上限分开解释，不把三类负载的总耗时直接相减归因。

### 2.4 长度和准备条件

两个真实来源均按原始输入/输出配对驱动生成数量，先使用 32-token 输出上限；记录原长度分布、上限后分布、请求截断比例和丢弃 token 比例。不得把有上限回放称为原始完整长度回放。

每条请求使用明确的生成数量与 ignore_eos=true，预测和正常运行核对实际返回数量。只固定生成长度，不强制生成原答案内容；出现提前终止或输出缩减时保留失败原因，不能按较小工作量评分。

原始语料按需流式读取，已有文件只读复用；各运行只保存选样身份和必要编码，不为每个 target 复制整份语料。

输入和目标池须满足页对齐、输出预留及额外一页的原生准入条件。无法满足的候选明确为资源不可行，不能接受偷偷缩短输出的“成功”请求。

每类 8 个准备请求及其长度、内容在正式采集前确定，所有配置使用相同准备策略。准备后排空既有后台工作，保留缓存状态；正式窗口不扣 gap、未归属成本、Prefill/Decode 或窗口内首次准备。输入初始状态按真实采集声明，不用 prepared 标记代替实际预热。

## 3. 搜索问题与最小实测集合

### 3.1 复用已有空间

保留同一 Qwen3-32B/BF16/TP2、Ascend 910B3、SGLang eager/FIA 和 buffered 文件 I/O 条件。具体设备在执行时核对空闲后声明，不占用他人任务；推理镜像沿用已验证环境。

| 参数 | 初始档位 |
| --- | --- |
| 设备 KV 容量 | 3,072 / 8,192 / 24,576 tokens |
| 主机池比例 | 1.32 / 2.5 / 4.49 |
| 页大小 | 32 / 64 / 128 tokens |
| 写策略 | 直写 / 选择性直写 / 写回 |
| 预取门槛 | 128 / 512 / 2,048 tokens |
| 等待策略 | 等待完成 / best-effort / timeout |
| timeout | 0.01 / 0.1 / 0.5 / 2 秒，仅用于 timeout 策略 |

参数积为 1,458 个候选；非 timeout 策略不重复枚举无效超时值。默认配置显式加入并去重。原生不可部署条件保留排除原因；实际合法数另报，候选数不等于不同执行行为数。

沿用 66/70/80/96 GiB 主机档位和已有报价情景；共同设备/CPU、固定预留和可变 KV 占用分别列明。报价是声明情景，不是实际账单，不为扩大收益修改价格或假造设备切片、带宽变化。

默认配置继续使用设备 8,192 tokens、主机比例 2.5、64-token 页、选择性直写、512-token 门槛、等待完成。数据规则和默认配置在查看 target 真值前确定。

### 3.2 一种搜索方法，两项结果

每类固定种子做 96 个不同配置的随机预算搜索，默认计入预算；共 288 次预测。沿用现有分批会话，共享源和只读模型，不重复加载整个 base。每批不超过 48 点。

主推荐是在不高于默认声明报价的可部署候选中，选择预测完整 HTTP 最短的配置；同时间按报价、稳定名字破同分。这个筛选放在实验调用层，复用统一预测和现有资源核算。

同时按现有接口报告“满足默认预测耗时 90% 上限的最低报价配置”。绝对秒数在读取正常真值前确定，后续不重算；不存在可行点时保留空结果，不临时降低要求。两项推荐可以重合，正常实测优先主推荐。

只有在尚未查看 target 真值、搜索阶段累计仍低于 1 小时且不挤占最低实测面板时，才把同次查询续至每类最多 192 点。扩展规则对三类一致，不按哪一类收益漂亮来分配。无需完整枚举、算法多种子对照或证明全局最优。

### 3.3 正常实测只保留两种主要角色

每类实测默认和主推荐，先各 2 次独立正常运行：最多 6 个条件、12 次完整运行。推荐与默认相同时共用测量，直接报告没有找到改善，不另挑实测较快的配置替代推荐。

正常运行关闭 profiler 和 Markov 探针，使用实际声明的主机配额；每次重建服务及本次缓存命名空间，运行相同的准备和正式请求。三类与配置轮换顺序，避免把整段系统漂移只留给某一方。

在全部最低重复完成后，剩余预算优先为真实来源增加第三次重复，再为人工负载增加第三次；同一场景的默认与推荐成对追加，每条件至多 3 次，最多 18 次。若有条件 CV>3% 或推荐与默认的样本范围重叠，报告不确定性；不能为得到显著收益无限追加或只保留快样本。

没有额外实测配额时，最低报价副推荐只保留预测结论。所有成功慢样本和失败尝试保留；部分完成的结果与计划面板分母一起报告。

## 4. 执行阶段和 12 小时安排

12 小时从本窗口第一次执行数据准备或运行命令开始连续计时，本次编写计划不计入；排队、下载、失败、恢复、设备等待、后处理及提交均计入，不因重启任务清零。设备不空闲时也不能靠延后记起点隐藏等待。

| 阶段 | 时间安排 | 实际工作与交付 |
| --- | --- | --- |
| A 请求与入口准备 | 0～0.75 小时 | 导入三类数据，完成有界输入生成和轻量例子编排；记录来源、长度、复用统计及预算 |
| B 估时、共享成本与 base | 0.75～3.5 小时 | 每类 20 请求的普通估时，检查成本覆盖，必要共享补采；采 3 份语义 base 并核对实际 token 与输出 |
| C 搜索与候选确定 | 3.5～4.5 小时 | 每类 96 点预算搜索，记录覆盖、资源、预测及两种推荐；固定实测条件 |
| D 独立正常确认 | 4.5～10.5 小时 | 完成默认/主推荐各 2 次，余量允许才补第三次；全部条件用同一计时口径 |
| E 整理与交付 | 10.5～12 小时 | 统一评分、画图、检查代码/文档/数据、分层提交推送，收束结论与限制 |

时间上限是停止条件，不是对未知请求耗时的保证。各阶段可以前移，不能用尽可选工作后再挤掉最低实测和最后 1.5 小时交付。

### 4.1 先估时，再启动长任务

估时只用默认配置的小片段，记录模型启动、准备、每请求完整耗时、输入/生成量和后台结束，不把 profiler 采集时间当正常真值。估时数据是开发输入，不作为正式收益证明。

用三类实际请求长度分布和试跑耗时估算：3 份完整 base、12 次最低正常运行、剩余启动及共享采样；预留至少 25% 的运行余量。每次长任务前核对累计耗用和剩余计划，只有预计能结束且留足报告时间时才启动。

若最低面板估算放不进剩余时间，在正式 workload 确定和采 base 前，将两个真实来源的输出上限统一从 32 调为 16；请求数、身份、输入和顺序不变，人工负载仍为 8。重新记录最终输入及截断比例，这项选择只依据耗时和预算，不依据 target 收益。正式输入确定后不再悄悄缩短输出。

若采用较短输出后最低面板仍不可行，立即说明 12 小时约束下的缺项；不把试跑、少量请求或单次重复冒充完整完成。不得减少 1,200 请求那一组来满足规模描述。

预算紧张时依次取消额外 96 个搜索点、第三次重复、额外图细节和非必要诊断；三类负载、最低搜索及默认/推荐确认优先。最迟第 10.5 小时进入报告，不启动预计无法按期退出的新设备任务。

### 4.2 累计资源上限

| 资源 | 本窗口累计上限 | 说明 |
| --- | ---: | --- |
| 总墙钟 | 43,200 秒 | 连续 12 小时，包含失败、等待、整理和交付 |
| base 采集 | 7,200 设备组秒 | 3 份 semantic base，含至多 1 次有记录的失败重试 |
| 估时及独立采样 | 2,700 设备组秒 | 3 次估时启动；独立采样最多 6 次启动、128 请求 |
| 正常确认 | 21,600 设备组秒 | 最低 12 次完整运行；最多 18 次，时间优先于次数上限 |
| 全部设备启动 | 32 次 | 包含三类任务及失败，不重置历史消耗 |
| HTTP 请求 | 14,000 个 | 包含准备、试跑、base、补采、正常重复及失败耗用 |
| 输入 / 输出 tokens | 3,000 万 / 32 万 | 累计实耗；未完成任务按现有任务合同保守记账 |
| 新增保留数据 | 目标 ≤16 GiB，上限 32 GiB | base、采样、正常真值、输入和报告分别统计 |
| 单任务临时文件 KV 与导出峰值 | 上限 192 GiB | 按实际去重页数、每页字节和 TP 估算，不与最终保留量混算 |
| 预测并发 | 最多 2 个进程，各 8 GiB | 初始并发 1，通过代表输入的内存观察后才升为 2 |

设备采集和正常测量严格串行；预测与后处理可以用 CPU，但内存与 CPU 放置不能干扰正常条件。复用既有超时、容器限额和进程树回收，不另造调度平台。

执行前按可能写出的独立 KV 页估算临时空间，磁盘可用量至少覆盖该任务预计峰值的 1.2 倍并保留 32 GiB 余量；超过 192 GiB 的任务在启动前报告资源不足。现有 retained_mib 检查会计入运行中的文件，任务限额必须容纳临时 KV，不能直接把最终 32 GiB 保留目标当作临时峰值限制。复用现有采集在正常退出后清理自身 storage 的行为；失败残留先登记，再只处理本任务确认无用的临时文件，保留输入、manifest、正常观察及失败证据。

宿主可用内存须覆盖已声明任务限额并留至少 32 GiB 或总内存 10% 的较大者。达不到则等待或停止，不能靠 OOM 试探；不清理他人资源或旧数据来强行启动。

## 5. base、共享成本和首次使用的处理

每类最终 workload 各采一份新 base，共 3 份；200 请求来源不能冒充 1,200 请求来源。使用轻量 semantic 采集、关闭 snapshot、关闭全目标 record_graph；不默认导出大 trace 或逐节点图。

先显式复用既有同部署的 39 类独立响应。检查新 query/context、Decode 步数与输出载荷范围；输入维度在范围内不等于长输出及新组合已经验证。结果发送的典型小输出响应仍有近似，不能因模型查询成功就声称完成真实长度建模。

确有缺口才进行有界独立采样，数据写入本窗口自己的维护位置；补采面向整组工作域共享，不采 target trace、不导入 target 正常真值、不回写历史成绩。补采达到同类缺口仍无新事实或时间上限时停止，不无限启动。

正式搜索和独立确认使用同一套明确选定的成本与规则；若必须根据新发现修代码或模型，已看过的结果转为开发证据，并按剩余预算重新安排独立确认。无法重验的部分保留限制。

首次使用不单独开展编译器研究。主要报告保留正式窗口内全部耗时，另按事先固定的连续请求块展示趋势：两个真实来源每 20 请求一块，人工负载每 100 请求一块。尾段趋势只作补充，不删掉前段来换更大收益，也不把预测 prepared 状态称为真实稳态。

1. **默认与自动推荐的实测耗时。** 三类负载各自归一化，标实际秒数、重复次数、样本范围及相对收益；资源/报价不高于默认的条件写清。
2. **预测是否支持实际选择。** 展示已实测条件的预测与正常均值，给 APE、WAPE、排序和收益预测；失败、同分、无明显收益不隐藏。
3. **搜索和资源代价。** 展示声明空间、实际预测点数、搜索时间、默认与推荐的原生设备/主机 KV 占用和声明报价。价格收益很小时如实给出，不放大坐标暗示巨大节省。

正文用一页 overview 列出平台、请求数、输入/输出分布、截断率、复用关系、搜索数、实测次数与全流程开销；随图说明两个真实来源各自保留和未保留的信息。前后请求块的变化必要时放补充图，用于判断收益是否主要集中在服务初期。

公式保持统一：单格 APE = |预测－正常算术均值| / 正常算术均值；WAPE 对独立条件汇总，重复先求均值、不重复算成多个配置。收益 = 1－推荐正常均值 / 默认正常均值；同时给原始秒数与全部样本。最低 2 次只能提供初步确认，样本范围不是置信区间。

完整正式 HTTP 从首个正式请求发出至最后响应完成，保留客户端间隔、CPU residual gap、未归属成本、HiCache I/O/control 及 Prefill/Decode。启动、8 个准备请求、后台排空、base/共享采样与预测时间另外统计，不与嵌套计时重复相加。

## 7. 完成、限制和交付

本轮执行完成需要：

- 三类正式请求分别达到 200 / 200 / 1,200，输入和生成数量与最终协议一致，公开来源与人工构造分清。
- 每类至少完成 96 点的声明搜索；不可行、缺成本及失败候选有明确状态，不填零参与排名。
- 默认与主推荐完成最低正常重复，或同配置时明确共用真值；预测、正常计时和资源核算保持同一条件。
- 三张主要图和 overview 有可复核原始记录；总耗时、失败、存储和剩余缺口可追溯。
- 代码、文档、数据分别检查；只为实际源码变化做必要 Docker 构建和代表入口验证，不启动无关矩阵或独立测试工程。

精度争取 WAPE≤3%、最大单格 APE<10%，优化收益争取至少一个缓存敏感场景≥10%。运行完成、精度达标和优化有收益分别判定；未达到任一项时如实标明，不能仅靠“全部执行成功”宣称第三阶段验收通过，更不能保证真实负载必然改善。

实现尽量集中在 examples/hicache_search 的输入与编排，复用正式 predict/search/measure/calibrate/maintain；不为三种 workload 在核心增加身份分支，不改 KTransformers、NodeScale 或历史静态回放能力。
