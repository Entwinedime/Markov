# 从性能预测到资源约束自动寻优

开始日期：2026-11-05。

目标：在当前 SGLang／Ascend 的支持范围内，完成“用户给定负载、资源选项与性能要求，系统准备数据、搜索配置、给出资源与策略建议，再独立实测确认”的完整流程，并形成可以用于研究汇报的结果。

本文的“第三阶段”指汇报路线中的自动寻优能力。原始 DAG、目标结构、成本与执行这三个建模职责继续保留，不再重新建设一套预测器。计划、当前资格和实际行动分别由 plan、status、log 维护。

## 1. 本窗口怎样算完成

用户提供模型与部署、workload、base、候选参数范围、可部署资源档位、价格依据和耗时要求。运行一次正式入口，得到以下结果：

1. 自动准备或复用 base 和独立成本模型；缺少成本时按整组共享补采，不向用户要求手工补齐逐项模型。
2. 在资源可行、成本覆盖明确的空间内搜索，给出满足耗时要求的低成本方案、预测最快方案，以及时间与成本之间的折中。无可行方案时明确返回无解。
3. 记录搜索实际评价过哪些配置、用了多少预测与准备时间、有哪些缺项，以及推荐的适用条件。
4. 实验侧用正常运行确认预先规定的少数候选，分别评价预测误差、实际性能要求和成本变化。
5. 用相同预测预算比较搜索方法，并交付结果表、图和可复现输入，能够回答“为什么需要搜索、比默认配置改善了什么、搜索本身花了多少代价”。

本窗口争取同时完成流程交付和效果验证。不能将入口跑通等同于推荐有效，也不能将有限候选中的预测最优称为真实全局最优。若效果判据未达，保留未完成项及原因，不以完成报告替代验证。

## 2. 范围和取舍

主线限定为 Qwen3-32B/BF16/TP2、Ascend 910B3、SGLang eager/FIA、串行固定输出。改变 workload 时重新准备与它匹配的 base；同一 workload 的 target 共用来源与独立模型。新模型、新平台、并发吞吐、P99、冷存储和任意网络存储留在范围外。

保留 KTransformers 的同级入口、默认关闭的 NodeScale、详细源 DAG、静态回放和独立评价。本窗口不为它们新增 HiCache 搜索功能。/home/markov 和 /home/markov-next 不作修改，deprecated 仅供只读机制对照。

普通预测仍保留 gap、未归属控制及 Prefill/Decode；结构生成不读取成本系数。工作先按规则产生，再绑定成本、推进同一仿真时钟，并根据完成、超时和缓存状态继续生成后续工作。评分与预测物理隔离，不通过 target 真值选择成本来源或补参数。

本次不恢复已终止的大搜索任务，不复用其超时或失败当作新结果。不新建调度平台、常驻预测服务、插件系统、独立测试工程或内部版本机制。优先改进既有正式入口及搜索例子。

## 3. 用户最终怎样使用

应用输入只要求用户能作决定的内容：

| 输入 | 要表达的意思 |
| --- | --- |
| 部署与模型 | 框架、设备、TP、模型路径、运行环境及可用预算 |
| workload | 真实请求或 token 输入、准备/正式边界、每请求生成数量 |
| base | 指定基准配置，或显式复用同一 workload 的已有采集 |
| 搜索范围 | 容量、页大小、写入与预取策略等允许选择的值 |
| 资源与成本 | 实际可部署的配额档位、固定预留、价格或透明的成本情景 |
| 性能要求 | 正式 HTTP 耗时上限及预测次数或时间预算 |

用户不需要手写内部维护请求、逐节点成本或中间模型包。已有数据自动复用；需要启动设备、补采或进入范围外工作时，在预览和结果中说明具体原因及预计规模。

正式 search 负责一个寻优任务的准备、评价与选择；examples/hicache_search 负责研究负载、算法对照、正常确认及跨运行汇总。实验与搜索共同调用同一个预测器，核心算法不识别面板、会话名称或候选编号。

优先支持用户给定绝对时间上限。相对 baseline 的要求在边界转换为一份明确的绝对上限，并记录基准来源；预测、筛选和正常确认使用同一门槛，不在看到实测后重新计算成更容易通过的要求。相对正常 baseline 的真实改善另行报告。

## 4. 实验先确定什么

### 4.1 两类负载与一个换 base 核对

主场景采用有实际前缀回访的请求，使工作集在不同容量下分别出现设备命中、主存回载、文件回载及重新计算。对照采用低复用请求，检查系统是否会如实给出“没有足够优化收益”。

从已有 ShareGPT 语料中按事先确定的规则选择未参与当前修复的会话，保留身份和选择范围。先确定请求与输出数量，再运行搜索；不能依据最终收益反复更换请求。两类场景优先匹配输入长度和输出规模，无法匹配时只比较各自场景内的方案，不将跨场景差异解释成复用的因果效果。

每场景初设 12 个正式请求、2～4 个准备请求，生成量选择 8 或 32 tokens，并以现有成本域约束输入长度。规模通过 workload 声明，不写入核心限制。先检查真实工作集和实际 I/O，不因设置了长输入就宣称覆盖了文件回载；确实未覆盖时，在查看收益前按既定工作集规则调整一次并记录原因。

主场景选一份中档 base 供所有 target 使用，再选一个页宽或策略不同的 base，对预先选定的 8～12 个代表目标复核；不为每个 target 采 base，也不额外恢复全矩阵。换 base 共用原正常真值和独立性能库，新 base 不进入成本训练。

### 4.2 搜索空间有足够规模，也有真实取舍

起始参数范围如下，实施时先核对原生配置含义、内存预留和已有成本域，再确定正式有效空间：

| 参数 | 起始安排 |
| --- | --- |
| 设备 KV 配额 | 紧张、中间、能覆盖大部分工作集的至少 3 档；从 3,072／8,192／24,576 tokens 核对 |
| 主存缓存 | 至少 3 档；按原生比例/对齐规则换算实际页数与 GiB，不伪造独立可设容量 |
| 页大小 | 32／64／128 tokens |
| 写入方式 | 直写、选择性直写、写回 |
| 预取门槛 | 以 token 表示，起始 128／512／2,048，按页几何转换 |
| 等待策略 | 等待完成、不继续等待、4 档 timeout；起始 0.01／0.1／0.5／2 秒 |

上述主要轴约产生 1,458 个组合，另显式加入 baseline，去掉重复和无效条件。正式空间争取保留约千个有效候选；如果因明确约束不足 512 个，在阶段交接前说明缺少哪个轴及原因，不能用无效 timeout 重复、候选改名或任意倍率凑规模。实验规模不成为产品分支。

容量增加必须同时体现在资源占用和成本中。至少存在两个可部署的不同资源档位，不能把最大缓存、最高带宽设为免费选项。对主场景预先声明宽、紧两个性能要求，观察资源建议是否随约束变化；没有形成折中时如实解释，不用极端价格制造漂亮曲线。

### 4.3 资源成本与带宽怎样处理

主目标为：在正式 HTTP 不超过声明上限、内存预留不超配额的前提下，最小化资源档位的单位时间成本。KV 池按真实布局计入 padding 和池内缓冲，权重、workspace、运行时等固定预留单列；主存和设备按各自作用范围计数，避免 TP 重复计算。

优先采用可追溯的部署报价或用户提供的价格；取得外部价格时注明来源、日期、单位和适用配置。没有真实报价时允许声明归一化成本情景，并至少检查三种合理价格关系；结果只称预留/报价情景收益，不声称节省了实际采购或账单。旧 PPT 的容量价格不直接当作当前真实报价。

双向传输分别核对主存→设备、设备→主存以及文件读写响应，保留各自工作量、计时口径和共享资源关系。当前硬件上的带宽是独立测量条件，不是一个可以随意改大的数字。

本窗口的第三阶段收口范围是同一已验证设备/runtime/I/O 条件下的容量与策略寻优。PPT 中将带宽本身、SSD 容量或存储介质作为可选硬件方案的部分，需要真实可部署选项、独立成本依据与实测条件：条件具备时加入；否则明确列为后续硬件搜索扩展，不混入主成绩，也不声称已完成任意带宽寻优。不得通过按比例缩放全部 I/O 耗时来冒充新硬件能力。

## 5. 三个实施阶段

### 阶段 A：整理使用流程，确定采集、负载和资源合同

联合处理正式准备入口、SGLang 观察、manifest 消费方、搜索输入和例子，先让一份任务能够自上而下读懂。

1. 收紧输入，删除搜索例子与正式入口之间重复的准备、解析和状态管理。保留现有预算、恢复和结果所有者，不再增加平行账本。
2. 区分普通 base 需要的观察和详细诊断需要的观察，试行仅保留必要 probe/客户端记录的 base 采集。去掉普通预测无消费者的逐算子记录；明确必须保留的请求、token、阶段、控制与残余边界。
3. 轻量和详细采集共用正式 manifest 交接，如实声明已采通道及用途。正常实测、独立校准和 base 记录不能混作同一种成功产物；未采设备 trace 时不能宣称具有详细源图资格。不得填空文件、伪造 profiling 状态或增加内部版本 fallback。
4. 用至少一组已有开发请求做同条件的详细/轻量 base 对照，使用同一成本选择预测预先规定的代表 target，再对照独立正常结果。比较请求工作、必要边界、E2E 和采集开销，不能只比较两份预测总时间接近。最终新会话不承担这轮修复验证。
5. 在同一预测调用内复用来源和成本结果，保证同一 base 的多个候选不会重复整理来源。先采用少量批次完成搜索，不为避免两次来源读取建立持久缓存、常驻服务或摘要校验机制；确有瓶颈再以实测说明必要性。
6. 确定正式场景、参数空间、资源计价和验证条件，准备整组成本。缺口先区分规则、观察与成本问题，仅后者按有界共享采样补齐；不为每个候选启动 serving。

交付：能运行的用户输入和预览、确定的场景与有效空间、明确的模型来源，以及 base 轻量化的资格和开销对照。

轻量化目标是显著减少保留量和导出成本，先争取语义 base 每份不超过 128 MiB、比同请求的完整采集减少 90% 保留量；启动/权重加载未必同比减少，分开报告。这是效率目标，不以牺牲必要信息达成。若轻量采集尚未通过，保留实验开关和完整采集的正式路径继续寻优，明确这项遗留，不能让它无限阻塞第三阶段，也不能提前宣传默认采集已变轻。

### 阶段 B：固定预测依据，完成搜索与方法对照

本阶段开始前固定场景、性能要求、价格情景、成本选择、搜索预算和随机种子。两组新会话在此时选定，阶段 C 前不查看其正常结果。只记录 Git 提交、真实选择和输入来源，不新建冻结副本或 SHA 等有效性机制。

1. 使用一份共同的模型选择准备整组候选，训练只来自合格独立数据。所有方法获得相同成本能力，不能某个算法在搜索中独占额外补采或因目标分数更有利而替换来源。
2. 实现最小的预算搜索：先按容量、写入和等待策略覆盖分组，再从有希望的配置附近细化；去重、资源不可行和缺成本分别处理。复用正式批量预测，不另写近似预测器，不引入没有必要的新依赖。
3. 与均匀随机搜索比较，预算初设 48／96／192 次预测，每方法每场景使用相同的 10 个预先声明种子；baseline 等共同点计入预算。完整枚举一次有效空间作为“有限集合的预测参照”，不采集全空间正常真值。阶段 A 已为成本覆盖运行的完整枚举，在输入、规则和成本未改变时直接复用，避免重复计算；参照路径不进入算法输入。
4. 完整参照只由评价侧使用。搜索方法只能看自己已请求评价的配置，不能先读全表再模拟挑选。可用已保存结果研究选点行为，但须标为离线重放；实际搜索总时间另作真实在线调用，不以查表或累加毫秒估计代替。
5. 报告随预算变化的最好可行成本、与有限集合预测最优的差距、找到可行方案的比例、预测次数及实际耗时，保留所有种子和失败。没有证据要求复杂方法必须胜过随机；若优势不稳定，交付更简单的方法，并如实给出负结论。
6. 普通搜索只保存紧凑结果，图诊断限于有解释价值的代表。来源整理、成本准备、目标仿真和报告计时分开，预算搜索的重复来源开销也计入总时间。

交付：可恢复的预算搜索、有限空间参照、随机与分组细化对照、可行方案与时间/成本折中。费用与效能结论仍为预测，尚不授予实测收益资格。

### 阶段 C：独立确认推荐，完成研究结果和交付

本阶段只评价固定候选，不再根据正常结果重新训练或挑选更有利的负载。若结果揭示必须修复的真实错误，先记录本次未达并返回实现阶段；用过的数据转为开发用途，之后另留一次小型确认，仍计入原累计预算，不能无限换数据维持“独立验证”的称呼。

1. 每场景事先规定确认角色：baseline、预测最快、性能约束下最低成本，以及一个用于检查接近门槛或明显不同资源档位的对照。角色重合时只测一次；两场景及两个性能要求合计不超过 10 个不同条件。阶段 A 已用 6 次正常开发对照，正式确认最多 10×3 加上最多 6×2 次追加，与开发对照合计仍不超过窗口的 48 次；不将整份额度复制给每个场景。
2. 每条件先做 3 次正常运行，采集前固定设备组、CPU 配额与放置、内存条件、初始化和存储冷热说明。轮换或交错测量 baseline 与候选，保留慢样本、失败和每次输入输出，禁止清空全机缓存或干扰他人任务。
3. 单个条件 CV>3% 或结果紧贴性能门槛时，按事先规则统一追加至 5 次；最多 6 个条件追加，共最多 48 次正常启动。仍无法区分就报告近似并列或不确定，不能一直采到均值通过。
4. 对每个确认条件分别报告完整 HTTP APE、是否满足同一绝对耗时要求、相对 baseline 的真实改善、资源预留及成本变化。不能用“单格误差 <10%”代替“推荐顺序正确”，也不能因预测合格就忽略真实约束失败。
5. 在另一个 base 下复核主场景的预定代表和推荐稳定性。不同 base 共用已有正常观察，不为换 base 再运行整套正常矩阵。
6. 最终规则和模型固定后，以同一候选复核原有 315 格，cross/self 都使用用户确认的严格 <10%，不恢复 self 3% 标准；保留 C3/w3 六次均值与原三次参考敏感性。复用正常真值，仅重跑预测，不新增矩阵采集。
7. 完成关联代码、文档和数据审查，归并稳定合同与结果，清理无用实现和临时诊断路径，分层提交推送。窗口关闭前把结论、实际范围和未完成扩展写回主工作流，随后撤下窗口文档。

交付：完整搜索案例、全部正常重复、研究图表和结论、用户使用说明、开销与适用范围。主场景应确认至少一个性能或成本方面的实际改善，另一项满足预先声明约束；低复用对照允许没有收益。若主场景无改善或推荐违反约束，明确“流程完成、效果未证实”，保留效果验证未达，不能改价格或换请求来包装第三阶段已通过。

## 6. 验收分别看什么

| 方面 | 本窗口要求 |
| --- | --- |
| 使用流程 | 从声明输入自动准备并搜索，能恢复中断、复用已有任务，输出方案或明确无解；不需要手拼成本模型 |
| 空间与资源 | 有明确的有效组合、实际配额及两档以上成本差异；没有免费的无限容量或虚构带宽 |
| 搜索研究 | 完成共同预算、种子和模型下的方法对照及一次有限空间预测参照；不要求人为保证提出的方法胜出 |
| 预测精度 | 原 315 格全部 <10%；新确认条件逐格报告，目标仍为 <10%，失败与缺测保留 |
| 推荐有效性 | 正常运行确实满足固定性能要求；主场景有可解释的性能或成本改善，近似并列不硬排唯一最优 |
| 泛化边界 | 新请求和换 base 有独立证据；数据一旦参与修复就转为开发用途，不继续声称留出 |
| 效率 | 真实报告从零准备、复用准备和纯搜索三种开销；不把逐目标毫秒或查表重放称为完整流程耗时 |
| 表达与交付 | 图表解释工作负载、折中、算法预算和实际收益；明确条件与局限，不只列命令和工程状态 |

单格 <10% 不等于所有结构已证明。代表仍核对命中/回载/重算工作、页发布和必要依赖，必要时调用独立评价。详细源图回放仅证明对应观察的自洽，不能代替正常精度。

## 7. 时间与资源安排

目标按连续 3 个工作日组织：第 1 日完成阶段 A 的完整切片及必要采集，第 2 日完成阶段 B 的方法和预测对照，第 3 日完成正常确认与交付。实施起点以实际启动为准；这是推进安排，不以到期自动宣布完成，也不扩大成多轮长期调参。

设备新增用量初步按下表控制，旧任务账本不清零：

| 用途 | 启动上限 | 设备组时间 | 请求／输入 tokens／输出 tokens 上限 |
| --- | ---: | ---: | --- |
| Base 及轻量/详细对照 | 6 | 3 小时 | 120／250,000／4,000 |
| 共享独立补采 | 8 | 1.5 小时 | 64／150,000／2,048 |
| 正常确认，含追加与失败余量 | 48 | 3.5 小时 | 768／1,600,000／24,576 |
| 合计 | 62 | 8 设备组小时 | 各用途分别累计，失败、加载、预热和导出均计入 |

同一用途所有子任务合计受该上限约束，不能给每个 cell 复制一份完整额度。设备组小时是整组墙钟，TP2 的卡小时另列。根据实际工作规模设置子任务预算，不将表内上限当成必须花完的配额。

新增保留数据初步不超过 32 GiB，其中新的完整诊断采集最多两份，其余优先轻量记录；启动前另核对临时 KV、profiler 导出及容器层的空间，初步预留 64 GiB 可用余量。记录保留量和能观察到的峰值，单次 du 不冒充峰值。只清理本窗口明确拥有且不再用于复核的临时文件，不删除原有 base、正常真值、独立来源或稳定结果。

纯预测与算法对照初步预留累计 2 小时宿主墙钟，最多 3 个并发、每进程 8 GiB，使用已有容器内存上界与进程树回收；设备采集严格串行。不因宿主内存大就放开无界并发，不与他人设备任务争抢。

确需调整初步额度时，先记录要取得的新证据、已有耗用及新的累计上限，再自主安排；不反复询问已经授权的上限，也不重置失败用量。相同问题无新事实时返回工作定义或规则，不通过无限补采延长窗口。

## 8. 修改、验证和记录方式

按完整职责链组织大批次，联合修改观察生产者、manifest/来源解释、共享准备、成本、搜索调用及例子，不逐文件修补收尾。阶段 A/B/C 是交接边界；在每阶段的相关功能基本齐备后，集中做必要格式、Docker 构建、真实入口和关联审查，再按职责提交推送。没有新改动或风险时不反复构建；同阶段不因几次预测或日志更新频繁提交。

实现期间用少量受影响代表，包括 self、正常命中、主存/文件回载、timeout 和低复用；最后一次模型与公式确定后才做完整 315 格回归。共同合同被修改时补查 KTransformers 公开入口、显式回放和独立评价；范围未触及时不启动无关设备采集。不新增 test 文件、CTest、fixture 或改名的自测脚本。

运行证据集中放在 data/auto_tuning_20261105/，保留用户请求、场景与候选定义、模型选择、算法顺序和种子、正常观察、资源用量及紧凑报告。详细数字留在 data，不另建平行总结、审查文档或版本档案。

status 只维护当前资格、起点、已证范围与下一步；log 原则上每阶段交接一条，重要数据有效性问题或预算调整另记，四个字段说明范围、改动、验证、结论与限制。进展用阶段的实际完成项说明，不以不断变化的总体百分比替代证据。
