# 三条主线自动化与配置预测扩展

开始日期：2026-11-16。

目标：让两款 Qwen 的跨 TP／HiCache 预测和 KT＋DeepSeek 的 CPU／专家卸载预测，都能通过同一套正式流程自动完成准备、预测和结果汇总，在此基础上尽量控制完整 E2E 的单格 APE。

本计划沿用同主题活动窗口，不另建并行计划。plan 只记录任务和判据，当前实施资格放在 status，实际行动与证据放在 log；已有代码改动、数据和运行任务保持原位。

## 1. 本轮交付什么

本轮优先级为：三条主线的自动化完整可用 → 统一实验验证 → 依据机制收敛误差。自动化是必须完成项，单格 APE 尽量低于 10% 是精度目标，不以无限补采或逐格补偿换取数字达标。

用户最终应能完成同一件事：提交一份输入，预览准备和预算，运行整组目标，得到完整 HTTP 预测及成本适用范围；中断后沿原任务继续。下文的阶段是实现和验收顺序，用户不需要按阶段操作。两款 Qwen 和 KT 各自都要证明这条流程可用，不能用其中一条的成功代替另外两条。

| 主线 | 必做范围 | 边界 |
| --- | --- | --- |
| SGLang＋Qwen3-8B | 同机 TP1、2、4、8；每个 TP 下的 HiCache 配置预测；TP 与 HiCache 同时变化 | 模型、dtype、框架后端和输入请求保持可比 |
| SGLang＋Qwen3-32B | 同机 TP2、4、8 及相同的 HiCache 能力 | TP1 先检查完整部署可行性，放不下就明确排除，不为纳入矩阵改用另一种量化 |
| KT＋DeepSeek-V4-Flash | 固定当前单 NPU 部署，预测 CPU 推理线程数、NUMA 线程池数和专家卸载数量变化 | 沿用现有模型及量化路径；先固定专家放置策略和其他执行设置，不附带扩展 KT 的 TP／EP |

两个 Qwen 模型各自使用对应模型的 base。本轮不要求从一个模型的 base 直接生成另一个模型的预测。

给定兼容的运行环境和模型权重后，用户只需提供模型、base 配置、workload、目标集合、运行资源和预算。正式流程自动完成：输入与资源检查、base 采集或复用、共享成本准备、目标预测、结果比较及导出。搜索在其上消费同一份预测结果；实验模式再独立完成预定目标的正常实测和 APE 汇总。

本轮不包含新平台适配、DP／PP／多机、生产并发和长期稳态、自动安装驱动、重新设计资源报价、完整问答质量评测，也不默认重跑历史大搜索。NodeScale 和现行静态回放保留。

## 2. 开始实施时先确认的事实

实施前核对当前分支、已有修改、三条主线的真实入口和可复用资产，再确定具体设备、请求与累计预算。已有资料只能作为基线，不能替新增 TP 或 KT 的预测授予运行资格。

重点核对以下条件：

- 两款 Qwen 的权重、HF 几何、tokenizer、现有 SGLang 镜像与注意力后端；TP4／8 的注意力头、KV 头、FFN 与词表分片是否适用，原生部署能否正常运行。
- 物理卡组与互联拓扑、驱动和 runtime、CPU 可见集合、NUMA、可用 RAM、模型盘与临时文件空间。先看完整模型、KV、workspace 和通信缓冲，不能仅以权重文件大小判断可运行。若明确的容量下界已证明放不下，可以直接记录排除依据，不要求先制造一次 OOM。
- KT 的实际安装来源、镜像、W8A8 与 GGUF、CPU 专家后端及当前服务设置；已有运行资格不等于已有采集和预测适配器。
- 现有来源和独立成本的实际模型、TP、量化、硬件及计时口径。合法来源优先复用；旧数据和旧预算原位保留，不隐式复制其他项目资产。
- 当前是否有其他设备任务或维护者修改共享文件。设备采集继续严格串行，不停止、删除或接管他人的服务。

## 3. 自动化要达到的使用方式

### 3.1 用户输入与应用流程

| 用户提供 | 流程负责 |
| --- | --- |
| 模型、框架、runtime、base 配置或已采来源 | 检查声明，选择对应适配器，采集或复用 base |
| workload 与正式窗口 | 核对实际 tokens、请求数、输出规则及准备状态，不静默截断或改写请求 |
| 一组 TP／HiCache／CPU／专家目标 | 生成目标工作、依赖和资源需求，不读取 target 真值 |
| 性能库及共享采集预算 | 读取已有选择，识别实际缺口，复用合格独立来源，必要时小型补采、去重入库并更新相关响应 |
| 运行资源、输出目录和预算 | 设备等待、资源限制、累计用量、失败记录、安全停止和恢复 |
| 搜索约束与已有报价 | 在声明的有限候选中比较完整耗时和资源，保留无解、缺项和不支持 |

CPU 参数只保留一份正式输入，原生参数由适配器映射。线程数不能借用 tensor_parallel 字段表达，专家数量也不能藏在模型名字中。具体字段在阶段 A 连同生产者、消费者一起确定，不另外维护一份与代码不一致的 schema。

应用预测不要求用户手拼性能包、逐个启动校准、搬运 manifest 或串联中间命令。缺口应先按整组目标归并，再选择最少的共享采集。相同缺口没有新证据时停止重复补采，保留可读原因；预算不足或未知工作不填成零成本。

每条主线交付一份可直接提交的请求示例，说明用户需要修改的模型路径、设备、workload、base 和目标参数。准备预览要列出将复用什么、还缺什么、可能启动哪些采集及预算；执行结束后给出各目标结果或具体停止原因。不能要求用户根据内部响应名自行决定怎样补采。

三份示例分别覆盖 8B 的 TP1→2／4／8、32B 的 TP2→4／8，以及 KT 的线程／池／专家联合变化；Qwen 示例各包含一个同时改变 TP 和 HiCache 的目标。它们调用相同的正式入口，不要求先运行矩阵脚本。正常实测是实验选项，普通预测不因此自动采集所有 target。

新增参数要贯穿 CLI、计划预览、本地面板、运行记录和结果导出。面板继续调用正式 workflow，任务句柄不代替容器和采集账本；不为三条主线各建一套脚本系统。

### 3.2 实验与应用分开

矩阵、留出、预选实测条件及跨任务汇总放在上层实验编排，复用正式 capture、predict、measure 和 search。用户可一次提交实验声明，由编排自动运行预定条件并生成评分，不需要逐格手工操作。

正常实测关闭 profiler、probe、region 和 snapshot，只在预测结果之外评分。target diagnostic 只用于独立结构核对。两者都不能作为本次预测输入、成本训练来源或误差补偿依据。

本窗不要求建设新的实验管理平台。已有面板负责预测、搜索、维护和查看结果；实验编排优先收紧已有示例入口，避免新增第二套设备生命周期和业务参数语法。

### 3.3 复用、停止与恢复

- 同输入重复运行，复用已完成 base、合格独立采集和现行模型；实际依据与复用结果可查。
- 停止只回收本任务的进程树和容器，用量、失败和已完成事实保留。服务刷新或重启不重复启动 worker。
- 机器或 worker 中断后，根据原记录检查实际资源再继续。恢复保证采集成果与账本不丢失；尚未完成的仿真可以重算，不承诺任意节点原地续算。
- 不同业务输入或需要保留独立报告时使用独立输出；沿用输出的更新行为必须明确。只读选择和显式维护继续分工，不扫描全部历史自动训练。

## 4. 建模方法和职责

### 4.1 共同框架

原始 DAG 只来自所选 base。目标结构阶段接收已解释的源依据、目标配置和 workload，声明工作量、依赖、资源及条件分支；成本阶段解析可迁移引用和独立响应，再由同一时钟推进执行。

base 只迁移已证明工作不变的成本；变化工作使用独立数据和离线模型，不直接复制带等待的源包络或用 target 残差补数。HiCache I/O/control、Prefill、Decode、真实 CPU gap 与采集额外开销分别归属；采集开销有依据时单独校正，不把所有 gap 一起删除。

结构规则不读取回归参数，成本提供者不创建操作或改变策略。时间相关的接受、等待、超时、取消和释放都在实际执行时触发，不先生成理想路径再修补耗时。

框架差异留在适配器。KT 虽由 SGLang 服务承载，也不能套用 Qwen dense、FIA 或 HiCache 的执行规则，更不能用空 HiCache 假装完成 KT 接入。两个实际消费者需要的装配差异可以抽出，共同核心不按框架名增加调度分支，不恢复旧 KT dense/Torch 链路。

### 4.2 Qwen：TP 和 HiCache 的联合变化

根据实际模型与目标 TP 推导参与者、局部分片、KV 页字节、必要通信与结果依赖。支持集合可明确声明为本轮 TP1／2／4／8，算法不能为每个 TP 配专用模板或倍率。先验证分片约束与物理部署，再赋予支持资格。

先在相同逻辑 KV token 容量下比较 TP，随后验证缓存容量、页大小、写入、回载和文件预取策略变化，最后检查联合变化。保持已有的设备／主机／文件容量、页宽、写策略、预取门槛／超时及四向带宽配额能力；实验只取代表组合，不据此收窄正式支持字段。相同逻辑容量不表示相同每卡显存或相同资源费用，报告应给出两种口径。

保留各 rank 自身的 CPU／设备前沿和必要 peer 依赖，不能把 base 已有 rank 数当成目标上限，也不能把一个 rank 的 CPU 残余复制给所有新 rank。闭合区域响应已包含的通信不再另行收费；需要单独建模的通信必须先说明计时边界。

跨 TP 可以使用目标 TP 的小型共享独立性能数据，并不承诺仅凭 TP1 的耗时就直接推得 TP8。卡组和拓扑属于测量条件，不能只用“卡数翻倍”解释通信变化。

### 4.3 KT：资源数量与实际工作量分开

当前原生参数需要区分：

| 变量 | 含义 | 预测需要保留的信息 |
| --- | --- | --- |
| kt_cpuinfer | CPU 推理线程总数 | 实际线程、可用 CPU、绑核与内存带宽条件 |
| kt_threadpool_count | NUMA 线程池数量 | 池与节点、线程分配、内存放置和必要汇合 |
| kt_num_gpu_experts | 每层 NPU 驻留的路由专家数量 | 每层驻留集合，及其余专家的 CPU 执行路径 |

专家放置规则先固定。仅改变专家数量时，也要知道哪些专家留在 NPU；不能认为所有专家被均匀访问。记录 base 每层实际路由及 token—expert 工作分布，按目标驻留集合推导 CPU／NPU 工作，保留 shared expert、路由、数据交换、结果合并和同步的必要边界。CPU worker、NPU 和 HTTP 的身份、时钟及因果应能配对；仅按时间接近猜测的关联不授予结构资格。

卸载专家总数不等于 CPU 实际工作量。Prefill 按专家聚集的多 token 计算与 Decode 的小批次访问分别建模，不能只用“剩余专家比例”或“线程反比”缩放耗时。CPU／NPU 可以重叠，结果通过依赖汇合，不简单相加。

不同卸载配置可能改变数值、输出或后续路由。目标路由只用于实验核对，不用于生成预测：先检查配置变化下沿用 base 路由的假设，再用未参与开发的文本检验误差。若只能完成给定 base 路由下的条件预测，应明确标注，不能把路由漂移丢给一个残差倍率，也不能靠读取 target 路由完成本窗。正常验证必须使用原生路由；强制固定路由的回放只能作诊断，不能替代真实请求的精度结果。

保持必要的语义粒度。按 MoE 批次、专家工作分布与资源池组织工作；只有会改变交错、同步或成本的内部边界才展开，避免每 token×每专家×每层全面展开。CPU 时间、阻塞等待、CPU↔NPU 传输和父区域计费分别归属。

首轮采用显式 eager、关闭调度重叠的串行 KT 设置，base、独立采样与正常对照保持一致；不能将该范围写成已经覆盖原生 NPU graph。先保留原生 submit／combine 端口和每层路由分布。若一个 MoE 区域内部没有对外的交错，可用包含 CPU／NPU 重叠的闭合响应计费，不必先重建全部专家任务；它不能与内部 CPU、传输或 NPU 成本叠加。出现跨区域的资源交错时才拆开相应工作与依赖，不能用闭合耗时遮盖配置引入的并行变化。

### 4.4 独立成本和资源报告

变化工作优先使用已有合格独立事实；不足时构造有界共享采样。计算、I/O、通信或 CPU 专家响应按实际工作种类维护，特征包括必要的 shape、字节、token—expert 分布与资源数量。参数来自独立观测，形式保持整体可解释；不把每个线程／专家组合做成专用成本表或完整 target 身份模型。同 TP 的 KT 目标仍可能有不同资源和工作量，不能因为现有选择按 TP 导出就忽略这些变量，也不能用逐目标复制模型包解决。

先检查测量口径和结构，再判断是否真缺数据。一次采样尽量覆盖多个特征点和响应；不设独立微负载实验阶段，也不为精度临时逐格追加 self 数据。更大矩阵只用于检验，不能自动成为训练集。

成本报告区分：工作未变而沿用 base、使用独立观测覆盖范围内的模型、带明确假设的外推，以及缺少数据。记录模型实际使用的变量、数据来源和适用范围；新增 TP 的通信条件、KT 的 CPU／NUMA 条件不能只靠相同 shape 认作已覆盖。外推结果可以展示，但不得记成已有实测覆盖。

资源继续采用三级预留容量和四向带宽的既定口径。跨 TP 按整组重新计算权重分片、KV、缓冲、文件与链路预留，不能把一个固定的每卡权重预留用于所有 TP，也不将组共享主存和文件服务按 rank 重复计量。KT 报告 CPU 核数、线程、NUMA 和主存需求，CPU 暂作资源约束，不擅自新增 CPU 或算力单价。

KT 的有限搜索先在声明的 CPU、主存和设备约束内按完整 HTTP 排序，报告可行性和耗时，不套用 HiCache 的七项报价，也不把无法报价填成零费用。Qwen 保留既有报价口径；本窗不要求两种框架之间按一个价格比较。

## 5. 分阶段推进

阶段按完整业务链交付，修改联合相关源文件，不按文件或单个缺口拆成一轮。实现期间静态联查，相关生产者与消费者基本齐备后统一构建和代表输入检查。每阶段集中审查、整理、分层提交推送后，才形成下一阶段起点；不为每格或每次小修重编译、写日志或提交。

推进顺序为：共用入口和最小结果 → Qwen 扩展 → KT 扩展 → 三线统一验收。B／C 的正常测量可在公共设备队列中继续，后续代码工作不必等所有测量结束；阶段交付仍须先达到各自的功能和代表验证要求。等待设备、实际运行和代码处理时间分别记录，不按已经花了多久估算完成比例。

### 阶段 A：三条主线共用入口，并取得最小完整结果

1. 盘点可复用资产与实际资源，确定三条任务输入及 CPU 参数的唯一归属；生成待执行清单和预算预览。
2. 打通框架／runtime 装配，让 CLI、采集、性能准备、面板和报告共同识别 KT。消除公共请求与 C++ 装配只容纳 SG cache 目标的限制，保留已有 SG 行为。
3. 为 KT 补最小语义观察、manifest、独立性能响应和共同执行程序。观察实际路由、CPU 池、NPU 计算、必要传输／同步与 HTTP 边界，默认轻量采集、不开 snapshot。
4. Qwen 两线复用已有支持范围各完成一个真实任务；KT 从当前已能启动的固定配置出发，取得一个完整正式 HTTP 预测。至少有一次必要准备由流程自行完成，而非手工拼成本文件；已有事实不故意重采。
5. 验证一次停止／继续和合法复用，保留预算；明确环境缺失、缺成本和不支持，不能把短请求能生成当作 KT 已会预测。

交付：三条真实任务均经正式入口取得完整预测，准备和来源可追溯。精度可以未达标，但 KT 仅有进程或生成响应不算阶段完成。

### 阶段 B：完成两款 Qwen 的 TP／HiCache 自动预测

1. 联合源解释、参与者与分片、控制、独立成本选择、采样、资源和结果，完成所有预定可行 TP。
2. 扩展 HiCache 目标配置及联合变化，处理必要的 host／file 回访、超时、释放和分配可行性；复核已有“实际失败却预测成功”反例，不写 ratio 特判。
3. 把新目标接入整组自动准备。TP8 使用全部八张卡时也遵守设备独占与串行采集，实际卡组和通信条件完整记录。
4. 完成主 base 预测、换 base 的正反向及少量独立结构核对，检查各 rank 工作量、必要依赖和成本计费范围。

遇到 HTTP 已完成、发送函数尚未返回等异步边界时，先核对事件含义、源成本切分和目标依赖，保留真实发送与 CPU 返回的区别。不能将负间隔归零、删除尾部成本，或把这类解释问题当作缺数据继续补采；共同解释规则变化时同时检查两种框架的消费者。

容量下界检查通过只表示没有被该检查排除，不代表实际分配一定成功。权重下界不可行、原生启动／请求分配失败、缺成本和预测完成要分别报告；已有紧主机池反例不能仅靠新增设备容量检查就记为已解决。

交付：两款 Qwen 的全部声明预测完成结构和成本绑定，各合法 TP 实际作为 base 与 target 出现；每款至少一个新增 TP 的正常对照，以及限定范围的独立结构核对完成。非法部署、成本缺口与合法预测失败分别保留。

全量正常评分集中在阶段 D，沿用已声明条件、顺序和重复，不在 B 收尾和 D 各采一遍。已启动的正常任务可继续运行，阶段 B 交付前检查其所有者、恢复信息和预算；其未完成或未达标部分不能写成已验收。这样阶段 C 的代码实现不必等待每一个正常窗口，但必须以上述功能与代表验证完成、审查和提交推送为前提。

### 阶段 C：完成 KT 的 CPU／专家变化自动预测

1. 根据原生运行和资源检查确定可行线程、线程池与专家数量，不把环境变量可填写当成能力已支持。
2. 按目标池与驻留集合生成工作和依赖，保留 base 路由来源，补充所需的有限独立成本与自动采样；同时检查 Prefill、Decode 及 CPU／NPU 重叠。
3. 将单项与联合目标接通正式请求、面板、共享准备、资源约束、搜索及实验评分；不留下只在数据目录运行的替代流程。
4. 从另一组合法 CPU／专家 base 做反向预测，验证规则不依赖开发时的 64 线程／32 驻留专家；核对 NUMA 绑定是否实际生效。

线程、池和驻留专家属于工作变量；系数来自共享独立测量。不能只为每个目标注册一份专用模型就称为泛化。报告应说明哪些响应可以跨资源配置复用，哪些测量条件必须一致，以及没有覆盖时会怎样停止。NUMA 核对使用实际 worker 的 CPU／内存放置证据，环境变量和启动参数本身不算生效证明。

实施优先补齐现有 KT 工作规则与采样链的真实覆盖，不重建第二套 MoE 仿真器。主集合共用同一小型独立采样，先覆盖线程、池和驻留数量的代表范围，再检查全部目标；反向 base 不作为独立成本训练数据。每次服务首次真实 forward 后记录一次 worker 的 CPU 亲和性和 NUMA 页面／策略摘要，不能用快照采集持续干扰请求；绑定失败时明确保留运行条件与限制。有限搜索使用资源上限内的耗时排序，不增加 CPU 报价。

交付：KT 的全部声明预测完成结构和成本绑定，支持范围内的 CPU 和卸载变化、失败及路由假设可见；至少一组改变线程和专家数量的联合预测经正常对照，NUMA 与路由假设有实际核对。其余全量正常窗口同样在阶段 D 统一评分，不重复采集。

### 阶段 D：三线统一验收与有限精度修正

1. 以同一候选程序及明确的独立成本选择完成三线声明面板的全部预测和正常对照。复用 B／C 已采结果，补齐剩余窗口；代码或模型变化时重算受影响预测，不因此重采兼容正常条件。开发期间用代表点，本阶段收尾核对完整清单，不得以同 TP 对照掩盖跨 TP 误差。
2. 用预先声明的新请求完成三线留出，自动采集正常对照并评分，保持训练与评价分开。若依据结果修正，该批转为开发证据，不能继续称未见验证。
3. 对大误差先用工作量／依赖／初始化和成本来源定位，再做一批有机制依据的修正。没有新解释时停止重复采样；误差仍超标的格子连同原因和影响交付。
4. 复用现有 315 格作最终一次纯预测回归，并用一个既有大 workload 的少量目标核对时间、内存和报告量。不重新采完整历史矩阵，不默认四组全扫。
5. 完成三线的浏览器真实流程、CLI 一致性、复用、服务重启、停止／继续、缺项和导出检查。新增能力不要求用户改内部 JSON 或转到专用脚本才能使用。
6. 统一整理代码、配置和文档中的职责、重复和失效说明；稳定接口进入正式操作说明，实际结果归入主工作流后关闭本窗口。

交付：三条主线自动化、实验结果和使用说明齐全，功能完成与精度资格分别说明；不以历史成绩或个别漂亮格子代替整组结果。

## 6. 有界实验安排

### 6.1 Workload 与准备状态

Qwen 开发优先使用现有独立请求和共享前缀回访两类输入，初始每类 12–20 个正式请求，16–32 个输出 tokens，另有少量准备。覆盖驻留、主存回载和文件预取；采集前根据实际工作集验证场景是否触发，不在看到误差后挑有利负载。

KT 先用两类短序列区分计算规模：较短输入与 Decode、较长输入与 Prefill；每类初始 2–4 个正式请求，32–64 个输出 tokens，另有 1–2 条准备。具体长度从已准备文本和原生耗时估计确定，先保住完整流程，再决定是否值得增加请求数。

三条线各保留一份未用于开发的新请求序列，其中至少一组包含 64-token Decode。优先取已具备来源的真实文本子集，保留选取规则、tokenizer 和截断说明。不同模型分别记录实际编码；固定请求历史，不将上一配置生成的回答改写进下一配置输入。

workload 的数量、长度、正式边界、准备／排空、输出规则和首次准备状态在正式预测与正常实测前保存。改变这些条件需要对应 base；不裁剪图节点或略过执行路径控制规模。KT 的 NPU graph、缓存及初始化按实际执行设置记录，不照搬 Qwen eager 的含义。

### 6.2 Qwen 面板

每个模型先用 TP2 作开发 base，在两类 workload 上分别预测所有合法目标 TP 与三类 HiCache 代表配置：参考驻留、主存回访、文件预取。具体原生参数在预检后按模型工作集确定，覆盖必要的容量、页宽、写入和预取策略，不要求做它们的完整笛卡尔积。

随后在回访 workload 上，让其余合法 TP 各做一次参考配置的 base，预测全部合法 TP 的参考配置。这样每个 TP 都实际作为 base 和 target 出现，并复用主面板的正常真值。

按 8B 四个 TP、32B 三个 TP，主 base 分别产生 24／18 个预测，参考配置换 base 分别增加 12／6 个。不同 base 对同一目标的预测分别计数，但共用一个正常条件。同配置指部署与配置均相同，只改变 HiCache 也属于跨配置。本轮面板与历史的 60 格跨配置实验不同，最终数量统一列在 6.4。

数字由实验声明推导，不进入算法或输入校验。若 32B/TP1 通过预检，在运行前按同一组合规则扩展声明；不可行时说明排除原因。已声明合法配置的预测失败不能从分母删除。源 HiCache 变化只检查下述代表，不扩成所有 base×target 的完整缓存矩阵。

配置名字不作为命中层级的证据，逐请求核对设备命中、主存回载与文件接受量。若既有代表组合混合主存和文件路径，每个模型另预定一个关闭文件后端、主存足以容纳工作集的 TP8 回访目标，复用 TP2 base。这样单独验证主存路径并覆盖联合 TP 变化，只增加两个预测和两个正常条件，不追加 base，也不根据误差挑点。

补充两种源缓存配置：8B 从 TP4 文件配置预测 TP1 参考配置和 TP8 纯主存配置；32B 从 TP8 纯主存配置预测 TP4 参考及文件配置，各加一个同配置预测。新增六个预测共用主面板正常真值；这两份来源也作为原 TP2 base 对相应目标的独立结构评价数据，一次采集同时检查联合变化和源缓存差异。选择依据是执行路径差异与采集复用，不按误差挑点；不将其称作留出验证。

### 6.3 KT 面板

初始候选先围绕已运行过的 64 线程、8 线程池、每层 32 个 NPU 驻留专家展开。以下是拟检查的档位，不是已支持资格：

- 总线程数先考虑 16／32／64／128，线程池固定为可用的八 NUMA 布局。
- NPU 驻留专家数先考虑 16／24／32，固定现有 prefix 放置策略；卸载量由真实模型与驻留集合计算。
- 在同线程数下增加合法的线程池变化，例如 32 线程／2 池和 64 线程／4 池，与主集合中的同线程目标作比较。核数不足、原生分配限制或绑定不生效的组合先处理，不制造表面合法的档位。

若上述档位均可行，主集合为 12＋2＝14 个不同配置，两类 workload 共 28 个预测及 28 个正常条件。可以根据预检缩小或调整档位，但不得在看到误差后删除难点，或只保留单一线程／卸载配置交付。

反向验证预选 32 线程／8 池／24 驻留专家作第二种 base，在两类 workload 上分别预测 64／8／32 和 16／8／16，共增加四个跨配置预测，复用主集合的正常真值。若预检发现该 base 不可用，在正常评分前选择另一组同时改变线程和专家数量的合法配置，保留调整原因。

复用现有矩阵入口时，每份 base 会自动附带同配置预测；两份反向 base 因此再产生两个同配置检查，无需新增运行规则或正常条件。在初始档位均可行时，KT 共 34 个预测：30 个跨配置、4 个同配置，对应 28 个正常条件；参考锚点增加两次重复后为 30 个正常窗口。三条线合计的留出正常条件初始不超过 8 个；KT 留出必须仍包含配置变化，不只做同配置回放。

### 6.4 正常实测与采样控制

同一目标条件的正常结果供不同 base 预测共同使用。每条件初始一次，在看误差前为三条线各指定一个参考锚点，总共各三次；已有完全匹配的独立正常数据可以复用，不必重新启动服务证明流程。

一次性正常结果报告波动限制；需要讨论小幅排名差别时用已声明锚点或少量预定重复，不临时追加慢样本让预测显得更准。本轮不追求证明全空间真实最优，也不要求每个 workload 都找到明显收益。
