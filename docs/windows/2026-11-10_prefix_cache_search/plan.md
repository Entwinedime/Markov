# 长文档前缀复用与 HiCache 全量搜索

开始日期：2026-11-10。

目标：用真实合同和审阅问题构造三个具有缓存压力的场景，把三级缓存容量及四向传输带宽纳入性能预测和资源计价，完整扫描声明的资源与策略面板；只采集三份 base，并正常实测每组预测最好、最差两个点，回答缓存配置在什么条件下能明显改变完整请求耗时。

## 1. 这轮要回答什么

场景是多人交替审阅长合同：同一合同被问及不同条款，每个请求都包含完整合同。合同正文作为相同前缀，问题放在正文后面。命中缓存可以省去正文的重复 Prefill；缓存放不下时，需要回载或重新计算。

重点是让不同合法配置在缓存保留、传输等待和重算之间产生有依据的差别。请求多不等于复用强，存在公共前缀也不等于它能在再次访问时保留下来。场景选择首先核对这两个条件，不通过看到 target 实测后更换请求来制造收益。

本轮区分三个结论：全量预测是否完成、两个端点预测是否准确、两个端点的正常耗时是否有明显差距。它们分别报告，不能用流程完成代替优化有效。

## 2. 范围与实验口径

- 沿用 Qwen3-32B/BF16/TP2、Ascend 910B3、SGLang eager/FIA，以及现有文件缓存后端；以相同硬件为上界，搜索三级缓存配额和四个方向的可执行带宽配额。
- 请求按确定顺序串行执行。完整正式 HTTP 保留 Prefill、Decode、HiCache I/O/control、CPU gap、未归属控制和正式请求期间的首次准备；后台排空、启动、准备请求另报。
- 三阶段预测职责保持：base 提供源执行依据，框架规则生成 target 工作与依赖，独立性能模型及合法源成本迁移提供数值。预测不能打开 target 正常结果。
- 优先复用正式入口和已有性能库。设备成功运行的计划是三次 base 加六次正常测量；不增加 target trace、微负载、正常 base 对照或独立成本补采。
- 研究构造、枚举与端点选择放在现有搜索 example；不为三个场景增加核心分支，不新建搜索算法平台、独立测试工程或第二套执行器。
- 本轮不扩展并发、模型、平台或新的缓存淘汰算法；接通有限第三级容量和带宽资源约束，不恢复已结束的历史搜索任务。KTransformers、NodeScale 和既有诊断保持。

## 3. 数据与三个场景

### 数据来源与选择

使用 [CUAD 官方数据](https://www.atticusprojectai.org/cuad/)及其[问答发布](https://huggingface.co/datasets/theatticusproject/cuad-qa)。CUAD 包含 510 份商业合同及 41 类审阅条款；保留原始合同、问题、答案和标注身份。选择实际携带完整合同的记录，不把段落问答误当全文问答，也不把同一问题的多个答案标注当成多个问题。

选择方法在搜索前确定：固定种子 20261110；优先选用目标 tokenizer 下全文约 4K–7K tokens 的合同，保留完整正文。固定模板为指令、合同全文、本次问题，编码后整个输入不超过 7,168 tokens。若长度不合适，选择其他完整合同，不截去回答所需证据，不拼接文档或重复正文扩长。

每个场景有 512 条正式请求，每个合同内的问题互不重复。按原有问题保留有答案和条款不存在的情况，报告各自数量；不凭模型生成的答案判断数据是否适合。文档长度及可用不同问题数必须从原始记录核对，下面的构造数量是实施目标，不是已确认的数据统计。

| 场景 | 构造目标与访问顺序 | 要观察的差别 |
| --- | --- | --- |
| 多合同交替审阅 | 16 份合同，每份 32 问，共 512 条；各合同轮流提问，再进入下一轮 | device 留不下整个工作集，较大的 host 有机会保住更多可复用前缀 |
| 大工作集长距离回访 | 32 份合同，每份 16 问，共 512 条；按合同轮流访问 | 回访距离及工作集增大，host 淘汰、文件回载与重算更可能影响结果 |
| 项目分组切换 | 优先沿用上一组完全相同的 512 条问答；合同分为每组 4 份，各组每次处理每合同 4 问后切换，经过其他组后再回访 | 全局工作集不变，只改变局部性，观察阶段性热点与写入、回载策略的关系 |

前两组能共享的合同优先共享，并匹配长度分布。第二、第三组保持逐请求内容、生成量和总问题集合相同，只改变顺序；不能把两者的差异归因于数据集变化。三个场景都是合同审阅中的访问模式，不称为三个独立数据集的泛化验证，也不声称请求顺序来自真实线上日志。

若长度合适的合同没有足够不同问题，允许在搜索前增加合同数、减少每合同问题数，保持每组 512 条及原访问模式，并一次性记录调整与实际工作集。若调整后不能形成三种可区分的访问模式，或无法得到足量原始问题，就明确数据构造未完成，不复制问句凑数。

### 输出、准备与初始状态

本轮沿用现行预测合同：`ignore_eos=true`，正式请求固定生成 32 tokens，关闭 thinking，其他采样设置各条件一致。这个长度是本轮有界性能实验设置，不代表 CUAD 原始答案长度或问答质量评估。记录参考答案长度与超出 32 tokens 的比例；不临时退回 8 tokens 来放大收益。

每组另有 8 条相同的准备请求，使用与正式合同不重合的输入，输出各 8 tokens；输入长度为 256、512、768、1,024、1,536、2,048、512、1,024。准备后排空后台；不预先装入正式合同。各条件新建私有 KV 文件目录、相同空应用缓存及 `kernel_cache_initial_state=empty`，记录实际采用的启动环境。操作系统文件缓存和驱动准备不能假称完全清空；不清理他人共享缓存。完整正式耗时仍含正式长规格的首次准备，本轮不称为长期稳态。

### 开始设备运行前要核对的机制

离线统计完整前缀树、最大可复用 token 数、不同正文工作集、首次访问比例、回访距离与局部活跃文档数，按原生 KV 几何换算字节。去重的是共同前缀，不是给每条请求重复计整份正文；device 与 host 可能保留相同 KV，也不能简单相加当成独立可用容量。

这些统计只表示复用潜力和容量压力，不是真实命中率或性能收益。需要能解释三组在声明容量下为何有回载或重算差别，不能用预测收益筛选文档或重新安排请求。

## 4. 完整配置空间与比较预算

搜索变量和价格系数分开。缓存容量、四向带宽和执行策略组成 target 的资源条件，决定会不会命中、哪些工作需要执行及何时完成；价格只用于计算资源费用和筛选，不进入性能预测。不能只增加七项收费字段，却让所有候选仍按同样的容量和速度执行。

每组完整枚举下面两个明确的面板并取并集，不做随机抽样、不提前按预测耗时停止。资源面板联合改变七项资源，策略面板保留原来的参数范围；本轮不枚举所有资源和策略轴的联合笛卡尔积。若全部相乘，每组会有 354,294 个组合，三个场景超过一百万点，不能继续按原来的时间估计执行。

### 容量与带宽资源面板

| 搜索维度 | 三档取值 |
| --- | --- |
| device KV token 配额 | 8,192 / 16,384 / 32,768 |
| host 与 device 池比例 | 1.32 / 2.5 / 4.49；报告按原生规则生成的实际 GiB |
| 第三级缓存总容量 | 16 / 32 / 64 GiB，所有 TP rank 合计 |
| device → host 带宽配额 | 该方向参考服务能力的 25% / 50% / 100% |
| host → device 带宽配额 | 该方向参考服务能力的 25% / 50% / 100% |
| host → 第三级写带宽配额 | 该方向参考服务能力的 25% / 50% / 100% |
| 第三级 → host 读带宽配额 | 该方向参考服务能力的 25% / 50% / 100% |

七个维度分别枚举，共 `3^7 = 2,187` 点。四个方向各自有参考值，不能假定读写相同；每个值明确是每 rank 还是整组共享，并统一换算成整组 GiB/s 计价。参考服务能力来自已有独立数据及其工作边界，不能把包含 CPU/轮询的整段响应简单除以字节就称为物理链路带宽。已有资料无法给出适用的参考值时，保持该能力待补齐，不能猜一个参考值来启动全量扫描。

四向配额不能超过实机能力。共同端口或存储介质上的竞争约束在枚举前明确，例如 SSD 读写不能各自独占同一份已售出的总吞吐。预先可证明不符合共同资源约束的点保留不可行原因，不伪造互不竞争的四条无限独立通道。

本面板固定 page 64、write_through_selective、wait_complete、prefetch_threshold 512，专门观察容量和带宽的联合取舍。host 配额仍通过原生 ratio 设置，不能把 ratio 直接当容量或价格。

### 执行策略面板

第三级容量固定为 64 GiB，四向带宽均为各自参考配额的 100%，完整保留以下参数：

| 参数 | 取值 |
| --- | --- |
| device KV token 配额 | 8,192 / 16,384 / 32,768 |
| host 与 device 池比例 | 1.32 / 2.5 / 4.49 |
| 页大小 | 32 / 64 / 128 tokens |
| 写入策略 | write_through / write_through_selective / write_back |
| 预取门槛 | 128 / 512 / 2,048 tokens |
| 等待设置 | wait_complete；best_effort；timeout 为 0.01 / 0.1 / 0.5 / 2 秒 |

timeout 采用固定秒数，per-ki-token 项为 0，base 与 max 同值；其他两种策略不重复枚举无效的 timeout 参数。本面板为 `3 × 3 × 3 × 3 × 3 × 6 = 1,458` 点。两个面板有 9 个相同配置，按全部实际参数去重后每组 3,636 点，三个场景共 10,908 个声明条件；资源不可行项仍保留分类。这个数不是所有资源与策略交互均已覆盖的证明。

统一 base 采用 device 32,768、host ratio 1.32、第三级总容量 64 GiB、四向参考配额 100%、page 64、write_through_selective、wait_complete、prefetch_threshold 512，已包含在两个面板中。`max_prefill_tokens` 设为 8,192，其他非搜索参数保持一致。这个 base 用于采集及定义小时费用上限，不是已知最优配置。

设备准入检查使用原生页对齐、输出预留与额外一页的严格容量条件，不能只比较输入长度和池大小。所有候选还须满足每 rank 64 GiB device、整组 128 GiB host 的共同部署上限；最终以原生 KV 预留和明确固定预留核对，不从 token 档位直接猜物理内存。

| host 容量 | 1 | 每 GiB·小时 |
| 第三级 SSD 容量 | 0.02 | 每 GiB·小时 |

这些数是暂定的资源分摊权重，不是七项已经核实的市场报价；尤其 PCIe 与 SSD 带宽之间的 1:10 没有直接报价验证。容量溢价量级参考 [HBM/DDR5 市场分析](https://www.trendforce.com/presscenter/news/20251218-12843.html)，容量和预留吞吐分别计费参考 [EBS 计价方式](https://aws.amazon.com/ebs/pricing/)。来源说明估价思路，不为表内每个倍数背书。真实单位带宽价格不同于链路速度，四向单列也不要求人为设四个不同价格。

费用为三项预留容量乘各自单价，加上四个方向预留 GiB/s 乘各自单价；共同物理资源按份额归属，不把同一套餐全额重复收四遍。固定存储预留仍为每 rank device 48 GiB、整组 host 64 GiB，加上原生 KV 池；第三级按已声明的总配额计价，不能因当前尚未写满而免费。128 GiB 容器上限不等于实际计价预留。不计 CPU、整卡算力租价或按字节的流量费，也不将资源分摊称为整机租金节省。

每组先完成两个面板并集的全部 3,636 点，列出成功、部署/准入不可行、缺成本、不支持和执行失败。可证明不可行的点保留原因且不运行假想成功；任何未解决的缺成本、失败或超时都表示覆盖不完整，不能宣称全量扫描完成并进入端点实测。

最好、最差从同一个集合选择：部署合法、预测成功且小时费用不高于该组 base 的候选。按完整正式 HTTP 最小/最大取点，不使用 90% 时间门槛、预测精度或事后实测筛选最差点。并列时均优先较低费用，再按配置名稳定选择。全部并列项保留，不能把平坦结果包装成明确排名；若两个角色重合，只测一次。

完整空间及成本—时间 Pareto 仍要展示，但测量资格只属于上述同预算两个端点。不同费用不等于不公平，比较的是共同预算上限下的可选配置，不能称为两个点费用完全相同。

## 5. 实现方式与成本边界

复用 `examples/hicache_search/run.py` 的候选生成和 enumerate 路径，增加两个面板及按实际参数去重，使用本轮独立 settings 和输出位置，不改写已有实验输入。CUAD 读取、去重与三种顺序属于 example 的数据构造职责，不进入核心或正式 workload 解析器。

首先补齐实际资源能力。第三级有限容量必须同时接通正式 target 合同、预测淘汰及真实文件后端的容量管理，避免只改变统计数字或用磁盘满错误代替缓存淘汰。下层已有的容量/LRU 机制优先复用，不重新发明同职责状态机；各 rank 的容量、索引可见性、在途读取保护及文件回收保持一致。

四向带宽设置必须在执行时影响对应搬运工作的占用、完成、发布和后续依赖，同一仿真时钟继续决定预取和超时分支。CPU 发起、查询、索引、固定准备、Prefill/Decode 不能随着链路速度一起缩放，也不能先预测一份结果再按带宽比例乘完整 E2E。已有闭合响应未分离固定控制与传输的部分，要先明确工作边界和证据，不能直接除以带宽倍率。

真实确认必须采用与预测相同的资源配额。若通过软件限速，应在同一数据通路定义配额，保留实际阻塞与完成边界，并明确它是服务配额实验，不是假装更换了 PCIe 或 SSD 硬件；简单在 HTTP 末尾补 sleep 不合格。SSD 读写共享介质、buffered 文件缓存及双向 PCIe 的原生竞争不能忽略。无法在当前环境忠实执行的设置保持未支持，不能让预测按低带宽而正常测量仍跑原速，也不能只把四向全固定为 100% 后宣称完成了带宽搜索。

现行默认确认逻辑选择 baseline/recommended，不能直接用于本轮。全量结果完整后，在 example 中生成明确的 best/worst 确认清单，复用现有 `confirm.py` 与正式 measure；每条件一次，不启用自动追加重复，不另外测 baseline。报告显式列两个端点的范围，不把现有 recommended 字段悄悄解释为最差。

在捕获长 base 前先核对已有模型的部署、特征、训练来源及范围，特别是 Prefill 长度、Decode 上下文、I/O 页/段数和文件 worker。导出一组只读成本选择，三个场景共享。历史存在某类响应不证明它覆盖本轮工作域；只能使用模型已声明且有依据的插值或外推，不能静默夹到最大长度、填零或按 target 身份借数值。

本轮独立成本采集预算为 0，不开放自动 sampling。出现缺口时先核对是不是合同、单位或过细工作描述错误；若确实缺少独立数据，保留受影响配置和需要的工作范围，阶段资格保持未完成。不能用 base 的采集时长训练变化工作，也不能用最好/最差的正常测量补参数。额外设备采集不属于本轮九次运行范围，需要增加时明确其原因及对本轮范围、时间和用量的影响，不静默加入实验。

三个 base 均采用语义采集，probe 不采 snapshot，不新增 profiler/native 细图输出。三个来源各归一化一次，同一场景的配置复用来源；目标保持独立缓存状态。预测只挂载明确来源、程序、只读模型和输出，正常结果不进入预测容器。

只在需要时修改正式调用链，且必须保持工作定义和已支持框架。相同缺口反复出现时回查逻辑，不逐格增加模板、例外或一串采样 wrapper。

## 6. 阶段与交付

### A. 把数据、声明与编排准备齐

读取 CUAD 原始记录并一次性核对真实全文、不同问题和长度资格；生成三组输入、来源映射及离线复用统计。根据实际可用问答修订构造数量时，在此阶段一次性处理，之后不得按结果换数据。

准备两个面板、七项计价、共同预算、成本选择和端点确认方式；把第三级容量及四向配额的正式接口、同钟执行与真实运行支持一并补齐。联合检查资源合同、适配器、执行器、数据生产者、候选生成、计价及报告，完成相关修改后统一验证；涉及 C++ 时在 modeling Docker 构建并用保留资产和正式入口检查。没有核心修改不重复编译，不新增 test 文件或另跑设备微负载。

完成条件：512 × 3 输入可追溯，顺序对照关系明确；两个面板并集精确为 3,636，base 在其中；三级容量和四向带宽确实同时影响执行和费用，所有可测设置有一致的真实实现。最小容量准入、最大物理预留、成本范围及开销已核对，关闭隐式补采及额外确认。新增资源能力的实现工时尚未估定，不能沿用此前只扩 workload 的进度预估，把接口占位当作阶段完成。

### B. 三份 base 与完整枚举

按场景串行采集三份语义 base，核对真实输入、生成数、完成原因及排空边界。每完成一个来源即保存 manifest 和累计用量，随后用相同成本选择完成该组全量预测。允许 CPU 预测与下一组采集重叠，但不能同时运行两个设备任务。

枚举可按现有机制分批恢复，每个目标仍只属于同一个完整集合；报告汇总全部批次。不因分批反复加载完整来源或无必要地重建相同工作；不为本轮新增泛化缓存管理器。出现缺口时保留失败，不额外采 target 或性能数据来补洞。

完成条件：三个来源合格；全部 10,908 条有最终分类，除明确资源不可行外没有未解决项；三组同预算端点及其预测、七项资源费用、模型来源已保存。此时确定六个正常条件，后续不改模型、请求、初始状态、报价或选点规则。

### C. 六个端点的正常测量

依次运行每场景最好、最差，三个场景交替端点先后顺序，避免固定把最好或最差总放在同一位置。具体顺序在首个正常测量前写入确认清单，不根据已见结果调整。

关闭 profiler、probe 与 snapshot，保持每组相同输入和顺序、定长输出、设备、CPU 放置、容器上限及缓存初态；应用端点各自的三级容量和四向带宽配额并保存生效依据，两个端点的资源配置允许不同。测量不触发 performance 准备。每个点一次，失败保留真实用量，不用 profiler 墙钟代替正常结果，不删除慢样本。

完成条件：六个条件全部成功，逐请求输入和输出工作量相同，完整正式 HTTP 可核对；若端点重合则按角色去重并解释。设备重启或额外重复不在本轮默认额度内，不能用未记录的重跑替换原观察。

### D. 汇总、解释与交付

## 7. 时间、请求与空间预算

本轮仍以完整实验在 12 小时内完成为目标，下载、编码、来源采集、仿真、正常测量及失败恢复都计入；文档制定不计入实验墙钟。新增资源接口与真实限速能力尚未实现，开发工时和新的预测时长不能从原计划推定。下面保留设备额度和总时限，执行前按新范围核对真实开销，不承诺此前的两小时 CPU 扫描预算仍足够。

| 环节 | 计划次数/工作量 | 累计时间额度 |
| --- | --- | --- |
| 数据准备和覆盖核对 | 三组输入、资源生效及整组已有成本检查 | 原定 30 分钟，新增实现耗时另如实记录 |
| base 采集 | 3 次，每次 512 正式＋8 准备请求 | 合计 3.5 小时 |
| 完整预测 | 3 × 3,636 条最终分类，最多两个 CPU 进程 | 原定 2 小时须重估；允许与后续来源采集重叠 |
| 正常端点 | 6 次，每次 512 正式＋8 准备请求 | 合计 5 小时 |
| 报告和余量 | 汇总、检查与异常收束 | 1 小时 |

总共 1,536 条正式输入位置；按 base、最好、最差各运行一遍，实际执行 4,608 次正式请求，加 72 次准备，共 4,680 次请求。三个场景可能共享原始问答，1,536 不是去重后的独立问题数；10,908 个声明预测条件不发送真实设备请求。两个面板去重后逐点保留状态，不能用新增面板结果掩盖原面板缺项。

固定 32-token 正式输出、8-token 准备输出时，总生成上限为 148,032 tokens。输入以上限 7,168 tokens 及八条准备长度计，每次最多 3,677,696 tokens，九次最多 33,099,264 tokens；这只是预算上界，实际按确定输入累计。

base 与 normal 分别最多 3/6 次设备启动、1,560/3,120 次总请求、49,344/98,688 个输出 tokens，wall 额度为 12,600/18,000 秒。失败和启动耗时计入，已有用量不重置；不增加 pilot、自动重复或设备微采样。可接管仍在运行的同一任务，已经失败而需要新启动的情况先记录对九次完整交付的影响，不静默扩量。

预测容器每进程 8 GiB，上限两个，总预测容器额度 16 GiB；设备容器上限为整组 128 GiB，严格单任务。设备启动前核对 CPU、内存和磁盘余量，CPU 任务用进程树回收，设备退出只处理本任务拥有的资源，不清理他人容器和缓存。保持 20% 可用内存余量；无法满足时先降低预测并发。

扩展预测条件后，保留目标调整为 40 GiB：base 不超过 24 GiB、预测/搜索不超过 12 GiB、正常证据不超过 2 GiB、数据与共享模型不超过 2 GiB。临时空间硬预算 192 GiB；启动前应能覆盖剩余预算并保留宿主余量。每个设备任务退出并保存必要日志、记录和 manifest 后，回收该任务私有的运行临时 KV 文件，不把九次的完整缓存目录长期叠加保留；未结束任务及其恢复依据不能提前清除。不给所有 target 展开完整细图，不复制整个性能库或原始数据归档；机器交接所需内容不能为凑预算被删。空间不够则停止并记录，不擅自清除历史数据。

任务自身输出时间与完成事件，设备阶段约每 10 分钟核对，预计接近结束或出现异常时缩短到 2–5 分钟；预测阶段按批完成检查，空闲时不密集轮询。不用高频 agent 唤醒代替任务管理，长任务期间仍响应用户消息。

新增资源能力完成后，先用全量集合中已开始的 CPU 批次核对剩余时间和存储，不额外启动设备 pilot。若全量扫描与后续六点实测明显无法装入总时限，先如实记录时间冲突和缺口，不能默默放宽时间、改成抽样或将部分扫描标为完成。额度耗尽时保留完整账本、成功观察和缺项；不得先看部分正常结果，再删场景、减少问题或换输出长度来称为完成。

## 8. 怎样判断这轮的结果

交付完成要求三份合格 base、完整枚举分类、六个端点正常结果及最终报告齐备；明确不可行的组合计为已解释，不算成功预测。没有未解决候选，才称全量扫描已完成。设备失败、成本不足或预算停止导致缺项时，保持未完成资格并说明下一步所需的最小工作。

精度单独报告六点最大 APE、WAPE 和逐场景端点排序，沿用单点 APE <10% 的期望；没有达到就明确本轮推荐尚不可靠，不通过重新选点或按残差修正完成验收。

每组正常耗时记为 `T_best`、`T_worst`：改善率为 `1 - T_best / T_worst`，加速比为 `T_worst / T_best`，同时展示带符号差值；若实测反序，不把标签或公式交换成正收益。力争出现至少一个改善达到 20% 的场景，作为研究目标而非允许调数据凑数的门槛。

每个点只有一次观察，不能提供波动区间、置信度或统计显著性；预测最差也未必是真实全空间最差。最终只能说全量预测选择的两个端点具有怎样的实测差距，不能称已证明真实全局最优。

全量仅指本轮两个明确面板的并集；页大小、策略和带宽的全部交互没有联合穷举。三级容量和四向带宽的声明、费用、仿真及真实测量缺一项，都不能称本轮资源搜索已经完成。临时价格比例不表示真实账单，改变参考价格后的 CPU 重新排序可以作为敏感性说明，但不能据此重选六个正常点或冒充新的真实确认。

本轮不关闭 radix cache，因此不直接测量开启前缀缓存相对关闭的总收益；得到的是已开启缓存条件下的配置搜索收益。也没有正常 base 对照，不能报告相对默认配置的实际提升。若没有明显差距，结论就是当前场景与支持空间下没有得到明显收益，不能引用其他平台的 TTFT 或吞吐倍数填补本轮完整 HTTP 结果。
