# Markov 项目交付总窗口计划

计划起始日期为 2026-11-19。

完成从**模型、候选配置集和请求 workload 集**到**可复现的性能探索结果**的正式工作流。用户声明采集部署和预算，项目选择代表来源，准备模板与成本，运行各目标并给出性能、证据和适用范围。

## 1. 交付范围

| 交付项 | 完成后能做什么 |
| --- | --- |
| D1 单机多卡性能 | TP、PP、EP、PD 的具名场景和代表性组合，使用同一正式预测入口，由独立成本驱动完整请求。 |
| D2 采样与资产复用 | 根据候选配置和实际工作归并需求，在预算内复用或采集模板及成本，报告仍缺的定义、角色或特征范围。 |
| D3 配置集探索 | 一次提交一个模型、多个配置和多个 workload，得到逐组合资格、TTFT、TPOT、吞吐和可比较的配置排序。 |
| D4 模型、调度与框架适配 | SGLang/Ascend 覆盖具名的真实权重 Dense、MoE 和已纳入的调度机制。第二框架用一个有限但完整的案例验证适配边界。 |
| D5 独立验收 | 用目标真实时间核对执行结构，用独立成本验证性能，发布支持范围、精度、吞吐排序及开销。 |
| D6 可复现交付 | 从干净检出和固定镜像出发，按用户文档完成冷资产创建和换 workload 后的有效复用。 |

单机多卡是主交付范围。多机保留探索定位，原生多节点部署、轻量控制器、新增 speculative/overlap 及多级实际搬运属于后续扩展。批级基线及相对现有工作优势的评估继续搁置。正式支持以原生框架可运行的具名配置为前提，用户按当前合同指定有限输入。

### 首批覆盖责任

S0 将下表收敛为带实际模型、镜像、设备、拓扑、调度选项和输入条件的具名清单。每种机制须有一个能触发其实际工作的例子，组合按原生可运行范围选取。模型、拓扑和 workload 的其他合法组合记录各自的适用条件。

| 责任 | 初选范围 |
| --- | --- |
| 单卡回归与多 rank 基础 | 延续 Qwen3-8B BF16、Ascend、TP1，优先用同一模型和请求族完成 TP2。另选至少一个原生可运行的高 TP 档位，优先现有 TP4/TP8 来源覆盖的档位。 |
| 异构角色与并行 | 非对称 PD 初选 Prefill TP1、Decode TP2，覆盖 KV 与 metadata 交接和源侧释放。PP 选有实际微批轮转的档位，EP 选已可原生运行的 MoE 及其实际路由分布。组合以已知可运行的 TP×PP、非对称 PD×TP 为起点，再按资格选择 EP 组合。 |
| 调度、缓存和资源 | 覆盖真正触发的 chunked prefill、混合组批，以及一级前缀缓存命中和释放或淘汰。选择长请求、页边界、并发上升和 KV 压力案例，核对实测范围与可复用范围。 |
| 模型与权重 | 至少一款真实权重 Dense 和一款原生可运行的真实权重 MoE，优先已有结构来源的模型。MoE 性能主线沿用给定 EP 路由及当前 padding 合同。自然路由有单独的真实观测资格，只有取得路由输入、执行路径和独立评价证据的范围才可发布自然路由预测结论。 |
| 第二框架 | 优先核查 KTransformers 在选定部署上的官方原生可运行性。若该前提无法满足，用另一款可原生运行的框架交付同样的有限闭环，并保留选型依据。 |
| 请求与规模 | 小案例用于静态审查后的联调。独立验收包含新常态与突发流量、未参加拟合的长度组合和必要的并发压力。保留单卡 100/200 请求测速口径，另选一个实用的多卡规模，以实际数据量和部署额度限定。 |

## 2. 里程碑和阶段依赖

一个窗口维护全部阶段。里程碑用于汇总交付，阶段用于实施、验收和推送。阶段内的批次沿同一职责链集中推进。

| 里程碑 | 阶段 | 对应交付 | 达成条件 |
| --- | --- | --- | --- |
| M0 交付基线 | S0 | D1–D6 的范围和前提 | 初选范围落为具名场景，确认可复用资产、观测前提、验收口径及预算。 |
| M1 多角色计时 | S1–S3 | D1 的共同能力 | TP2 和非对称 PD 能独立估时，局部工作、协调与传输进入同一计时接口。 |
| M2 配置集探索 | S4–S5 | D2、D3 | 成本需求、采样、发布和复用形成有界流程，用户入口能从空资产运行并在下次复用。 |
| M3 正式支持范围 | S6–S8 | D1 的覆盖、D4 | 单机代表拓扑、真实权重、调度机制及第二框架的交付案例完成开发闭环。 |
| M4 独立验收与交付 | S9–S12 | D5、D6 及 D1–D4 的交付复核 | 最终工作流、两条验证路径、支持表和干净环境复现均有证据。 |

主线顺序为 S0 → S1 → S2 → S3 → S4 → S5 → S6/S7/S8 → S9 → S10/S11 → S12。S6、S7、S8 都依赖 M2，阶段启动时按资源和共享接口的实际状态安排先后。S10 和 S11 共用冻结快照，分别形成自己的结论。

可以提前用现有 TP1 样例审查配置集输入、结果结构和评分边界，也可准备第二框架的原生可运行性证据。固定输入的 CPU 后处理可以与设备采集并行。共享计时合同的修改和同一设备组上的原生实测按已确认的资源顺序进行，避免互相改变证据。提前准备的工作纳入其所属阶段交付。

## 3. 阶段计划

### M0 交付基线

#### S0 确认范围、资产和预算

- 按每个支持责任选择原生可运行的模型、配置、角色、请求族和部署，核对现有代码、依赖、镜像及可复用来源。存在旧环境或资格不明的观测时，列出具体差异和需要取得的证据。确定第二框架的候选、最小入门案例和原生失败时的替代条件。
- 以正式入口为起点追踪工作描述、角色、CPU 协议和传输的生产者与消费者。明确本窗口需要开发、复用、重取或保留限制的事项。盘点可用设备与磁盘，登记采集、后处理、尝试和存储累计预算，确定结构与性能的留出策略。
- **交付条件** 具名场景清单、开发及验收输入责任、资产适用范围、预算与起点可以直接用于 S1。变更较大的场景先写清原生前提。未取得原生资格的项保留原因和替代目标。

### M1 多角色计时

#### S1 统一各类工作的时间交接

- 从正式入口追踪动作图、rank 间 CPU 协议、传输和通知如何进入时间线。将有自身服务开销的动作内工作、CPU 协调及传输接入同一成本查询合同。工作身份包含实际执行的定义和区间，角色、阶段、资源和必要特征由各自所有者声明。逻辑等待由图和资源就绪决定。
- 扩展成本资产装配，以实际选中的实现条件与工作身份装载各参与者所需成本，等价角色的共享必须有测量依据。实测旁路逐项绑定跨 rank 工作、CPU 消息和传输端点，与独立成本使用同一执行接口。沿调用方完整删除已被替代的专用路径。
- **交付条件** 同一任务能够为多个已声明角色取得相应成本。对 CPU 消息两端的服务、传输和等待有清晰的所有者及计费边界。用必要的编译与公开入口开发回归核对三种时间输入和既有单卡结果。

#### S2 跑通 TP2 的独立成本预测

- 用有资格的 TP2 来源把两 rank 的 CPU、分片设备工作和搬运映射到模板。扩展按角色的轻量 CPU 采样和请求时延实测入口，确保输出端及稳态窗口独立可核对。
- 本地工作可在原生分片等价的条件下用代表角色采样。真实 collective 用双卡测其传输、完成和必要进度。先核对实际数据量、参与组和启动条件，再决定成本特征。等待、完成交接和资源占用保持在执行层。
- **交付条件** 同一具名双卡任务能完成成本发布、自主预测和原生轻量评分。开发例可解释首个 collective 的前置、服务和后续就绪。现有 TP1 与 TP2 可从相同入口选择各自资产。

#### S3 用非对称 PD 检验多角色接口

- 选择原生可运行的非对称案例，沿预约、Prefill、KV 与 metadata 传输、Decode 接纳和释放核对边界。分别取得本地成本、CPU 控制消息和传输服务，沿资源生命周期检查远端可见和物理重用。
- 用实际 PD 同时检验成本装配、跨实例完成反馈和源/目标的资源口径。若发现 S1 合同遗漏，回到共同表示补齐机制并核对 TP2 受影响路径。角色和传输细节由 adapter 提供。
- **交付条件** 非对称 PD 的开发例完成结构对照和自主性能评分。TP2 与 PD 共用工作身份、计时交接和预测入口。已知误差、时钟限制和未取得实测的工作有明确位置，供后续统一验收。

### M2 配置集探索

#### S4 将成本需求和补采接成有界流程

- 扩展已有来源规划、粗图需求检查和在线成本缺口。用实际执行域、归一化定义、工作区间、阶段和特征归并不同目标的需求，先查已明确发布的资产。静态需求取自已声明的工作参数和可达布局，动态调度中尚未展开的部分明确为未知。
- 优先落实同一执行域的精确复用。闭合的批次数组操作在运行环境、完整定义、实参范围及局部实现一致时可跨角色复用，保留实测来源并由适配层确认适用条件。该流程覆盖开发验收暴露的同一操作随组批变化失去样本的问题。
- 将已知需求交给有限原生采样配方。先落实长度/成员变化、需要上下文的工作、可重现的分配或合并形态，以及按传输量和参与组采样。采用共享原生生命周期的短请求或有同底层证据的测量入口，记录实际组批、形状、角色及实现。合并可共用的配方，优先从同一会话获得多个观测点。
- 区分有样本、可查询和独立验证通过。找不到合格配方、重复配方无新增证据或达到累计预算时，输出具体未覆盖需求。发布新增资产后，目标从统一初态重新预测。独立留出目标始终留在评价侧。
- **交付条件** 对同一批多个目标集中产生采样需求，命中的原生样本自动关联到工作并发布资产，缺口和停止原因可以由输入和证据复核。用有、无合格样本的实际案例走通复用和补采。

#### S5 交付配置集正式入口和结果

- 用现有来源规划、采集、模板编译、拟合和 `predict` 拼成一次用户任务。沿一个输入合同处理模型、配置集、workload 集、部署及预算。任务层统一安排资产、各目标执行、失败状态和恢复，目标组批和资源变更由现有执行链处理。
- 成本准备使用正式采样入口，来源和补采共用本次任务的原生、后处理和存储额度。原始来源及成本资格检查需要的材料归各自生产者持有，简明结果只呈现用户需判断的信息。集中处置已知缺口，再从初始状态运行目标；新出现的未覆盖需求进结果。
- 以一个带 UTC 时间的任务根交付输入、来源、资产、目标、结果和日志。默认输出简明表格及必要机器结果，完整图和轨迹按需开启。对可比较的组合给出延迟、吞吐、排序及适用范围，明确原生限制、模板缺口、成本缺口和验证资格。
- **交付条件** 同一份示例能消费多项配置和 workload。一次从空资产按预算准备和预测，另一次更换请求并复用仍合格的资产，两个任务都能复核输出与资源用量。单目标入口继续服务直接预测和验证。

### M3 正式支持范围

#### S6 扩大单机并行和组合覆盖

- 从 TP2/PD 的已交付接口扩展到高 TP、PP、EP 和具名组合。覆盖真实使用的 rank/阶段及其成本。按实际实现、传输和角色等价条件决定代表采集与复用。PP 核对微批/激活/输出，EP 核对路由与通信，PD 保持两个独立状态与明确传输交接。
- 为逻辑结构、样本可达性与成本有效范围分别给证据。先维护共用机制和明确的 adapter 声明，再补代表性数据。新增模型形式只在特征、传输或争用证据表明现有常量和单轴曲线不足时引入。
- **交付条件** S0 清单中的单机拓扑责任和具名组合均有正式开发结论。拟交付项能跑完预测和原生评分，原生失败或证据缺口能够定位到具体配置、角色和责任。

#### S7 覆盖真实权重、调度和缓存

- 在 SGLang 上完成确认的 Dense 与 MoE 真实权重案例，维持原生采集与预测的输入语义一致。给定路由和 padding 按当前合同核对。自然路由的证据应由真实原生运行提供，并明确输入内容、权重及是否能用于预测。
- 验证实际触发的 chunk、混合组批、前缀命中和回收，以及它们对执行结构和成本适用性的变化。覆盖新增机制首先补齐实际结构和工作合同，再为新路径采集独立成本。
- **交付条件** 具名真实权重及调度案例通过正式开发工作流。由请求变化、实现机制变化和输入内容导致的能力边界均可解释，并体现在用户结果。

#### S8 接入第二个原生框架

- 按 S0 的原生可运行证据确定框架和小规模案例。从观察切点、工作声明、原生控制、资源绑定及成本观测接入现有接口。原生进程维持真实生命周期，项目核心消费同一模板、工作和完成合同。
- 先做单实例小案例，验证取得来源、发布成本、展开执行、预测和独立对照的链路。审查每个新增共同接口的实际消费者，框架特有的逻辑集中在适配层，删除过渡分支和重复代码。
- **交付条件** 第二框架有一个端到端场景，能展示换框架时的代码和产物边界。SGLang 的同类场景继续通过既有入口。保留两个框架各自的验证条件。

### M4 独立验收与交付

#### S9 功能收口和统一冻结

- 从最终用户入口追踪到采集、模板、模型、执行、结果和评价。集中清理过渡路径和无消费者产物，核对目录边界、原生测量资格、数据隔离和镜像。以静态推导为主，集中构建并做必要公开入口验证。
- 核对单卡测速与代表多卡规模的墙钟和存储。按实际瓶颈决定是否集中优化，按同一输入、时间依据和业务结果复测。准备独立评价器及具名用例，先检查两条路径各自的证据链完整性。
- **交付条件** 冻结代码、运行镜像和构建产物、模板与成本资产、用例、指标口径及评价器。记录各结构与性能目标的资格和累计额度。已有原生记录可在与冻结条件相符时复用，独立资格按请求组与运行来源核对，确保与建库、拟合和开发修复隔离。

#### S10 在冻结快照上验收执行结构

- 从目标原生观察发布逐工作、逐端点的真实时间条件，交给 `--execution-inputs`。同时独立核对目标图体、必要因果、KV/槽位状态和请求输出。原生控制及共同核心自行生成组批、绑定和执行图。
- 全节点资格逐项核对实测端点或经验证的纯逻辑关系，保留校准不确定性。实际工作只有宽时间包络或间接后继上界时，报告对应的受限结论。覆盖目标与实际取得的证据逐项记账。
- **交付条件** 冻结结构矩阵全部产出可解释结论。拟发布支持的案例具备与声明相称的完整结构证据，局部或受阻结果保留具体缺口。

#### S11 在同一快照上验收自主性能

- 用 `--costs` 对冻结留出目标运行完整预测，由执行器和原生控制自行生成完成时刻和后续批次。目标的轻量原生请求时延只供评分。按统一预热后窗口、请求身份和调度器 token 发布边界核对 TTFT、TPOT、吞吐及配置排序。
- 保留每个配置和 workload 的覆盖、逐请求及汇总误差、提交偏差和首次特化情况。验收前固定统计分组及排除项，性能目标沿用 TTFT、TPOT 的 MAPE 分别低于 6%。原生差距落在测量波动范围内时，排序标为未能区分。同步记录采集、后处理、仿真与存储用量。
- **交付条件** 冻结性能矩阵全部完成或有可复核的未通过/受限原因。只有满足依赖证据和精度目标的范围取得性能资格，原有结论和失败均保留。若需修复，在冻结结果汇总后集中定位共同根因，按受影响范围重新冻结和验证，参与修复的数据转为开发用途。

#### S12 从干净环境复现并交付

- 按正式命令构建 Docker 环境，用公开示例验证一个配置集的冷资产运行和换 workload 后的复用。检查实际支持表、数据目录、出错定位、默认精简输出和按需明细。README 与用户使用说明以真实可执行命令为准。
- 完成总窗口代码、文档、数据及发布检查。记录最终镜像/提交、支持范围、复现入口、未完成项和资源开销。将项目级结论汇总到主工作流后按窗口约定关闭。
- **交付条件** 干净检出后，另一名使用者只依据正式说明、支持的模型与配置集、workload 和部署预算即可复现预测并取得可读报告。D1–D6 各自满足验收条件并可追溯至交付证据。

| 职责 | 所有者 |
| --- | --- |
| 原生工作切点、调用参数、模型/角色解释、测量入口 | 框架 adapter 与 runtime adapter，各自从实际原生实现取证。 |
| 模板定义、区间、参数和必要依赖 | 共同模板与图层，结构复用通过明确的接口和绑定。 |
| 需求归并、合格样本、模型及适用范围 | 性能层和正式 workflow，离线与在线共用工作身份及特征。 |
| 组批、请求进度与完成消费 | 原生控制通过共同接口作决策。核心持有模拟资源、在途工作、时间线和完成反馈。 |
| 任务装配与独立评价 | 正式 workflow 维护用户任务与资产生命周期，`example` 维护实验编排、留出与原生对照。 |

两条时间路径共享控制、模板展开、依赖、资源和时间线。结构验证将目标的实测条件按本次已确定的工作和端点绑定。正常预测只用已发布的独立成本和 workload，通过时间线推导全部输出时刻。给定统一耗时用于开发和测速。实测原生启动、预热、设备活动、服务和等待的边界保持可追溯，父子工作和传输各按自身责任计费。

## 5. 阶段管理与收口

1. **启动时定基线。** 用依赖阶段已推送提交核对代码、资产、环境、未决限制及预算。在状态中给出阶段起点和下一次验收，在日志中说明本次计划调整。可以根据证据拆分、合并或重排后续阶段，变更同时记录原因、影响和仍待交付的责任。
2. **开发按完整链路推进。** 优先从代码、职责和原生合同定位根因，集中修改后在对应 Docker 环境做 C++23 构建与必要运行。按项目工程约束进行周期审查，重点看层次、逻辑、风格和精简。完整独立矩阵在功能冻结后运行。
3. **采集按累计预算执行。** 先确认旧证据能解决什么及新增证据的价值，记录原生、后处理、尝试和存储的额度与实耗。可复用的原生事实反复用于离线复核。新增或失败的采集沿原预算记录。整理仅限本任务已确认无用的产物，保留正式资产、原始依据、关键失败与恢复信息。
4. **每阶段审查并交付。** 按 Git 起点检查本阶段全部改动及受影响调用方，核对共同层与适配边界、资源生命周期和可收紧的冗余，完成代码、文档、数据及必要验证检查。之后以英文 `type(scope): summary` 分层提交、推送开发分支并核对远端提交，作为依赖阶段的起点。数据、模型、构建产物、凭据及 `deprecated` 保持在交付 Git 范围之外。
5. **冻结失败先汇总。** 运行期间冻结核心、适配、来源、成本和评价器，保留整个已选矩阵的结果。冻结后按结构、采样/模型、原生环境、评价四类根因定位，优先完成同一职责链的集中修复，再对影响范围做新的独立验收。超预算、被原生约束阻塞或精度未达标的责任保留在状态和最终支持表，范围变化与原目标一并记录。

### 总窗口完成与停止

以 S0 确认的必交付责任逐项核对 D1–D6。全部验收并推送交付后关闭。原生、设备或预算阻塞影响到必交付责任时，记录阻塞和解除条件，继续独立工作。具名案例可替换为原生可运行且覆盖同一责任的案例。六项交付范围或验收口径发生实质变化时，先确认取舍，再调整计划并保留原责任的结论。

总窗口只有三个管理记录。计划维护目标、阶段和验收。状态保留当前进度、基线、阻塞和下一步。日志保留已发生的工作、验证、阶段交付和重要取舍。详细证据留在各任务目录。
