# Qwen 小模型、跨 TP 预测与自动化使用流程

开始日期：2026-11-13。

目标：在现有三阶段预测器上增加一个 Qwen 小模型，实现限定范围内 TP=1 与 TP=2 的双向预测，再通过自动化流程和可实际使用的用户面板，让用户完成准备、预测、搜索与结果查看；代码整理围绕这一使用过程展开。

## 1. 本轮做什么

本轮按 A、B、C 三个阶段推进。A 解决换模型，B 解决换 TP，C 提升自动化和可用性，交付用户面板。每阶段应交付能独立使用的完整能力，不把全部结果留到最后。

| 阶段 | 核心问题 | 交付 |
| --- | --- | --- |
| A：Qwen 小模型 | 实现能否按模型参数工作，而不是暗含 32B 的假设 | 新模型的采集、独立性能维护、同 TP 预测和正常评分 |
| B：跨 TP | base 的设备数量与目标不同时，怎样生成正确工作和估计成本 | 同机 TP=1↔2 的结构生成、共享成本准备与完整 E2E 结果 |
| C：自动化与用户面板 | 用户能否完成输入、自动准备、预测或搜索、查看和复用结果 | 可实际运行的本地面板、共用的 CLI/后台流程、自动准备与恢复、明确的阶段交接 |

KTransformers＋DeepSeek 由另一位 agent 负责，不列为本窗口开发或验收任务。本轮不修改其专属适配器、镜像或实验资产；公共合同发生变化时，需要说明对该接入工作的影响。KTransformers 的公共接入、NodeScale、源图回放和独立评价继续保留，KT 专属能力的调整由负责该工作的 agent 决定。

本轮不扩展 PP、DP、EP、跨机通信、MoE、在线并发调度或任意模型间的直接预测。小模型与 32B 各自使用自己的 base；这里验证的是同一实现可以适配两个模型，不是用 32B trace 直接预测 8B。

TP=4 是 TP=1↔2 完成后的扩展项：先核对同机拓扑、运行支持和成本覆盖，再决定是否执行。未做的 TP=4 不能写成已支持，不以它代替必须完成的双向验证。

## 2. 三阶段建模各自负责什么

```text
用户输入：平台、模型、workload、base 部署与配置、target 集合、预算
                    │
base 采集 → profile_manifest.json → 原始 DAG 与源语义依据
                                      │
模型信息、target 部署与配置、框架规则 ──→ 目标工作、资源与依赖
                                      │
独立小型采样 → 性能库 → 离线模型 ───────→ 成本绑定与同钟执行 → 完整 HTTP
```

| 部分 | 拥有的事实或状态 | 不能代做的事 |
| --- | --- | --- |
| 采集与适配器 | 实际模型、部署、原生调用、请求与观察边界 | 用 target 真值替预测补结构或参数 |
| 原始 DAG | 所选 base 的工作、依赖及可证明的来源关系 | 把其他 TP 的 trace 混成同一份来源 |
| 目标结构 | 分片几何、rank、通信、缓存状态、资源和执行条件 | 读取成本系数决定结构，或只克隆 base 出现过的分支 |
| 成本提供者 | 未变工作的合法迁移、独立模型查询、适用域与缺口 | 创造操作、改变缓存策略，或按目标残差补参数 |
| 执行器 | 同一时钟下的依赖、资源占用、通信到齐与时间条件 | 完成仿真后另加倍率、等待或 E2E 修补 |
| workflow | 准备、预算、复用、恢复和产物生命周期 | 在编排脚本中复制模型几何或 TP 算法 |
| 实验与搜索 | 候选构造、正常对照、评分和选点 | 将评分输入挂载给预测器，或把实验身份写入核心 |

模型结构信息读取一次，目标工作描述携带成本所需变量。第二阶段说明工作和资源是否保持不变，第三阶段核验对应源服务是否真的可迁移；两者通过工作描述与来源引用交接，不传递另一套隐式规则。

源、目标的模型与 dtype 本轮保持相同，允许目标 TP 不同。模型位置、TP、rank 数与设备组的所有权必须一致：实现时为 target 明确目标部署，省略时继承 base 部署；不把 TP 同时塞进多个 configuration、再用硬检查维持一致。沿现有输入合同做最小扩展，先贯通解析、准备、模型选择、核心与报告，再删除旧的单部署假设，不维护新旧两套格式。

三个实验报告分别评价源图自洽、目标结构对应和正常 E2E 精度。普通应用只输出预测、来源、缺口、范围和开销，不承担完整实验诊断。

## 3. 阶段 A：让同一流程支持 Qwen 小模型

### 3.1 模型与运行范围

主选 Qwen3-8B，沿用 BF16、SGLang、Ascend 和现有 eager/FIA 路径。官方配置给出 36 层、hidden size 4096、32 个注意力头、8 个 KV 头、head dim 128，这些可整除关系使它适合首轮 TP=1/2/4 检查；是否能在本机运行仍需实际核验。参数依据为 [Qwen 官方 config.json](https://huggingface.co/Qwen/Qwen3-8B/blob/main/config.json)。

开始采集前核对权重、tokenizer、镜像依赖、有效设备内存和目标页几何。主线先保持 TP=2，单独确认 TP=1 的启动和分片可行性。若确需替代模型，须在采集前说明原因并更新模型与实验声明，不能测过后挑误差较小的模型。

### 3.2 实现任务

1. 联查模型元数据、计算工作、KV 页字节、内存预留和首次准备，找出隐含层数、维度、头数、dtype 或模型身份的常量。
2. 参数归回真实模型描述与适配器。公共工作和执行器只消费描述，不按 Qwen3-8B、32B 名字分支。
3. 按新模型的工作描述选择独立数据。已有数据只有在实现、硬件、计时边界和特征域均满足时才复用；不能因为模型属于同系列就直接沿用 32B 系数。
4. 缺项按整组需求归并，使用小型独立请求维护现有数据库；保持其他模型的现行选择，不通过一次补采重训整个库。
5. 贯通 plan、base 准备、性能准备、predict 和独立 measure。核对正式 HTTP 及各项资源统计在新模型下的单位与归属。

### 3.3 阶段交付

用第 6 节的两类请求和三个配置完成 6 个同 TP 预测，其中 2 self、4 cross。对照独立正常运行，报告全部误差和成本来源。小模型采集与性能库维护必须通过正式入口完成，不能依靠手填性能包才能预测。

至少一份小型 diagnostic base 完成源图回放；语义采集没有细图资格时如实保留限制，不把缺诊断解释成普通预测失败。

## 4. 阶段 B：跨 TP 的结构与成本

### 4.1 先明确源部署与目标部署

现在一组请求只有一个 deployment，区域帧和资源也与 base 参与者关联。先沿真实调用链梳理这些假设，不能只放开输入校验。

需要联合检查的范围包括 `python/markov/artifacts/`、`python/markov/workflow/`、SGLang/Ascend 适配器、目标规划、成本上下文、执行资源及搜索资源统计。最终每个 target 都有可解释的有效部署，同一批次能预测不同 TP；预测不要求用户为每个目标手拼一份来源和模型文件。

base 的实际部署由 manifest 记录，目标部署不能反过来改写它。普通预测只声明目标的虚拟 rank、资源和拓扑，不为 target 启动设备；base 采集使用源 TP 的设备组，独立正常测量使用目标 TP 的设备组。仅持有 manifest 时，预测所需的模型结构也应由已记录元数据提供，不要求在预测容器重新加载模型权重。

### 4.2 目标结构主动生成

从模型结构、真实框架规则、目标 TP 和硬件拓扑生成目标工作，重点处理：

- 每 rank 的权重、线性层、Q/K/V、注意力头、KV 头、页字节、输出与必要的 padding；不适用的整除或复制规则明确拒绝。
- TP=1 没有 TP 集合通信、TP>1 新增的合法通信分支，以及从多 rank 合并回单 rank 的情况。TP=1 的 base 不能成为目标通信是否存在的依据。
- 集合通信的操作、参与者、数据类型、消息字节、发起、到齐和消费依赖；沿框架实际实现说明哪些层重复通信，不根据 kernel 名硬拼模板。
- 各 rank 的本地完成、CPU 调用、设备流与全局汇合；不能用各 rank 总耗时求平均或简单相加替代真实依赖。
- TP 改变后的缓存布局、备份/回载、文件分片和取消行为。逻辑 token 容量、每卡 GiB 和整组 GiB 分别记录，不混为同一个容量约束。
- 后台完成与前台回收分开：预取撤销、未接受缓冲和写入保护必须在原生调度器处理相应控制队列时释放。按共同执行时钟保留这段资源占用，正确报告无法分配的情况；不能为了继续运行提前释放主机页或增加原生流程没有的等待。

保留语义区域和必要端口。需要表达通信交错时，用重复层区域和外部端口描述，不把全部算子展开成细图。没有可观察外部差别的内部细节继续合并。

### 4.3 独立成本与通信怎样计费

先列清每个成本响应包含什么，再决定是否新增响应。现有 batch/current-stream 区间可能已包含通信或等待，必须核对；不能在原包络上再叠加一份通信。

首轮采用以下原则：

1. 改变的计算工作按目标分片后的实际特征查询成本。不能把 TP=2 的整体响应除以 2，当作 TP=4 的响应。
2. 当区域被拆为计算与通信时，计算采样使用与该计算片段一致的边界；通信独立记录消息量、参与者、集合类型、拓扑、返回和完成。确实保留闭合区域成本时，其内部部分不再重复计费。
3. 首次通信初始化、稳态通信与新规格准备分别核对。可以用有来源的启动项和传输项，但不预先规定必须线性；模型形式由独立样本和工作范围决定。
4. 同一目标组共享计算和通信数据。需要在某个 TP 下做小型原生采样时，明确这是独立成本覆盖，不称作“仅凭 TP=1 成本泛化到所有 TP”。
5. 源成本只迁移工作、资源和部署条件均保持不变的部分。按 rank 数复制源 CPU gap、复制源同步等待，或沿用原 TP 首次准备，均需要独立依据。
6. 成本库和导出选择必须容纳不同模型、TP 与拓扑的适用域；不能让一个目标的选择覆盖另一个部署，也不能靠用户手工拼接 JSON 绕开选择问题。

### 4.4 验证顺序与交付

先完成一个 TP=1→2 的完整请求切片，核对生成的 rank、分片、通信与依赖，再完成 TP=2→1。之后使用同一机制扩展到两类请求和三个缓存配置，不逐格补分支。

首轮有 4 份 base，分别对应两类 workload × 两种 TP，均使用各自部署下的 K0 配置；它们构成不同预测行。每行只读取自己的 base，另一个 TP 的 base 在该行只能作为独立评价资产，不能通过共享目录进入预测。

完成 24 个预测：2 workload × 2 base TP × 2 target TP × 3 target 配置。其中 self 为 4 个，同 TP 改缓存为 8 个，跨 TP 为 12 个；后两项合计 20 cross，不混称为 24 个跨 TP 预测。阶段 A 的 6 个结果属于该集合，不重复计数。

从 TP=1 和 TP=2 的基准互预测开始，再用必要的独立 target diagnostic 对照容量压力与限时分支。结构核对包含通信字节、调用数量、资源归属、必要可达关系、缓存可见性和正式完成边界；不能按节点数相近就判正确。

TP=4 仅在双向主线已交付后评估。只有实际完成相应规则、拓扑/成本覆盖和独立评分，才能列为已验证范围。

## 5. 阶段 C：自动化、可用性与用户面板

C 的主要成果是用户能方便地使用完整流程。用户面板属于必做交付，需要连接真实任务和结果；只画界面或展示已有实验成绩不算完成。全项目的代码、配置、Docker 和文档整理服务于这个目标，重点消除需要用户手工对接的环节，并理清各阶段的职责和数据交接。

围绕 A/B 的实际结果，完整检查自有 Python、Shell、C++ 及相应配置、Docker 和工作文档，按完整业务链联合修改多个文件。KT 专属部分由另一位 agent 处理，本轮覆盖它与公共流程的接口影响；不能因此声称已完成 KT 内部审查。先交付本地单用户场景，不扩大为云服务、多租户或集群管理平台。

### 5.1 从用户输入到结果

用户提供部署、workload、base、target 集合和准备预算；面板和 CLI 使用同一份输入合同，调用现有 workflow 完成预览、采集或复用 base、选择或补齐共享成本、预测或搜索，并返回结果。实验评分和配置搜索继续位于预测器上层。

用户应能知道：将启动哪些准备、缺少哪类数据、预计或已经花费多少、能否复用、失败后从哪里恢复。已实现的能力先复用，不为面板再写一套准备、预算、恢复、搜索或评分逻辑。

自动化重点包括：

1. 根据用户选定的模型、镜像和设备核对运行条件，按实际支持范围提供 TP 与框架配置。文件或镜像存在只表示找到了资产，不显示成运行已验证。
2. 导入 workload 后展示请求数、输入规模、输出上限与正式边界；调整规模使用请求/token 参数，不隐藏裁剪或图大小限制。
3. 检查已有 base 与性能覆盖，能合法复用就复用；缺数据时在用户给定预算内自动准备，整组 target 共享采样。不会要求用户先手拼性能 JSON 或手改 SQLite 才能继续。
4. 用一次任务提交串起准备、预测或搜索、结果生成；正常条件下不要求用户逐条复制命令、寻找内部目录或手工搬运产物。
5. 复跑识别已完成工作，失败和中断保留累计预算并从现有入口恢复。不能因刷新页面或重启面板重复启动设备采集。

首次启动只要求用户补齐必要的本机配置，模型、workload 和运行设置可以保存并再次使用。需要维护者处理的驱动、镜像兼容和范围外能力，给出具体原因及下一步，不把这些问题转成静默默认值或无休止重试。

当前应用于新模型/TP 的最小配方须有实际运行证据，不能只列一串未经执行的命令。一个 workload 的不同 target 共用准备，改变 workload 仍按当前合同准备对应 base；不默默宣称能无 base 预测任意新请求。

### 5.2 用户面板的最小完整范围

交付可在浏览器访问的本地面板，默认限本机使用。界面围绕四个实际任务组织：

| 用户要做什么 | 面板提供什么 |
| --- | --- |
| 创建预测或搜索任务 | 选择模型/平台/框架、导入 workload、选择或声明 base、设置 target 配置或候选范围、资源预算和搜索约束 |
| 确认准备内容 | 显示已有资产、可复用数据、缺少的性能域、计划采集内容，以及已知时间/空间预算；未知开销明确标明 |
| 跟踪与恢复任务 | 展示当前阶段、实际完成目标数、设备等待、预算消耗和具体错误；支持安全停止、查看原始信息和继续任务 |
| 理解与使用结果 | 展示完整 E2E、相对选定基准的变化、资源占用/费用、排序和适用范围，支持配置比较及请求/结果导出 |

用户可以查看已登记 base、性能库的覆盖与来源，以及可复用的历史任务；性能维护通过同一 workflow 发起。数据页只管理本项目登记的资产，不递归扫描整机，不默认删除历史证据。

面板以模型、请求、配置、进度和结果表达主要流程。manifest、成本模型内部字段、原生 probe 和详细日志放在按需展开的区域；必要的缺口和限制仍应以人能读懂的文字显示。容量和带宽标明单位、单 rank/整组口径；实验价格显示为相对权重，不能冒充市场报价。

前端只负责输入与展示；本地服务负责调用、任务句柄和状态读取；现有 workflow 继续拥有资源生命周期。沿现有任务记录恢复，不额外维护一套与采集容器或预测进程不一致的状态。进度优先展示真实阶段和已完成数量，没有可用依据时不编造百分比和剩余时间。

输入在公共边界校验，前端提示复用同一合同的含义，不在页面硬编码另一套模型/TP 支持表。启动、停止和恢复只作用于本任务拥有的进程与容器，不把任意 shell 命令暴露为面板功能。

前后端的最小依赖和目录归属在实施时结合现有工程确定，以本机启动方便、维护量小和真实调用链清楚为准。CLI 保持可用，相同输入经面板或 CLI 应得到相同的有效请求和预测结果。

### 5.3 职责与代码清理

- 对照第 2 节逐项核对事实和状态的唯一所有者，删除重复模型解析、TP 规范化、格式转换、部署校验、临时模型导出及编排中的业务分支。
- 重点检查 `artifacts → workflow → adapters → planning/cost → execution → report` 的交接，避免结构规则调用成本提供者、成本模型反向修改策略，或报告再运行一份状态机。
- 移除真正无消费者的代码、调试输出和重复报告。必要验证及数据边界保留；不以拆文件、压行或移出统计目录充当瘦身。
- C++ 头源按同职责同目录维护；Python/Shell/C++ 按逻辑分组留空行。拆大文件以真实职责和实际读者为依据，不新增大量几行转发文件。
- 不新增独立测试工程、历史格式 fallback、版本/冻结系统或 checksum 管理。源码净变化和剩余复杂度据实记录，行数不是硬验收门槛。

### 5.4 时间与空间

保留同一会话中只准备一次 source 的能力，联查全量扫描按 48 点反复启动后重复解释来源的开销。普通预测复用已解释来源与离线模型，目标状态独立；不以跨任务常驻守护进程解决本轮问题。

区分用户摘要、机器交接和可选诊断，解决完整报告被复制到日志、分区汇总和总报告的问题。诊断在生产端按需启用，不先完整生成再裁剪。保留原始正式证据，只处理本窗口拥有的无用中间产物。

用固定来源、模型和候选比较整理前后结果。主要目标是去掉重复准备与输出，而非单纯提高并发。确需优化事件处理时，保持页发布、检查、超时、取消和返回的同钟语义；不得跳过会改变分支的中间事件。

效率同时报告冷启动调用、source 准备、边际 target 仿真、完整批次、内存和输出量，不把毫秒级边际时间写成从零耗时。不设未经基准支持的 10× 承诺。

### 5.5 从面板完成一次真实任务

在设备可用、模型与兼容镜像已具备的前提下，使用阶段 A/B 的小型真实输入验收：

1. 用户从面板提交一个没有可复用 base 和完整性能覆盖的任务，预览准备内容，运行后自动完成必要准备与预测，并在页面拿到结果。已有覆盖可以复用，不为证明自动化故意重采已具备的数据。
2. 再提交可复用上述资产的任务，核对面板清楚说明复用内容，后台没有重复采集；运行一个现有有限候选搜索并展示配置比较。
3. 验证页面刷新、服务重启后的状态恢复，以及一次任务安全停止和继续；沿已有任务记录保留用量和错误，不把“重新开始全部工作”当作恢复。
4. 对一个已知不支持输入和一个准备缺口，检查页面能给出可操作说明；仍须保留后台正式状态，不能把失败、缺项当作耗时为零的成功配置。
5. 选择同一份已准备输入经 CLI 核对有效请求和结果。浏览器中检查表单、阶段状态、结果阅读、错误提示与导出；截图和 dry-run 仅作辅助，不代替真实流程。

优先复用本窗已有采集和运行证据，把确需增加的小型采集计入同一预算。面板验收不重跑整个实验矩阵，不为 UI 建立独立模拟任务或测试工程。

## 6. 实验布局与评分

### 6.1 请求与配置

先固定一份独立请求负载 W1 和一份有明确共享前缀回访的 W2。W1 以 12 条正式请求、256–2,048 输入 tokens、16 输出 tokens 为初始规模；W2 以 16 条正式请求、1K–4K 输入 tokens、32 输出 tokens 为初始规模。每组另设少量准备请求，精确 token、顺序和正式边界在采集前保存。

W2 的工作集与回访距离按模型实际 KV 池设计，确保预定配置确实包含设备驻留与主机/文件回访差别。根据运行可行性调整请求规模时，须在读取正常误差前确定；不能通过限制图节点数或裁剪预测路径控制规模。

配置只保留三类代表：K0 基准；K1 容量压力与回载；K2 写回和限时预取。具体值从支持的原生规则、可用容量与请求工作集确定，开始采集前写入同一份实验输入。跨 TP 初轮 K0 固定逻辑 KV token 容量，先观察分片和通信；K1/K2 再核对每卡预算变化产生的缓存影响，报告其联合变化，不能混称纯 TP 收益。

### 6.2 真值、隔离与计数

- 主面板 24 个预测共用 12 个正常条件：2 workload × 2 target TP × 3 配置。不同 base 预测同一条件时复用同一组正常真值。
- 单列 4 self、8 个同 TP cross、12 个跨 TP cross；同 TP 与跨 TP 分别统计，避免前者较好的结果掩盖并行策略变化的误差。
- 每正常条件先做一次；预先指定 W2/K0 的 TP=1、TP=2 两条锚点各做三次，共 16 个成功正常窗口。重复安排在查看误差前确定，不因某格误差大而追加慢样本。
- 正常采集关闭 profiler、probe、region 和 snapshot；target diagnostic 单列，用于结构评价，不能替代正常真值。
- 同一 workload 的 tokens、输出长度、thinking/采样方式、正式边界、准备排空和首次准备状态保持可比。CPU 放置、设备组与拓扑记录在实际调用中。
- 独立模型来源与 target 评价来源分开。主面板中用于修复的格子归为开发/回归，不能继续称未见验证。
- 在读取独立结果前，另固定一个较小的未用请求序列作留出确认，只验证 TP=1↔2/K0，不再铺开完整矩阵。其数据规模和实际完成范围单列。

以下是实施前的初始工作额度，不是耗时承诺，也不在本次文档任务中启动。实施阶段按模型和设备实际情况核对后填写具体请求预算，新增额度说明收益、累计消耗和停止条件，不反复向用户询问上限。
