# 单格误差修复

开始日期：2026-11-02。

目标：修复现有完整 HTTP 预测中的共同偏差，使验收面板的跨配置和同配置的每格误差均严格低于 10%。本窗口只修误差，不扩展配置、模型、平台或 workload，不开展搜索。

## 1. 验收对象和“同配置回放”的含义

固定 Qwen3-32B/BF16、Ascend 910B3、TP2、SGLang eager/FIA，沿用已有输入、输出数量、串行请求、初始化和正式窗口规则。验收使用目前已有完整正常真值的两批资产：

| 面板 | 跨配置预测 | 同配置预测 | 用途 |
| --- | ---: | ---: | --- |
| 原面板及扩展/确认部分 | 186 | 33 | 主要修复对象和原有对照 |
| 上一窗口新增的配置与请求 | 88 | 8 | 防止修好旧问题却破坏新结果 |
| 合计 | 274 | 41 | 本窗口完整验收范围，共 315 格 |

其余 96 个已有预测尚无正常真值，继续单列。本窗口不为它们新增正常条件，不把缺测记为零，也不声称全部 411 个预测均已达标。两批已有面板在本窗口均按开发/回归数据使用，不再称作新候选的独立留出验证。

这里将用户所说的“同配置回放”按 self 预测验收：base 与 target 配置相同，输入与初始化相同，正式预测对比无 profiler 的正常 HTTP。它必须走正式预测流程，不能直接返回 base 的正常实测时间，也不能另设 self 专用倍率或绕过成本模型。

原始 DAG 使用观测成本的静态回放另外用于检查构图与时间自洽，不能拿它接近零的误差替代 self 的正常预测门槛。同配置消除了配置变换差异，适合优先定位问题；但仍需核对采集开销、成本重估、后台时序及实际执行路径，不能未经检查就把“图和正常运行完全一样”当作事实。

因此 self 先核对“没有配置变化时，究竟改了什么”：逐项说明哪些工作和必要依赖保留、哪些被重建、哪些成本沿用或重新估计。重建后的节点编号和数量可以不同，但必须说明逻辑工作、执行条件和时间边界是否等价。若差异来自预测流程本身，修正这条共同流程，而不是增加 self 专用捷径。

本窗口按职责组织完整修改批次、统一必要检查并在阶段交接时审查交付。WAPE 等统计继续报告，完成门槛以用户最新指定的统一单格目标为准。当前成绩、未达项和恢复起点只写入 status；实际行动写入 log，不把滚动结果堆进计划。

## 2. 统一的逐格门槛

按用户最新要求，取消同配置 3% 的验收标准。跨配置和同配置都使用下列 10% 门槛，仍分别报告成绩；不再用 3% 阻止本窗口收口。

```text
APE = abs(predicted_formal_http_sec - normal_mean_sec) / normal_mean_sec

全部 274 个跨配置预测：每格 APE < 0.10
全部  41 个同配置预测：每格 APE < 0.10
```

10.000% 不通过，使用未四舍五入的数值判断。每格对该条件全部有效正常重复的算术均值评分；保留样本数、范围、标准差和所有失败，不能只保留较快或更接近预测的样本。

完整 HTTP 保留 HiCache I/O/control、Prefill、Decode、CPU residual gap、未归属时间及正式请求间隔。准备阶段只按既有声明排除，其状态连续推进。不能删去难解释的成本、缩短窗口或扣掉真实等待后宣称达标。

WAPE、P90、误差方向、逐 base/workload 分组和 6% 分布是辅助指标。平均变好不抵消任何一格未达；跨配置 6% 不额外设为本窗口硬门槛。已较准格若明显退步仍要解释，不能仅以未超过 10% 为由忽略共同模型变坏。

成功条件是跨配置和同配置两个集合同时全通过，且没有缺失、失败或错误工作量混作通过。归因完成、代码提交、构建成功、只修最大一格、完成新面板，均不能代替这一条件。预算不足或仍有格未达时，如实保留未完成状态，不沿用上一窗口“带精度限制收口即完成”的取舍；调整范围或门槛须由用户明确决定。

## 3. 先判断误差在哪里，再决定改什么

以 self 为优先入口，同时对照同一 target 的 cross。相同目标在不同 base 和 self 中反复出现同方向偏差时，应先检查共用响应和计费关系；偏差随 base 改变时，再检查源迁移、初始状态与源残余。它们是定位方法，不是预设根因。

每个代表保留以下证据，复用现有产物，不新建一套诊断框架：

| 核对内容 | 要回答的问题 |
| --- | --- |
| 正常对照与正式边界 | 请求、输出、初始化和测量边界是否一致，波动是否足以解释差异？ |
| 采集条件 | source、正常对照与独立性能数据使用了哪些实际设备、容器 CPU/内存限制及运行环境？同名平台是否已有计时可比证据？ |
| 实际工作 | Prefill 新算 tokens、Decode 次数、缓存前缀、回载/备份、首次准备和实际执行量是否对应？ |
| 依赖与重叠 | 哪段服务或等待决定请求结束，是否增加了屏障、漏掉重叠或把同一等待付了两次？ |
| 成本响应 | 同一工作描述下，独立测量与模型是否有稳定偏差，CPU、caller 返回和流进度的边界是否匹配？ |
| 源成本迁移 | 工作不变的成本是否被不必要地重估，迁移中是否夹带 profiler/probe 开销或不可迁移的等待？ |

按逐请求差异找到影响正式结束的区间，再查对应因果链。Prefill tokens 一致只排除了部分工作量问题，不证明全部结构正确；请求间隔差很小也不能排除请求内部的等待或 gap。

只在解释具体问题时记录目标执行图。固定路径成本替换、缩放或 oracle-cost 回放用于定位敏感部分，不进入正式成绩，不读取 target 真值重选预测分支。多个 lane 的重叠时长不能直接相加，组件差值也不能直接当作同样大小的 E2E 改善。

诊断结论必须区分已经证实、已排除和仍待验证的可能。不能把所有误差统称为 CPU gap，也不能只因出现外推标记就认定补采能解决。

## 4. 实施顺序

### 第一阶段：核对基线，优先修正 self 与 cross 的共同基础

1. 从明确的两份当前结果读取全部 315 格，保留原始正常观察引用、角色、配置、请求和未达清单；不复制大 trace，不扫描目录猜输入。起点与当前未达名单放在 status。
2. 联查正常窗口、source 和独立数据的实际采集条件，再确认 self 所需的语义工作、资源次序及计费边界。核对保留的容器启动参数，不仅比较模型、请求和配置；没有记录的 CPU/NUMA 条件保留未知。检查“不变工作被重估”“沿用成本带采集额外开销”“等待被当成 CPU 服务”等路径，但不预设必须重写迁移机制。
3. 先选择一对稳定高估/低估的 self，以及对应 cross、相近的已达标对照。优先联合处理能同时解释 self 与 cross 的共同原因，不为 self 添加第二套预测器。
4. 沿完整职责链修正必要的观察、工作描述、成本绑定或执行依赖；跨 Python/C++、适配器和调用方一起处理，待一批完整改动基本齐备后统一检查和构建。

本阶段要交付可复核的原因、修正前后代表结果及尚未解释项。同配置路径与跨配置原因耦合时联合修复，不强行按目录拆开，也不为了进入下一阶段把尚未达标的 self 标成通过。

### 第二阶段：消除跨配置尾部，并补齐剩余 self

1. 按同一目标/工作特征下的共同偏差组织任务，优先处理 cross≥10% 和 self≥10%，同时观察原来接近门槛及已较准的格子。
2. 对成本问题先核对工作变量、测量边界和原生执行机制，再决定改响应形式或数据选择。初始化与稳态是否应拆开、分段是否必要，都要有对应工作和独立数据依据；不能因为某个页宽的拟合变好，就假设能解释其他页宽的尾部。核对一次维护实际重训了哪些响应，必要时固定其余响应做单项诊断，区分补齐一种工作和整包重训的影响；诊断结果不能挑格拼入正式成绩。
3. 对等待、提交和流响应问题修改依赖、资源占用或计费归属，不把等待塞入传输速率或放大计算系数；也不靠恢复逐算子细图绕过抽象问题。
4. 只有现有独立数据缺少必要变量、端口或工作范围证据时，构造小型、共享的原生工作点补证据。核对真实执行的 I/O 页数，不能用输入长度代替传输覆盖。不得读取 target E2E 拟合、按 cell/base/workload 标签增系数，或逐格增加模板。目标诊断 trace 只进入评价器；profiler 成本不自动当成正常服务真值。
5. 每批先运行受影响代表、self/cross 配对及较准对照，记录同一共享改动改善了谁、破坏了谁。没有新修改、失败或未决风险时不重复编译和跑矩阵。

候选修正应同时解释观察与数值变化。只改善独立成本点的拟合指标、却不能解释请求级偏差时，不继续盲目加样本；返回计时边界、依赖和工作定义检查。

### 第三阶段：固定候选，完整验收后交付

1. 规则、公式和独立训练选择稳定后，固定本轮最终候选；只记录 Git 提交、实际模型选择和来源，不增加内部版本、SHA 校验、冻结副本或一致性平台。
2. 复用原输入与正常真值，统一运行旧 219 个预测和新增 96 个预测，共 315 格；包含全部 274 cross 和 41 self。最终运行使用当前工作树构建，不能把旧报告当新结果。
3. 逐格核对统一的 10% 严格门槛，分别报告旧/新、cross/self 的通过数、最大误差、误差方向及所有未达项。cross/self 仍分别统计，不改变分母或用新面板稀释旧尾部。
4. 若最终运行暴露失败，先修对应完整链并验证受影响格，再对最后候选补齐全量结果；不同候选的较好格不能拼成一张达标表。没有新变化时不反复跑完整矩阵。
5. 完成关联审查、文档/数据整理和分层提交推送。全部逐格门槛通过后，将稳定原因、结果和限制归入主工作流，再撤下本窗口 plan/status/log；没有通过不得以整理文档为由撤下任务。

## 5. 正常真值和补采纪律

默认复用全部既有有效正常重复。预测不准本身不是重测理由。只有输入/环境不可比、已有测量无效，或真实波动需要确认时才复测；不能反复测到均值越过门槛。

同条件同环境的有效追加样本一并纳入；环境或计时合同确实改变时，另列可比范围和新旧结果，不静默替换原真值。边界附近的格同时展示样本范围和阈值敏感性，达标仍按既定均值计算，不因噪声放宽门槛或靠显示位数通过。

不同物理设备组的追加测量不能仅因型号相同就自动并入原均值；先核对可比性，未确认前分别保留。发现已有汇总混入条件不一致的样本时，按采集证据纠正引用，保留原始观察和历史分数。训练来源也须说明适用条件，不能按目标残差挑选更有利的采集。

同一 target/workload 的正常真值由全部 base 共享。同一真实成本族的独立补采也组内共享；新 base 不进成本训练库。沿用现有 SQLite 有效事实及现行独立观察合同，不为缺 iteration 等元数据的历史原文件新增兼容分支。

## 6. 时间、空间与实现规模

以 CPU 分析和复用资产为主，不重采 41 份 base，不重跑整套正常矩阵，不新增配置/请求覆盖。完整验收只需重新预测已有 315 格；显式图诊断限于能区分根因的代表，不默认记录全矩阵细图。

新增设备任务初步预留累计 2 个设备组小时，新增保留数据先按 16 GiB 安排。这是本窗口新增用量，不借用上一窗口未花完的额度，也不把原任务账本清零。无补采依据时不使用额度。

每次新增采集前说明要解决的问题、已有证据为何不足、最小请求/token 规模、启动/加载/预热/导出/失败的累计时间与空间，以及何时停止。使用现有任务预算、容器限制和串行设备入口，不新建管理系统；确需调整初步额度时先记录具体收益和新的总量，不以无限补采代替机制分析。

单份 source/target profiler 资产可能较大，仅在必要语义缺失时采集；正常对照和独立性能数据保持轻量、snapshot-free。中间分析默认保留摘要及复现输入，不复制历史数据，不删除正式来源、正常窗口、独立模型、失败或原稳定对照。

保留 SGLang/KTransformers 同级能力、默认关闭的 NodeScale、显式回放和独立评价；只对本次修改实际触及的共同链做必要保留核对，不扩大成第二轮泛化。普通预测继续按语义区域和必要端口执行，不通过百万级逐事件展开、source 重复解析或大量诊断输出来换精度。预测时间/RSS和模型/代码增减另报，不用未完成的旧工程对照宣称 10×。

## 7. 工作批次、证据和完成条件

按共同原因联合多个源文件推进，每批覆盖一条完整修正链，不按单文件或几个检查点拆轮次。实现期间以静态联查为主，统一运行必要格式检查、modeling Docker 构建和代表输入；不新增独立测试程序、CTest 或 test 脚本。第一阶段单独交付；第二、三阶段联合收尾，在完整验收后集中审查、维护并分层提交推送，不为每个格子、每次采集或日志更新提交。

继续复用 examples/hicache_matrix 及正式 predict/evaluate/replay/maintain/capture 入口。面板、批量运行与汇总属于 example；生产代码只维护真实建模职责，不能把验收阈值、格数、配置身份或回归编排写进核心。

正式证据放在 data/cell_error_repair_20261102/，复用现有 preparation/predictions/measurements 和评分格式。最少保留起点引用、共同原因与代表反例、独立数据选择、统一候选的全部结果、单格门槛判断及资源用量。详细数字留在 data，状态只保留恢复起点，日志原则上每阶段交接一条；影响数据有效性或预算的重要失败另记。

最后按以下清单审查，不以代码量或分析篇幅证明完成：

- 所有 274 个 cross 和 41 个 self 均严格小于 10%，没有缺失或执行失败。
- 全部成绩来自同一最终候选及明确可比的正常真值；逐格报告和阈值判断可复核，两个面板及两种角色分别保留。
- 每项共享修正有工作/时序或独立测量依据；没有 target 真值拟合、自预测绕过、删成本、逐格补偿或错误等待计费。
- 结构可观察量、未解释路径、正常波动及成本外推限制如实保留；低 E2E 误差不冒充完整原生 DAG 证明。
- 关键能力和粗粒度预测流程保留，必要检查及当前公开入口验证有真实证据。
- 结果、原因、资源和后续限制归入主工作流；完成审查和最终分层交付后才关闭窗口。
