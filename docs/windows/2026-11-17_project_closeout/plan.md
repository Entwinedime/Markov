# 项目阶段性收尾计划

开始日期：2026-11-17。

目标：把已支持的两款 Qwen 和 KT＋DeepSeek 三条主线收敛成可以独立使用的阶段性交付，修正影响多格的共同误差，验证真实用户流程和搜索推荐，并把精度、开销与适用范围说明白。

本窗口维护任务与判据；当前资格、基线和恢复起点由 status 单独维护，实际行动与证据写入 log。

## 1. 交付范围

最终应能向用户交付一条清楚的流程：给出模型、workload、base 配置、target 集合、资源及预算，流程自动准备或复用 base，按整组需要准备独立成本，再预测和比较完整 HTTP 耗时。需要寻优时，在同一预测器上提交有限配置空间与约束，输出推荐及其依据。

| 主线 | 本轮保留和验收的范围 | 不扩大承诺的部分 |
| --- | --- | --- |
| SGLang＋Qwen3-8B | 同机 TP1／2／4／8，HiCache 容量、页宽、写入与预取策略及联合变化 | 不等于其他模型、runtime 或卡组已有精度资格 |
| SGLang＋Qwen3-32B | 同机 TP2／4／8，保留相同 HiCache 能力 | 当前硬件下 TP1 的容量排除依据保留，不改量化凑进面板 |
| KT＋DeepSeek-V4-Flash | 当前单 NPU eager，CPU 线程、NUMA 池和每层 NPU 驻留专家变化 | 路由与放置有条件；不附带扩展 NPU graph、TP／EP、radix 或重叠调度 |

本轮不新增平台、模型或数据集，不开展生产并发、长期稳态、问答质量、复杂搜索算法或新资源报价研究。现有静态回放、独立目标评价和 NodeScale 保留，NodeScale 默认关闭；HiCache 仍只属于 SGLang。

整理针对实际职责和重复链路，不另起一轮全仓架构重建，不用行数、文件数或新增拒绝分支代替问题解决。

## 2. 什么算收尾

必须完成四项交付：

1. **共同问题得到处理。** 可复现的执行分支、计费或采集问题修在共同规则里；无法唯一归因的差额保留证据和边界，不能改成零成本或每格补偿。
2. **用户能够独立运行。** 三条主线均有可提交的示例，准备、缺口、复用、恢复和导出不依赖开发者在后台拼文件。
3. **结果有独立验证。** 修正后的完整 HTTP 有当前评分；新请求与搜索确认不进入训练，也不重新包装成开发前的未见数据。
4. **项目能够交接。** 输入、性能库维护、运行开销、结果解释和已知限制集中维护，代码、文档和数据职责一致。

精度目标是同配置和跨配置的单格误差均低于 10%；不恢复同配置 3% 门槛，也不以总体 WAPE 掩盖尾部。原有 110 格及其中 17 个超标格全部保留，不能只展示改善项。

区分两种结论：

- **精度达标的阶段性交付：** 本窗声明的完整评分范围全部达到单格 <10%，必做流程和独立确认也完成。
- **带限制的阶段性交付：** 必做工作、验证和交接完成，但仍有精度或收益未达；逐项列明影响格子、原因是否已证明、适用范围及后续需要。不能称作精度达标，也不能把没有完成的修复或验证归入“限制”后直接取消。

确定性的语义错误必须修正或明确保留为未完成项。时间敏感路径的单次不同则先检查规则、成本和运行波动，不能只为匹配一次观测强行固定路径。预算耗尽、构建通过和流程执行成功都不单独构成收尾依据。

## 3. 实现顺序和职责

| 阶段 | 主要问题 | 阶段交付 |
| --- | --- | --- |
| A：共同误差修复 | 为什么会系统性偏慢，为什么缓存路径不同 | 有机制依据的修正、代表验证、完整问题清单 |
| B：用户流程与规模开销 | 用户能否从自己的输入运行，成本和时间是否可预期 | 三线实际使用闭环、必要流程精简、开销报告 |
| C：独立终验与搜索确认 | 修正能否用于新请求，推荐是否真的有用 | 小型独立评分、有限空间全量预测、少量正常确认与最终回归 |
| D：整理和交付 | 代码、资产与说明能否交接 | 统一文档、资产取舍、分层交付和窗口关闭 |

A／B 是主要实现阶段。实现按完整调用链联合修改，多文件一起处理；相关功能齐备后统一检查、构建和少量代表运行，不按每个文件或每个成本缺口写一条日志、编译一次。

每个阶段交接前，审查该阶段起点以来的全部变更及受影响的未修改调用方，分别完成代码、文档、数据检查和少量分层提交推送，核对远端后再进入下一阶段。设备等待期间可以做独立静态分析和文档工作，不跳过交付边界提前实施下一阶段。

C 开始正常确认后，不再改变模型形式、结构规则或选点规则。D 以文档和资产整理为主；若 C／D 发现必须修改行为的问题，返回对应实现阶段，说明哪些结果失去独立资格，不把旧分数继续当作最终成绩。

### 先做什么，遇到问题怎样调整

先处理会让多个结果一起出错的问题：KT 来源计时与迁移、主存回载分支，再判断独立成本和限时预取还剩多少偏差。正常时间减去 profile 时间只能提供线索，不能直接成为修正量。每项问题先写清预期改变的工作、依赖或计费，再决定需要哪些新观察。

| 发现 | 下一步 | 可以结束这一项的依据 |
| --- | --- | --- |
| 确定性的工作、依赖或重复计费错误 | 在共同规则中修正，用原反例与一个未出错代表核对 | 原反例得到解释，相关工作与计费正确；不能只看总时间下降 |
| 结构一致，独立成本仍系统偏差 | 核对计时合同、覆盖和变量，必要时补一组共享事实 | 新估计有独立数据依据，并检查不同 base 和资源组合 |
| 同配置仍偏慢，但无法区分观察扰动与真实等待 | 做最小同条件观察对照，不扩整个矩阵 | 证明可剥离部分，或明确仍缺的因果证据与迁移限制 |
| 真实路径随短 timeout 波动 | 保留共同时间规则，按预定重复观察路径和耗时范围 | 说明预测对应的路径及不确定性，不要求复制每次随机路径 |
| 相同问题重复补采仍无新信息 | 停止该项扩采，回查工作定义和计费归属 | 形成可执行的修正，或明确尚未完成；不能因花完预算宣布解决 |

阶段 A 不以重跑全部结果作为日常推进方式；阶段 B 不以新增面板选项代替减少人工步骤。对结果和交接没有直接作用的美化、通用化或新诊断功能，本窗不做。进度按已经取得证据的交付项说明，不能把编译、启动或等待耗时当成完成比例。

### 三阶段建模边界

- 原始 DAG 及源依据只来自所选 base，通过 manifest 交接。
- 目标结构负责工作量、资源、依赖和条件分支，不读取回归系数；合法工作不能因缺成本而被删除。
- 成本层解析已证明工作不变的源引用及独立模型，不创建操作或改变缓存策略；条件在同一仿真时钟触发。
- HiCache I/O/control、Prefill、Decode、真实 CPU gap 和采集额外开销分别归属。完整 HTTP 不扣除难建模部分。

上述归属用于厘清责任，不新增一套逐函数硬编码的“影响边界”，也不要求所有内部细节都对应单独模型。

目标中的合法操作和分支由配置、workload 和执行规则主动生成，不能受限于 base 已出现的模板；缺少必要语义事实时明确指出，不逐格补模板。

## 4. 阶段 A：修正共同误差

### 4.1 先建立问题和证据的对应

复核既有逐格结果、正常原始窗口、来源报告和成本选择。把差额分别放到工作／分支、依赖／等待、源时间迁移、独立成本、采集扰动和正常波动中；一个格子可同时受多项影响。

以下是优先检查入口，不表示每行都要重新采集：

| 问题 | 代表 | 要回答的问题 |
| --- | --- | --- |
| KT 同配置偏慢 | 64 线程／8 池／32 驻留，长、短输入 | 图和工作没变时，额外时间如何进入了源成本和最终预测 |
| KT 多线程目标偏慢 | 主 base→128／8／24，长输入 | 独立 MoE 响应、非 MoE 时间和观察差额各能解释多少 |
| KT 池数和反向 base | 主 base→64／4／32；32／8／24→64／8／32 | 共同修正是否依赖某一份 base 或某个池数 |
| SGLang 限时预取 | 8B TP2 驻留→TP2 文件；32B TP2 驻留→TP8 文件 | 接受页数、剩余 Prefill 与等待为何不同，TP 变化是否改变了问题 |
| SGLang 纯主存来源 | 32B TP8 纯主存来源的同配置预测 | 为什么预测进入失败回载／重算，而原生能够回载 |
| SGLang 同配置时间差 | 32B TP8 驻留→同配置 | 请求工作一致时，源时间、独立响应与正常时间的差额来自哪里 |

先使用已有记录进行静态联查、时间分解、工作量和分支核对。目标 probe／真实成本只用于诊断，正常数据只用于评价，不能回写预测或训练。

### 4.2 KT：先处理来源和计时，再判断是否需要改模型

1. 联查原生观察、层响应、batch 残余、HTTP 边界和执行绑定。明确哪些是 CPU 服务，哪些是等待、搬运、结果处理和采集动作；父区域与内部响应不能重复收费。
2. 检查路由统计、设备事件、同步、记录写出带来的干扰。确需补证时，在同配置、同请求、同初始条件下做少量有目的的观察对照；不直接将 profile－normal 的差值当作可扣除常数。
3. 只有具备计时边界和依赖依据的采集额外工作才能剥离。保留与真实 NPU 执行重叠的部分、真实等待和 CPU gap，不按观测到的总差额整体缩放。
4. 非 MoE 工作若受资源变化影响，重新明确迁移条件或用独立事实估计对应变化，不能继续称作已证明不变，也不为每个目标添加残差项。
5. 上述边界明确后，再判断共享响应是否缺少必要变量或采用了不合适的粒度。串行前向内部无对外交错时，可以整体闭合，避免将“MoE＋相减余量”当作唯一表示；代价是旧逐层记录可能缺少完整结束边界，需要小型、成组的重新观察。新变量必须对应可观察机制，参数来自独立测量和算法，而非 target 耗时。
6. 同时检查另一份 base、不同线程和池数，保留原生路由漂移与 NUMA 放置条件。路由直方图差异不直接等于耗时误差。

若必须修改采集，优先保留预测必需的信息并降低扰动，不新增常态 snapshot 或逐专家／逐 token 的全面展开。CPU／NPU 内部没有对外交错时继续采用闭合区域；需要区分交错时只保留必要端口。

配置名称、base 身份、workload 标签和 target 残差不进入拟合特征或补偿。模型整体要能说明工作变量、参数来源、训练和预测方式，不要求每个内部细节单独建模或逐项赋予物理解释。

### 4.3 SGLang：先修缓存工作和分支，再修时间数值

1. 对照正式请求的设备命中、主存回载、文件接受和剩余 Prefill；逐请求区分预测工作不同与相同工作耗时不同。
2. 对纯主存来源，核对分配、保护、发布、消费、释放及失败返回的真实先后；修正资源状态或依赖，不用扩大池容量、忽略失败或改 ratio 特例绕开原反例。
3. 对限时文件路径，核对发起返回、后台进度、查询回合、最终检查、停止和接受。超时与取消仍在共同执行时钟中决定，不在执行后按 target 接受量修补。
4. 区分确定性规则错误与短时间窗口下的真实运行波动。必要重复在看新误差前声明，不能反复补慢样本或快样本让均值靠近预测。
5. 已正确的主存／文件路径和不同 TP 共同检查，防止只修某一种来源。原生动态分配可行性仍须如实报告，容量下界不能冒充完整部署保证。

### 4.4 阶段 A 的判据

- 每项确认缺陷都有共同修正位置、计费依据和代表运行证据；没有唯一归因的项明确缺什么观察。
- 同配置差额、目标 MoE 成本和 HiCache 分支不能混成一个全局校正倍率。
- 可复现的主存回载分支错误有对应反例验证；限时预取报告工作量与时间条件，不能只比总耗时。
- 修正检查正向、反向及原来较准的代表，列出改善与退步。不会因为当前分数接近 10% 就取消该问题。
- 联合源码及调用方审查、必要 Docker 构建和代表入口完成后交付；不在每次修改后跑完整面板。

## 5. 阶段 B：验收用户流程和运行规模

### 5.1 三条主线都从正式用户输入出发

以现有三份模型请求为起点，核对用户真正需要填写的部署、workload、base、target、资源和预算。参数在 CLI、面板、预览、有效输入和结果导出中保持同一含义。

三条线各完成一次正式使用闭环：预览→准备／复用→整组预测→结果与来源说明→导出。至少覆盖以下情形，但不要求每条线都重复一遍全部故障：

- 新 base 的真实采集；同任务重复运行能复用，不新增 native 启动。
- 性能库已覆盖、实际缺一类响应，以及一条代表性的空库自动准备。按整组需求共享采样，不要求用户手拼模型文件。
- 预算不足、设备等待、非法部署、缺成本与运行失败分别给出原因和继续办法，不将它们都标成普通预测成功。
- 停止、继续、服务重启后原 worker 的处理，以及本任务资源回收和历史用量保留。
- CLI 与真实浏览器的有效目标、状态和预测值一致，JSON／CSV 完整可下载。

复用 A 已通过正式入口形成的采集，同时证明机制和首次使用，不为了验收再造一套相同数据。空库验证只选择一条能代表自动准备的任务；其余主线可使用已维护的兼容库，不重建全部性能库。

静态预览可以说明已知准备动作与上限，不虚构尚未生成工作时的精确校准费用、完成时间或覆盖保证。

### 5.2 性能数据库的交付要求

- Base 只提供可迁移成本及结构依据；变化工作使用独立事实。各模型、TP、硬件和计时条件匹配后才能使用。
- 同一组目标共享准备结果；去重入库、模型选择、只读导出及本次实际来源清楚，未选中的历史数据不自动参与训练。
- 补一项缺口只更新相关响应；既有合格响应不因无关补采被覆盖。相同缺口未解决且无新事实时停止重复采样。
- 输入和报告区分已测工作点、新组合、允许的外推与缺数据，不能只给出一个没有依据的置信度。
- 改计时边界时先判断哪些旧事实仍兼容。必要更新由正式维护入口完成，不静默复用不兼容模型，也不增加内部版本、冻结包或 hash 握手。

### 5.3 规模和效率

KT 的资源可行性必须检查原生实际的逐 NUMA 绑核配方，不能只比较线程总数和 NUMA 节点总数。Base 记录各节点物理核对应的逻辑 CPU 和容器允许的 CPU；目标按原生均分规则检查，不能把绑核失败后继续运行的退化路径当作正常资源伸缩。不可行目标保留明确状态并从推荐排除，不用新的成本系数掩盖；缺少拓扑的旧来源保留未验证资格。

小型代表和已有大 workload 分开测量。大 workload 复用原 520 请求、原输出长度和三目标，只核对开销，不再采它的正常真值。

记录外层完整墙钟、模型启动／准备、base、共享性能准备、来源解释、目标仿真、报告与空间。无法分离的部分标为未分离，不填零。首次运行与复用分别说明；多任务等待、进程 RSS、容器上限和实际保留量不能混为同一指标。

检查同一批目标是否只解释一次 base，是否重复读取性能库、解析事实、序列化、启动进程或输出没有消费者的细图。发现整条冗余链时统一消除，不为缓存本身再加一套管理层。

同输入、同成本和相同诊断条件下核对时间、工作量与内存。必要正确性修复引入额外工作时说明代价；不以省略工作换提速，不承诺尚未证实的固定倍数。工作规模通过用户声明的请求数和生成长度控制，不硬截断图或跳过执行分支。

阶段 B 交付需包含：三份请求、用户实际操作说明、首次／复用记录、开销拆分和规模边界。与任务相关的无用分支、重复转换和 debug 输出在进入 C 前清理，避免终验后再改行为。

## 6. 阶段 C：联合独立终验和搜索确认

### 6.1 在正常结果出现前确定实验

从已有真实文本资产中选择未用于本窗开发的记录，保留身份、tokenizer、截断和回访规则；不引入新的数据集或长度范围。旧 110 格和上轮 8 格用于本窗修正后都作为已见证据，不能重新称作本窗未见验证。

两款 Qwen 各采用一组约 12–20 个正式请求、16–32-token 输出的有界前缀回访序列，实际工作集由 tokenizer 与原生页几何核对。KT 采用 2–4 个正式请求、32–64-token 输出的新文本，输入保持已有独立数据可覆盖的范围，至少一组输出为 64。

## 8. 评价口径与必做检查

正式 HTTP 从首个正式请求发出到最后一个正式响应结束，准备边界由输入声明；真实请求间隔、CPU gap、未归属控制、HiCache I/O/control、Prefill、Decode 和首用影响全部保留。

`APE = 100 × |预测正式 HTTP − 正常均值| / 正常均值`。同时报告有符号误差、样本数、范围、WAPE、最近秩 P90、最大值及 ≥10% 的格子。跨配置／同配置、各模型和各 base 分开；没有完整评分时完整指标留空，子集另列。

有符号百分比误差为 `100 × (预测 − 正常均值) / 正常均值`，正值表示预测偏慢。`WAPE = 100 × Σ|预测 − 正常均值| / Σ正常均值`；P90 是将有效格子的 APE 升序排列后取第 `ceil(0.9 × 格数)` 项。正常运行关闭 profiler 和 Markov 采集探针；环境、输出长度、准备边界及缓存初态必须与声明条件一致。历史 110 格、315 格回归与本窗新请求分别报告，不相加冒充独立样本数。

### 三阶段各证明什么

以下三阶段指建模职责，与窗口 A／B／C／D 的工作顺序不同。实验按需取得证据，应用预测不要求用户采 target：

| 建模阶段 | 本窗实验报告 | 不得由此推导的结论 |
| --- | --- | --- |
| Base 原始 DAG | 对具备详细观察的代表做源静态回放，列请求边界、时间及依赖冲突；只有语义记录的来源说明观察资格 | 语义来源已完成细图验证，或 profile 回放接近就说明正常预测准确 |
| Target 工作与依赖 | 原反例和代表目标逐请求核对命中、回载、接受、重算、生成迭代及必要依赖；未观察部分单列 | 节点数接近、query 向量相同或 E2E 达标就代表整张目标图正确 |
| 成本与最终执行 | 完整 HTTP 评分、可迁移成本和独立模型来源、覆盖／外推及运行开销 | 真实成本替换回放就是正式预测，或少量新请求证明任意配置泛化 |

详细观察优先复用已有兼容记录；只有本轮修改影响了原证据，才对受影响代表补采。不能为了凑齐三份报告把所有语义 base 升级成大 trace，也不增加与正式流程平行的评价框架。
