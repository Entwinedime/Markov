# 全量重构：保留建模思路，重建实现

开始日期：2026-10-27。

目标：用清楚的三阶段流程重新实现现有预测能力，减少重复工作和维护负担，争取同输入批次至少 10× 提速，
并形成能表达资源成本的负载与搜索问题。参考旧实现的机制和证据，不整体复制或继续叠加旧流程。

阅读时先用第 1—5 节确定范围、交接与阶段依赖，再按第 6—12 节实施；第 13—14 节用于核对旧机制和处理取舍。
阶段开始前重新核实输入与依赖；下面的实现方法是指导，不要求为每段文字创建类、文件或单独工作流。

## 1. 起点与范围

以归档旧实现为机制与行为对照，重新建立正式源码、配置、环境及文档。
保留本地完整归档、第三方依赖与必要数据，不因重构恢复旧自动寻优研究。
计划只记录任务、方法和判据；当前基线、执行资格与恢复起点由同窗口 status 单独维护。

本次重新建立正式源码，保留这些能力：

- manifest 交接、base 采集及已有来源复用、原始 DAG 与源静态回放。
- SGLang HiCache 状态、I/O/control、Prefill/Decode 目标工作与依赖生成。
- 未变工作成本迁移、独立性能采集/数据库/离线训练、目标成本填充与统一仿真。
- 完整 HTTP、独立结构/性能报告、现行规则下的显式静态 oracle-cost 诊断。
- KTransformers 同级采集及普通 DAG/仿真，默认关闭的 NodeScale。
- 直接预测、矩阵准确性实验、有限配置搜索三个上层用途，以及必要的外挂复现示例。

本轮不扩充任意模型、TP、框架版本、分布式部署或复杂组批，不设计新的原生调度器。
采用 markov-next 的完整工程与文档维护规则；建模仍沿用本项目的三阶段 DAG 路线，不移植其模板控制系统。
不恢复旧研究的大空间、SMAC 对照和预算耗尽后的补算，也不为精度逐格增加参数。

### 1.1 支持范围如何落到实现

“保留能力”必须落到具体运行路径，不能只保留模块名。阶段 A 先从已有配置、来源与依赖声明中列清实际支持条件，
后续能力按条件判断，不用 C1–C5、workload 名称或实验格数作为开关。

| 能力 | 本轮应交付 | 不应据此声称 |
| --- | --- | --- |
| SGLang HiCache | 原面板所需页几何、容量、写策略、回载、预取、超时及控制语义 | 任意 SGLang 版本或缓存后端都支持 |
| Prefill/Decode | 支持模型和后端内，随命中、上下文与生成步变化的工作量及依赖 | 任意模型、算子融合、组批或并行方式通用 |
| 完整 HTTP | 准备状态连续，正式起止明确，保留计算、I/O、CPU、等待与残余成本 | 生产吞吐、P99 或请求内容生成预测 |
| KTransformers | 自身采集、manifest、普通 DAG 与仿真进入共同流程 | 为其套用 SGLang HiCache 规则 |
| NodeScale | 按原操作匹配并调整成本，默认关闭 | 用倍率修补正式预测误差 |
| 静态回放 | 源观测回放，以及现行规则下固定目标结构的 oracle-cost 诊断 | 恢复所有历史版本，或用 target 成本决定新结构 |
| 上层应用 | 用户预测、示例矩阵、有限资源/策略搜索共用预测器 | 本轮完成任意大空间自动寻优研究 |

新模型或配置只有在来源语义、结构规则、成本适用域均具备依据时才纳入支持范围。
已有资产缺失与能力不支持分别处理；不以“没有验证数据”删除应保留能力，也不以“代码能分支”授予泛化资格。

## 2. 什么保持，什么重新设计

| 保持的主思路 | 重建的实现方式 |
| --- | --- |
| base trace → 原始 DAG | 原生字段在适配层解释一次，源图和语义依据明确归属 |
| 原图加目标配置 → 目标工作与依赖 | 使用统一紧凑目标程序与条件规则，不反复复制原生 trace 片段 |
| base 未变成本与独立模型 → 预测耗时 | 工作先确定，数值后绑定，测量、模型和查询分别维护 |
| 依赖、资源和状态共同决定 E2E | 一个执行器和时钟，只在有语义作用的边界推进相关模块 |
| 实验独立评价 | 原始图、目标结构、完整性能分别报告，报告不成为算法输入 |

三阶段不要求三个进程或三份大文件。阶段二可以输出尚待完成/发布/超时触发的条件程序，
阶段三提供服务时间并驱动执行，到必要边界后调用结构规则产生后续工作。
成本不决定合法操作，但服务时间可以通过真实执行条件改变之后的分支。

### 2.1 用一个请求贯穿全流程

以“同一请求在 target 中可复用更多前缀，但需要从主机回载”为例，整条链应当能这样读懂：

1. source 解释层取得请求 token、前缀关系、模型布局、执行资源与观测依据；不把 source 命中结果当成 target 命中结果。
2. target 状态规则根据当前可见缓存、容量与策略决定复用、回载和剩余计算，输出页范围、操作和依赖。
3. CPU 提交、传输服务、完成通知、缓存发布是不同边界。需要等到发布的计算只依赖对应发布，不依赖无关后台队列全部排空。
4. Prefill 的待计算 token 和有效上下文由上述结果决定；Decode 使用实际生成步骤及逐步增长的上下文。
5. 成本层按工作描述查询独立模型；只有工作与条件确实不变时才引用 base 服务成本。
6. 执行器推进同一个时钟。若预取超时先发生，调用规则处理取消、继续回载或重新计算，再为新工作绑定成本。
7. 正式请求完成边界给出 HTTP 时间；实验评价随后独立读取 target 观察，不能反过来修改本次预测。

这个例子同时是审查方法：若必须打开多个报告、依靠 cell 名称或阅读成本系数才能解释结构，就还没有理顺职责。
不要求把全部流程写在一个函数中；顶层应显示这些步骤，细节各有所有者。

## 3. 重构必须达到的效果

### 3.1 可读性与规模

新实现争取约 40,000—45,000 行、尽量少于原规模一半，50,000 行不作为硬门槛。
按相同扩展名统计 Python、Shell、C/C++、头文件、采集、应用与 examples，不将代码迁出范围凑数。
归档不算删除，旧代码行数单列；新实现的规模来自减少职责重复，保留合理空行和注释。

完成后应能回答：谁解释来源、谁决定目标工作、谁提供成本、谁拥有状态、谁推进时间、谁评价结果。
修改一种 HiCache 策略不同时修改成本公式；修改一种模型形式不改结构生成；增加一种报告不改执行器。
同一规则若需要在多个流程修改，应先合并职责，不增加适配检查或转发层。

### 3.2 预测效率

争取相同机器、输入、目标集合、并发、成本与诊断条件下，完整批次至少 10× 提速。
同时报告单目标延迟、准备开销、吞吐和峰值内存。局部查询提速、减少输入或提高并发不能冒充整体提升。
历史运行只作量级参考，受控新旧比较须在最终验证阶段重新建立。
首轮不额外承诺 30×、100× 或扫完旧 10,152 点空间，以免再次被无关实验拖住。

### 3.3 正确性与精度

优先保持支持范围内的工作、必要依赖、缓存决策、发布顺序和完整 HTTP 含义。
数值默认对照相同成本输入；修复旧机制造成差异时，明确旧问题、依据和影响。
最终恢复原 60 cross，再恢复扩展 72 与留出 54，共 186 格；self 参照单列并按实际调用计费。
完整 HTTP 保留 gap、未归属成本和 Prefill/Decode。沿用 WAPE≤3%、P90≤5% 的评分口径，逐格尽量低于 6%。
本轮不以强行达到历史尚未达到的精度门槛作为重构完成条件，也不通过 refit 或清除成本制造通过。

## 4. 分工与交接先定清楚

### 4.1 五项必要共同合同

| 合同 | 需要说明 | 不应携带 |
| --- | --- | --- |
| 源上下文 | 不可变源图、逻辑身份、请求/资源、语义事实与成本依据引用 | target 真值或目标执行状态 |
| 工作描述 | 操作、实现、计时口径、shape/页/字节/参与者与条件 | 回归系数、数据库路径、预测耗时 |
| 成本绑定 | 未变源成本引用，或独立工作查询；说明适用条件 | 选择结构分支的逻辑 |
| 目标程序 | 操作、依赖、资源、端口及时间触发条件 | 原生框架对象、逐节点报告字符串副本 |
| 执行结果 | 时间、完成/发布、必要来源与近似 | 另一份自行推算的缓存状态或图 |

这些是信息职责，不强制每项新建一套类、文件或序列化格式。
共同类型要说明单位、生命周期和可变性；入口校验一次，不在内部逐层解析原始 JSON。
源节点身份与压缩执行编号可以不同，必须能追到对应来源；不使用摘要或内部版本证明有效性。

### 4.2 细粒度与粗粒度

保留命中、分配/释放、提交、入队、服务完成、缓存发布、取消、重试、通信到齐和 HTTP 边界。
连续页用范围；没有外部消费者或状态改变的连续服务段可以汇总。
CPU、worker、设备可能重叠，静态子图要保留各必要入口和出口；区域会与外部共享资源交错时不能直接压成总时长。
零耗时标记也可能有因果作用，不能按 duration=0 删除。压缩前绑定原操作成本及 NodeScale，避免舍入或计费变化。

### 4.3 独立成本与残余成本

base 只迁移已证明不变的工作成本，发生变化的操作查独立模型。
CPU 服务、队列等待、设备服务、I/O 服务、残余 gap 与 probe 开销分开；可解释等待由依赖产生。
尚不能解释的 gap 保留明确来源和近似，不把它塞进 I/O 或计算系数。
模型训练与选择基于独立工作样本，评分和 target 真值不得进入需求、训练或 readiness。

### 4.4 状态归属与生命周期

| 对象 | 唯一所有者与存活范围 | 其他模块怎样使用 |
| --- | --- | --- |
| 原始记录、源图、语义索引 | source；一次准备后供同源目标只读使用 | 引用稳定身份与必要视图，不逐 target 重做解释 |
| 目标缓存、容量、前缀与发布状态 | 每个 target 的 HiCache 状态组件 | 规则统一读写；报告只读结果，不自建另一份缓存模型 |
| 节点执行、worker 队列、资源占用与时钟 | 每个 target 的执行器 | 工作声明资源和条件，不能另设隐式排队时钟 |
| 独立模型和覆盖索引 | 一次预测会话的只读成本提供者 | 多 target 共享；每个 target 的查询统计和运行时特征分开 |
| 采集预算、启动与恢复事实 | preparation 的单任务对象 | 子采样动作回传实际消耗，不各建完整工作流 |
| DB 测量与训练输出 | performance 维护流程 | predictor 只消费选定模型，不训练、不打开 target 评分 |
| 比较与评分结果 | 独立 evaluator | 不回写 source、预测状态、模型或准备资格 |

结构层与执行器通过有类型的动作、端口和完成事件协作；不再让每个节点遍历所有模块询问是否有事可做。
一个操作可有 CPU 返回、设备完成、缓存可见等不同端口，不能把它们塞进同一个“完成”时间。
共享的是不可变定义，不是目标运行状态；不能用 target 之间共享的可变缓存换取速度。

### 4.5 跨语言交接、时间与失败

Python 负责外部输入、采集准备与应用编排；C++ 负责源图、规则、成本求值和时序执行。
JSON 只出现在正式边界，进入核心后使用类型与紧凑索引；不要在每层重新生成字典或把完整模型包塞入每个 target 配置。
首版沿用显式文件/进程交接即可；不为重构增加 RPC、常驻服务或新二进制协议。
同一会话的 base 和成本包各装载一次，target 请求只携带差异与必要引用。

内部预测时长与相对时间使用整数 ns，原始观测坐标保留其单位与时钟来源。
源时间用于关联和校准，不默认变成 target 的释放时刻；目标请求到达由 workload 的到达规则决定。
尤其是串行请求，下一请求从预测的前一请求完成继续，不能照搬 source 的绝对到达时间造成隐藏等待或错误重叠。
旧 us 数据在读取边界转换，输出秒数在报告边界转换；舍入规则在比较前确定，不按结果调整。
墙钟区间、线程 CPU 时间和服务估计不能混用；线程 CPU 时间不包含阻塞等待，嵌套墙钟也不等于自身服务。

输入非法、缺来源事实、缺结构规则、缺成本、成本域外、资源不可行、运行失败、评价缺真值分别表达。
错误要指向一个可处理的原因；缺成本不能变成零，有限的近似结果必须说明近似是什么。
同组中一个目标失败不伪造全组成功，也不应丢失已完成目标；调度器按错误类型决定继续其他独立目标或停止公共准备。

历史提交仍可恢复归档，不删除本地内容。业务源码从新的开发分支开始，不直接在主分支交付。

### 5.1.1 B—D 联合实现与交付

B—D 采用一个联合实现与维护交付批次，分别保留来源解释、目标工作生成、成本与执行三项职责和各自报告。
原有任务和收口条件全部保留：KTransformers 真实来源、不可变源坐标、同源多目标复用、主动生成合法分支、独立成本与完整 HTTP 都必须形成证据。
中途的源码检查点、局部回放或限定范围运行不等于联合批次交付，也不授予尚未验证的框架和场景资格。

这样安排是因为模型布局、已解释工作、成本引用与目标工作描述存在同一条生产消费关系。
有实际消费者时一起定义并接通，能够删除无人消费的原始参数副本和占位字段；不能要求 B 先复制完整参数表，再由 C/D 各解释一次。
实施时先有原始来源与原始坐标，再接逻辑工作与状态规则，最后绑定成本和执行；目标耗时不得反向决定工作是否合法。

来源语义索引在同一次准备中建立，目标之间共享；真正的多目标连续执行在 D 验证。
联合期间可前移取得缺失事实所必需的 E 环境和最小采集；KTransformers 验证及关键源事实仍须在联合交付前完成，不能留到最终验收补名额。
不因此提前恢复整个数据库维护平台，E 剩余职责仍单独交付。约每五个实质批次的整体审查和必要检查照常执行。

### 5.2 阶段 0 的筹备收口

核对旧源码、文档、配置、环境和必要来源的归属，区分已提交历史、工作区文档和本地运行资产。
在取消 deprecated 跟踪前，确认需要保留的旧内容已有明确历史提交或本地保留位置；不使用删除文件的方式整理索引。
创建开发分支并完成筹备文档交付，阶段 A 从该已推送提交开始。根入口、格式配置和忽略规则的变更同步说明。
这里不重新运行旧搜索，也不为证明归档而加载大型 trace、构建旧程序或清理 data。

### 5.3 每阶段采用一个完整工作批次

阶段启动先确认输入、消费者、范围和必要检查；优先沿“生产者—合同—消费者—入口”一起修改多个文件。
阶段收尾审查这一整条链，再运行能支持本阶段结论的最小验证，最后整理文档、数据引用和分层提交。
没有可运行增量时明确只交付设计或源码资格；不得把帮助命令或 dry-run 当成业务恢复。

状态文件只写当前快照，日志只记录有意义的交接、取舍或失败，实施细节留在代码和正式结果中。
不为本计划新增任务平台、检查生成器或逐函数迁移账本，也不按每个小步骤单独计一次阶段完成。

## 6. A：先建立能读懂的主干

本阶段解决“用户从哪里进入、各层交接什么、后续代码怎样构建”，不先写一组没有消费者的接口。
输入是归档合同、实际配置和已声明资产；交付是能被 B—F 连续扩展的最小正式主干。

### 6.1 输入和模块装配

1. 将输入收敛为部署、模型、base、workload、targets、性能依据与执行资源；base 配置采集和已有 manifest 复用采用明确分支。
2. 区分外部校验与内部类型。目标配置不能携带真实耗时、评分目录或模型修正参数；实验标签仅保留在上层定位结果。
3. 说明源上下文、工作描述、成本绑定、目标程序和执行结果的交接，逐项指出生产者与消费者；只实现本阶段实际消费的字段，其余随消费者引入。
4. 明确框架、runtime、模型布局与资源的适配接口；共同核心不读具体框架配置或原生函数名。
5. 将配置到类型、类型到结果的转换放在边界；顶层直接表达“准备源—规划目标—填成本—执行—输出”。
6. 用最小真实输入说明适用范围；不先建设通用对象工厂、可编程规则语言或动态插件注册中心。

源码按 Python 的 workflow/instrumentation/artifacts/adapters 与 C++ 的来源/结构/成本/执行职责组织。
C++ 头源同目录，以 src 为 include 根；CMake target 按真实依赖建立，不为每个小文件单建一个库。
根构建、modeling Docker、Python 包导入和薄 Shell 入口在这一阶段恢复；真实原生 SDK 依赖仍留在推理侧。
最小正式程序应实际解析并表达输入合同，不用空 main 或虚构结果证明构建链完成。

### 6.2 用户入口与失败输出

入口形态先作为实现候选，实际交付时再写入操作说明；矩阵编排留在 examples：

```text
scripts/markov.sh predict --request scenario.json
scripts/markov.sh profile --request capture.json
scripts/markov.sh prepare-costs --request performance.json
scripts/markov.sh evaluate --request evaluation.json
scripts/markov.sh search --request search.json
python3 examples/run_matrix.py --request experiment.json
```

按真实能力逐个提供子命令，不先创建返回成功的占位入口。最先交付输入预览，随后连接源回放与已准备预测。
预览仅解析、核对已有来源并列准备动作；没有读入源语义时，必须说明结构和动态成本需求还未求得。
预览不启动设备、构图、训练、仿真或清理。执行入口遇到缺口应指向具体输入或维护动作，保留底层错误位置。

### 6.3 代表输入和验收安排

按语义选择最少必要输入：普通 self、命中改变计算、跨层 I/O、容量压力、超时/取消、尾部发布。
补充一个 KTransformers 普通来源及一组 NodeScale/静态回放用途；可以由同一真实案例覆盖多个机制。
记录来源 manifest、请求工作量、部署、成本与正常真值的角色，查看 target 结果前确定选择理由。
这些声明放在正式 example 配置或运行输入中，不额外维护大型验证清单系统；最终 186 格的具体枚举由例子负责。

**必要检查：** 配置边界、导入无副作用、帮助/预览行为和 modeling Docker 内正式最小目标的构建。
预览未运行业务的边界必须在输出中看得见；现阶段未接通能力不得被写成已恢复。

**收口条件：** 后续阶段可沿同一入口接入能力；已实现字段有真实消费者，未启用部分只留设计说明，不预建类型和占位代码，构建链不依赖 deprecated。

## 7. B：源信息只解释一次

本阶段把 base 的原始观测变成可复用的源依据，并交付源静态回放；不开始用 target 数据弥补语义。

### 7.1 从 manifest 到源事实

1. 只读取 manifest 指定的通道、窗口、部署及关联输入，不扫描 data 选择看起来合适的文件。
2. 统一时钟和请求身份，保留原始记录位置；不直接用事件名称或数组顺序当作跨线程依赖。
3. 框架/runtime 适配器解释 CPU 调用、提交、worker、设备、同步与通信；模型适配解释必要布局和计算工作。
4. 对嵌套区间明确包络与自耗时，不能把父调用墙钟、子调用和设备服务全部计费。
5. 建立请求/调用/资源归属和必要索引；按需解析语义字段，原生大字符串和参数表不进入每个目标的热数据。
6. 对无法解释但在窗口内的成本保留来源与未归属标记；不要先删掉它们再宣称完整源图。
7. 同一原生记录在同资源、同一时刻的端口共用事实节点；不同记录不因时间相同而合并。提交与同步连到该事实，不能只约束它的平行副本。

源图表达观测到的关系。尚未证明的等待不能因“时间刚好接近”就连接成硬依赖；有歧义时保留定位信息，
回到适配器或最小补充观察，而不是在核心累加事件名判断。

### 7.2 共享来源与时间边界

源上下文包含不可变图、语义索引、请求事实、资源和成本依据；同源目标共享这些对象，目标状态独立建立。
source 成本校正使用单独视图，不能覆写原始坐标和观测值；普通构图/回放不创建一份目标迁移图。
先使用同进程内只读引用实现共享，进程并行到 D、F 再处理；不先增加持久共享内存服务。

准备请求与正式请求连续构图，区分三种边界：采集范围、准备完成与正式窗口、后台最终清空。
序列外的设备工作只有在依赖上影响正式请求时才进入其完成条件；源静态回放保留原始观测时序。
普通回放所需的就绪、依赖和资源调度作为后续执行器基础，不另留长期维护的回放实现。

### 7.3 源报告与交付

报告给出已读取/可解释/未归属的范围、正式起止、回放差异和不能关联的事实。
设备服务、等待、零时长边界与采集开销分开对齐；核对导出箭头表示调用开始还是实际提交，不将二者混同，也不使用设备空闲补时掩盖缺少的执行事实。
原始记录总数、活动节点数和执行节点数分别表达；不能以节点数量减少来证明信息正确。
SGLang 与 KTransformers 的正式来源都应进入同一构图与回放入口，专属事实在各自适配器解释。

**必要检查：** 一份小而完整的 SGLang 来源、一份适用 KTransformers 来源；核对请求起止、嵌套计费、同步和源回放。
在同一次准备中复用同一 source，确认不会第二次解析 trace、建立相同索引或复制全套属性；以计时/计数及所有权审查为证据。
缺少真实 KTransformers 资产时前移最小采集依赖，不能因 SGLang 跑通就将该能力记作完成。

**收口条件：** source 解释一次，原始坐标不变；源回放有当前结果和未解释范围，后续目标修改不污染它。

## 8. C：主动生成目标工作，减少重复落图

本阶段的重点是“哪些工作必须发生、依赖什么”，不以成本是否好拟合决定要生成什么。

### 8.1 HiCache 的状态、工作与效果

将状态规则、操作生成和资源映射分开：规则决定合法动作；适配器给出实际执行方式；执行器报告真实完成事件。
页、前缀和容量状态只维护一份，操作的执行量、完成量、发布可见量分别保存。

| 机制 | 必须表达的语义 | 应避免的捷径 |
| --- | --- | --- |
| 前缀命中与页几何 | 从真实 token/前缀关系和 target 页规则得到可复用范围；处理不满页、分裂和有效长度 | 把 source 命中率按容量比例缩放 |
| 分配、引用与淘汰 | 哪些页占容量、哪些被引用、何时真正可释放；申请失败后的合法等待/重试 | 按请求结束一次性假定所有页释放 |
| 写入与回写 | 策略触发、提交、设备/主机/存储完成及可见性，必要尾部工作 | 将提交返回等同于持久化或发布 |
| 回载与逐层消费 | 传输范围、资源、层间消费依赖与可见页；工作可部分完成 | 强制整批 I/O 全完成后才允许所有后续计算 |
| 预取、超时与取消 | 何时启动、超时从何时计、取消后哪些工作仍完成或继续占资源 | 先看 source 的最终命中再决定 target 分支 |
| 后台工作与请求结束 | 背景工作可继续影响后续请求，正式响应无需等待无关尾部 | 用全局队列清空时间当 HTTP 时间 |

阶段实现前从支持的框架代码和已有观察确认这些机制的实际含义；表格是需要解释的范围，不预先规定所有后端行为相同。
base 未出现过的合法动作由规则和工作描述生成，不要求查到 source 的同名模板。
传输的成本单位和发布粒度须与实际后端一致：整批跨层 DMA 只生成一次对应服务，不能按层均摊后虚构提前可见；真正逐层传输的后端才按相应层边界发布。

分配工作还须区分常规执行、内核规格首次准备和运行时首次加载。目标维护自己的分配/归还轨迹与已准备规格；
适配器据此解释实际索引视图和编译缓存键，不能照搬 base 的编译次数、指针视图偏移或缓存命中。
声明内存/磁盘编译缓存的初始状态，分清已准备、重新加载与需编译的工作；没有必要输入时报告缺口，不能默认免去准备成本。
成本来自对应独立样本，首次加载与常规编译若行为不同应分别表达，不能让一个平均残余常数吸收所有情况。
来源确实不足以生成时，给出缺事实；不能借 target trace、target E2E 或逐格特例补洞。

### 8.2 Prefill/Decode 的工作描述

缓存规则先确定可用前缀、待计算 token 和必要 I/O，再生成对应的计算工作。
线性层等普通计算由参与 token、模型尺寸与实现决定；注意力还依赖有效上下文、query 长度、布局和 mask 等真实条件。
不要把全部 Prefill 按一个 token 比例缩放，也不要把 Decode 每一步都当成相同上下文。

Decode 的步数由声明/回放的生成工作决定，上下文随每步增长；本轮不预测自然输出内容和未来 EOS。
父层、融合算子、CPU 提交、worker 和设备/通信按实际后端界面划分；不能父层成本与子算子双算。
若相同计算可以引用 source 区域，应同时证明部署、shape、实现、资源及外部依赖兼容，不能只比较算子名字。
变化工作走共同生成器，不为 host、allocator、collective 各复制一套相近的图拼装主流程。
输入准备除分配外，还包括请求页表写入、位置生成和注意力元数据；按真实工作变量生成其必要调用及依赖。
调用间区间先核对是否包含尚未建模的原生提交、同步或编译/加载，不能把这些已知工作藏进 residual。
输入准备保留调度流与计算流的交接；Prefill 在采样调用之前的序列位置减一也属于实际工作，不能因贪心采样未消费该参数而删除。
需要新增内核族时，规格缓存与首次加载须按实际共享支持库、启动器接口和内核程序区分，不能把原有单接口假设推广为任意初始化。

### 8.3 有条件的目标程序

第二阶段输出操作、端口、资源与条件规则，并非强行提前确定每个超时后的分支。
触发点用有类型的动作登记到节点/事件；普通节点只推进自身状态，不能广播遍历所有请求、prefetch、wait 和模块。
规则接到“完成/发布/超时”等事件后生成后续工作，成本层为该工作估时，执行器继续推进同一个时钟。

图改写必须原子提交，明确组件所有权、新工作入口/出口、资源归属和失效节点。
已开始工作不能回写依赖或成本；取消遵循原生语义，不能简单回收已经在途传输占用的资源。
同刻事件的顺序由因果和原生语义确定，不按容器遍历顺序或为使结果更准确临时排序。

### 8.4 共享、压缩和依赖稀疏化

| 区域 | 首选表示 | 必须保留 |
| --- | --- | --- |
| 未变的重复层/计算区域 | 一份定义加各实例的绑定与执行状态 | 实例身份、资源和外部依赖 |
| 无外部交错的连续服务 | 一段可汇总工作 | 原操作成本与诊断映射、总服务时间 |
| 多入口/出口的静态子图 | 共享局部定义，必要端口执行 | 中间消费者和资源重叠，不简化成单一 duration |
| 逐页状态变化但同质连续页 | 页范围和必要分界点 | 取消、发布、消费或淘汰引入的真实分界 |
| timeout、发布与容量释放 | 显式事件/动作 | 即使零成本也保留因果作用 |

不要先生成千万级节点再压缩；在工作生成时选择表示。也不要为追求压缩引入第二套规则或报告专用图。
依赖优先连接必要的资源前沿；去重在插入/批量构造时完成。只在可证明传递关系时减少同步扇出，
不能把所有 sync 边都当冗余；多 stream、多出口和通信到齐要分别考虑。

**必要检查：** 用真实来源的受控变换核对工作量、资源和端口；重点是新增合法分支、部分 I/O 完成与 Prefill 工作改变。
时间相关分支在具备实际成本的 D 阶段闭合验证；如果不能形成独立的结构交付，合并 C、D，不能用零成本假运行。

**收口条件：** 每种已支持变化都能解释工作如何生成；规则不读模型参数，不变区域不被无谓删除重建，压缩依据清楚。

## 9. D：成本与执行汇合，保持一套时间

本阶段先消费有依据的已有独立模型，把单目标预测真正接通，再优化反复发生的查询与执行工作。
数据库导入、训练和设备补采在 E 完善，不能让它们成为每次预测的隐式动作。

### 9.1 绑定方式与成本口径

| 成本来源 | 何时可用 | 必须保留的依据 |
| --- | --- | --- |
| source 服务迁移 | 操作与部署、shape、实现和条件确实未变 | 源记录引用、原始与校正值、迁移条件 |
| 独立模型 | 工作改变或新生成，且存在适用模型 | 操作/实现/计时口径、工作变量、测量范围和模型来源 |
| 单列残余近似 | 有来源但暂不能由因果与服务解释 | 源区间、适用假设及不确定性；不伪装为 I/O 或算子系数 |
| 缺失 | 无合法来源或不允许外推 | 具体缺口，不返回零或暗中沿用无关 source 节点 |

CPU 自身服务与队列等待分开，父包络和子服务分开。正常 CPU 校正只作用于对应观测服务，不再次扣减设备或其他区间。
源 residual gap 迁移只能在明确上下文下作为近似；目标中新生成而无依据的残余成本要报缺口，不通过“执行成功”掩盖遗漏。
完整 HTTP 不能删难以解释的部分；报告分别说明未归属来源、残余近似和真正无法给出的预测。

第一轮先保持已知模型形式与测量依据。旧成本包若需要转换，使用显式一次性转换，保存来源与单位，不长期同时支持多套旧字段。
结构/成本接口稳定前不更换成更复杂的学习器；修正规则和改变公式必须区分原因与证据。

### 9.2 各类成本应如何解释

先归并具有相同计费含义的工作，再决定是否共用模型；不能把同一瓶颈人为切成许多逐函数参数。
下表是审视模型的起点，不规定所有服务必须线性，也不要求重构时立即替换已有形式。

| 成本类别 | 工作变量与模型含义 | 数据与边界 |
| --- | --- | --- |
| I/O 服务 | 方向、通道、有效字节/页、批次；可从固定启动项加字节数/有效速率起步 | 系数来自独立传输服务测量；主机缓存、存储状态和批量行为决定适用域，排队另算 |
| 固定/规模相关 CPU 控制 | 操作类型、页/对象/批次数等真实工作量；典型响应或固定项加规模项 | 使用校正后的自身服务；不能用父包络、等待或 target 总误差训练 |
| 普通计算 | 算子实现、M/N/K、token 数、dtype、布局；几何相同工作共用响应 | 对应原生实现的独立样本；层数表示执行次数，不能同时乘到单次成本与节点数量 |
| 注意力 | query/context 长度、head 布局、批次及实际实现；按有效工作而非整段 Prefill 比例估计 | 融合、分页和 mask 条件需要对应依据；Decode 是上下文变化的一系列查询 |
| 通信 | 字节、参与者、拓扑、实现及必要到达偏斜 | 分清测量是否含等待；仿真已表达的到齐等待不能再完整包含在服务里 |
| residual gap | 先明确源区间与保留假设，不另设吸收各类残差的万能系数 | 暂不可可靠外推时标明近似或缺失，不靠调其他成本覆盖 |

每种实际模型都应能回答：输入变量是什么、哪些条件只限定适用域、公式或插值怎样得到耗时、系数从哪些测量产生。
在独立数据上比较候选形式，只有简单形式不足且证据支持时才增加复杂度；不要求每个系数都有单独物理解释。
当前成本形式的恢复与之后的精度改进分开记录，避免无法判断变化来自结构重写还是重新拟合。

### 9.3 快速且正确的成本查询

模型在会话准备时解析一次，按操作、实现、计时口径和部署找到有限候选，再检查工作域。
特征中哪些进入公式、哪些只限定覆盖要明确；每个维度都在范围内，不等于该组合已有测量支持。
离散已测组合建立索引，曲线按坐标有序查找，不为每次查询线性遍历所有测点。

重复的完整工作点可复用数值和覆盖结果。查询键包含所有有影响的条件；通信 arrival span 等运行时特征确定后才查询，
不能缓存“尚未到齐”的中间结果，也不能把不同参与者的条件合并为同一调用。
统计逻辑请求次数、不同工作点和真实求值次数；命中缓存仍更新该目标的覆盖/域外摘要，不用高命中率冒充模型可靠。
模型数据不可变，查询缓存的作用域明确，不能跨不相容模型包或可变 target 状态偷用结果。

### 9.4 执行器的唯一职责

依赖满足、请求可到达且资源可用时才开始工作；运行完成释放对应资源并触发指定动作。
CPU 提交、worker 入队/返回、设备服务、通信到齐分别推进；等待由资源与依赖产生，不又作为服务相加。
参与者实际到达与算法中的通信服务不能互相重复收费，服务定义以独立测量口径为准。

恢复 CPU 路径时，以一个实际原生调用贯穿 caller 提交、worker 执行、设备完成和 caller 返回，复用源中已有的任务关联，不另建同义关联器。
异步调用允许 caller、worker 和设备重叠；派发延迟只推迟就绪，不占用 caller 或 worker 的服务资源。CPU 自身服务和 residual 分开绑定，不整段复制父调用墙钟。
同步读回应等待其实际生产者，再执行同步及返回的有效服务；读回后的测量不能覆盖同步 API 本身，也不能把源等待时间另加一次。
先让这套共同调用过程服务注意力元数据和现有计算，再接请求控制与响应；不为每个原生函数复制调度流程。

用紧凑数组/索引维护未完成依赖、就绪事件与状态；不为每个节点创建大字典、多份集合或 Chrome TraceEvent 副本。
失效工作退出热路径，但保持必要来源映射和在途引用；生命周期由持有对象管理，不靠例外分支补悬空引用。
图事务按共同规划批量提交，局部变化定位邻接影响；保留端点、环路和已开始工作不变等必要约束，
不为少扫一次全图而削掉正确性检查，也不在每个节点的正常路径重复验证整个图。

### 9.5 一套实现支持预测和诊断

NodeScale 在原操作成本确定后、合并执行段前应用；无匹配不改成本，默认关闭。
源静态回放仍用原始观测，正式预测用对应迁移/模型成本；两者共用调度基础，但口径不混用。
oracle-cost 诊断先取得正式生成的目标结构，再替换固定图成本；不因 target 数值改变已有超时分支，也不覆盖正式结果。
详细图与逐操作日志只在显式开关下生产，紧凑摘要由执行结果直接生成。

### 9.6 批量目标的执行生命周期

一次会话持有已准备 source、已选模型和共同只读索引；每个 target 创建自己的状态、工作实例、队列与查询摘要。
先保证单进程连续执行多个目标时不重复准备、不串状态，目标完成后释放其运行存储并保存紧凑结果。
搜索后续送入的候选继续使用本会话准备结果，不要求重新启动 C++ 进程或重写整包模型。

再根据实际峰值选择有界并行方式；若使用进程共享，确认只读部分不会因统计或析构被无谓写脏，
并把各 worker 的目标增量内存纳入准入。不能把旧流程已有的 fork/source 共享当作新收益，优化的是仍重复的解释、复制和执行。
一个目标异常结束时保留根因和已完成结果，清理其资源；公共来源或模型准备失败才停止依赖它的整组目标。
不为这些生命周期引入常驻服务、全局可变单例或第二套业务调度框架。

**必要检查：** 同一真实来源的 self 与变化目标、C 的时间相关分支、已测/新组合/域外成本、诊断开关与 NodeScale。
模型缺失返回明确结果；对相同输入关闭和打开诊断，正式预测必须相同。比较优化前后的服务、因果和舍入，不只看总时间。

**收口条件：** 代表 self 和至少一种跨配置变换取得完整 HTTP，其余缺口可解释；不能仅凭正确报告失败就判定预测恢复。
成本不产结构、执行不训练、报告不修状态。
逐请求广播、每次查询线性扫测点和每个目标复制全源语义这些旧组织方式不进入新主路径。

## 10. E：恢复好用的准备与性能维护

本阶段把“开发者会手工准备”变成用户能完成的流程，同时保持 source 与独立成本两条数据线分离。

### 10.1 采集和原生环境

恢复 SGLang/KTransformers 的推理 Docker、hook、probe 和共同采集生命周期；modeling 环境复用 A 的底座。
将必要上游改动提取为适配器补丁与依赖声明，在对应推理环境核对行为后再恢复第三方的上游工作树；保留历史提交便于追溯。
不顺便升级上游或清掉未归属修改；原生 C++/SDK 依赖不得进入纯预测构建。

设备采集严格串行，流程清楚表达启动、就绪、预热、有效请求、导出和回收。
probe 默认 snapshot-free，只采结构解释和服务测量所需事实；需要 snapshot 时显式诊断开启，并不混入正常时间。
workload 控制请求数、输入和生成上限；自然输出记录 token 与终止原因，强制回放保持工作和停止条件一致。
准备请求维持缓存与背景任务连续，不混入正式计时；失败与中断记录实际完成量，而不是填成完整样本。

### 10.2 base 准备和用户体验

已有 manifest 能用则直接复用；新平台按用户配置采 base，并给出缺来源、缺校正或缺成本的具体原因。
需要 CPU 开销校正时，自动组织与来源绑定的有效对照，原始与校正数据分别保存；不能用目标正常耗时反推校正。
同一 target 组共享 source 准备和模型选择，用户不必理解内部 CPU 配对文件、exporter 参数和模型包拼装。
正式输出保留复现输入、阶段结果与紧凑摘要；缺口汇总到用户能采取的动作，不只输出几千个函数名。

### 10.3 性能数据库与离线模型

以现有 SQLite 能力为起点，分别组织采集来源、测量事实、部署/实现条件和训练选择，不建设新服务。
重导入同一 capture、原始位置和计时口径不能增加样本权重；不同真实采集的相同工作、相同数值仍是独立观测。
来源身份冲突或显式校正不能被静默覆盖：保留原始事实及校正关系，使用明确导入/替换动作，不用 checksum 或内部版本握手。

按操作、实现和计时口径分组，不按每个 cell、层或 Python 函数新建一个模型。
先用典型响应、线性项或插值解释数据；训练/验证按采集会话或请求组隔离，不能把同一次执行的不同层随机拆成独立留出。
模型输出包含特征、形式、系数、单位、覆盖和样本来源；预测只加载这些已选定响应，不连数据库重新拟合。

当前 base 不自动当作独立训练数据；显式导入的其他 runtime trace 必须符合测量及部署合同。
跨模型或跨配置复用依赖操作实现和工作域，不凭模型名相同或字节数相同认定可迁移。
实验声明来源角色与交叉关系：被用于拟合或修正规则的 target 证据不能继续宣称该项为独立泛化验证。

### 10.4 整组缺口与最小共享补采

处理顺序为：可证明迁移的 base 成本 → 已有独立模型及其允许的外推 → 确实不足的独立采样。
其中 base 只能迁移未变工作；发生变化的计算/I/O 不临时从当前 base 拟合一个 target 专用模型。

| 缺口 | 下一动作 | 是否采集成本 |
| --- | --- | --- |
| 结构规则或工作变量未知 | 查执行机制与来源，必要时补最小语义观察 | 不能用成本采样代替 |
| 已有测量未导入或未训练 | 复用事实，执行明确的离线维护 | 不重新启动模型 |
| 在允许外推域内 | 使用已有模型并报告域外/新组合 | 不为“点没见过”机械补采 |
| 缺可用模型或超出可信范围 | 归并共享工作需求，选择有限独立采样 | 需要，且有预算与停止条件 |
| 原生不支持或结构超出范围 | 明确不支持，保留原因 | 不循环尝试同一无效采样 |

先从 target 配置及可知工作量归并需求；受完成时间影响才可知的分支，在真实预测中遇到时回传有限需求。
不能用零成本把全部路径跑完来假装一次预检，也不承诺在未运行条件分支前知道所有需求。
第一次缺口得到的采样供整组及后续任务共用，允许有界多次补采，但不按单格误差逐个加点。

一个采样方案必须写出要覆盖的操作/工作范围、独立 config×workload、为何比逐 target 采集小、预计成本与结束条件。
优先复用一次框架启动覆盖多项工作；样本要核对实际执行了所需操作，不能把“计划触发”当作有效测量。
简单按缺口覆盖和采集代价选择配方即可，不先建设自动搜索采样器或独立校准平台。

### 10.5 预算、恢复和失败

同一任务统一记录启动次数、请求/tokens、设备运行、后处理、磁盘保留和峰值；重复、失败、换请求与恢复均不清零。
断点恢复只复用明确完成且用途相容的输入，不因文件存在就复用半写结果，也不重新读取所有历史目录猜状态。
数据库导入使用事务，文件交接完成后再发布可消费结果；中断留下的临时内容不当成成功产物，不另造摘要或版本校验系统。
预算触顶、设备不可用、原生失败和成本仍缺分别结束；收回本任务进程/容器，保留已得到的有效测量与定位信息。
同一预测会话可继续接收 target 批次，不建常驻网络服务、跨任务隐式缓存或另一套恢复账本。

**必要检查：** 已有来源直接预测、从新 base 准备到预测、小型独立维护、重复导入、真实重复测量、恢复与预算退出。
采集验证选择少量能覆盖多个条件的真实任务，不反复用完整面板检查流程；检查纯预测与评价不会触发采集或训练。

**收口条件：** 用户能用部署、模型、base、workload 与 target 集合开始工作；无需手拼内部资产。
新增成本数据有独立来源、共享范围与累计预算，原生失败和未覆盖范围能被理解并恢复。

## 11. F：上层用途与资源成本搜索

### 11.1 三类上层用途

直接预测接收一个 base 与多个 target；矩阵实验负责来源选择、运行和独立评分；搜索负责有限空间与预算选点。
三者调用同一准备和预测接口，不各自解析目标配置、生成工作或解释成本。
矩阵构造、留出安排、批量复现、算法比较与跨运行汇总留在 examples，正式包维护单任务生命周期、搜索和通用评价能力。
普通结果紧凑，三份实验报告按需产生；报告消费结构与执行结果，不重新推导一份工作清单。

### 11.2 选择一个确有取舍的场景

选取具有真实前缀复用、复用距离变化、设备/主机容量竞争和跨层回访的短负载；优先复用现存 ShareGPT 输入。
先按请求内容和 base 观察说明为什么会触发不同路径，避免看过 target 收益再挑场景。
同时保留低复用负载作边界对照，接受“更复杂缓存没有收益”的结果。
输入规模由请求数和生成上限声明，不硬编码案例身份，不缩短 trace 或遗漏准备工作。

### 11.3 空间与资源成本

资源选项和缓存策略分别声明。资源包括实际可部署的容量/设备方案及其受限 I/O 能力，
策略包括页宽、写策略、预取、门槛和超时；不能给容量、带宽和价格各设一个互相独立的理想旋钮。
设备总内存要计入权重、工作区、KV、dummy buffer 和必要运行开销，host/SSD 同样明确可用与分配口径。
若 SSD 容量尚未影响状态和淘汰，先不把它当可搜索变量；新增轴须先有执行规则与性能依据。

目标为满足完整窗口时间要求的最低资源成本，或输出时间与成本的 Pareto 取舍。
配额计价和真实购置/租用支出明确区分：固定设备空出 HBM 不自动减少账单。
真实价格未提供时使用显式资源量与有声明的价格情景，不宣称实际省钱；价格和单位必须随结果保存。
窗口完成时间约束不称为生产 P99、吞吐或 SLO。

### 11.4 第一版搜索保持简单

空间能算完则枚举，否则使用有固定种子和明确预算的分层随机；先与默认策略和简单固定策略比较。
不先增加新的搜索依赖或算法框架。只有明确证明预算选点需要时才讨论其他算法。
模型排名完成后，串行正常确认少量事先选定配置，重复次数预先声明，失败保留且不按耗时挑样本。
本轮不要求新大空间研究，先证明场景、约束、成本与正式预测接口能一起工作。

### 11.5 可展示的最小完整结果

输出至少包含：场景与输入规模、可部署空间和剔除理由、预算、已评估候选、时间/资源成本取舍、默认方案及选中方案。
单纯增大内存却没有成本约束的理想配置不构成优化问题；未知成本或不支持的候选不能按零耗时进入排名。
预测值并列时按已声明的资源成本与稳定次序处理，并报告并列，不能把相同预测值包装成不同的性能收益。

正常确认集合的选取规则事先确定，例如默认、预测最优、一个预算边界和一个有区分度的对照；
可以根据预测排名执行规则，但不能看过正常实测后再挑确认对象或删除慢样本。
确认输入保持请求、tokens、准备状态和正式边界一致；报告预测排序与实测是否一致、是否误判约束、真实改进与未确认范围。
没有完成全空间正常实测时，只能声明已比较集合的效果，不能声明真实全局最优。

**必要检查：** 在不用设备和 target 真值的条件下完成有界搜索；所有候选通过与直接使用相同的预测接口。
再串行正常确认少量候选；缺价格时明确报告资源量/假设，不能把示例价格说成现实节省。

**收口条件：** 普通用户路径、矩阵示例和资源搜索各能完成其职责；场景存在可解释的取舍，失败、并列和不确定性可见。
不因研究展示需要新增核心策略、额外调度器或另一套成本模型。

## 12. G：整体验收与最终收束

### 12.1 审查和构建

从各阶段交付提交核对到最终工作树，联合检查未改动但受影响的调用方，不能只审查最后一个 diff。
检查源解释、状态归属、成本口径、资源释放、错误传播、CMake/Docker、CLI、配置、示例与文档是否形成一条正式链。
确认没有活动代码依赖 deprecated，没有独立 test/CTest、转发旧路径或只为复现旧结果而存在的分支。

执行 Ruff、格式、Shell/配置检查和 modeling Docker 的 clean Release/validation 构建；原生 hook 分别在推理 Docker 构建。
只使用已恢复的正式目标与真实输入入口，不为本次检查另建测试程序。修正按影响范围复查，格式变动不触发全矩阵复跑。

### 12.2 先验证机制，再跑完整面板

下表说明需要的证据，不要求每行另建一个脚本或一份测试夹具；尽量让少量真实输入覆盖多个条件。

| 代表机制 | 主要核对内容 | 最早形成证据的阶段 |
| --- | --- | --- |

| Decode 连续步 | token 数、上下文增长、分配/释放、最终响应边界 | C、D |

| 预取超时、取消与重试 | 时间条件、在途工作、资源释放、合法后续分支 | C、D |
| 容量压力与写策略 | 引用、淘汰、回写、回载以及等待因果 | C、D |
| 尾部后台工作 | 正式结束不等待无关队列，后续请求仍受已有状态影响 | B—D |

每阶段已有充分证据的机制不无理由重跑；最终只对集成影响、改动和尚未闭合的风险补验证。
数值比较先用同一份成本依据，分别核对工作量、因果、服务成本和完整 HTTP；不能仅凭 E2E 接近判定内部正确。

### 12.3 60/186 格与三份报告

原始 60 cross 是五种配置之间的有向跨配置预测、三个 workload，即 5×4×3；self 另列，不混成同一分母。
扩展 72 与历史留出 54 按原实验声明恢复具体配置和工作量，不根据总数猜组合，也不在核心代码写固定格数。
每格由实际部署、base、target、workload 和成本来源唯一说明；只供报告使用的编号不能进入规则或模型特征。

正常真值、target 结构观察与预测输入分开准备和保存。预测进程/容器不挂载 target 评分目录、不导入 evaluator；
全部选中预测结束后，再由独立评价读取相应真值。某来源在另一格被用作 base，不授予当前格读取其 target 观察的权限。
性能维护输入另外声明，不能把完整面板的所有 self 数据自动合成训练库。

| 报告 | 最小结果 | 不代表什么 |
| --- | --- | --- |
| 原始 DAG 回放 | 来源、观测与回放正式时间、未解释范围、关联失败 | 正常运行精度 |
| 目标结构 | 逻辑工作/页/字节/分支、资源及必要依赖的匹配与差异 | 原生节点数必须相等，或未观察部分也正确 |
| 完整性能 | 每格预测/正常均值、误差、样本与失败、分组统计及模型局限 | 结构已全部验证，或任意部署可泛化 |

结构比较按逻辑身份对齐，保留无法对齐与缺观察项；静态 oracle-cost 也只能对有合法对应的部分替换，并报告覆盖。
压缩定义到原操作的映射用于解释与诊断，不能为了评分重新按旧方式生成整套巨大图。

逐格报告绝对百分比误差 APE、带符号偏差，汇总 WAPE、P90 APE、最大误差与成功/失败/缺真值数量。
WAPE 使用绝对误差之和除以真值之和；P90 用有效 APE 排序后的最近秩，同时明确有效覆盖数。
整体、逐 base、workload 与 target 分组报告，不用总体好结果掩盖一类配置持续失败。
正常重复取预先声明的有效样本算术均值并保留波动范围；不能按结果删掉慢样本。
对照还应包括直接沿用 base 正常耗时，说明预测相对简单基线的价值；此参照仅由 evaluator 计算。

历史留出复验不等于本次首次未见数据。若资料已用于修正规则或训练，明确标为开发/历史验证；
需要新的独立泛化结论时另行声明未使用的输入，不用重命名掩盖数据角色变化。

验收前固定规则、公式和输入。发现机制错误后转回开发，保留该次失败和全部已完成结果；
修复后的受影响格使用新代码重跑，未受影响格只有在依赖与行为确实未变时才可保留，并写清结果对应提交。
成绩按实际资格报告；缺项未解决时不能宣布完整 186 格恢复，也不能把未达精度目标写成已通过。

### 12.4 10× 效率怎样证明

先在独立旧基线 checkout 和新实现间选定相同输入、成本与目标集合，不修改 deprecated 或 markov-next 跑基准。
分别计两种时间：已准备预测的全流程时间，以及从采集/性能准备开始的用户总耗时；离线准备不能被藏在预测计时外再宣称用户总流程提速。
构建、采集、离线训练、预测和评价各自说明是否计入。10× 主比较以同输入完整预测批次为准，不能只比较成本求值函数。

先单目标定位开销，再固定并发比较完整批次；冷/热条件一致，使用无采样 profiler 的运行做主时间对比。
主结果说明重复次数和波动，不只挑最快一次。若旧实现受资源或预算限制无法完成，只报告可比子集及完整运行限制，不给虚假的总倍数。

| 改造方向 | 应消除的重复工作 | 证据 |
| --- | --- | --- |
| 共享 source | 每 target 重建调用、资源索引或复制原始图 | 同源准备次数、目标附加内存 |
| 共享工作定义与安全压缩 | 未变区域先删再复制、无意义的内部事件 | 定义/实例/执行事件数、语义等价与时间 |
| 动作定向处理 | 每节点遍历所有请求和模块 | 实际动作调用、空检查量与 CPU 开销 |
| 成本索引与复用 | 每次扫全部已测点、重复解析模型包 | 模型读取、不同查询点、真实求值与覆盖结果 |
| 稀疏依赖与局部事务 | 同步扇出、线性去重、重复全图重建 | 必要边/变更范围、构图与事务耗时 |
| 紧凑运行与按需诊断 | 大字典、重复集合、全量明细生成后丢弃 | 峰值内存、输出量、诊断关闭时的行为 |

记录读取/构图、来源解释、目标规划、成本、执行和输出的非重叠计时；嵌套函数耗时不相加冒充总耗时。
同时记录总 CPU、峰值内存和批次吞吐；共享内存按 PSS 或容器整体用量观察，不简单加总多个进程 RSS。
优化收益不能简单相乘。如果整体未达 10×，按剩余占比和可消除工作量判断下一步，不能继续只优化已经很小的阶段。
减少输入、删 gap、关闭必要能力、提高并发或只统计成功格都不属于同口径提速。

### 12.5 资源控制和并发

先测一个有代表性的高负载目标及共享 source/模型占用，再给并发准入设置保守峰值估计和主机余量。
容器硬限、最大进程数、运行中内存观察与可回收进程树共同约束；不能只根据刚启动的低 RSS 放行更多任务。
内存上界按共享部分加各目标增量估算，运行峰值超过估计时停止新准入并保留失败原因，不能等宿主 OOM 后才处理。

单目标本身过大时回到表示和执行粒度，不用不断加宿主内存或切分计时掩盖问题。
采集仍串行；后处理、预测和评价的并发分别受资源预算控制，互不默认抢占所有 CPU/内存。
计入数据导出与临时产物的磁盘上界，空间不足先说明本任务可清理范围，不能删除仍被引用的输入和历史证据。

### 12.6 第二轮清理与最终交付

沿完整运行链删除无消费者类型、重复状态、临时输出、旧字段别名、只为过渡存在的 wrapper 和多余配置。
逐职责核对业务源码与 examples 的规模及重复规则；不把业务代码搬到例子、生成代码或其他后缀逃避统计。
复核 Py/Shell/C++ 逻辑留白、注释、所有权与失败释放；代码量只作为设计反馈，不压行或删除必要诊断来达标。

最终交付必须有：用户最小可用输入及实际命令、支持/不支持范围、三类报告、完整面板状态、同口径性能与资源数据、
成本适用范围和未解决问题。证据保存在运行资产中，文档只写复核入口和结论，不增加平行总结档案。
代码、文档与数据整理检查完成后，分层提交推送开发分支并核对远端；本地历史归档保留原内容，运行资产不提交。
窗口确已完成或被明确终止时，再把自足结论与遗留项归入主工作流并撤下窗口，不能靠删计划消除未完成任务。

## 13. 如何借鉴旧代码而不照搬

先解释要保留的机制、证据和不变量，再按新消费者实现；不是复制旧模块后把名字改短。
读旧代码时沿一次真实输入的生产者和消费者走通，不为“了解全仓”重复通读全部报告与历史脚本。

| 旧参考位置或职责 | 借鉴内容 | 不搬回的组织方式 |
| --- | --- | --- |
| `deprecated/src/modeling/trace_graph/src/source_dag/` 与 `src/adapters/` | 时钟关联、请求身份、调用和模型工作解释 | 每 target 重建来源索引、在共享核心匹配原生词条 |
| 同一旧 C++ 树的 `src/cli/workflow.cpp` | 原始回放、校正与迁移的先后边界 | 目标级整图副本、CLI 承担业务状态 |
| 同一旧 C++ 树的 `src/modules/hicache/model/`、`runtime/`、`patch/` | 页几何、分配、CPU 排队、取消、逐页发布和尾部完成修正 | 按功能片段堆生成器、全部节点广播全部模块 |
| 同一旧 C++ 树的 `src/simulation/` 与 `src/cost/` | worker/设备关系、成本口径、独立查询及迁移条件 | 节点字符串属性主导执行、查询逐点扫描 |
| `deprecated/scripts/internal/markov_internal/modeling/cost/` | SQLite 测量身份、导入去重、独立训练形式 | 逐函数模型扩张、每 target 序列化整包响应 |
| `deprecated/scripts/internal/markov_internal/preparation/` | 真实采集生命周期、CPU 对照、预算与恢复事实 | 每类校准一套完整主流程、层层异常和 JSON 转换 |
| `deprecated/src/profiling/` 与 `deprecated/docker/` | manifest、时钟、probe/hook、依赖和容器边界 | 只服务历史调试的 snapshot 与环境转发层 |
| `deprecated/examples/hicache_reproduction/`、`hicache_search/` | 原面板声明、正常确认、研究对照 | 将研究编排塞回正式预测核心或重启旧大空间任务 |

独立算法可在核对单位、边界和消费者后复用；需要整套旧上下文才能工作的方法应重新设计。
每阶段只需说明参考了哪些机制、替换了哪些职责链、保留了哪些限制，不为每个函数建立迁移账本。
新模块必须有当前业务理由，不能因为旧模块存在就照着恢复；旧代码中的防御检查先理解其保护的不变量，再决定保留或删除。

## 14. 风险、取舍与停止条件

| 风险或未知 | 处理与明确边界 |
| --- | --- |
| trace 不足以解释目标合法分支 | 回到最小语义事实与适配，不能改成本或逐 target 添加模板 |
| 压缩隐藏排队、发布或中途资源交错 | 保留相关边界；先安全串行段，再考虑固定多出口子图 |
| 旧数据库或包与新工作合同不一致 | 显式一次性导入/转换必要来源，不能永久维持双格式或反推伪测量 |
| CPU residual gap 仍难外推 | 完整 HTTP 保留且单列近似，不吸收进其他组件 |
| 原 186 格部分数据不可用或环境变化 | 先明确哪些来源缺失，最小必要重采；不能拿旧汇总代替当前运行 |
| 真实价格或可部署资源方案缺失 | 资源与价格情景分开报告，不能发布实际经济收益 |
| 部分目标仍缺规则/成本 | 保留具体缺口，回到共同合同和机制；无新事实时停止同类补丁和重复采样 |
| C、D 的动态结构与时间合同互相等待 | 前移最小共同事件能力，或合并交付；不以 stub/零成本掩盖缺失 |
| 既有成本包来源或计时口径不清 | 先核实真实来源；不能为保持旧数值反推测量或套一个全局倍率 |
| 一条新增分支带回大量旧依赖 | 回查抽象和所有者，重写整条职责链，不继续增加转发层 |
| 新表示失去静态诊断能力 | 保留逻辑身份和必要端口映射；报告未覆盖，不恢复第二套主执行路径 |
| 资源不足或基准超出预算 | 明确停止范围与可比结果，收回本任务资源；不能把超时记为零或无穷性能 |
| 精度不达目标但机制与流程已闭合 | 报告模型局限和独立证据；不延长为无期限逐格拟合 |

执行遵守累计资源预算，失败、中断和设备等待分别保留；独立验收期间不改规则或补分支，发现问题后转回开发处理。
代码阶段结束、公开能力恢复、代表语义与完整面板有明确结果、效率/规模有当前证据且遗留限制写清后，才可声明重构完成。
构建通过、代码少了、命令退出零或历史精度好看，都不能单独构成收口。

### 14.1 需要在实施前落定的选择

以下问题由相应阶段结合实际资产决定，决定与理由记入已有日志即可，不新建决策数据库：

- A：首轮真实支持的部署/后端、代表输入、入口合同，以及资源成本使用配额还是实际支出。
- B：各观测通道的时钟关联、必要语义事实和无法解释区间的保留方式。
- C、D：压缩边界、同刻事件顺序、迁移条件、动态成本特征及旧单位转换后的舍入规则。
- E：可复用独立测量、最小配方、模型覆盖/允许外推范围、补采与后处理的累计预算。
- F、G：搜索场景/空间、正常确认规则、正式比较输入、资源余量和完整运行的停止预算。

能从代码、部署或已有来源核实的事实先核实，不把每项实现选择都推给用户。
涉及取消既有能力、改变完整 HTTP 定义或扩展本轮范围的取舍才单独说明；不能静默降低标准。

### 14.2 完成与停止的区分

重构完成要求：支持范围内正式流程恢复、规定面板有完整可追溯结果、语义缺陷处理完毕、维护交付完成；
性能和精度目标分别给出是否达到及证据，未达不能被改写为通过。代码行数下降不是独立完成条件。

明确无新事实、预算耗尽或已超出支持范围时，应结束对应试验并保留限制；这不自动等于整个重构完成。
若完整面板仍缺应支持格、关键能力只剩接口、阶段未交付或资源风险未处理，状态保留未完成，给出具体下一步。
本计划只指导实施，不因文档写完就自动启动设备、恢复旧研究或改变其他仓库。
