## 1. 这次整改改变什么

此前的任务安排有三个相互放大的问题：来源解释、目标生成和成本绑定合成了很大的联合阶段，局部实现又拆成许多小检查点；缺少一种端口成本就继续向底层展开；正常请求的完整结果一直排在这些局部缺口之后。

整改不降低因果和成本要求，而是改变默认实现单位和交付顺序。

| 原有倾向 | 改后的做法 |
| --- | --- |
| 沿原生函数、事件和旧模块清单逐项恢复 | 先明确一次请求的语义工作、对外端口和资源需求，再决定内部实现 |
| 先把所有缺口补齐，再得到完整 HTTP | 先交付受支持范围内的完整请求；近似、结构正确性和精度资格分别说明 |
| 发现缺成本就增加采样或模型 | 先检查工作定义、匹配条件、重复计费和现有数据，再决定是否补采 |
| 原始 DAG 越细，目标程序也必须同样细 | 原始图保留观察；目标只展开影响决策、依赖、资源和必要测量的边界 |
| 一个联合阶段承担多个框架、所有成本和自动准备 | 用一个完整 SGLang 预测建立主干，再扩展用户准备和其他框架 |
| 频繁验证、记日志和提交局部补丁 | 跨模块完成一条职责链后统一验证，阶段结束集中维护交付 |
| 以组件、模型数或主观百分比表示进度 | 用固定交付物的实现、验证和交付资格表示进度 |

这不是再从头推翻已有代码。可用的来源解释、状态规则、队列、时钟与采样能力应优先复用；无法说明当前消费者或价值的部分可以合并、改写或删除。已经投入的实现量不构成继续保留的理由。

## 3. 三阶段仍然清楚，但不要求逐节点复制

### 3.1 每一层负责什么

| 环节 | 输入与职责 | 输出与边界 |
| --- | --- | --- |
| 原始 DAG | 只解释选定 base 的 trace、语义观察、请求和资源身份；同源只做一次 | 不可变源图、工作依据、必要端口及成本来源引用；原坐标不改写 |
| 目标工作与依赖 | 用 target 配置、workload、框架规则和目标状态主动生成合法工作，包括 base 未执行过的分支 | 工作量、操作、必要依赖与条件程序；不读取成本系数或 target 真值 |
| 成本绑定与执行 | 判断未变工作能否迁移，变化工作查独立模型；推进资源和事件 | 完整请求时间、后台完成、成本来源与不确定性；不创建业务分支或训练模型 |
| 外围准备与应用 | 用户输入、采集维护、矩阵编排、评价或搜索 | 调用同一个预测器；不重复实现缓存状态、工作量或调度规则 |

三阶段不要求三个进程、三套图文件或三次序列化。阶段二可输出含发布、取消、超时等条件的程序；阶段三在同一时钟到达条件后调用结构规则产生后续工作。成本改变完成时间，规则据此决定后续动作；不能先运行理想结构，再用另一套时间修补结果。

### 3.2 共同交接保持最小

| 信息 | 必须保留 | 不应混入 |
| --- | --- | --- |
| 源上下文 | 源身份、语义依据、资源、原图与成本引用 | target 运行状态、目标真值 |
| 工作描述 | 物理或语义操作、实现条件、shape/页/字节/参与者、计时口径 | 回归系数、数据库路径、预测耗时 |
| 成本绑定 | 未变工作来源引用，或独立工作查询；来源、单位和适用域 | 结构策略、采样或拟合动作 |
| 目标程序 | 必要操作、资源、端口、依赖和条件 | 逐节点原生属性副本、无消费者的观察字段 |
| 执行结果 | 完成/发布、HTTP 与后台边界、近似和失败原因 | 第二份缓存状态或自行重算的结构 |

这些是信息职责，不要求每行新建类型、目录或格式。身份与单位在输入边界解释一次；内部使用稳定引用与紧凑索引，不增加版本别名、SHA、冻结、指纹或多层合同检查。

## 4. 先决定仿真需要多细

### 4.1 默认用能说明工作的区域

从构图时就把 trace 归纳为查询/准入、必要缓存传输与控制、Prefill、Decode、结果整理/发送、释放和后台工作。每个区域说明实际工作变量、资源、入口和外部消费者；区域不等于一个串行总耗时节点。

base trace 可以大，但正式源 DAG 和目标程序不逐 trace 事件建节点，也不先强制构造完整细图再压缩。源准备一次提取语义工作、必要端口和原记录引用；细粒度原图只在诊断确有需要时按需生成。静态回放按声明的区域与端口检验原始观测，不以全部底层事件一一对应为门槛。

Prefill/Decode 优先按计算区域和有效工作量估计；I/O 使用批次、字节与必要发布进度；CPU/control 使用有工作变量的控制区域。不同资源可重叠，不能把整个阶段的墙钟直接视为独占服务。

只有下列理由成立时才继续展开内部操作：它改变配置决策或合法工作量；存在外部读取、发布或资源释放；与其他工作共享资源并可能交错；模型确实需要独立边界；或已有独立证据显示该细节造成重要误差。说明理由即可，不新增逐节点审批或登记系统。

| 情况 | 实现选择 |
| --- | --- |
| 逐页发布影响后续命中、预取超时或容量 | 保留发布粒度与状态；可对连续页作范围表示 |
| CPU 返回、后台发射、设备完成分别有消费者 | 保留相应端口与资源前沿，不把三者串行相加 |
| 内部连续步骤没有外部交错，且工作/实现条件一致 | 使用一个有明确口径的区域响应或共享静态区域 |
| 只有 profiler 可见的包装、函数层级或零时长标记 | 先判断因果作用；有作用保留端口，无作用不复制成目标工作 |
| 原图内部因果尚不完整 | 判断是否跨越必要端口；影响目标依赖则补事实，内部未知单列范围，不宣称整图已证明 |
| NodeScale 关闭 | 不为潜在缩放需求强制展开全部原操作 |
| NodeScale 开启 | 保留命中操作的成本归属，调整后再安全汇总，不能放大整个不匹配区域 |

没有外部交错的证据前不能随意压缩；也不以还原全部 CPU 函数、runtime API 或 trace 事件为完成门槛。细化后的表示仍须共用同一状态和执行器，不能增设局部时钟或第二套补偿调度。

### 4.2 时间与成本各归其主

| 项目 | 如何进入完整预测 | 不能怎样处理 |
| --- | --- | --- |
| CPU 自身工作 | 按区域或必要端口绑定正常服务估计；已证明未变才迁移 base | 将含阻塞的父包络和子操作同时收费 |
| 可解释等待 | 由生产者、资源、队列、发布或通信到齐产生 | 复制源等待并再等待目标依赖 |
| I/O 与计算服务 | 变化工作使用独立性能数据；保留实现与资源条件 | 用字节数相同或 shape 相同替代实现一致性 |
| CPU residual gap | 保留独立来源和适用假设，报告不确定性及可能影响 | 塞进 I/O 系数，或未经证明作为 CPU 服务占资源 |
| 采集开销 | 原始回放保留；正常预测使用有来源的剥离或校正估计 | 用 profiled 墙钟冒充正常测量，或按 target 残差反推倍率 |
| 编译/加载/初始化 | 由声明的初始状态决定是否发生；可封闭计费，必要端口才拆开 | 将 prepared 的稳态与 empty 的首次成本混在一个平均值里 |
| 响应后的工作 | HTTP 完成后仍保留资源、缓存引用与队列；drain 独立 | 发送完成即删除后台工作，或等全部后台排空才返回 HTTP |

正常线程 CPU 总量与 profiled 内部分段推得的端口值属于估计，不是直接正常端口测量。同一组总量派生出的多个端口不增加独立样本量；数据库保留原始观测、派生关系及计时口径，训练和报告不抹掉这种区别。

完整 HTTP 必须交代所有时间的归属，允许有明确依据和范围的近似，不允许用零成本、静默丢弃或把整个正常 HTTP 当作一个模型来凑闭合。缺少任何合理依据时明确缺成本；有数值不代表正常精度或结构正确性已通过。

| --- | --- | --- |

### 5.1 批次与检查怎么安排

一批沿生产者、合同、消费者、用户入口联合修改多个源文件，完成可审查的职责链；连续实质实现以二十分钟以上为窗口参考，不硬凑时长或文件数。实现期间主要静态联查，不为一个缺口单独构建、采样、写日志和提交。

相关实现基本齐备后，统一格式/静态检查、Docker 编译和必要代表运行；失败集中修正，仅复查受影响范围。编译/ABI 真正阻断实现，或涉及设备、数据、资源安全时，才提前做最小检查。必要检查不能全部拖到 R5，也不能每批重复全矩阵或完整 Debug 面板。

阶段交付时统一关联审查、代码/文档/数据整理与少量分层提交推送，核对远端后进入下一阶段。批内允许静态核对和保留现场，不把每次修正当成阶段。纯文档任务不启动构建或采集，也不自行恢复已暂停的开发 goal。

默认一大批一条精简日志，保留关键失败与决策，详细数据留在运行资产。记录起点、实际变化、必要证据与限制；不每轮复制待办或为进度新增平台。

## 7. R1：先得到完整且可解释的 SGLang 预测

### 7.1 独立准备输入，区分两种采集规模

首轮使用现有代码支持的单一模型、TP、执行后端和串行请求；配置与 workload 用正式输入声明，不写案例身份分支。选择能触发前缀复用及 I/O/计算变化的请求组，先跑一个有区分度的 cross，再增加第二个 target。self 只用于核对，不冒充跨配置预测。

base 采集追求信息充分，允许较大 trace，预算单独声明。用轻量语义观察取得 token 关系、模型布局、请求边界和必要状态；不能为了降低仿真开销而截断 trace 或遗漏工作。初始缓存、内核准备状态、正常 HTTP 与响应后后台边界在采集前确定。

性能校准在本项目单独采集，供整组 target 共享；优先一次启动覆盖多个语义区域，确有缺口时允许有界追加。正常 base 对照只用于未变工作和采集开销依据，变化工作不从当前 base 临时拟合，也不读取 target 残差补参数。

首轮性能采集的工作预算为累计 15 分钟、持久数据不超过 256 MiB，均属实施前预算而非已证明成绩；启动、预热、失败、有效采样和后处理都计入。base trace 与独立正常评价另列，不能把性能采样转名成 base 或评价绕过预算。预算不够时先检查测量边界、复用和工作域，确需调整须说明机制与收益，不逐个底层算子无期限扩采。

默认保留轻量计时、工作变量、必要来源与模型；独立性能校准不长期保存每个工作点的整套 profiler 导出。有必要时只采一段短诊断 trace。未完成任务所需的原始证据不擅自删除，也不为缩小存储把派生估计冒充直接实测。

### 7.2 一批代码闭合请求，然后统一验证

1. 从 source 一次提取语义区域、工作变量、资源和必要端口，保留原始坐标引用及未证明处；不要让每个 target 重做细图构建。
2. 依据 target 状态连接查询/准入、命中或回载、Prefill、连续 Decode、结果发送与释放。只有影响决策、数据可见性或外部资源交错的位置才进一步展开。
3. 为全部区域确定成本归属：未变工作的合格源成本、变化工作的独立响应、单列残余近似。CPU 服务、可解释等待、设备/I/O 和采集开销区分，父子包络不重复收费；不为了闭合把缺项填零。
4. 同一执行器处理缓存发布、通信、超时、资源释放与下一请求到达；必要的 CPU 返回、结果可读、HTTP 返回和后台 drain 各自保留端口。
5. 接通正式 Python predict 与 C++ 入口，预测阶段只读 base、workload、target 配置和选定模型。紧凑报告从真实执行结果生成；实验评价在预测完成后单独读取正常真值。
6. 相关生产者与消费者齐备后统一编译和运行首个 self/cross；集中修复阻止完整请求的错误，不为单个端口反复全量 Debug、记录日志和提交。

成本响应以 Prefill/Decode 区域、传输批次与控制区域为主；特征由工作规则提供，例如 query/context tokens、字节、页或必要控制次数。解释模型形式、变量和参数来源即可，不强制每个原生调用都有独立响应。

已有原生队列和备份链可在确需细化的局部继续使用；没有外部作用的内部步骤合并。遇到缺成本先检查是否拆得过细、匹配条件错误或重复收费，再考虑共享补采。完整请求得到结果后再分析主要误差，不以恢复旧 1,700 多项响应作为前提。

### 7.3 本阶段的判据

- 首份交付先给 self 与一个 cross 的完整 HTTP、正常实测及误差；R1 收口时补齐第二个 cross。未建模区域不能通过改报告标志冒充已建模。
- 每类实际工作有且仅有一个计费归属；gap、未归属来源时间、Prefill/Decode、后台工作均有处理和限制说明。
- 必要端口的工作量、依赖、资源与状态无已知矛盾；target 真值仅在评价路径出现。
- 有正常实测对照，给出误差而不据此逐格调参数；完整预测可用、结构已证明范围、精度是否达标分别报告。
- 同源多目标不重复解释 source。首份报告分别记录 base 采集/解释、性能校准、首次及后续 target 的耗时、节点/边数、峰值内存和保留字节；以实际数据证明粗粒度收益，不用提高并发或减少请求冒充提速。
- 首份结果不等待严格精度门槛通过，误差和近似如实列出；精度改进随后依据机制与共享数据推进，不能变成逐格参数修补。

本阶段不要求一般并发组批、全部原生内部因果、所有冷启动/压力组合或完整 186 格。已知问题若影响所选请求的必要端口或合法路径，仍须解决；不能以“粗粒度”隐去。

## 8. R2：把已闭合预测变成用户能用的流程

### 8.1 用户只声明必要输入

本阶段分两批完整调用链推进。先闭合配置任务复用、实际 token 输入交接及数据库中的现行模型选择，
用同一用户请求完成首次与重复运行；再连接整组成本缺口、独立配方生成、预算执行和恢复。
两批共用同一预测器与性能库，不另建准备平台；第一批可运行不代表自动补采和 R2 已完成。
初始化先用真实规格/执行事实解释差异，缺少证据时保留范围与不确定性，不阻断无关的用户流程整理。

输入是平台/部署、模型、base 配置、workload、target 集合和资源预算，可显式复用已有 manifest 与性能数据。用户不手拼 CPU 配对文件、逐类导出器、模型包或诊断命令。

主流程明确为：检查输入 → 准备/复用 base → 准备整组成本 → 批量预测 → 输出紧凑结果。独立性能维护是另一条共享数据线，不是每个 target 再训练一次。应用只使用预测结果，实验可额外请求三份报告。

SGLang/KTransformers 的推理环境和 modeling 环境分离。设备采集串行，probe 默认不采 snapshot；客户端计时不包含导出与本地报告处理。环境差异和必要补丁留在适配器，不能让纯预测依赖 SDK、网络或真实设备。

### 8.2 性能数据先讲清含义，再谈覆盖数量

继续使用本地 SQLite 和离线训练，不建设新服务。来源、正常直接观测、profiled 观测、校正/派生估计、训练选择与模型输出分别保留身份。

先核对区域工作定义及初始化条件，再增加样本。首次 phase 和新输入长度只能描述调用历史，不能直接代表实际编译/加载；
准备规格应从执行配方和最小主机事实取得，按 caller 维护首次出现，不能以原始长度代替真实规格。
若同类调用仍可能走不同的初始化工作，应补充能区分该工作的最小事实，或明确可复现的准备状态。
不能用逐长度、逐请求位置或 target 残差系数替代缺少的事实；扩大域前分别检查结构依据、测量口径和预测资格。
结果控制按实际缓存实现匹配，避免未启 HiCache 的 CPU 响应进入启用分支；完成区间与 caller 响应保持重叠，不相加。

去重按同次真实采集与原始记录/口径进行，不按数值相同合并独立重复，也不把换路径复制或派生分段当新独立采集。事务和完成后发布保障恢复，不用 checksum、版本兼容层或额外账本。

按操作、实现、计时口径和必要条件组织成本响应；模型数量不预定，也不以继承历史包的数量作为完成要求。先用典型响应、线性项或小范围插值，复杂算法须有独立留出收益。说明特征、系数来源、形式、训练/推理方式和适用域，允许整体自然语言解释，不要求每行实现对应一句原理。

其他模型或配置的 runtime trace 可以显式导入，但须符合工作、部署与测量合同。base 的已变工作不偷偷变为独立训练数据；用于改规则或模型的 target 退出该项独立留出资格。

### 8.3 只补整组真正缺少的数据

处理顺序为：已证明未变的 base 成本 → 现有独立模型及允许的外推 → 仍不足的共享独立采样。

| 发现的情况 | 先做什么 |
| --- | --- |
| 缺合法工作或必要依赖 | 查执行机制和最小来源事实，不能用成本样本补结构 |
| 同工却匹配失败 | 核对条件是否属于该工作、是否误带 caller/base 身份及重复切分 |
| 测量已经存在 | 导入或离线训练，不再次启动设备 |
| 模型工作域覆盖新组合 | 使用并标注范围，不因精确点未见而机械采集 |
| 真正缺模型或超出允许范围 | 合并整组需求，设计有界共享采样 |
| 外部环境干扰或原生不支持 | 明确失败或不支持，不扩大面板掩盖 |

采样由机制与工作需求决定，不由 target 误差决定。每次说明需要区分的假设、所需端口/工作范围、复用现有数据为何不够、能覆盖整组哪些需求和结束条件；优先一次启动覆盖多种必要工作。

时间条件产生的需求可以在预测中逐步发现，允许有界多次补采；不以零成本遍历假装静态知道全部分支。同类缺口反复出现且没有新机制事实时，暂停该试验并检查抽象、计费和测量可辨识性，不继续“新模型—新缺口”的循环。

预算累计启动、请求/tokens、设备运行、后处理、磁盘和峰值；失败、换输入、恢复不清零。沿用已授权范围自主安排，不重复请求上限确认；新增用量有收益说明，不能清理他人资源。

### 8.4 共享与效率同步处理

source 和选定模型同会话只加载/解释一次，多目标共享只读定义；目标状态、资源前沿与执行数据独立。工作查询使用工作键与已选响应，不逐点扫描旧测量，不每次复制 JSON 或完整模型。

目标程序优先复用不变区域和页范围；报告明细仅在需要时生成。并发由共享内存、目标增量峰值和余量控制，异常回收完整进程树，不以提高并发替代算法提速。

**交付判据：** 有已有来源直接预测和从新 base 到整组预测的真实入口结果；缺口能自动归并并恢复，维护支持重复导入与离线训练；普通用户无需理解内部资产组合。小批次效率比较必须覆盖完整链，未达到 10× 不能提前报达标。

## 9. R3：补齐保留能力和关键分支

KTransformers 使用自己的真实推理环境、采集、manifest、原始 DAG、工作规则及成本进入共同预测流程。至少完成真实来源回放及受支持的目标预测与正常边界对照；不将历史 hook 的给定耗时结果当成完整模型资格，不套用 HiCache。模型或环境确实缺失时明确资源依赖，不能用接口替代交付。

恢复 NodeScale：默认关闭；开启时按命中原操作调整已绑定成本，保留依赖和计费归属。恢复源静态回放与现行规则下的显式 oracle-cost 诊断；固定预测结构后替换可对应的 target 成本，只供实验定位，不能据此改变主预测结构或恢复过时运行规则。

在同一正式链补齐原面板所需 HiCache 页几何、有限容量、写策略、主机回载、文件预取、逐页发布、超时取消、释放和准备状态。优先少量真实输入联合覆盖多个机制，不为每一项建设独立流程。

核对跨请求后台/在途 KV、通信到齐、CPU/worker/设备交错及响应边界；实验未触发不等于覆盖。不能为减少原始图警告而伪造事件、按时间近邻配对或删除零时长依赖。

**交付判据：** 上述能力均有当前实现的真实证据和范围；必要因果无已知矛盾，保留能力没有只剩接口。未支持的新部署或组批另列，不能扩充成还原全部 runtime 的任务。

## 10. R4：上层实验和有意义的资源搜索

直接预测、矩阵准确性实验、资源搜索并列调用同一预测会话。矩阵、留出、研究对照与跨运行汇总放在 examples；正式工作流维护单任务、评价与必要搜索，不复制工作量或成本规则。

先选短小且确有前缀复用、复用距离变化、容量竞争和跨层回访的场景，优先现有 ShareGPT 输入；保留低复用负载作边界对照。场景选择不能靠 target 实测收益倒推。

资源轴必须是可部署容量/设备方案及对应 I/O 条件，策略轴包括已有规则支持的页宽、写策略、预取、门槛与超时。计入权重、工作区、KV、缓冲区和运行开销；不能把容量、带宽、价格当作互不约束的理想旋钮。SSD 容量尚不影响状态时不列作有效搜索轴。

目标采用完整窗口时间约束下的资源成本，或时间/成本 Pareto 取舍。配额与实际支出分开；没有真实价格就报告资源量和明确价格情景，不能声称真实省钱，也不把窗口耗时称为生产 P99 或吞吐 SLO。

空间可算完则枚举，否则预算明确的分层随机；先比较默认与简单固定策略，不新增搜索框架。预测并列保留并列及稳定选择规则，缺成本或不支持候选不进入零耗时排名。

事先确定少量正常确认规则与重复次数，例如默认、预测最优和一个有区分度的边界；预测后再独立实测。保留失败与全部样本，不看正常耗时重新选对象。没有全空间真值就只声明已比较集合的效果。

**交付判据：** 用户能从必要输入经准备、预测、候选选择到正常确认完成一个有界实例，最好由一个外挂 example 命令从零运行；有真实资源/策略取舍、误判和不确定性说明。不恢复已终止的大空间研究，不用干跑或四个并列预测冒充有用优化。

## 11. R5：完整回归、效率与最终清理

### 11.1 三种报告分别回答问题

| 报告 | 应证明或报告什么 | 不能混称 |
| --- | --- | --- |
| 原始 DAG | 同观测成本的静态回放、请求边界、已证明依赖和未观察区域 | 回放零差等于因果完整、正常开销已剥离 |
| 目标结构 | 对齐语义工作、必要依赖、命中/传输/发布、取消和资源行为；细粒度编号不同不强求同图 | E2E 相近等于结构正确，或 target 成本帮助生成结构 |
| 完整性能 | 不排除 gap、未归属成本及 Prefill/Decode 的正常 HTTP 误差，来源与不确定性 | 组件链、profiled 回放或模型 ready 等于真实精度 |

报告仅在实验开启，应用预测不需要 target 真值。目标结构对照可以用 target trace，但隔离在 evaluator 中；不把诊断匹配变成预测前置输入。

### 11.2 面板与精度

首份完整结果之后，才进入原 60 cross、扩展 72 和留出 54 的面板目标，共 186；输入与数据由独立项目重新准备，不复制旧实验资产，不让恢复面板阻塞 R1。self 单列并按实际调用记录。所有应支持格均须有完整可追溯结果；失败、缺项、不支持和资源不可行分别保留，不改分母或用旧成绩补格。

完整 HTTP 沿用总体及逐 base 的 WAPE≤3%、P90 APE≤5%，逐格尽量低于 6%；报告偏差方向、最差格、正常重复波动和沿用 base 时间的简单参照。总体好看不能掩盖分组问题，也不把看过真值后的修复回归继续标为首次盲测。

重构功能恢复与精度达标分别结论：不要求靠无限拟合超过历史尚未达到的精度，但精度未达必须明确未达。不能降低门槛、删成本或加 target 专用参数制造通过；没有完整预测或存在必要语义缺陷时不能宣布重构完成。

### 11.3 10× 要用可比的完整流程证明

在 R1/R2 已建立的小批次计时基础上，按同机器、同输入、同目标集合、同并发、同成本和同诊断条件比较新旧完整批次。旧实现如需运行，使用归档前提交的独立 checkout，不从活动代码调用 deprecated。

报告准备、加载、首次/后续目标、执行、产物、总墙钟与峰值内存。只排除预先明确不属于预测的步骤，给出停止预算；缩短 workload、增加并发、少写报告或只量查询速度不能冒充全链路 10×。

### 11.4 内容审查与维护交付

联合检查输入、来源解释、工作规则、成本所有权、执行、失败回收、CMake/Docker、CLI、examples 和文档；不仅看最后一次 diff。对无消费者、重复状态、重复转换、临时输出、旧字段别名和过细职责整链删除或合并。

新自有源码争取约 40,000—45,000 行、尽量少于原 88,814 行的一半；不是必须填到这个规模，50,000 行不是硬门槛。同口径统计 Python/Shell/C/C++、头文件、采集、应用与 examples，含空行；归档另列。不能压行、删必要注释或迁出统计范围凑数。

统一运行必要静态工具、modeling Docker clean 构建及真实公开入口；原生桥在相应推理 Docker 构建。不新增独立 test/CTest、fixture、mock 或改名自测系统；Debug 仅覆盖有未决风险的代表路径，不机械重复全部面板。

最终提交当前用法、支持范围、三类报告、完整面板、效率/规模证据与遗留项；代码、文档、数据分别检查，少量分层提交推送开发分支。运行资产不提交，未交付不进入下一阶段；窗口真正收口后将自足结论归入主工作流，不用删除计划掩盖欠项。

## 12. deprecated 应当怎样使用

先用框架执行逻辑、正式输入合同和必要不变量描述问题，再定新实现。需要确认历史行为、公式单位、实际分支或失败原因时，针对性查旧代码和证据；不再按旧目录逐个建立对应模块。

- 可以复用经核对的独立算法、时钟关联、测量事实和反例，但复用条件由新消费者决定。
- 不要求重建旧节点数量、原生词条表、模型数量或内部调用层次；历史包只选择确有当前用途的响应。
- 转换旧格式是有消费者的一次性动作，不是永久兼容层；旧数值恒等只验证转换，不能成为新建模逻辑的总验收标准。
- 旧实现与新规则冲突时，用明确机制和独立证据解释差异；不能为保持历史数字恢复已知错误的依赖或成本。
- 现有新代码同样接受整链简化，不因已提交、采过样本或写过文档就成为不可改变的架构。

本节约束设计选择，不授权本次文档整改删除历史文件、清理数据、运行旧代码或变更第三方工作树。

## 13. 风险、停止与完成条件

| 情况 | 应采取的动作 |
| --- | --- |
| 缺少影响必要端口的事实 | 明确要验证的假设，用已有证据或最小观察解决；不改成本遮盖 |
| 同类细分/模型持续增加而完整结果不前进 | 回查区域边界、所有者、重复计费和测量是否可辨识，优先合并职责 |
| CPU residual 难以稳定预测 | 单列来源、适用假设及不确定性；正常 E2E 仍计入，不假装精确可学 |
| 内部因果仍有未知 | 区分是否跨外部端口，不伪造证明；必要依赖未知时保留未完成资格 |
| 数据或环境缺失、原生不支持 | 区分缺资产与不支持；停止对应试验，保留必需交付的实际欠项 |
| 资源不足、预算耗尽或外部干扰 | 保留消耗和失败，回收本任务进程；不触碰他人资源、不把超时当性能 |
| 精度或 10× 未达 | 如实报告差距、可复用结论与下一步，不改口径或无期限逐格拟合 |

阶段按“待做、实施中、限定范围验证、待交付、已交付、暂停”记录，完整 HTTP、正常对照和面板数量给出实际计数。没有固定权重和完整证据时不再报总体百分比；行数、组件数、模型数和日志数都不能代替用户结果。

功能恢复、必要语义、完整面板和维护交付满足后，才可声明重构完成；精度、效率目标另列是否达到。用户暂停、预算停止或一轮分析结束均不自动等于目标完成。已暂停时只处理当前明确授权事项，不能因更新计划自行重启开发。
