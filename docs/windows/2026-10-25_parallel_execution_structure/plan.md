# 单机多卡并行拓扑、调度与执行结构闭环窗口计划

开始日期：2026-10-25。本文维护范围、实现方法、阶段交付与验收条件；当前进度和限制单独维护在 [status.md](status.md)，实施经过保留在 [log.md](log.md)。

目标：在已有 TP/PP/EP/PD 与代表采集能力上，直接运行原生逻辑控制代码，经 adapter 操作核心资源服务及动作/反馈接口，验证子图提取、归一化、变换、连接和动态展开的完整链路。原生闭环覆盖单worker→TP/EP→PP/PD及具名调度/缓存机制；完成单机整合和全量独立验证后，再初步探索多机并最终验收。性能采样、成本建模与精度评价继续后置。

**当前范围：原生控制后端是唯一推进与验收主线，轻量控制器留待开发。** 保留轻量代码及共同控制接口，后续不安排其能力补齐、运行回归、双后端比较或交付验收，也不据历史局部运行声称其已完整支持。共享合同修改按原生闭环需要收口，不为维持轻量行为增加兼容分支；受影响轻量路径标为待开发/待复验，不阻塞本窗口。将来恢复轻量后端时单独制定范围和验证计划。本轮仅取消后端重复覆盖，七模型、配置与请求泛化、并行组合、调度/缓存、生命周期和全流程代码审查的范围保持。

轻量专属策略或接入缺口可以后置；由轻量案例暴露、但涉及共同IR、模板、资源、依赖或执行的共因缺陷，仍须判断对原生主线的影响，不能借后端后置忽略公共正确性问题。已完成阶段与旧报告按当时范围保留，下述涉及双后端的既有设计仅说明接口复用，不追加当前运行或验收义务。

原生资格是预测的前提：固定框架及环境必须能运行该模型和配置，官方支持列表只用于筛选，不能代替实际运行证据。原生不支持时保留原因并移出正向预测范围，不修改框架算法、模型维度或并行实现来凑覆盖；adapter负责观察和绑定已有原生能力。优先选择学术界常用且来自不同厂商/研究机构的模型，不能把同一厂商多个模型等同于跨实现泛化。原生失败、适配缺陷和核心缺陷分别报告。

## 1. 本窗口要交付什么

工作围绕三个问题展开，不能分别做成互不相通的功能库：

| 方向 | 要解决的事情 | 交付结果 |
| --- | --- | --- |
| 子图自身变换 | 同一工作在分片、层区间、成员及路由变化时如何实例化 | 有依据的参数关系、有限实现条件、可复用定义与角色绑定 |
| 子图之间连接 | 不同 rank、stage、服务实例之间如何交接数据和完成条件 | 明确通信组、发送/接收、collective、状态交接与资源依赖 |
| 控制、缓存与执行反馈 | 如何组批和复用前缀，各 rank/stage 何时交接或释放资源 | 原生控制经统一动作/事件合同推进，缓存具有明确所有权与就绪条件；接口允许后续接入轻量控制 |

阶段主线：**S0–S7 环境、共同合同及并行组合 → S8 提前结束并移交未完成项 → S9 原生控制闭环 → S9 后代码整理 → S10 调度优化与一级前缀缓存 → S11 单机整合与全量独立验证 → S12 多机探索 → S13 最终验收**。代码整理是独立维护任务，S10–S13编号保持。P/D 实例及目标 rank 限定在同一台机器；EP 按拓扑提供路由，配置与 adapter 解释专家部署。

**先接通真实控制，再统一核对结构。** S8 的未完成项按职责移交：阻碍共同接口和原生闭环的问题在 S9 解决，其余结构/评价收尾及完整独立验证在 S11 完成；不再以 S8 验收通过作为 S9 前提。原生后端只启用本轮具名的调度机制，不因运行原生代码就自动支持所有优化。CPU/设备 overlap、自适应 chunk、请求抢占、speculative、多级缓存的实际搬运与 CPU/磁盘后端均不纳入本轮；PP 流水仍可并发，不另写微批次调度启发式。

“完整闭环”指选定合法组合从用户输入、代表采集、模板生成/复用、动态决策与展开，到输出、KV/任务资源释放和独立原生结构对照全部连通，不以孤立模板示例代替。它不等于任意并行组合、所有原生启发式或内容相关路径均受支持；条件和未完成项必须公开。

对性能层的判断：**按工作种类选择模型、用节点特征预测服务时间，这个方向成立**，但结构正确不意味着性能层只剩独立查表和求和。模型还需考虑 shape、dtype、实际实现、通信参与者和拓扑；执行器要处理资源共享、等待与重叠。语义子图和成本单元不必一一对应，父子和整体/内部工作不能重复计费。本窗口用给定节点耗时或同条件真实边界时间检验结构，保留后续所需特征与资源边界，不预建性能系统，也不以结构通过保证未来精度。

各模块围绕同一输入、模板和执行合同扩展，主要改动职责如下。

| 入口 | 负责内容 | 本窗口扩展边界 |
| --- | --- | --- |
| [ServingControl](../../../src/markov/controller/control.hpp)、[BatchExpansion](../../../src/markov/templates/batch_expansion.hpp) | 动作/完成端口共同接口，承接单实例、PP 和 PD | 组合拓扑继续消费同一合同，不各复制一套闭环 |
| [KvPool](../../../src/markov/resources/kv_pool.hpp)、[PD 控制](../../../src/markov/controller/disaggregated.hpp) | 现有页/槽位、P/D 驻留和交接反馈 | 共同资源独立于控制器；原生接入后两个控制后端共用唯一资源状态 |
| [Executor](../../../src/markov/execution/executor.cpp) | 就绪后服务、多任务反馈、活跃历史回收 | 联查跨组、跨 stage、跨实例的完成因果，不重建时钟 |

来源资格绑定实际镜像及实现域，旧补丁镜像的结论不转授。模型、dtype、backend、并行实现和页布局约束来源复用；等价 worker 复用不自动授予跨模型、跨 TP 或跨实现域迁移。

## 3. 正向闭环与共同合同

```text
固定模型 + 配置集合 + 请求集合
  → 解释逻辑拓扑、角色及合法组合
  → 匹配已有来源，选择必要的代表角色采集
  → 生成共享子图定义、布局、参数关系和角色绑定
  → 控制器接收到达/完成事件，作出带身份的动作
  → 实例化本地子图，连接数据、通信和状态端口
  → 执行反馈按所选时间依据、就绪条件和资源推进模拟时间
  → 返回相应任务的进度/输出/完成事件
  → 控制器更新逻辑进度，核心提交对应资源状态并反馈，直到请求与必要交接完成
```

### 3.1 拓扑与角色

逻辑 rank、通信组、PP stage、P/D 服务实例与物理 host/device 分开表达。TP/PP/EP 是参与关系，PD 是服务职责和 KV 交接，不能把四个参数无条件相乘生成 rank；组可以相交，成员、局部坐标和原生合法组合由 adapter 解释。

采集部署决定在哪张卡观察，目标 placement 决定模拟时哪些工作共享主机、设备或链路。本窗口正式入口只接收单机目标，逻辑 rank 不等于物理设备编号；本地部署约束由装配边界维护，图和控制算法不散布单机判断。更改 placement 不默认重建本地计算子图，但涉及 transport 或局部实现变化时，需要相应事实；跨机探索的改动应集中于拓扑/资源绑定与通信适配，不提前发布多机输入选项。

### 3.2 控制与执行接口

在已有 Batch、BatchEffects、BatchProgram、BatchExpansion 和执行端口基础上收紧合同，逐步替换单批次假设，不另造一套平行流程或万能消息总线。以下是需要表达的语义，不预先要求每一项成为一个新类：

| 交接 | 最小内容 | 所有权 |
| --- | --- | --- |
| 可见状态 | 模拟时刻、到达、可用资源、已完成的任务端口 | 执行器提供时间与完成；控制实现维护逻辑进度，核心资源服务维护资源事实 |
| 工作动作 | 稳定任务身份、成员的阶段/token 范围、stage、目标角色组、输入与状态效果 | 控制器生成不可变快照，模板层消费 |
| 执行片段 | 参数化工作、依赖、资源、输出及状态提交端口 | 模板实例化与连接层；不自行决定下一批 |
| 完成事件 | 任务身份、端口、模拟时间和该端口允许提交的效果 | 执行器产生，控制器只在相应事件到达后更新状态 |

执行器拥有唯一模拟时钟；到达、控制就绪和工作完成按时间推进，同刻事件使用稳定顺序。多个任务不能继续共用无身份的 Published/Completed 和一份 BatchEffects。中间 chunk、PP 中间 stage、纯传输可以没有用户输出，发布端口不再强制每个动作都有；混合批次的输出与状态效果按成员分别提交。

一次模型调用可由多段准备组成，其间发生的原生行选择沿实际调用立即交接，不能积攒到最终准备时回放，也不能只保存最终混合成员再猜测中间过滤。选择只携带批次视图和请求身份，分配快照来自同一资源服务，不因此增加第二份请求或页状态。上一轮结果的筛选、后续运行批次的筛选须分别更新对应保留列及合并关系，不改变与前缀查找等工作的必要顺序。

请求逻辑进度由所选控制实现唯一维护；槽位、KV页、前缀索引、引用、驻留和就绪由核心资源服务唯一维护。S9先交付基础KV资源，前缀匹配、发布及淘汰在S10接入同一服务。原生选批期间的查询、申请和回收经adapter直接调用共同服务，轻量后端使用同一服务；不保留原生独立页账或事后同步缓存树。原生请求中的长度、句柄等是逻辑进度或资源视图，不替代真实资源状态。图中的资源身份及状态变化绑定服务结果，图值和存储版本继续用于依赖构建，不再次决定分配或命中。

资源服务在就绪后才能开始。支持多任务时，不能因先装配一个未来任务，就永久预占资源或算死后来任务的时刻；先用明确资源串行规则和固定服务时间建立正确事件闭环，连续带宽争用模型留到性能阶段。图回收须保留所有在途任务、消息和状态引用，不沿用“一个批次结束就回收全部历史”的假设。

### 3.3 统一控制接口与当前原生主线

```text
原生逻辑控制 → 框架 adapter ─┐
                           ├↔ 核心资源服务：容量、分配、前缀、引用、就绪
轻量控制器（留待开发）─────┘
          两者 → 同一工作/等待接口 → 模板实例化、连接与事件执行
               ←──────── 模拟时间和具名完成反馈 ──────────┘
```

S9先实现第一条路径的基础控制与KV资源，S10再接通调度优化和一级前缀缓存：实际调用固定版本的原生调度及请求处理代码，资源调用由adapter转入核心服务，工作提交和完成经共同值类型交接。原生决定下一批及逻辑进度，核心管理资源并以模板生成CPU/设备/通信工作、推进模拟时间，反馈驱动原生继续。资源服务负责实际匹配、分配、引用和淘汰，框架具体语义须有源码依据并对照验证；不把原生资源操作后的状态复制当作接管。不能将原生算法翻译成自写控制器、照抄几个原生函数或回放记录称为原生后端；真实 serving 采集/验证也不能直接充当仿真。

两种控制实现复用 ServingControl、BatchExpansion 及现有事件执行合同的职责，必要时连同生产者/消费者一起收紧；不再增加一个与之平行的通道。workflow 只选择和装配后端，不读取原生队列或轻量 KV 容器。Python 侧运行原生对象并作框架适配，C++ 侧保留共同资源、动作、模板和执行，跨语言只传必要资源查询/结果、工作快照与反馈，不传框架私有对象或完整 tensor 数据。

本轮所有正式探索、开发回归和独立验证输入显式指定`control: native`，不依赖当前缺省值，也不自动回退到轻量或回放。共同接口的可扩展性通过职责、依赖方向与原生多角色消费者审查，不以同时维护第二套可运行控制器作为前提。现有轻量实现不删除，也不要求修复其本来不支持的prefix cache等机制。

接口既要表达模型批次，也要表达确实影响下一步决策的接入、释放、等待和无模型清理；只覆盖 `run_batch` 会继续遗漏控制历史。按统一流程及必要因果取得这些边界，不将原生所有函数都变成动作。原生后端依赖的时刻、到达及完成来自唯一模拟时钟，不能使用本机运行快慢决定目标调度；原生控制代码的实际执行时间不直接当作模拟 CPU 耗时。

批次记录回放保留为固定组批条件下的诊断消费者，不作为第三种在线控制实现，也不替代 S9。原生后端依赖的框架软件环境在装配边界声明，核心构建不引入 SGLang/Ascend SDK；纯预测无需设备、网络或目标验证数据的边界保持。设备工作、目标通信和 KV 数据搬运由图模拟，不为每次预测运行完整真实推理；初始化若仍依赖设备/真实权重或大量私有对象补造，须在 S9 首个闭环中查清并解决或明确报告阻碍，不能降低交付条件或暗中回退到轻量/回放。

### 3.4 抽象对应代码层次

| 层次 | 固定职责 | 差异如何表达 |
| --- | --- | --- |
| contracts | 工作动作、端口事件、角色/组、状态效果 | 简单值类型，避免把具体控制器和框架对象带过边界 |
| controller | 定义共同控制交接，承接原生逻辑控制 | 原生 adapter 转换相同合同并唯一维护请求逻辑；轻量实现保留待开发 |
| KV / cache 组件 | 核心统一维护前缀索引、引用、分配、驻留及就绪 | 两种控制实现使用同一资源服务；通用机制共用，框架具体资源语义通过有依据的策略/绑定表达 |
| templates / graph | 共享定义、有限变换、实例连接 | 共用算法与角色/参数绑定，沿用 BatchExpansion 隔离装配差异 |
| execution | 时间、工作就绪、资源顺序及完成反馈 | 消费共同合同，不识别框架函数、控制器具体类或特殊 rank |
| adapters | 原生来源、控制入口/完成交接、实现条件、角色和 transport 解释 | 调用原生代码并转换合同，不复制调度算法或核心图逻辑 |
| workflow | 选择并装配上述对象，维护单任务生命周期 | 具体实现的依赖集中在装配入口，不扩散到核心算法 |

需要运行时替换的职责使用抽象接口和浅层继承；同一算法确实服务多个编译期类型时使用 C++23 模板、concepts 或局部特化。仅 rank、层区间、分片大小不同则使用值与绑定；多个并行机制优先组合，不为 TP×PP×EP 的每个组合建立子类。类、目录和依赖方向共同体现这些层次。

清理被新抽象替代的旧职责链、散落的特例分支、重复状态和无消费者代码。抽象的验收是改变一种策略或装配方式时修改集中、其余层可继续复用；不以接口数量、继承深度或模板技巧衡量可扩展性，也不预建尚无用途的未来实现。

## 4. 子图如何扩展并控制数量

### 4.1 内部变换和来源

| 变化 | 优先取得的依据 | 处理方式 |
| --- | --- | --- |
| 成员、token/context、容量 | 控制快照、原生参数及 fake/meta 关系 | 求值 shape、索引、页读写、重复子调用；遇到真实实现分支选已有原型 |
| 模型分片、层区间、expert 归属 | 原生模块和并行元数据 | 实例绑定与组合；分片、复制、padding 和首尾职责保留条件 |
| 数据搬运、collective、P2P | 实际接口、参与组、端口和数据布局 | 计算传输范围，连接对应生产/消费；不从 kernel 名猜拓扑 |
| 新融合或新控制/资源行为 | 新来源及有限适配声明 | 增加确有差异的局部原型，不复制整套模型与 serving 图 |

小范围参数化成功不代表可跨任意 TP 或模型。已有分片公式、实现条件和角色映射足够时，复用可证明不变的部分；否则仍为新 TP/模型建立来源，自动归并其中相同子结构。不能把“跨 rank 共享”写成“任意 TP 无需采集”。

### 4.2 等价 rank 共享

分开共享计算叶子、共享组合布局和共享完整角色三种情况。两个 rank 可以共享 decoder layer，却因输入接收、发布、首尾 stage、KV 复制或 padding 而不能共享完整角色。

归一化沿现有确定性定义和布局机制扩展：局部值/资源重编号，物理卡号、全局 rank、层起点和消息目的地进入绑定；工作、端口、别名/读写、CPU 服务切口、实现条件及分片几何仍参与等价判断。不同实例永远有各自资源绑定，不因引用同一定义而共用 KV 存储或执行 stream。

后续采集改为：**解释目标拓扑和原生角色条件 → 在启动前分出有依据的等价角色 → 每类选择必要代表及局部实现分支 → 观察代表 → 为各目标 worker 绑定实例 → 用留出 worker 核对**。已有完整角色来源可以作为等价依据和开发证据，不要求每个新组合先采全体 worker 再去重。

等价依据由 framework/runtime adapter 提供，优先读取原生组坐标、模块分片、层/专家区间、实现分支和接口；共同模板层维护同一套绑定与连接算法。不建设第二套图等价证明器或逐 rank 例外表。须核对工作/端口、类型/布局、别名/状态效果、CPU 服务和实现条件；差异只有身份或可证明的参数映射时才复用。首/中/尾 stage、接收/发布角色及 padding 不同的 worker 不能简单并类。

派生 worker 使用代表来源和显式映射，不复制并改写原始 trace 冒充本 worker 已被观察；各实例保留独立权重、KV、stream、事件和通信端点。EP 的专家编号及路由工作量进入绑定与实例，同一角色的不同路由不是新的完整角色模板。无充分依据的角色按必要来源处理，真实新分支明确增加局部原型。

**减少观察和减少原生参与者分别计算。** 可隔离 TP 角色时，代表复用应减少模型会话；真实 PP/EP/PD 协议仍可能要求全部 peer 同时运行，此时只选择代表观察和导出，不声称只运行一个 worker 已验证多 rank 通信。验收分别记录原生会话、启动参与者、被观察角色、导出量和保留量。

验收同时报告共享定义数、布局数、角色绑定数与实际采集角色数。扩 rank 或重复层时，纯身份变化只增长绑定和实例；新增定义必须能解释为工作或条件变化。不给所有模型规定一个模板数量上限，不以隐藏差异凑少数模板。结构共享不自动授予耗时共享。

### 4.3 子图之间连接

数据端口沿生产者/消费者和存储版本连接；通信端口还需通信组、参与者、操作种类和调用身份。PP 消息、EP 交换和 PD 搬运带 stage/请求或微批次等必要身份，不能把并发调用按 trace 中的全局序号配对。

collective 保留各参与者输入就绪和本地完成；P2P 区分发送可读、发送返回、接收可用以及缓冲区何时可释放。协议确实要求哪些参与者到达，就等待哪些参与者，不为简单装配增加全 rank 全局屏障。P2P两端可跨动作到达，但必须属于同一工作身份、通信组、方向、channel和field；待连接完成端口阻止其消费者，其他就绪工作仍可执行。没有可继续推进的工作或后续输入，或者整个流程结束时仍缺对端，才报告明确缺口，不能伪造零耗时通信。回收历史图仍须保留未配对端点和必要前沿，不能依赖完整明细模式才能运行。

### S6：EP 的结构能力与内容边界

MoE主线为完整Qwen1.5-MoE-A2.7B；其他模型仅在原生框架可运行的配置内接入。选型同时检查EP、PP和P/D路径，模型支持列表不代替具体并行组合的运行证据。HBM按总参数、dtype、分片和工作区估算，不按激活参数估算；沿用完整官方配置的原生dummy权重方式，不裁层、缩专家或改维度。使用原生serving生命周期，不实现指定状态单步入口。

EP 包含路由、token 分发、专家计算和合并；不同 expert/rank 的 token 数可能不同。先核对真实后端、已装包、通信和内存，再以 EP1 参考及 EP2/4 的合法配置取得必要来源。当前 `ascend_fuseep` 会将 EP 设为 TP，后端及 dtype 约束由实际源码/接口核对，不把二者相乘计算卡数，也不提前承诺固定 fused mode 可用。取得专家分片、路由输出边界和传输接口；融合 dispatch/combine 按原生切口表达，不拆出不存在的 kernel。

`ep_routes`按EP拓扑ID保存请求/层/token到全局专家的分配及补齐行路由。配置与adapter负责专家部署、分片、实际补齐数量和通信；系统不从请求长度推导内容路由，不增加真实权重补齐元数据获取或自动fallback。

本阶段同步完成以下交接：

- 输入解析与组合规划：采集前核对 workload 的逻辑路由覆盖、专家范围与 top-k，再核对各配置的部署及后端条件；缺项明确报告，不补采路由或默认均匀分配，不影响其他合法组合。
- 控制与实例化：路由按请求、模型层及逻辑 token 位置索引，按目标成员选择对应片段，不依赖来源 batch 序号；S10的chunk、mixed和前缀命中继续使用这些逻辑位置。公共合同交出工作所需分配，不暴露原生框架对象。
- 模板与通信：从专家选择及目标分片推导各 expert/rank 工作量、dispatch/combine 和不等长通信；保留零接收与合法多目标分发。已知路由本身不删除本次仍需执行的 gate/top-k 等计算工作。
- 后端适配与结果：原生 padding、排序、容量截断等行为由实际实现规则解释，输出明确标为给定路由的条件结构；输入路由不能替代原生 MoE 工作和传输证据。

若当前栈没有可运行的 MoE/EP 来源，则停止该分支并记录明确阻碍，不建立假模板充数；EP 保留为未完成能力。路由输入已纳入本轮，真实文本输入、自动路由预测和路由成本模型不在本轮实现范围。

#### 路由合同和分工

workload按拓扑给出真实token与补齐位置的全局专家选择；adapter根据目标批次计算实际补齐数量、原生分片、专家归属、工作量及通信，用户不维护逐batch状态。真实token的逻辑位置贯穿Prefill、Decode、chunk和P/D；按拓扑组织输入不要求这些token的专家选择改变。比较配置差异时固定实际输入、权重或明确的给定路由条件；dummy自然路由不代表真实权重行为。

### S7：组合拓扑与采集前代表复用

保持简单控制，按“每个 serving 实例的逻辑拓扑 → 组/角色及分片 → 代表采集 → 本地实例 → 跨组/实例连接 → 完成反馈”统一组织。P/D 各有自己的 TP/PP/EP 结构，PD 是两实例间的交接；两侧沿同一已选定的拓扑路由合同消费请求逻辑位置。共同 rank、组、工作身份和资源合同继续复用，不为每个开关组合增加控制器、workflow 或图类型。

先落实采集前角色分类和代表绑定，再用它推进新增组合；组合开发不默认重采全部 worker。已有来源用于取得分类依据，缺少依据的角色保留必要观察；新增功能按原生机制补齐，完整比较和案例矩阵由 S11 承接。

本阶段按以下顺序实施，每项先沿生产者和消费者收齐能力，再进行必要开发核对：

1. **采集规划与角色派生。** framework adapter 在启动前区分请求接收/发布、PP 首中尾、层与专家区间及实际实现条件，输出代表和目标绑定。共同模板层应用映射，各 worker 的权重、KV、stream 和事件保持独立；固定数值操作数只有明确原生语义才能改绑，不按相等整数替换。先用已有 TP/PP/EP 事实审查映射，不伪造派生 worker 的观察记录。
2. **实例内组合。** 沿现有 ServingStructure、RankStructure 和 ParallelComposition 统一 TP/PP/EP 的角色装配、路由作用域和通信端口；先闭合 TP×PP 与 PP×EP/TP 联合案例。真实协议需要全部 peer 时仍启动全组，只减少选定角色的插桩和导出；可隔离 TP 的等价角色则减少完整会话。
3. **实例间交接。** 将现有 PD 的“两实例”与“每实例一个 worker”拆开，P/D 复用前一步的实例装配；控制器继续维护两池和唯一请求进度。KV 的层、head、页及布局映射取自原生注册和分片元数据，传输等待实际生产、目标预留及完成端口；删除被替代的固定两 rank 装配链，不并存一套多 rank PD 流程。
4. **开发收口与冻结。** 核对下表所选组合、代表采集的实际节省、请求/页回收及默认/明细一致性，再做阶段代码/文档/数据审查和推送。S11 另用未参与分类或修正规则的 worker/运行独立对照；S7 的开发材料不冒充留出证据。

原生构造参数不一定能仅由config得到：隔离TP先取得始终必需的根角色，再规划其余会话；原生组则在必要peer加载模型后比较模块类型、几何、stride、offset、设备类型、局部存储别名和标量条件。身份使用明确绑定，只为代表启用语义/runtime/profiler观察，保留统一预热和原生停止屏障。层区间来自实际attention模块，专家区间切片沿实际发布的view声明。

PP返回token使用当前批次语义，proxy局部分片使用实际端口几何；入口与子调用共用命名轴绑定，不通过倍率重建proxy。开发来源不作为后续独立目标证据。

| EP 与 TP/PP | 真实 MoE 的 TP/EP 组关系、PP×EP，以及一组合法 TP/PP/EP 联合配置 | 路由到局部 expert、变长分发/合并、跨 stage 成员与逻辑 token 身份 |
| PD 与 TP | P/D 各侧多 rank，包含对称及非对称并行度候选 | KV head/页片段映射、对应发送/接收、首 token 及源释放条件 |
| PD 与 PP | P/D 侧的 stage 层区间与交接；多 stage 不能缩成一个来源 rank | 每层 KV 的实际所在者、目标消费者，以及聚合完成条件 |
| PD 与 EP | P/D 内分别执行 MoE 路径，关联给定路由与交接工作 | 专家/模型工作不与 KV 所有权混同，输出与背压仍由唯一请求进度推进 |

组合实例的rank数由原生组的交叠关系确定。单机八卡下，TP2×PP3为六个参与者，EP=TP2、PP3时仍为六个；P/D两实例的设备数则相加。候选优先覆盖互相独立的机制和一个较高阶组合，不枚举所有参数乘积。每项先区分原生明确不支持、项目尚未实现、缺少来源及已验证，不能将项目自身的装配限制当作后端限制。

P/D开发固定有限输入，额度与失败累计保存在各任务中；实现阶段不遍历请求配方或任意并行乘积。

原生PD的Decode PP必须等于Prefill PP或1，此条件在adapter输入边界解释；启动、长生成和停止由总native额度约束，保留短就绪查询及控制接口期限。采集通过Torch NPU的`analyse_flag=False`先停止并落盘，再离线使用官方analyse，避免PP的串行解析延长记录窗口；不新增后台导出线程或第二套profiler。SDK文件存在不能代替语义和exporter完成资格。

来源恢复仅接纳语义与解析均完整的实际记录，不能补造成功session-summary；物理覆盖与exporter完成资格分别保留。预算增加、失败及累计费用写入日志，只回收已消费或无有效语义的原始导出，不重置费用或峰值。后续独立验证使用独立材料，不将开发证据计为验收。

P/D 分片相同时绑定实际片段；并行度或 stage 切分不同时，从模型、KV 布局和原生传输协议推导 head、层、页及有效 token 区间的对应关系，必要切片/聚合/重排进入执行结构。不同布局不能直接连接整页，也不能用总字节相等代替映射。非对称候选纳入能力核对；缺少合法原生协议时保留未完成，不能通过平均分配、零耗时搬运或放宽条件通过。

采集前复用的交付必须同时具有：代表选择结果、每 worker 的来源/映射、本地展开与跨 rank 正确连接，以及实际节省。至少一组多 worker 案例的被观察角色数小于逻辑 worker 数；可隔离的 TP 角色还应减少完整原生会话。PP 中间角色、EP 同职责专家 worker 按实际等价条件验证，不把输出 head、首尾职责或不等布局一并复制。

结束条件是所选合法组合从同一入口完成请求、交接及资源回收，代表来源能服务多个独立绑定的 worker。采后归一化仍保留，但仅文件变小或共享定义变少不算完成采集节省。完成必要开发核对、代码/文档/数据审查和提交推送；新增范围的独立资格仍由后续完整验证取得。

### S9：直接运行原生逻辑控制，共用核心资源和执行

**目标：** 原生代码负责请求逻辑、基础组批及进度，核心统一管理槽位、KV页、映射、就绪和回收，以及模板与事件执行；轻量控制器使用同一套服务。四项调度优化/前缀缓存由S10实现。原生在决策期间查询/申请资源，模拟反馈恢复原生执行，不在两侧各养一份页账。具体源码切口、环境关卡、接口改动和验证方法集中在 [S9指导文档](s9_native_control.md)，本节维护阶段交付。

| 步骤 | 做什么 | 完成依据 |
| --- | --- | --- |
| S9.1 单worker闭环 | 核对未交付改动；参考SGLang Simulator接管设备入口，运行真实原生选批/结果处理，接共同资源与图执行 | TP=EP=PP=1、关闭PD及新增优化；请求到达、计算、结果、下一批与释放完整，轻量仍用同一资源服务 |
| S9.2 TP/EP协作 | 先TP组内一致控制与通信，再EP给定路由及专家分工；复用现有分片和模板绑定 | 具名合法TP/EP案例闭环，成员/token和反馈一致、分片资源独立；单worker保持可用 |
| S9.3 PP/PD交接 | 先PP微批次和异步事件，再PD准入/预分配/传输；最后核对与既有拓扑的合法组合 | 原生继续决定轮转和准入；对应模拟事件正确唤醒，无提前使用/释放，必要无模型清理完成 |
| S9.4 收口与移交 | 关联审查、旧路径删除、代码/文档/数据整理及分层提交推送 | 正式入口无设备/网络/目标记录依赖，唯一状态与分层成立，具名基础闭环及来源范围交给后续代码整理任务 |

**严格按简单到复杂推进。** S9.1先收口单worker，S9.2完成TP/EP后再进入S9.3的PP/PD；不把多个接入问题同时摊开。每步先完成明确功能，再以必要开发案例核对，并检查相关代码的放置、依赖、状态所有权和可删除部分。完整阶段维护交付在S9.4进行，随后单独整理全项目代码；S10承接优化，全量独立矩阵归S11。基础连续组批、PP轮转及PD准入属于S9，不能一并后置。

S9.1须区分模型host返回、结果实际可读、结果处理完成三个观察点，沿原生读取调用等待已有子图端口，不能以整设备屏障替代。资源压力下仍由原生选择撤回成员；共同资源在相应释放工作完成后更新可用身份，再恢复原生容量判断。重新Prefill保留已有生成进度，不能把资源释放当请求结束，也不能靠增加容量绕过撤回。

资源压力来源核对须覆盖空闲页耗尽时的释放形态；混合dtype、空输入及物理复制分支按runtime原型取得依据，不能把同dtype原型直接用于混合类型。实现与来源资格分别记录：控制逻辑已接通不能替代模板覆盖，新增来源也不能替代成员顺序、资源归还和重新Prefill的闭环检查。

同dtype拼接保留可变长集合和有限归约；固定类型顺序的混合拼接用已有命名端口表达各输入长度，在runtime声明空输入与转换条件。代表原型随同一采集会话取得，核心根据实际端口选取已观察执行形态，不按目标请求追加规则。

**复用原生规则，接管硬件接口。** 原生代码已有TP/EP协同、PP轮转及PD准入，adapter将它需要的资源查询、计算/通信和等待接到核心。PP/PD的新增工作是模拟完成信号与原生等待位置的交接，不预判需要重写控制器或必然复杂。实际接管代价和合法范围通过各步闭环确认。

S9.3的接入先明确每个原生参与组的资源域、lane及工作身份，再拆开提交与完成反馈，并按实际调用逐段连接模板。 来源与目标共用运行上限、实际槽位容量和传输元数据身份的含义；先完成具名输入几何和prebuilt按请求/按批次工作的变换表达，再扩并行组合，不以固定采集成员数或逐批次补采维持闭环。通信尚未遇到对端时必须保留明确的待连接完成条件，不能当作零耗时或全局同步。现有轻量装配中的提前准备、接收和等待须在同一套模板/连接实现中调整；原生PP完整入口、异步交接和正常停止都属于交付条件，控制循环探索不代替正式核心闭环。

**无设备方法与边界。** 优先参考上游tools/sglang-simulator；它不同于简化的debug_utils/schedule_simulator。允许有明确用途的模型/设备/kernel加载替身、CPU元数据及模拟事件接口，保留原生控制语义；不能伪造组批、资源命中或把所有通信立即完成。固定框架按自身接口适配，不为直接安装参考工具自动升级；完整上游工具、版本兼容层和性能系统不随之引入。

**代码位置先于扩展明确。** C++contracts/controller/resources/templates/graph/execution维护共同能力，具体SGLang图绑定留在现有C++adapter；Python原生控制接管放独立的src/control/markov_control，框架与runtime差异分别在相应adapters，进程/桥接生命周期在workflow。采集继续归src/collection，example只编排验证，Docker只组装环境。完整位置表由S9指导文档维护；新目录随真实消费者创建，不只移动文件而保留越层依赖。

**共同资源和工作合同。** 原生保留请求队列、阶段/output进度与控制上下文；核心维护槽位/页、映射、在途引用、就绪及回收。S9关闭新增优化，不预建前缀树、LRU或多级存储实现；S10在同一资源服务中增加缓存职责。资源查询在原生选批过程中回答，分配只生效一次；原生准入估计不等于实际占用，原生准备字段也不等于设备内容完成。结果可读后继续执行原生结果处理，取得真实输出/释放动作，再按相应端口提交；不预先猜完整结束效果。

原生真实控制耗时仅是本机处理开销，目标CPU/设备/通信由图和给定耗时表达。提交、模型结果可读、输出、资源可重用与动作完成分别交接；等待挂到对应模拟事件，其他实例仍可推进。只为规定流程及必要因果取得工作片段，不把原生每个函数变成模板。

原生控制运行适配属于正式src，独立于采集插桩；共同桥接复用必要值合同，不向workload加入组批回放字段，不放入example，不建分布式RPC平台。只有采集/验证的真实serving保留原生物理资源管理，预测路径使用核心模拟资源。原生和轻量分别声明已实现能力，不强行为轻量重复实现本轮所有原生优化。

正式入口统一管理核心容器、原生控制容器及其worker、时限、日志和清理；模型元数据从已选模板取得，不另让用户选择权重或第二份模型配置。尽量直接复用原生主循环、接收分发和空闲检查，适配只接请求来源、资源协议与工作/完成边界。收口时分别核对模型调用返回、CPU读取结果、结果处理完成与资源重用；普通请求跑通不能替代这些边界，也不能用全局等待全部完成掩盖差异。资源压力引起的原生回退按实际支持范围验证，未实现项明确保留。

### S9 后代码整理：按维护职责重组实现

**目标与范围：** 在S9.4已交付行为上，重新组织全部自有代码，让主流程可顺着阅读、同一规则集中维护、框架差异局部替换。范围包括此前未修改的业务文件，以及关联的example、脚本、安装/构建、Docker和文档；独立维护交付后才进入S10。本任务不增加调度/缓存能力、不建设性能层，不代替S11独立验证。

**方案选择原则。** 从项目需要的流程和状态所有权推导结构，再决定怎样复用现有实现。现有目录、类和已写出的未交付重构都只是候选材料，不因已经存在就保留；允许整文件、多文件合并或重写，并删除被替代的整条路径。最小完整方案指维护职责和执行路径简单，不指Git diff最小。优先比较保留、合并、拆分、重写的实际收益：读懂一次流程要跳转多少处，同一事实有几个所有者，改一种框架行为会波及哪些模块，是否增加独立安装/构建负担。只为名称好看或层次对称而新增目录、接口、父类和转发没有收益。

#### 目标职责与依赖

先围绕两条可直接阅读的主线安排代码：

- 建库：任务输入 → 原生观察 → 来源解释与投影 → 层次归一化/资产生产 → 正式模板库。
- 仿真：任务输入与模板库 → 运行装配 → 控制动作 → 模板绑定/展开/连接 → 事件执行 → 完成反馈与资源提交 → 结果发布。

| 职责 | 维护内容与边界 |
| --- | --- |
| 外围任务 | 一次任务的输入、预算、恢复、进程/容器生命周期、产物发布；调用采集、建库和仿真入口，不解释图或替控制器组批 |
| 原生观察与解释 | 公共调用记录与原型观察生命周期；框架adapter识别原生语义，runtime adapter解释设备/API事实；适配器维护具体采样点、输入构造和原生调用，交出共同来源合同 |
| 模板生产 | 从来源投影、提取并归一化共享定义/组合/绑定；编译临时索引随生产结束释放 |
| 模板消费 | 读取正式资产、选择合法结构、绑定参数、实例化并连接；不依赖采集会话、来源路径或编译器临时状态 |
| 控制与资源 | 所选控制实现唯一维护请求逻辑进度；核心资源服务唯一维护页、槽位、驻留和就绪；原生adapter只翻译交互与提供必要视图 |
| serving推进与执行 | serving只协调共同动作、展开和反馈接口；执行器维护模拟时钟、依赖和完成事件；框架具体装配在外层 |
| 验证 | example构造案例、独立对照、矩阵和汇总，调用正式能力；不复制核心规则，业务不依赖验证 |

外层装配选择具体adapter，共同serving/模板/资源/执行依赖稳定值合同和必要接口。框架adapter可组合runtime；runtime不反向识别框架。不得为了拆目录新建中间JSON、重复解析或第二份状态账本。C++以类组合实际职责，运行时替换才用接口/浅继承，同算法的编译期类型差异才用模板或局部特化；不预建尚无第二种实际行为的扩展体系。

| 通用文件发布、输入解析、预算恢复、example工具 | 按真实消费者合并重复实现，输入边界只校验一次；纯验证编排归example。没有独立职责的小目录可以折回所属模块 | 不新增宽泛utils，不以一个文件一个目录制造层次；不给验证留下复制业务逻辑的另一条路径 |

内部模块路径调整同步全部调用者，不留旧包别名、转发头或兼容启动器。保留已有公开用途和命令含义；只有无消费者的字段、命令或路径才整段删除。Python包调整须核对插件注册、安装清单、PYTHONPATH、镜像COPY、子进程模块入口及源码根定位；外层任务包不能迫使无设备预测安装采集插件或设备依赖。C++头源同目录，CMake target依赖也体现职责，不能只移动文件。

每批允许跨多个目录完成整条职责链，也允许重写比局部拼补更清楚的实现。拆大文件时按独立算法、状态和生命周期划分；合小文件时消除无意义跳转，避免把不同职责重新堆成大类。必要空行与重要注释是可读性的一部分，不以压行、删说明、搬出统计范围凑缩减量。删除覆盖实现、类型、调用、配置/CLI、注册、构建、产物及说明，不只隐藏入口。正式机器交接、输入校验、数据保护和资源释放须保留。

**编译与运行节奏。** 开发中以阅读、调用关系和所有权推导为主，修改时完成关联调用者和引用。完成一组相互关联的大范围修改后统一编译检查，能够共用一次构建的批次合并检查；不修一层就编译、不每搬一个文件就启动容器。构建反馈先汇总再集中修正，除新修改、失败或明确未决风险外不重复检查。C++在modeling Docker构建/运行，Python在实际支持环境核对语法、安装和导入；变化涉及哪一种镜像才构建并核对哪一种。

**行为核对。** 修改前选定S9已有输入、来源、给定耗时及结果，按受影响链路选取必要案例，集中在较大批次完成后通过公开入口运行。总体覆盖原生单worker、TP/EP、PP、PD及已交付组合，以及必要回放诊断、默认/明细、资源压力或晚到/延迟传输、退出清理中受影响的路径；当前不安排轻量运行，也不为每个局部改动重复整个集合。采集/建库变化优先复用保留事实重解释和建库，不因目录调整启动完整设备采集；确需新观察时先列缺失事实、有限额度及结束条件。

比较请求结果、动作与完成顺序、资源分配/归还、必要图关系和错误边界，不能只比较退出码。模板内部编号或输出布局因合理重组改变时，比较对应关系和实际语义，不以修改预期掩盖差异。确认原有缺陷须单列触发条件、影响与修复证据；无法解释的行为变化阻止交付。保留有用途的轻量控制和批次回放诊断，历史partial、失败、来源与费用不升级或清零。

**维护性验收。** 除构建和行为对照，还须沿“改变一个观察入口”“改变模板绑定规则”“替换控制实现”“调整任务输出”四种实际维护场景静态追踪：修改集中在其职责，公共消费者不重复解释同一事实；不为这些推演新增功能。顶层方法保持相近抽象层次，文件和目录能说明责任，跨语言交互只含必要合同，新增接口/字段都有当前消费者。分别记录业务与example净增减，以及真正删除或合并的职责，不以行数、目录数或接口数代替质量。

**交付条件：** 全部自有代码审查、重组清单、跨模块所有权和正式/验证边界落实；代码、当前文档、构建安装入口及数据引用一致，必要运行通过且差异有说明。只清理本任务拥有且确认无用的数据和产物，保留在用资产与历史失败；不动用户其他改动、官方third_party、deprecated或格式配置。整理后按可独立审阅的职责分层提交推送并确认远端，以最终提交启动S10。

### S10：调度优化与一级前缀缓存

**目标与前提：** 以S9后代码整理任务已审查并推送的最终提交为基线，继承S9原生控制/并行闭环，在同一套控制、资源和执行接口上实现chunked prefill、混合组批、Decode优先及一级prefix caching。原生继续决定动作，核心维护资源；不增加第二套控制路径。启动时核对实际原生能力、来源和所需接口调整；S9基础闭环或后续代码整理尚未交付时，先完成前置任务再进入本阶段。

| 步骤 | 交付 | 完成依据 |
| --- | --- | --- |
| S10.1 Chunked prefill | 逐成员token范围、context、输出资格及chunk准备来源 | 中间chunk无输出，完整prompt不重算，页和EP路由按逻辑token绑定 |
| S10.2 混合组批与Decode优先 | 真正mixed入口、共享模型工作和明确优先行为 | 不叠加两份完整模型图；持续Prefill到达时就绪Decode得到所需预算，不以配置名称代替行为证据 |
| S10.3 一级前缀缓存 | 统一内容身份、核心前缀索引/引用/LRU/就绪、原生facade及必要来源 | 匹配、发布、淘汰、尾页与原生规则一致；采集/预测内容一致，缓存状态仅一份 |
| S10.4 组合复核与维护交付 | 四项机制与TP/EP、PP/PD的合法交互；关联审查、文档/数据整理及分层提交推送 | 具名能力和来源范围有开发证据；基线交给S11整合和全量独立验证 |

每项先完成单worker实现，再按TP/EP→PP/PD核对合法交互，组合复核沿用已建立的闭环；不按模型或开关组合复制控制、图算法和模板库。功能修改先成批收口，再安排必要开发复核；完整独立矩阵仍在S11执行。原生与轻量分别声明能力，不要求为轻量重复实现所有原生优化。

控制推进还须区分原生局部工作和图工作：PP的准入共识、微批次轮转可在没有图任务执行时继续，不能将一次空接收或图序号未变视为死锁。容量不足的运行保留原生准入结果，并由已有运行时限约束；若要提前判定无法推进，必须有覆盖原生局部控制的依据，不能通过限制接收轮数或复制准入公式处理个别请求。

正式探索任务显式选择`control`（`lightweight`或`native`，缺省保持轻量）；原生模式复用已有无设备启动入口。为让新增机制有完整产品消费者，这项入口选择随S10接入，不等待S11；S11仍负责整体整合与独立验证。共同实例以可选`prefill_chunk_tokens`声明正整数、页对齐的chunk预算，PD使用`pd.prefill.prefill_chunk_tokens`，均需原生控制和同机制来源。PD按P1/D1→TP/EP→PP组合取得逐块发送资格，不能沿用整段PD的已有结论。来源按机制分域，以固定代表chunk取得模板，目标chunk长度不作为逐值建库依据。

#### Chunked prefill

使用原生固定 chunk 设置和 `PrefillAdder.add_chunked_req/add_one_req`。成员合同保存本轮逻辑起止、已有 KV、命中前缀、新增页和输出资格。`ScheduleBatch` 准备和结果处理保持原生路径；中间 chunk 不产生用户 token，最后一个有效 prompt chunk 才进入首输出。`max_prefill_tokens` 与 chunk 上限不互相冒充。

模板参数沿该成员事实传播，不因切成多个 chunk 重复完整 prompt，也不为每个 chunk 序号建立新模板。页面尾部利用、模型 padding 与 EP 路由分别按实际机制绑定。

实现按一条完整的调用链展开，先建立逐次工作合同，再接来源和公开配置：

1. 原生在提交批次时交出该次工作的输出进度快照。核心据此区分计算完成与生成新token；中间块保持原输出计数，最终块增加一次，撤回后重算也沿用原生保存的输出历史。快照随工作释放，不建立第二份请求进度账本。
2. 资源预约时更新已分配的KV范围，内容就绪由模型及传输依赖决定；中间块结果不加入Decode视图、不发布输出、不宣布PD可接管，也不回写已分配范围。原生下一轮真正保存chunk索引时才展开对应子图；保存的索引端口跨图回收保留，并作为下一块准备的输入。不能把这段工作挪到前一轮结果处理中，也不能用空索引替代已有KV。
3. 采集与目标使用相同机制。取得非零context的准备/attention及调度期索引保存来源，按已有声明规则归一化；chunk长度是目标参数，不按序号或请求长度建库。公开开关在控制、来源及目标展开均接通后才开放，旧的整段Prefill证据不自动获得chunk资格。
4. 必要开发核对覆盖整段、连续多块、尾页、撤回重算、不同到达时刻；随后接TP/EP和PP。PD需单独衔接原生逐块发送、末块元数据及接收准入，不能直接把现有整请求交接改为跳过中间块。完整泛化矩阵仍由S11完成。

PP还要区分资源已预约的范围、设备内容就绪与原生结果处理。原生流水可能在处理上一块结果前，保存其索引并为同一请求安排下一块；不能从迟到的结果回写下一次分配的起点，也不能把索引可用当作设备内容已完成。沿共同资源服务和已有工作依赖表达这个区别，同时核对轻量控制、PD预约和撤回释放，不为PP另建KV账本。

PD按原生`process_prefill_chunk/send_kv_chunk`取得实际发送范围：非末块只发送完整页，尾页和请求元数据在末块完成。适配器交出发送范围和元数据资格，共同传输层维护在途片段及完成状态，图装配连接对应源计算和目的预约；全部必要片段及末块元数据完成后才允许Decode接收。替换当前“每请求一次全量发送”的实现，不保留分块与整段两套交接流程，也不把中间块当作完整请求重复传输。

同一原语在不同服务角色中出现互补执行分支时，优先检查已有观察能否复用：明确逻辑操作、固定参数、分支条件，以及调用线程、设备队列和事件的资源绑定，再建立调用角色的选择。适配层声明同会话、同实现及同逻辑worker的兼容范围，核心以双方实际执行过的共同操作建立完整且唯一的资源对应。只补缺失条件，保留原有绑定，操作私有事件独立分配；来源冲突时不选取，借入分支不参与后续推导。共享定义或相同资源编号本身不构成跨角色复用依据。缺少这类依据时保留覆盖缺口，后续来源补充按明确分支条件安排，避免通过反复更换请求碰撞所需分支。

组内成员可经过不同原生分支，例如空前缀创建初始位置、已有前缀读取末尾位置。适配层声明对应的输入成员、输出及来源条件，核心按实际成员选择和展开同一调用族，再交给集合消费者；不能把一批成员都当成同一常量的重复。集合仅约束共享的属性，成员所在设备和存储依赖由实际端口与被选中的调用约束，避免把空host前缀与已有设备前缀强行归成同一种值。

混合组批与chunk共用上述工作合同，但原生可能先为新Prefill分配，再为running Decode分配，最后合为一个模型批次。资源预约与最终模型工作必须分开表达，不能依赖“一轮分配一次即确定整批”的旧前提；在接入mixed时统一替换该前提，不增加并行的特例状态机。

#### 混合组批和 Decode 优先

`PrefillAdder.__init__` 先从输入/chunk 预算中减去已有 Decode token；`_get_new_batch_prefill_raw` 满足 mixed 条件时调用 `prepare_for_decode` 和 `mix_with_running`，保留 `decoding_reqs`。这些源码证明存在原生 mixed 途径，尚不证明当前所有 Ascend/PP/PD 组合可以运行。

实现先取得实际 mixed 工作：一份共享模型调用、逐成员阶段和不同 KV context、必要 attention 布局。不能把独立 Prefill 图与 Decode 图完整叠加。

按原生的“准备Prefill → 准备已有Decode → 合并成员及列 → 一次mixed模型工作”接入。资源预约保留各次申请的范围和顺序，最终组批单独固定成员顺序与逐成员进度，不能让第二次预约覆盖第一次工作；模板装配复用两种准备入口，再展开实际mixed合并和模型入口。mixed状态及来源必须显式区分，不能因`is_extend()`为真而沿用纯Prefill的attention或过时的请求prefix索引。核心维护共同工作/资源合同，原生是否合并和如何排序仍归原生控制，采集及列/模型接口解释归框架adapter。 普通子调用与可替换调用族都从已连接的输入几何绑定局部参数；不能把嵌套合并的局部参数提升为调度器专属字段。模型入口的列同时保留形状、依赖和已知整数内容，不能仅有形状就宣称资源操作数已闭合。

代表来源须实际触发非空running Decode与新Prefill相遇，记录最终启用状态及真实mixed入口。开发核对分别覆盖可容纳两种成员、Decode预留后不足一页、继续chunk及持续新到达；逐成员证明Decode得到预算，也核对Prefill不因此无界停滞。原生不支持的模型/backend组合保留其适用边界，不为完成计划修改推理框架；PD两侧本来分离，不人为制造跨实例mixed批次。

Decode 优先需要单列行为定义：已有就绪 Decode 能获得所需预算，并且不会被持续到达的 Prefill 不断推迟。若还要求独立 Decode 批总先于所有 Prefill 批运行，则是更强的另一要求。当前普通路径先选 Prefill；请求 priority 排序也不是这种阶段优先。S10启动时核对实际原生模式是否满足计划要求，实现后用持续到达、预算边界和非空running batch验证。未满足时保留明确缺口并报告，不在 adapter 中新增选择器、不自动扩大成原生算法修改。

原生 `server_args.py` 还会针对某些模型/backend 关闭 mixed/cache；例如 dual-chunk attention 的相关处理。配置写了开关不等于最终启用，必须核对实际解析结果和调用路径。

取得mixed来源前还须检查预算变化后的原生attention资格。Decode占用预算可能使Prefill前缀不再页对齐；底层API未执行或未写输出不能被归一化为合法的空执行分支。明确的原生参数限制由runtime观察边界检查，不在核心按模型、请求长度或目标错误增加规则。替换原生开关或backend须同时核对KV布局、纯Prefill、mixed和Decode；单个入口可用不能替代整条原生生命周期。原生组合不可用时保留缺口和证据，先寻找官方可运行的实现，不通过修改原生算法或缩窄输入隐藏问题。

官方环境替换分两步：先在隔离环境取得完整请求证据，明确覆盖Decode结束后、非页对齐前缀继续纯Prefill的路径；再选择包含所需能力且尽量接近现有基线的完整上游提交，审查采集和无设备控制共同使用的原生合同。不要从新版摘取函数回补旧框架，也不同时维护两套版本兼容分支。依赖构建参数归环境adapter，新增硬件调用归runtime解释，请求字段及原生资源接口变化归框架adapter；公共控制、资源和模板核心仅因真实共同合同变化而调整。正式切换前同步两侧环境与来源身份，重新取得受影响的代表来源并检查已有并行、缓存和分块路径，不能沿用旧库却只更新镜像标识。环境运行通过不等于模板生产或目标展开通过，二者分别留证。

框架attention调用是可组合的语义区域，不能默认等同于单个设备操作。原生实现若包含长度归约、设备读回或等待，这些协调步骤须保留公开边界及必要因果；仅对具有明确输入、输出和读写效果的设备接口作不透明封装。实际接口选择与shape依据归框架/runtime适配，公共生产器保持统一组合规则；不为通过生产而隐藏CPU读回、强改原生参数，或按观测标量值扩张模板种类。

公开区域前，沿实际调用链统一核对输入几何、局部变量、后端元数据及KV写入视图；观察后汇总全部shape错误和来源要求，再成批调整。输出布局沿原生分配或视图语义推导，stride随输入几何变化，不能把一次采集的布局整数当作通用关系。不同调用中的同名字段分别确认所有者，不能只修首个报错或将相同数值当作同一来源。原生算子对象保持完整，使用框架提供的函数/dispatch观察机制，不替换其overload注册身份。

#### 一级 prefix caching

核心先提供设备存储层的前缀索引、页引用、LRU和就绪，原生通过facade执行match/lock/insert/evict调用。区分空闲、可淘汰、受保护和未就绪；请求结束不直接清掉共享缓存。按照所选SGLang语义处理页对齐、重复前缀合并、分裂节点和尾页；首期不支持多级实际搬运，也不实现所有原生cache变种。

采集和预测共用确定的内容身份规则：workload 的共享前缀身份、长度、父关系映射为可复现的 token 序列，其余后缀区分开；替换采集中的全1输入方式，避免开启缓存后制造未声明命中。固定长度输出也要防止用同一占位 token 串人为制造共享；只对声明的内容关系授予缓存复用，真实文本、自然输出引起的额外命中不属于当前预测。共享内容规则独立于采集/控制包；按父前缀下的分支分配可区分token，私有prompt后缀与生成部分使用同一私有分支。原生保留采样工作再注入条件输出，PP输出环及PD元数据传递实际值，不从形状重新填占位值。

缓存算法必须看到足够的内容等价关系，不能只靠 token 数。采用逻辑 token 身份或确定 token 序列时，要检查页内部分匹配、父子前缀、词表合法性及非共享后缀；采集与预测一致。完整 prompt 已缓存也不直接产生 logits，仍沿原生 `_compute_max_prefix_len` 和末尾执行规则处理。

统一预热后清空逻辑前缀状态，再开始每个目标配置×workload；保留预热后的编译/workspace 环境。首期 PD 仅 Prefill 侧本地缓存，Decode 仍经显式 KV 交接；前缀相同不代表可跨模型、布局、实例或不同路由条件共享物理页。EP缓存以token及该位置按层声明的有序专家选择共同构造缓存键，采集与控制使用同一编码；padding不进入请求内容。路由区间拆法不影响等价，首次分歧后不再共享；不按完整请求隔离而丢掉较短公共前缀，也不修改实际模型输入token。原生物理缓存及等待队列逻辑索引都使用条件键，核心继续只管理一份索引和页状态。保守比较全部声明层，不另建逐层KV等价推理或新缓存策略。

按以下顺序接通一条完整路径，再扩大组合；mixed的原生资格暂未解决时，可以推进独立的缓存工作，但不取消mixed及两者交互的完成义务：

| 顺序 | 实现边界 | 必须一起替换的旧前提 |
| --- | --- | --- |
| 1. 内容合同 | 采集与原生控制共用确定的prompt及生成后缀内容规则；核心消费同一内容身份 | 移除两侧全1输入和全1输出的假设；分歧位置需要真实可区分的词表token，不用取模哈希冒充无碰撞，词表资格在输入边界确定 |
| 2. 缓存资源与原生视图 | 核心资源层唯一维护压缩前缀索引、物理页、引用及LRU；SGLang facade翻译match/insert/lock/evict及容量查询 | 不保留原生RadixCache作为另一份树；节点句柄只引用核心身份。继承原生请求处理方法时不运行其建树、分裂或淘汰算法 |
| 3. 请求及释放交接 | 保留原生`cache_unfinished_req/cache_finished_req`对请求进度的处理；核心提交实际持有、替换及释放效果 | 删除`finished`就等于归还该请求全部页的假设，分别表达重复前缀页、未对齐尾页、缓存持有页和槽位释放；PP在途引用不得因请求完成被清掉 |
| 4. 来源与图连接 | 在稳定缓存服务边界采集索引产生、替换和释放工作，绑定缓存身份及页；沿既有执行依赖表达内容就绪 | 索引可用不等于KV内容已就绪；不能只增加树查找RPC而没有目标图端口，也不为每个树节点或请求复制CPU模板 |
| 5. 限定闭环 | 先单worker，再TP/EP、PP及PD Prefill本地缓存；复用公开入口与既有评价 | 完成时允许缓存页留存，分别核对空闲页与缓存页的身份分割、保护引用及请求槽位；精简结果报告数量，明细才附带实际身份。终态守恒不能代替中途引用、释放和设备内容就绪检查；命中前缀仍按原生末尾logits规则保留必要计算 |

原生入口以`radix_cache.py`的match/insert、inc/dec_lock_ref、evict和请求包装方法，以及`schedule_policy.py`的准入临时锁为依据；核心索引须保持页对齐匹配、分裂继承引用及叶节点淘汰语义。不能将压缩节点逐页拆开后默认LRU回收顺序仍等价。请求逻辑字段继续由原生维护，核心资源效果与模板端口通过共同动作交接；采集、控制和执行不分别维护同一缓存事实。

原生控制也会使用同一种树结构记录等待队列的内容关系；这种索引不持有物理KV页，属于原生选批逻辑。通过原生缓存后端注册接口只替换KV资源实例，不全局替换`RadixCache`类。核心索引移除条目只产生待回收页，页重新可分配仍须经过对应图操作完成；不能在树中删除时提前增加空闲容量。

选批期间的缓存淘汰可能先于新模型批次，应有自己的资源动作与完成反馈，不能等一个尚未建立的批次来归还页。索引动作只描述有限的服务调用、读、切片、复制、拼接、映射写与释放，不携带虚构批次；原生视图的存活身份用于保留图生产者，不作为另一份资源账。Decode集中释放按原生顺序作为结果尾部工作，在输出发布之后执行，不能因为拆出索引动作而将它提前。结果交接分别携带请求读取的完整映射和实际释放片段；命中或重复前缀替换时同步更新核心驻留映射，图端口保留其真实生产者及KV写入依赖。不能把“实际释放页已被记录”当作这些交接已经完成。

请求准入按核心缓存句柄取得已有页，绑定操作不再次查找内容或刷新LRU，也不隐式分配、回收页。已有请求的未对齐尾页继续属于请求；重复前缀的旧页由实际释放效果归还。完整映射是本次图读取的只读快照，不成为第二份资源账；轻量控制和原生控制都按这个共同合同交接，不能只修改原生一侧。

索引核对沿实际映射写入、视图偏移及缓存读取，使用已有资源记录和目标图，不为验证增加业务张量解释器。绑定的整数内容、按这些内容推导的写入结果、实际设备内容分别说明；未记录具体内容的host长度数组不能冒充已完成数值验证。构图顺序下的映射一致也不能替代设备依赖与就绪检查。

缓存来源按“稳定服务 → 实际索引操作”组织。match、insert、引用和淘汰的私有树遍历归CPU服务；真实发生的索引切片、复制、映射读写、拼接及页释放保留为可调用子图。树节点、请求和访问次数只改变绑定及子调用组合，不生成逐节点模板。等待队列的逻辑索引不进入物理KV观察。来源记录实际缓存启用状态；关闭缓存的来源不能冒充命中/淘汰来源，取得新来源也不等于目标动作及就绪交接已经闭合。

核心交出本次访问的压缩边、匹配长度、新建前缀句柄及被淘汰句柄；adapter只保存句柄对应的索引张量视图，按原生顺序切片、复制、拼接和释放。视图中不保存内容树、引用或淘汰策略，不从返回的页号重新生成整段索引来代替原生生成过程。协议元数据计算与将进入目标图的张量工作分开，图连接保留这些视图的生产者；局部模板可组合不等于完整请求生命周期已接通。

PD的Prefill缓存命中只减少本地计算，Decode未启用缓存时仍须收到完整prompt的KV。发送范围来自原生请求映射，不能从新增计算token数推断；传输完成依赖应连到实际解锁/回收的缓存动作，后续槽位释放可以复用其完成端口，不重复生成释放子图。

#### 来源与 CPU 工作范围

[NativeServingSession](../../../src/collection/markov_collection/adapters/frameworks/sglang/session.py) 和PD会话须按启用机制采集，不能以关闭chunk/cache时的旧库完整覆盖新路径。新增来源按机制取必要代表片段：chunk 准备、mixed 模型入口、缓存 match/发布/引用/淘汰等；优先复用不变模型片段，不按开关笛卡尔积复制整库。缓存配方在同一会话内保留基本batch/页边界观察，再按固定有限分组覆盖冷启动、命中/分裂、不同结束路径、驱逐及再次访问；内容身份贯穿全部分组，组间不清缓存，baseline/capture窗口间仍按统一规则重置。不将分组增加为用户workload字段，不通过运行全部目标请求来反推配方。

缓存与chunk组合的固定代表块为两页：一页块会逐页插入前缀，无法形成可分裂的多页压缩边；两页块配合已有长请求、共享一页/两页前缀同时覆盖中间块保存和分裂。此选择属于SGLang采集adapter的机制覆盖，目标chunk继续作为参数变换，不按每个目标chunk分别采集或在核心补虚构调用。

仅把规定流程内、影响必要依赖或后续性能的 CPU 服务作为工作。原生执行了多少 Python 函数，不等于新增多少 CPU 模板。按稳定服务和工作量表达缓存处理，不为树中每个节点造模板；但仍保持状态变化与控制观察的真实顺序。运行控制适配与采集插桩共享语义身份及输入解释，不互相调用来代替对方职责。

**多级存储扩展边界。** 区分逻辑前缀身份、各层驻留/引用及可用性/迁移；首期只实现设备层，不预建空CPU/磁盘后端。异层命中将来通过真实搬运和就绪端口接入；PD交接可以共用传输表达，但不是缓存命中。共同资源服务不替原生决定下一批，也不建设任意策略引擎。

**开发复核与交付。** 以下机制检查与S9基础生命周期回归共同使用；开发证据不计作S11独立验收。四项能力的必选语义未满足时保留缺口，不以原生代码存在或开关已启用记为通过。

| 验证主题 | 最小有辨识力的条件 | 检查什么 |
| --- | --- | --- |
| Chunk/mixed | 长短 prompt、不同输出长度、非空 Decode 加新 Prefill | token 范围不重不漏，中间 chunk 无输出，mixed 共享工作一次 |
| Decode 优先 | 连续 Prefill 到达、预算刚好/不足 | 实际保证的优先语义和未支持条件，有成员级证据 |
| Prefix cache | 页内部分匹配、父子前缀、相同前缀不同后缀、命中后请求结束 | 匹配/引用/尾页正确，共享页不重复占用，未就绪内容不被提前消费 |
| 缓存压力 | 活跃引用与可淘汰条目并存，释放后重入 | 不淘汰受保护条目，LRU/回收顺序有原生依据，不把所有页当可用 |
| EP 内容 | chunk/mixed/命中后的逻辑 token 变化 | 原有路由与 padding 条件仍按实际 token 绑定 |

中途资源核对使用资源所有者产生的实际变更事实，不从调用名称或终态反推引用生命周期。若现有明细缺少插入、分裂、加锁、解锁、替换或回收身份，只在details下补充必要差量，默认输出不增长；评价放在example，不在核心重演缓存策略或建立另一份页账。设备内容就绪另按KV写入、实际消费者及释放复用的依赖核对，不用描述张量已返回代替。

请求进度与资源核对分别负责自己的事实：前者检查到达、连续输入范围、撤回重算、逐次输出及结束；后者检查实际预约与成员快照、首段缓存绑定、共享页/槽位、传输对应和释放。冷KV与缓存使用同一套检查，不保留“遇到缓存就跳过请求进度”的旧路径；PP已预约的下一块范围不能被上一块迟到的结果回写。报告须注明只证明记录自洽，不能凭该项matched升级整体独立验证资格。

区分记录时序与因果证明：先用动作提交时的真实页绑定、模型/搬运设备区间检查回收没有早于已提交消费者；再核对目标操作数与共享KV内容身份，以及跨调用/队列的写入→读取和使用→复用依赖。前者通过不授予任意节点耗时下的安全资格，不能将host返回或请求输出当作设备消费结束；不为验证增加核心资源策略或调度分支。

操作数核对先覆盖模型入口的KV位置、请求槽位与长度，再沿接口声明的持久存储核对同rank/layer绑定和跨动作设备完成路径。路径检查与给定耗时无关，但只覆盖已声明读写；backend内部索引变换、缓存视图位置和PD搬运地址须分别根据适配合同及原生事实核对，不用整存储别名掩盖位置错误。原生复制地址与两端注册缓冲区按会话和rank对应，地址只保留在来源证据，不进入模板身份或目标规则。代表复用时区分接收端注册/协议声明与实际接收观察，不能把未观察worker的完整接收行为记为实测。这里的内容正确性指逻辑token对应的KV位置与读写资格，不要求运行真实权重计算KV浮点数值，也不以逐算子数值重演扩大仿真核心。

新增硬件调用由runtime适配，原生策略由框架adapter接入，共同资源和图算法不按模型标签分支。S10结束须对比阶段Git基线，审查资源服务、原生/轻量消费者、采集、模板、执行及公开输入，删除被替代路径；代码、文档、数据检查并分层提交推送后，才进入S11。冻结时纳入本阶段的内容规则、缓存资源语义及影响决策的适配代码，性能建设继续后置。

### S11：单机整合、分层收尾与重新全量独立验证

**目标：** 在原生控制后端下承接 S8 未完成的结构覆盖义务，验证原生采集、模板提取/归一化、变换、连接、动态控制、执行反馈和资源回收的全流程，并完成单机闭环及扩展边界审查。先把功能与评价收稳，再冻结执行完整矩阵；不能只证明原生调度代码能运行、只核对模型主体，或只跑原先失败项。轻量控制器不纳入本阶段推进和验收。

| 步骤 | 交付 | 进入下一步的条件 |
| --- | --- | --- |
| S11-A 单机整合与分层收尾 | 统一公开入口串联原生控制、子图生产/展开和所选机制；处理S8遗留、关联审查和冻结准备 | 原生链路已知必修问题闭合，核心/适配/评价责任明确，代码/文档/数据检查及修复基线交付完成 |
| S11-B 重新全量独立验证 | 在原生后端重建完整矩阵，保留原S8的模型/配置/机制覆盖并纳入S9/S10能力；核心及评价冻结，适配受控更新 | 全部计划案例执行并形成结论，必选覆盖具有真实独立证据，完整报告及维护交付完成后进入S12 |

后续按以下顺序推进，不将修复与全量验收混在一起：

1. **先建立可复用的真实案例对齐流程。** 建立真实完成事件旁路，再选定要完善的模型、配置和请求目标，取得固定原生ground truth。仿真器在相同输入、初态和反馈下自行控制、构图及管理资源，完成全链路比较、根因分析和完整修复计划后集中实现，再仅重跑仿真器。具体步骤及边界如下；不继续从两条时间历史不同的最终图中逐告警修补。
2. **有限开发复核与阶段交付。** 在同一真实案例提供的性能依据下闭合控制、资源及执行结构，以此作为当前开发闭环的完成标准，不追加关闭旁路的结构验收。优先复用原始事实重解释、重建受影响模板，仅在确认缺少必要事实时有界采集。完整审查相关业务链，整理代码、文档、数据后分层提交推送，不在每次修复后重启全量矩阵；自主性能预测和精度验证留到性能层建设。
3. **固定单原生后端矩阵。** 明确七模型及A–L组的具名配置、请求、来源域、未观察worker、实际触发门槛、独立留出、判据与额度；给每个原覆盖机制列出去向。编排留在现有example，核心不吸收案例逻辑。
4. **一次完整独立执行。** 按冻结规则执行全部计划案例，包括错误和受阻记录；验证期间不修共同核心或评价，不因新场景失败便中途拟合修复。允许的来源适配更新遵守既定范围、暴露目标及复验规则。
5. **汇总再决定修复。** 完整报告分别说明原生资格、适配、公共核心、评价工具、资源限制及未知风险，给出支持/条件/未验证范围。必要结构与泛化证据成立后才交付S11；仍有必修问题则按共因返回A，不把局部通过或取消轻量任务当作验收通过。

**单机完整闭环。** 从统一公开入口串联S0–S10的选定能力，核对后端选择、本机设备组绑定、模板来源、组批/缓存状态、通信交接和逐请求结果。请求结束后活跃引用和槽位应释放，缓存持有的 KV 可以继续驻留；不能仍以“所有页都回到空闲池”判定完成。选定拓扑与调度/缓存交互纳入后面的完整矩阵，不把几个独立脚本当产品闭环，也不生成所有开关的笛卡尔积。

沿模块依赖与状态所有权审查代码，合并公共流程，删除旧单批次/固定rank特例和临时双路径。PP的stage、PD的控制实例和TP/EP的角色绑定通过共同合同交互；两种合法控制实现可以有不同决策，不能各复制workflow、模板算法或执行器。缓存页、真实输出及逻辑任务均有唯一所有者。

核对异步边界时分别检查提交、准备、等待与消费，按原生调用时机展开各段；共同动作反馈相应host返回或实际等待完成，不能把整段准备延后到结果消费。对照须包含中间穿插的其他请求工作，节点清单一致不能替代调用顺序和设备依赖检查。

**扩展边界检查。** 沿原生单worker、TP/EP、PP/PD的实际消费者检查共同接口：框架差异集中在装配及adapter，模板和执行器消费统一工作/完成含义，不向共同图算法泄露原生对象。静态审查后续接入轻量控制及多机placement、transport和资源绑定的修改落点，不为此运行或补齐轻量后端。不能以物理卡号代替全局rank或把本机地址写进共享定义；发现接口耦合就修共享边界，不预建网络服务、多机平台或占位选项。

历史输入、错误、资产、费用和报告保留；开发批次不重新获得尝试额度，只作修复材料，不冒充新留出证据。S11-B沿用“核心冻结、适配受控更新”，首轮严格全冻结调查的历史口径不追溯修改。

#### S11-A：收尾——先确定合同，再分别收口核心与适配

**1. 按职责定位第一处不一致。** 原生实现随模型、dtype、拓扑、backend和页布局变化是正常现象；需要新来源不自动算缺陷。沿“原生事实 → 适配交接 → 核心图生产/变换/执行 → 评价”定位，按没有履行的职责归因，不按最后抛错的文件或语言归因。

| 责任层 | 维护内容及对应落点 | 向外交出的边界 |
| --- | --- | --- |
| 公共合同与核心 | contracts、production、graph、templates、controller、resources、execution及共同观察/编码合同 | 定义合法图、参数作用域、端口、状态与完成含义；通用提取、归一化、有限变换、连接和执行，不读取模型名或原生私有对象 |
| 框架适配 | Python/C++的sglang adapters | 从原生模块、调用及组信息取得层/head/expert布局、角色、生命周期和执行上下文；按公共合同交出事实与绑定 |
| Runtime适配 | Ascend/PyTorch adapters及相应SDK桥 | 提供真实算子API、几何/布局、实现条件、队列/stream/event和workspace依据；以有限原型表达环境差异 |
| Workflow与验证 | 正式任务生命周期；example中的矩阵和比较编排 | 装配已有能力、安排范围/预算、记录来源与错误；判定可比工作及各自状态不变量，不复制核心状态机 |
| 原生或外部环境 | 固定上游、依赖、设备和原生协议 | 区分已确认的原生不支持、设备受阻和项目错误；下游无合格来源时标为受阻，不计成新的核心缺陷 |

共同合同表达不了既定合法行为时，属于核心设计缺口，须在A阶段修改公共合同及生产者/消费者；不能让adapter私自补一套调度器、图算法或页账。反之，原生事实漏采或误声明不能用核心兜底、放宽合同或忽略节点解决。高层主流程消费统一值类型及必要抽象接口，框架/runtime在下层实现真实差异；共同算法一份，参数差异用绑定，实际运行时替换用已有组合/浅层继承，确有编译期共用算法才用C++模板。Python负责原生观察与逻辑控制适配，C++负责共同资源、处理及必要框架装配；语言和目录本身不决定问题归属。

原生会话以自身完成摘要发布采集事实；解释成功与否不改变这项事实，也不能触发另一轮Engine。来源重新解释经正式入口读取原始目录，在外部工作目录发布语义声明、物理事实及必要会话/传输元数据，不回写原始记录或加载采集preload。SDK会写输入旁缓存、表和日志时使用临时可写副本，先读入解释所需事实再释放，分析日志随派生结果保留。不以旧物理文件存在代替本次完成；失败或缺原始导出时撤下对应工作结果的完成资格。独立调查保留SDK事实在原位置，不靠搬目录规避清理；普通精简任务按既定策略释放原始导出后仍可使用模板，但不承诺重建物理事实。已发布模板的恢复与显式重解释分开，不增加版本兼容或隐式补采。

**2. 先理清代码机制，再用固定真实案例验证。**

**开发解耦目标。** 执行结构与性能建模分两阶段推进。旁路在当前阶段提供真实运行的性能依据，提前补足尚未建设的性能层，使结构错误不再与临时耗时造成的调度变化混在一起。旁路不是另一套模拟器，也不是把真实控制轨迹直接当成预测结果。

两阶段共用同一业务链：输入 → 原生控制 → 子图变换与展开 → 执行及资源推进 → 完成反馈 → 下一轮控制。当前由真实案例提供性能依据，后续由cost model预测同一类工作的性能；替换的是性能依据的提供者，控制、图算法、资源管理及执行反馈仍使用同一实现。结构在旁路下通过验证后，性能层以该结构实现为基础接入，不再建设第二套执行流程。

本窗口的完成结论是：在已验证的模型、配置、请求及真实性能条件下，仿真器能够正确产生控制动作、资源变化和完整执行结构。不同目标通过独立案例扩展结构泛化证据；cost model的覆盖、误差及端到端自主预测精度属于后续性能阶段。没有可信性能模型时，不以关闭旁路后是否复现真实调度轨迹作为结构验收条件。

**开发以代码推导为主，验证用于检验机制。** 恢复后先自顶向下阅读输入投递、原生控制、adapter交接、模板展开、资源状态及完成反馈的整条链路，明确每项事实的所有者、产生/消费时机和必要不变量。将已有差异按这些职责归并，形成统一修改方案；代码已经能证明的问题直接修复，不先运行一轮等待报告指路。必要时整段删除或重写重复状态、旧表示和过渡路径，不以现有函数和目录为必须保留的边界。

每批修改覆盖一个完整机制的生产者、消费者、调用方及旧路径清理，完成关联静态审查后统一编译，并选能区分本批机制是否正确的必要案例。只在静态阅读无法确定实际原生行为或修改效果时安排针对性取证，运行前说明待回答的问题及结果如何改变实现决定；没有新的代码变化或可检验假设，不重复比较。禁止按报错节点逐个补字段、分支或来源，也不把报告减少、运行次数和验证数量当作开发进展。全量泛化留给S11-B，A阶段不提前反复展开矩阵；必要编译和运行检查仍须完成。

修复前先比较保留现有组织与整体替换两种方案：以必需输入、状态所有者和输出合同为起点，判断现有动作划分是否成立，再选择实现。若需要多处补条件才能维持旧前提，应替换该段机制并连同调用方删除旧路径，不能在旧机制外再包一层纠偏。审查说明本批消除了什么重复责任、还保留什么真实差异；不以改动行数小作为更安全的依据，也不为满足删减数量移除必要合同。

本阶段采用以下七步，先建立旁路，再选目标和取得真实案例。它们是同一开发闭环的工作步骤，不各自增加提交阶段、审批或验证平台。修复循环固定在第4–7步；原生执行不随仿真器修改重复。记录集中在现有日志及案例结果中。

| 步骤 | 必须说明或完成的内容 | 进入下一步的依据 |
| --- | --- | --- |
| 1. 建立真实性能旁路 | 先从代码明确workload投递、工作身份、调度/资源状态变化边界及时间交接，再核对已有记录并集中实现；复用原生控制及执行反馈链 | 旁路只提供必要边界的真实时间依据，仿真器自行控制、构图和维护资源；子图内部沿用结构对照，不以逐节点实测耗时齐全作为旁路前置门槛 |
| 2. 选定完善目标 | 固定具名模型、框架环境、并行/调度配置、请求序列、预热/初态及要检查的能力；先用有限目标闭合当前问题，记录运行、后处理、存储额度及停止条件 | 场景原生可运行，输入和比较范围明确；目标选定不代表全局支持范围缩减，也不因当前结果不好临时换成容易通过的输入 |
| 3. 取得原生ground truth | 真实执行选定案例并保留原始事实；已有同条件、信息充分的案例直接采用，无须重跑。一次执行保存控制动作、必要资源状态、完成事件、结构观察及全部解释所需伴随文件 | 原始记录足以独立重建本次对照和事件回放；缺失事实明确列出，不用仿真输出补写真实记录 |
| 4. 运行仿真器 | 使用固定输入、初态及模板来源，旁路提供真实时间依据，经共同执行链生成控制、资源及展开结果 | 输出注明性能依据来自真实案例；记录本次源码、模板与解释/评价规则，用于结构验证，不作为cost model准确性的证据 |
| 5. 全链路比较并归因 | 比较控制动作、批次输入、资源转移、子图工作、数据/通信依赖以及窗口结束；定位第一处分歧，收集同次结果中其余可独立判断的差异 | 完整报告区分确认错误、评价问题和未知风险，说明证据及责任层；后续连锁差异不能重复计成独立Bug，也不边比较边改规则 |
| 6. 制定完整修复计划并实现 | 用代码职责链解释差异，修订已有统一方案，明确核心/adapter/评价落点、上下游影响及要删除的旧路径，再集中修改 | 关联静态审查和必要集中编译完成；不按失败节点、shape或模型增加补丁，不以放宽评价代替修复 |
| 7. 重跑仿真器并比较 | 沿用同一原生真实案例；必要时从原始记录重建派生解释和模板，然后回到第4–5步，原生执行次数不随修复轮次增长 | 同条件下控制动作与资源变化对应，展开工作及必要依赖完整，拆分/组合差异有统一解释，窗口内无未解释的缺失、重复或必要顺序冲突 |

**workload是请求到达的唯一输入约定。** 原生采集与仿真使用相同时间起点、到达序列及同刻投递约定；先核对原生提交入口是否真正执行arrival_ns，而非只提交请求内容或按分组顺序发送。调度器何时轮询、如何组批属于执行过程，实际接收记录只用于诊断，不能替换workload、要求用户补一套输入，或直接规定目标模型批次。原生与仿真的输入执行不一致时先修投递链，不用接收时刻猜配掩盖问题。

输入评价消费同次采集的投递记录，检查请求按声明到达时刻完整分组、未提前发送及发送次序；发送延迟作为诊断数值，不设拟合阈值，也不回写到达输入。发送端检查不能证明调度器已在同一时刻收到请求，更不能证明实际组批一致；缺接收事实或未覆盖错峰到达时明确保留该限制，不由边界时间或发送检查代证。

**旁路与内部结构对照分工。** 旁路提供影响调度推进和资源状态变化边界的真实时间依据，包括必要的返回、等待解除、传输完成及结果反馈；原生控制仍自行决策，核心仍维护资源。子图内部的工作、操作数、shape/别名、数据依赖、通信依赖和必要顺序沿用已有结构对照方法，不由旁路通过与否证明，也不为旁路先建设完整CPU或逐节点成本模型。两种检查以同一工作身份及完成端口对应；边界反馈通过不代表内部图通过，内部图通过也不代表跨批资源历史通过。

旁路通过共同性能依据/执行接口交接，原生事实获取归adapter，案例装配与比较归example；不复制ServingWorkflow、原生控制器或KV状态机，不预建成本模型插件平台。沿控制组交接顺序核对请求、动作、rank和完成含义，禁止用真实批次、页分配或目标图替仿真器补决定和补边。边界时间与内部服务耗时分别解释，外层墙钟不能叠加到子节点重复计费；边界对应失败及必要因果冲突明确报告，不模糊匹配或强行拉回真实轨迹。未来成本模型替换时间依据，继续使用同一控制/资源交接合同。

实现时先分清两项职责：节点计时由内部工作和依赖计算就绪，边界反馈决定何时向控制器交付发布/完成事件。现有NodeDurations只有节点时长查询，不能把真实边界时刻编码为某个节点的补偿时长，也不能用全零内部耗时制造通过。ServingWorkflow保留提交、构图、资源及反馈主循环；普通执行与真实旁路通过共同工作身份及发布/完成合同交接。旁路输出真实边界反馈，内部节点未计时就不输出伪造的执行时间线；既有结构评价继续检查工作、操作数和依赖，依赖内部时标的检查明确区分为本模式未测量。接入批次须同时调整应用装配、反馈实现、结果说明及评价消费者，不能只给核心增加一个没人使用的接口或把旧报告直接套在新模式上。

时间依据的替换不改变工作流的结构要求：任务身份、完成/发布端口和图的等待/操作数绑定在共同交接处核对，删除只在某一种时间提供者内维护的重复检查。图摘要只交出来源及表示边界，控制、完成和耗时来源由实际提供者说明，不保留图层固定写入的旧结论；独立评价仍负责结构与原生事实是否相符。

完成时间作为独立观察输入交给反馈实现，不加入workload，不由用户人工填写，也不从目标预测结果反推。adapter负责从原始记录解释同一时间起点、控制组、请求/token范围、阶段及发布/完成含义；同语义重复工作按其出现次序消费，本地任务编号只用于目标内部交接。案例装配确认模型、机制域、输入及初态相同；核心消费经解释的边界事实，并检查工作匹配、事件顺序和完整消费。原始观察的自动转换及一个真实案例闭环是旁路完成条件，只有消费入口或编译通过不能算完成。

异步工作沿原生对象的生命周期保持归属。PP发送句柄交付提交与等待完成，接收载荷保留原框架实际消费的批次；同一stage的TP参与者合并组完成，不把不同PP stage视为同一个控制组。PD后台复制须连接实际发送分片与接收会话，再解释传输完成和接收准入；发送函数返回不能代替复制完成。共同转换消费这些事实，不按当前批次、相邻时间或固定字段数量猜配，不为每种拓扑建立独立反馈流程。

PD分片由实际发送调用及其保留的原生数组关联，数据复制与末片元数据各自保留成功返回和接收会话；按实际rank端点合并传输完成，不复制拓扑推导算法。接收和prebuilt分别描述准入与已接收prompt，不能把prebuilt当成一个Decode计算token。释放观察覆盖原生缓存、尾部回收及槽位释放的完整helper；结果中已合并的释放仍归结果动作，独立释放保留自身完成。转换按rank提取后只保留边界记录，避免把所有原始大图同时留在内存。

原生动作的返回与设备就绪分别维护：控制反馈沿真实调用的返回端口继续，KV交接的生产者依赖保留CPU返回及所需设备尾部；不能为PD预约、接收、接入或释放统一增加设备排空屏障。同步传输仍在其实际复制完成后反馈。完成时间转换直接读取原始rank观察，在内存中复用来源解释中的调度和结果接口标注，不要求先生成完整物理trace解析，也不修改原始观察文件。

旁路与模板构造共用纯数据控制接口解释，包括调度、结果读取及实际缓存匹配结果；辅助primitive原型只为构造模板候选服务，不成为serving控制动作。准备调用拥有自身的分配交接，预约内部的分配不拆成模型准备动作。不能凭字段名相似、同一个原生函数名或source观测标签就把不同用途的调用混合。

**PD握手须与资源预约区分。** 按“目的预留→元数据广告→来源收齐广告→复制→源端发布成功→目的端收齐通知→接收消费/来源释放”确定状态所有者。Decode接收器完成初始化后即可等待输入，不等待具体Prefill请求注册；Prefill则必须等后台收齐目的元数据才进入WaitingForInput。本地预约只保留资源，广告动作提交后交接才进入在途状态；来源收到广告与目的发送调用返回是独立边界，接收可能先于发送返回。图中用独立调用入口和返回端口表达这个关系，不能增加统一CPU返回或设备排空屏障。适配器继续执行原生poll、归约及metadata gate，核心维护资源、在途交接及数据完成；删除的是adapter发送后无条件进入Transferring的旧行为，不能把原生metadata gate的合法降级也删掉。

同一合同贯通采集、模板、控制和反馈：直接观察发送元数据调用及来源状态更新，以原生接收会话确定端点，不能从首个模型批次、轮询次数或相邻时刻反推握手时间。轻量控制后端继续待开发，不为其扩充新协议。性能层后续必须覆盖元数据准备/通信/接收服务，不能将状态写入的CPU自耗时当作全部握手时延。先检查固定真实案例的原始观察/SDK事实，列齐必要缺口后才规划一次完整补充，不能逐个信号补采。

原生后台可能先收到目的广告，随后本地才处理Prefill请求并创建发送对象；握手不能以该对象注册为前置条件。房间号与请求的对应由实际输入驱动统一分配并交给观察器，用于关联较早到达的真实事件；不等待请求handler后才建立观察身份，也不复制任何调度或资源状态。

**状态发布与控制读取分别交接。** 状态何时就绪不能代替控制器何时读取它。PD在原生共同状态采样入口保留一项请求列表查询动作，采集、模板、原生控制和旁路共用同一含义；动作只交接观察边界，不指定返回状态、TP/PP共识或组批结果。尚未分配资源的请求同样能够查询，不能为此构造带假槽位、假页或假token范围的Batch。空列表不读取任何请求状态，不为它生成额外查询动作；真实查询数来自原生调用，不以轮询次数阈值裁剪。原生控制继续执行原有失败处理、归约和metadata gate。跨rank采样与就绪并发时的交接仍需真实事实检验，不能用共同完成时刻直接宣称原生观察已等价。

纯CPU交接服务显式声明为共同执行工作，资源身份读取自有scope记录的真实线程，不以profiler是否生成后台线程marker决定是否创建端口。SGLang adapter统一声明广告、握手、提交、成功发布及状态查询；核心只消费工作种类与具体资源绑定。已有scope事实充分时，仅离线解释并重建模板，不重采或虚构线程/时间；设备和runtime关联仍来自实际物理观察。

**预热后的控制起点也须明确。** 资源已清空、workspace已预热，不代表原生PP的循环局部状态重新初始化。共同起点采用原生空转后停驻的入口：仿真先不给请求，让原生循环自行经过各组空闲，再停驻各实例入口；这段准备不产生目标图或占用workload时间，不复制PP内部变量，也不规定预跑轮数。准备及正式运行共用入口停驻规则：本实例各组都报告原生空闲后才停驻入口，此前入口继续空控制轮次，让下游完成交接。下游不参与额外停驻屏障；有到达、同实例未完工作或关闭时，由共同控制端释放入口。

采集在统一预热和资源清空后，于完整原生循环的空闲边界发布阶段完成；下游先发布完成并继续推进控制环，入口确认同实例实际参与者均完成后，最后发布完成并阻塞等待输入。参与者来自输入驱动的真实worker列表，不按模型或TP特例猜测；不能让入口过早睡眠，截断下游尚未完成的flush或Profiler控制消息。Profiler启动同样遵守此交接，再提交观测请求；NPU workspace保持预热，释放完的元数据槽位恢复统一顺序。清空请求负责唤醒入口，沿原生延后flush等待实际发送和设备工作排空，再做资源重置和观察准备；不能先等待一个无法唤醒入口的文件标记，也不能在未排空时清空池。采集与仿真不导入彼此的执行模块，原生生命周期差异留在各自适配器，共同核心只处理入口交接。初态语义进入观察域，旧原始数据不补写起点声明；首个lane仅作诊断，不能充当状态或对齐参数。

传输完成按端点交接：复制工作保留实际源/目的路由，握手与成功发布用“请求＋控制组”标识，不构造带假槽位的Batch，也不将一次端点发布复制为每路由一份。源端发布等待其所需复制，目的端发布等待所需源端通知；源端释放与目的端准入分别消费本地发布。图复用同一传输依赖前沿，从复制延续到端点发布，不增加平行状态表。采集直接观察原生状态真正变化，转换与模板共享KvReady/KvComplete的含义，不能由查询返回值反推更新时间。删除发送对象注册RPC和路由双方共享Complete的旧链。

发送准备通过原生入队服务前的KvSubmit标记交出传输意图：标记之前保留索引、元数据及必要设备准备，标记之后保留调用尾部，但尾部不阻挡后台复制。采集、目标反馈端口及完成转换读取同一真实边界，沿用现有动作与端口，不增加平行异步事件框架；未实际提交的辅助调用不产生Send动作。集中修改及构建后，按下一项范围一次取得完整事实；不能将静态或编译通过当作真实旁路资格。

上述调用链经集中修改及必要入口检查后，只安排一个具名原生开发案例：沿用Qwen3-8B、P/D各TP1×PP3、page128、P侧chunk256/前缀缓存及原六请求压力输入，集中取得KvAdvertise、KvReady、KvSubmit、KvComplete、KvPoll及新起点的直接事实。复用不变的SDK观察工具和模型，原生尝试上限1次，原生1800s、后处理1800s、临时64GiB/保留32GiB；额度新增及旧累计费用同时记录，不因重启清零。先保存不可变原始案例，再从同一事实解释完成记录、重建受影响模板和做旁路/内部结构比较；解释需要写回数据时使用本次派生工作区，不覆盖原始记录。任一阶段失败或超出分配即停止该运行，不自动补采，回到整条职责链判断根因。该开发案例不替代S11-B全量独立验收。

控制循环的空轮询与实际请求工作分别解释。工作观察在实际接收请求时开启，在原生完整空闲交接处关闭；PP尚未收尾的模型张量发送继续保留观察，不能把逻辑空闲当成传输已结束。采集和控制适配分别遵循这一生命周期，不复制彼此模块或按记录剩余数量启停。观察范围内的工作仍须严格匹配，不以任意轮询数对齐证明结构正确。PP槽位进展不一致时先查状态转移和初态，保留原始工作身份；不能按首次空轮询平移槽位、删除身份或放宽匹配来掩盖不同控制轨迹。完成调用链静态推导和集中修改后统一编译，固定案例与全量矩阵各在对应收口点运行，不围绕现有ready布尔值或失败记录继续叠加分支。

已取得可复用来源、完成记录和模板后，纯仿真异常先沿多进程控制推进、动作/图端口及资源状态生命周期集中审阅。有限定位未能取得明确位置时，停止重复运行，先理清现有状态机和消息等待的所有权；不以错误文本相同推定根因相同，也不由单次超时断言死锁。只有新的代码推导、成组修改或必要事实问题才能触发下一次有限运行，不继续扩采或改输入绕过。

自动转换读取采集适配器发布的原始调用、会话及投递记录；图生产链保留同一原始调用的引用和边界事实，不另行生成一份时间来源。资源分割只决定工作归属，合成子段不能继承父调用耗时或用相邻资源调用推算反馈时刻。分段反馈从原始观察中读取对应控制交接位置的直接记录，时间不参与模板定义、布局或执行模式归一化。投递起点与语义scope使用同一主机时钟，profiler的另一时间域须经明确关系转换，不能直接相减。动作与原生调用不保证一一对应：同组各rank的完成、分段准备、发布与结果提交、缓存服务和异步传输分别按实际完成含义解释；不把内部索引操作数量、节点位置或调用编号当成语义身份，也不按最近时间猜配。旧观察缺少共同起点或必要边界时先确定实际缺口及其影响，不制造时间原点或立即全量重采。

转换先贯通共同实例，再接PP阶段和PD交接，沿用相同工作/完成合同，不保留按拓扑复制的转换流程。TP参与者以同一语义工作及重复次序对应，按共同控制的实际组完成规则合并，结果发布保留真实发布者；来源需与消费模板的模型、角色、机制和运行环境相符，输入相等不能替代来源资格。PP发送返回、等待解除和PD传输完成按各自原生语义取得，不把发送提交当作传输完成。所有清理工作归属实际控制动作，准备输入消费已选出的批次列；不由图层或完成时间转换器另造空闲清理事件。单次动作的CPU返回与已提交设备尾部排空分别处理，后者不生成新的图工作或控制决定。

分割和重新编号必须保留对同一原始观察的引用，用于读取调用时已记录的请求和传输信息；该引用不是跨运行匹配身份。原生wrapper在实际准备、筛选和缓存服务边界记录请求身份，并从原生调用上下文区分筛选的previous/running视图；没有控制交接含义的内部筛选仍只属于子图。准备输入的反馈位置与控制adapter使用同一原生缓存容量检查入口，不能以首次逐出或分配替代。观察上下文只在调用期间存活并在退出时恢复，不保存第二套请求或调度状态。core只消费共同服务/请求语义，内部切片、拼接和访问细节留在图对照。共同插桩只传递元数据，不认识SGLang对象；同一含义的服务名称不在解析、旁路和报告中各维护一份。

原生调度观察以完整一轮选择为单位，不以框架恰好拆成几个Python方法来划分Schedule。普通路径直接包围原生选择方法；PP+PD Prefill将处理上一块、准备新批、批次协调连续纳入同一观察生命周期，在协调返回后登记一次最终批次，并保留准备完成与调度返回的实际交接时刻。适配器仅管理观察上下文，不提前调用、跳过或重排原生方法；正常返回和异常退出都必须恢复scope及dispatcher。对应关系先从原生控制、采集及图展开的调用链推导，再确认已有观察能否提供完整证据；缺失整个调用范围时修正采集边界，不能让转换器按编号拼凑或伪造完成记录。

**统一表示在生产者和消费者处收口。** adapter将框架事实转换为共同的值、存储/视图、工作与完成端口表示，core维护统一语义，评价器消费同一含义。具体shape与存储内容、动作完成与窗口结束等差异先从这条链确定统一合同，集中修改相关实现并删除旧表示，不增加长期双格式、框架特例或评价兼容分支。

工作归属同时覆盖批次与独立请求集合；已声明的辅助原型批次优先决定其范围，不能仅因复用请求名字就进入serving窗口。CPU服务和普通工作按共同资源类别/身份对应，存储内容按独立来源声明的opaque合同核对，普通张量继续核对几何。诊断从已经按语义匹配的完成记录取得源区域与目标task引用，再按实际工作范围、公开输入和依赖建立对应；引用仅供评价，不向控制器提供批次、状态或图答案。多边界/多片段共用引用，输入生产者推进到稳定状态并再次核对；不围绕整线程序列继续增加猜配规则，未建立的对应和范围仍保留partial。

评价按三种实际对象分工：完整窗口核对全部公开操作和必要因果，原生模型调用核对请求/token对应的主体复用，结果scope核对槽位、请求效果、回收页及池状态。原始批次标签保持不变，不为取得局部对应将整条请求的CPU/传输重挂到最后模型批次；预约等非模型工作仍使用自身真实批次操作数。完整性判据不依赖人为整批CPU切片，所有合格工作（包括没有模型批次标签的请求传输）仍进入窗口总量，状态、模型和窗口的确认差异均保留。

收口时从原生调用、controller交接、来源提取及目标展开共同审清三个机制：页池合并的真实调用与原型须使用同一公开表示；完成时间取自最终marker，工作引用则覆盖该动作实际包含的准备、等待和读取；prebuilt须按原生选择、接收准备及结果处理的完整调用链确认动作边界，再决定修正来源归属、控制交接或展开位置。adapter按真实批次、消息字段和调用组合关联已有区域，评价不靠扩大分组取得通过；相同调用清单也不证明时点正确。观察窗口资格与语义调用归属分别维护，并清除被实际引用替代的批次/作用域猜配，不能让请求重挂逻辑改写来源资格。

页池整理保留在实际分配调用内部：资源服务维护可回收与直接可分配的逻辑状态，adapter用这两份池输入选择原生分配分支，模板保留原生页数计算、读取、条件整理及分配的顺序。普通准备和PD预约共用同一分配族；外围调用沿已声明资源接口切出前后续段，不另插一次提前合并。局部原型直接运行分配入口，按分配算法分界及普通/空ready池/非空ready池的有限状态取依据，删除独立合并采集链。原始算子的执行条件使用当前调用继承的公开shape合同，私有实现仍由外层接口负责，不从历史值的参数名推断当前输入。

代表来源统一保存自身配置、请求与可选内容/路由条件，不只为特殊模型或缓存路径提供完整输入。需要确认当前采集配方时，选择一个既有实现域，按同一正式来源链完成原生观察、解释、建库和有界消费者检查；真实参与者完整、单连续序列且输入相同的来源可以兼作开发时间依据，无须另跑Engine，隔离分片或分轮发现不取得这项资格。

正式恢复按缺失产物选择工作：原始来源未齐才进入采集准备；来源已齐而资产未发布时，使用保存的角色计划解释和建库，不因当前采集镜像变化阻断后处理，也不重建无消费者的采集工具。生产环境身份保留在原始事实，不能用离线处理授予新采集资格。已有完成标记仍须有实际结果和模板文件，人读摘要由保存状态生成，不决定是否重做计算；恢复行为在维护收尾时集中作必要运行检查，不为验证临时数据反复启动原生。

控制交接方式变化后，先沿实际调用链核对旧记录的来源资格，再解释和建库。解释器能补充声明，不能恢复从未观察的端点交接或轮询调用；缺少整段新协议事实时，将该来源域作为一次完整观察来刷新，不能逐个补CPU模板、借用另一模型来源或放宽选择。新观察前同时核对P/D两侧挂点、代表角色、原生可运行输入及有限额度，收齐结果后再判断是否还有机制问题；不以一次缺入口就预设采集必然解决后续所有交互。

大分配成员共用原生的已有尾页、完整新页、新尾页三段关系，覆盖冷前缀和非零前缀，不以额外缓存分支修补。原型范围由三段有/无、单元素退化、单/多成员及原生小/大分配和延后池合并条件确定；用实际allocator准备前缀，删除原先冷前缀专属条件及偏移公式。源码能确认的关系先完整实现，必要采集可以直接运行独立allocator，不为这条适配重启serving。旧资产的来源条件不追认新覆盖；新声明、建库/变换和serving集成分别记录资格，未覆盖范围继续进入独立矩阵，不临时按失败长度补点。

改动仅涉及诊断引用时，先确认工作身份、输入、发布/完成时间与顺序逐项不变，并核对旧预测确实保留相同记录顺序，再为已有预测附加新的来源依据、离线重新对照；无需重跑原生或仿真。原图和决策保持原样，报告明确这是重新解释诊断而非新一次预测。代码、模板或控制行为改变时，另按受影响链路安排必要构建及运行，不以旧结果替代。

**一次真实执行形成长期可复用的案例。** 保存模型/环境与实际输入、预热及初态依据、原始控制/完成/资源观察、结构与物理记录，以及会话、通信注册等必要伴随数据。原始事实只读，派生解释、模板、仿真结果和比较报告明确对应来源。每个开发批次收尾时清理确认失效且不再被引用的中间副本、重复导出和过期结果，移除其活动入口；保留固定真实案例、当前使用的资产、阶段交付证据及解释未决失败所需的最小材料。保留失败事实和累计费用不等于永久保留每次派生产物；不能删掉重新解释必需的原始事实而迫使原生重跑。

仿真器、模板规则或评价代码修改均不构成重跑原生的理由。仅在新增模型/环境/配置/请求案例，或明确证明旧案例缺少且无法推导的必要事实时安排原生执行，并说明缺口、有限范围及累计额度；保留失败事实及仍有复用或诊断用途的旧案例。原生框架本身变更属于另一个真实案例，不能以新结果覆盖旧基线。用于修复的案例归开发回归，未用于修复的真实案例可预先采集留作独立验证，不因其已采集而丧失独立性。

本闭环通过后完成阶段代码/文档/数据审查及分层提交推送，进入使用同一旁路机制的完整S11-B独立结构验证。S11/S13的真实对照均以性能依据已知为条件，保留既定模型、配置、请求及生命周期覆盖；不增设关闭旁路的验收阶段。必要编译、运行安全及接口检查仍随实际修改进行，不以任意给定耗时跑通证明结构准确。后续性能阶段接入cost model并验证其误差及端到端自主预测；本窗口不实现或验收性能层。

优先理清以下三个机制，它们决定后续修复方式；下述事项是分析与实现责任，不预先断言某个未闭合失败的具体根因：

每批修复先从职责、数据来源、状态所有权及提交/读取/完成顺序推导完整机制，再决定保留、合并、删除或整段重写哪些实现。已有目录、接口和分支不构成保留依据；修复范围覆盖生产者到消费者，替换后的旧路径、临时诊断和无用输出同时删除。源码推导主导修改，必要运行只确认成组修改的结果；运行差异是证据，不能不断生成新的例外分支。按整块机制统一编译和有限回归，不围绕报错点逐改逐测，也不通过字段改名、扩大兼容或放宽评价收口。

模板入口的候选归资产维护，消费者按语义角色查询并保留阶段和实际输入条件，不重复持有整表筛选逻辑。固定、动态及可替换子调用均须交出真实值端口与输入集合；成员参数推导和聚合量的作用域共用已有规则，不能因调用方式改变而丢失集合或沿用父调用的同名计数。源合同已接受但当前开发资产尚无实例的组合，修复时单列源码证据和运行缺口，不将旧回归移作新组合通过。

建库的几何声明归不可变来源所有，区域只索引本地声明，使用时按最近作用域解释；不复制祖先整表或再复制一份用于排除内部值。布局输入与自身操作仍保持各自合同，纯所有权整理可用既有来源的完整建库结果核对，不因此重启原生或仿真。

- **模板的变化与组合边界。** 分层存储与独立变换分开核对，检查父布局是否仍固定整套来源子调用。子实现的可替换性由端口、形状、别名、固定角色/权重绑定、状态效果及完成责任共同决定；有合法组合但当前表达不了时修组合机制，有真实联合条件时保持它，不把所有模块自动设为任意可替换，也不为每个组合重采整次serving。
- **执行准备状态的唯一所有者。** 沿输入字段的产生、保留、筛选/合并、清空和重建理清原生控制、adapter及C++符号视图的关系。逻辑控制仍归所选控制器，资源和在途执行仍归核心；adapter交接本次工作实际可用的输入及必要效果，核心不从残留来源片段另猜框架字段生命周期。先检查现有动作/端口合同能否表达，确有缺口才统一修改生产者和消费者，不增加平行状态机或逐字段兼容分支。
- **有限来源的覆盖依据。** 来源自身无合同缺口，不等于承诺变化所需分支已备齐。依据原生API的实际分支、角色及已有模板条件列出必要有限原型，分别判断参数变换、已知局部分支组合和确需新来源；不按任意shape枚举，也不实现全框架路径证明或全局能力登记平台。

模型计算与外层准备的组合收口采用原生模型forward调用边界：框架adapter提供完整输入/输出，读取实际批次及所选backend对象的缓存/attention上下文；PyTorch模块API提供参数和buffer绑定，runtime继续负责设备接口、几何及执行依据，不解释框架私有字段。核心按子调用自身条件选实现。外层保留原生token准备、sampling及必要顺序，不为新组合重采整段Decode。选择前核对隐式状态、资源视图、别名及角色绑定；候选展开在私有图内完成并统一发布，不能给旧固定子调用简单添加替换标签，也不能在失败后留下半个图。现有实现妨碍这份合同成立时，重写相应选择和发布职责，不维护第二套补丁路径；不自动推广成所有模块任意互换。

结果和调度的工作归属沿完整原生调用确定。普通结果中的缓存保留与释放由同一结果动作接收实际调用顺序，资源在规定完成端口提交；前缀索引服务、调度准备与PD发送前的保留各有实际边界。无模型决策须与非空决策共同检查过滤、准备、协调和Schedule完成的交接，保留窗口中间及末尾的实际工作；不能固定追加尾图、只凭模板存在性猜一次调用，或提前关闭父调用后再补一个父调用。

准备内部按实际资源调用交接：先展开调用前的输入构造，再执行原生选择的逐出及分配，最后连接调用后的准备工作。框架只声明可暂停的原生资源接口，来源生产按真实调用及值的生产/消费关系提取两侧工作；不为目标案例列操作或依赖边。资源申请前的需求描述不包含尚未分配的页身份，实际保留及完成各有唯一边界。分段展开归共同图接口，本轮核对原生控制的消费链；跨动作值、输入组、调用栈和已完成准备结果须存活至消费者接收。删除原先最终prepare统一重放的路径；不能添加反向依赖、延后必要资源反馈、放宽评价或构造另一套通用代码解释器来绕过顺序问题。

分段不能改变原调用的输入合同。父调用实际已有的数据列与资源接口当前消费的子集分开表达，各连续段保留同一父调用的输入约束，再按当前值核对几何、别名及状态。不能为了允许消费子集而丢弃父调用条件，也不能让准备结束后重新执行本已完成的输入工作；这类错误应在公共选择与调用交接处修复，不按列名或模型增加特例。

所有入口和嵌套调用共用输入闭合规则，不保留根调用自动补出动态数据的宽松路径。先静态检查实际可调用范围内的未绑定输入，再沿原生操作数补全来源接口和目标生产者连接；只有观察前已有的状态存储或显式绑定的状态视图可以无独立数据生产者。跨调用的先后差异须按实际读写、完成和控制历史判定，不能复制独立运行的全部串行顺序，也不能用评价器弱化真实操作数缺失。

已知目标资源初态须在第一次子图调用前由所有者建立。页池向量的身份和内容一次交接给图，分配、保留、释放、逐出及归并只消费和产生相应版本；不允许先实例化空缺输入，再从调用结果倒补初始数据，也不为首次使用维护另一条宽松选择路径。

新增分段或改变绑定规则时，先对整个来源库静态核对新增接口的端口和必需参数来自哪里，再做有界的完整回归。检查使用实际调用参数、有效输入几何及已有关系，不手填缺失值；不让整链运行承担逐个发现参数的职责，也不因此建设平行能力登记或检查平台。

观察、目标展开及独立评价须采用相同的请求工作起止含义，覆盖批次派生的异步发送、等待和资源提交，并与空闲轮询区分。先沿真实工作所有权和完成端口确定窗口，再集中调整相关职责；不能一端按请求成员为空结束、另一端按全组退出累计，也不能以首末Schedule标记内无漏包代替整个工作窗口完整。给定目标时延与原生实测时延不同，额外调用须先核对窗口、控制进展和执行条件，不按轮次或操作数量拟合。

采集阶段由真实请求入口交付，活动与排空沿原生循环的真实空闲通知及既有work取得；新请求使空闲事实失效，不维护平行进度。预热、基线与正式来源共用顺序：请求输出完成后会话发起关闭，全部参与rank确认空闲、发送消费及设备同步，再重置池/缓存，执行观察辅助准备、同步、快照/发布，最后全部确认阶段完成。辅助采样不能插在原生通信收尾之前，重置也不能改写仍在观察的请求状态。原生控制只在空闲判据确实成立时交出idle。评价另列来源结束依据及双方起始lane，缺失事实保持未知；新采集生命周期结合必要来源任务核对，不能以CPU预测通过代替原生采集验证，也不为相同轮次重跑相同目标。

SGLang普通、PP和PD选择通过共同的批次协调adapter交接准备、实际协调及调度完成，浅层替换交接步骤、保留原生选择与Gloo元数据逻辑，删除各selector的重复准备路径。影响原生分支的MoE后端/模式从来源交付，不通过关闭原生协调来代替设备隔离。核心用独立调度操作及完成端口表达无模型工作，准备只返回自身子调用，最终完成后才允许模型；来源解释统一登记空/非空调用并重建受影响资产，有限回归后再进入独立验收。

**同类问题再次出现时回到机制分析。** 出现新的长度、模型或拓扑触发同类缺口，停止该机制的追加采集和局部补丁，检查上次根因解释遗漏了什么条件或所有权；其他无依赖工作可继续。只有明确证明必要事实缺失、明确新增来源将覆盖哪个有限原生分支后，才安排有界采集；已登记额度不是自动补采指令，不以扩大额度解除这个要求。不能把已有局部分支的组合失败当作缺图，也不能通过删除guard、忽略工作或放宽资格掩盖它。

正式详细输出保留实际提交/完成顺序及返回页，example只消费已发生的状态变化，不选择批次或复制分配策略。已有目标输入就绪和资源检查由原所有者维护，不另建平行验证链。公开实参中的同一张量可同时作为赋值目标、索引或载荷；值去重不能抹掉读取角色。无法证明的状态/依赖保留未验证范围，不能靠忽略端口、固定名称豁免或降低比较条件使报告通过。

mixed原生控制的就绪判据沿已有结果提交建立：未结束且无需继续Prefill的成员可进入本执行组/lane的下一轮Decode，释放/撤回移出；准备批次须与该就绪集合一致，不能遗漏已有Decode或提前消费未返回结果。含Prefill时核对新增token和Decode成员合计不超过chunk预算，纯Decode不受该Prefill上限约束。统计实际检查次数并设置覆盖门槛，使用当前请求/资源检查验证有限序列最终完成；不复制原生等待队列、分配策略或声明无界公平性。

局部与整体评价共享已经建立的对应：同一request/token模型主体的操作配对可用于整窗口，不能因外层Schedule划分不同而丢弃，也不能覆盖与实际工作引用冲突的配对。子调用沿实际源区域和目标任务引用定位，接口名只在同一工作内帮助确定唯一图顶点，不单独证明归属。调用者序列只能在已知边界之间建立完整区间的对应，输出合同和已知输入生产者不得冲突。排除序列配对的输入冲突后，沿已对应生产者推进到稳定状态，再核对先前候选，重复调用的歧义仍保留。局部与模型比较只检查已建立的配对，不将未对应列表按位置比较；未对应部分作为覆盖缺口保留。原始设备工作及异步复制总量按完整窗口独立核对，不能因局部批次归属不同误报漏算，也不能因投影遗漏而漏查真实工作。完整对应窗口可以证明单批切片看不到的跨批依赖，但不能覆盖单批的状态错误、身份缺失或其他未知项。额外轮询须沿原生调用、实际输入输出和当时的传输完成状态解释；未配对工作、几何错误和依赖差异继续保留，不按名字或固定次数豁免。初始排空需要成功同步及此前提交范围的事实，仅出现同步API事件而没有成功返回依据时仍属未验证；先查清运行时观察路径，再安排必要采集。

接收前阶段的开发证据时，分别登记已检查的逻辑位置/依赖、未记录数值的host数组、未观察角色，以及无法复原的历史差异。内部数组沿原生来源及实际消费者核对；影响所验工作或状态却缺少必要身份时，在适配边界补事实，不建设通用张量数值解释器。历史摘要存在时差但缺少旧完整图或对应源码时，保留不可判定结论，不能靠重复当前运行、相同节点数或调整耗时宣布回归通过。A阶段使用完整当前图和原生观察核对相关PP/PD工作与必要因果，发现确认缺陷先修复，再冻结B；旧差异仍保留，新的独立证据不冒充历史归因。

相同的当前请求和token长度只足以定位模型调用，不能单独证明其准备与回收工作可比。过滤/合并还取决于此前保留的批次成员，KV端口还取决于当时池状态。沿实际命名调用和输入参数核对局部模板，再核对各自轨迹的状态与必要依赖；局部展开复用公开入口，不回填正式预测。分支是否需要由正式控制合同及必要数据/完成依赖确定，目标图缺少节点本身不是排除依据。经此确认的原生额外控制分支单列为来源范围差异，保留错误和调用依据；正式目标需要该分支时补相应能力。局部一致不直接改变整例结论，未对应工作仍保留未验证范围。

工作身份与序列化位置分开：沿实际调用边界、公开参数和输入输出建立对应，再检查数据、资源、通信及等待的必要顺序。整窗口也覆盖观察范围内没有模型计算的筛选和空决定；原生与目标使用对应的起止边界，不能一侧截到最后模型批次、一侧仍计入终止清理。观察范围依据原生记录的serving归属，辅助原型不属于请求生命周期；整窗口配对须与已定位的请求/token批次一致，不能用重复调用的新配对覆盖原配对。只匹配有模型工作的批次时必须保留该覆盖缺口，完整配对后仍检查这些控制工作的必要因果。不同线程的记录排列不能直接当成依赖；操作清单相同或排序后相同也不能证明因果等价。存在重复调用歧义、外部前沿或未对应工作时保留具体未验证范围。模型输入由准备输出及显式通信端口交接，批次过滤视图只管理其跨批次保留的列，不能反向决定模型需要哪些输入。

原生调度协调由框架适配在真实函数边界标记，独立评价核对其对共同工作的数据/存储、设备/runtime和通信边界后单列；原始操作不删除，未声明或有外部工作关系的部分不自动排除。模型TP通信、P/D数据及元数据搬运、准备/释放与等待仍属于必要执行结构；不能以控制器不同为由整体忽略它们。采用轻量控制器的范围和原生策略/控制开销的未验证部分分别报告。

等待核对以必要因果为准：在未修改的完整目标图中检查所需完成路径，不要求裁剪后的flow内仍存在同一条直接边。逻辑依赖还须有生产调用CPU返回到消费入口的路径；原生线程的实际总顺序单列为观察结果，不把独立请求因完成时机换序当成必要依赖错误。整窗口覆盖不完整时，仍检查已对应调用之间的关系；有差异则报告，全部已检查项成立也不能因此授予完整窗口资格。范围外前沿必须属于原生实际等待的stream；额外内部关系和不属于该等待的边界仍报告差异，涉及范围外工作则保留partial，不能由路径存在推导策略或时延等价。

请求输出完成不等于原生批次清理完成。所有控制组均需经过原生清理并报告空闲，随后在统一输入边界接收停止；单组与多组使用相同终止规则。结果回调只交付工作结果，不另行触发原生主循环退出；末尾空批次过滤仍属于已声明的执行结构。

PD同步传输按原生接口合同核对：KV片段完成后才发送最终元数据，接收方在成功通知后读取，源端在传输完成后解锁资源。观察中的成功返回、实际目标session/请求身份及接收/释放边界分别提供依据；不要求把不透明同步服务内部的每个硬件任务逐项归属。目标图的交接检查必须覆盖每一个生产端完成端口，并确认它能到达接收动作等待的完成端口；只有其中一个生产端有路径不足以通过。设备消费者到页归还的关系另由资源检查核对。检查在example维护，不向控制器增加第二套资源状态；内部一致与限定原生边界证据不升级为整窗口或载荷数值等价。

PD的上一批筛选、索引保存和发送沿实际调用边界交接；P实例保留筛选视图但不合并成Decode，接收模板已包含的成员工作不重复展开。PP的观察范围包括准入前的旧批次处理。预热和池重置后的设备工作须在采集窗口开始前排空，不能从初始化完成或复用预热助手推定队列为空；历史初态证据不足仍记partial。评价可以使用窗口外的实际同步证明初态，但须确认此前相关提交均已返回、同步成功结束，之后未引入新的未完成工作依赖。后续事件等待只有在事件身份、记录顺序和同步覆盖流均明确、记录已被同步完成时，才能证明不引入外部依赖；新复制、重录或无法排序的提交仍不通过。未归属设备工作先核对统一流程范围与不透明服务合同；只有时间接近、位于某段窗口或同一kernel名称，不足以取得归属或排除依据。成功事实可来自实际返回值或已核实只在成功分支触发的原生回调，不从API名称、时延或提交开始时间推断。交接检查沿完整执行图核对完成端口路径，不以动作间是否存在直接边代替必要因果。

工作参数和几何关系由实际原生调用声明，再经共同符号机制向后传播；不得在采集结束后只修部分输入/输出。请求级端口及槽位在请求边界取得，不能以batch中最后一个成员替代。相同参数下先核对原生切片和公开端口，再检查改变长度/容量后的完整展开；旧来源保留，不手改其JSON获得通过。

设备实现的适用条件须区分空与非空操作数，连续存储不代表二者执行相同工作。运行时适配从当前调用的局部形状合同生成条件，不沿用复用张量在旧作用域中的符号；后解释会补充局部声明，各消费者须查询当前最近作用域，不能提前复制完整继承表再使用旧快照。不透明端口和重复输入组沿自身合同解释。已有来源同时包含所需分支时，复用事实重新解释和建库，不为条件声明的错误补采。请求拥有的接收、释放工作按动作与实际完成端口归属，PP消息保留模型批次归属；不能把未配对误写成目标漏执行，也不能因操作对应就忽略设备工作差异。

容量变换同时覆盖资源账目与持久张量及其视图。原生池的容量、预留页和布局由对应adapter从实际对象/实现取得，目标装配交付容量参数，共同表达式传播几何；资源守恒不能代替张量容量正确，也不逐算子修补固定维度。

资格澄清可以先行确定实验对象；功能开发不与逐目标修补验证混为一条循环。所有新增取证在启动前记录有限额度，复用来源与新原生事实分开统计。重新验证保留固定边界回归，并使用未参与修复的预定请求获取独立证据，不把原输入重测称作新输入泛化。

先收口已知机制，再做少量能区分机制的开发回归：覆盖不同模型的同类API、普通/PP上下文、P/D组批及新旧专家模块。原触发案例可用于回归，使用过的目标数据转为开发材料；只为明确的新事实安排必要采集，不逐节点、逐长度追加完整serving。先核对候选模型的无插桩原生运行；来源固定配方与目标的组批/池配置可能不同，资格分别按实际启动条件解释。初始化受阻需保留所处边界及费用，区分原生/环境与采集影响，再决定后续取证；处理留在任务生命周期与适配边界。各模型只覆盖自身具备原生资格的组合，不修改推理框架实现。

**3. 备齐下一轮编排。** 调整既有example清单和输入生成，使正式预测、条件与生命周期案例都显式选择原生后端，停止生成轻量重复项及双后端比较任务；来源和真实原生观察仍按原模型/配置域规划。核对每个原覆盖机制在新清单中的去向，按实际原生预测及评价开销重新估算额度，不另建验证编排系统。

在原example入口中区分冻结的共同处理/评价与允许更新的adapter，按Git、镜像及运行记录核对边界；启动前列明具体路径和已审查提交，语义归属由关联审查判断，不能只放行adapters目录或新建自动语义分类器。完成/依赖判断须区分资源待执行、业务失败及实际覆盖，来源未启动不算覆盖完成。记录受影响来源域和案例，复用现有任务状态与报告，不新建版本兼容、指纹中心、能力登记平台或另一套矩阵系统。

验证和条件展开复用正式任务的预测入口，保持所选控制后端、预算、发布及容器所有权一致。独立原生比较先固定本例原生观察，再转换真实边界时间并交给任务预测；不复用以给定耗时生成的既有预测。时间转换与结构投影属于同一采集案例的派生产物，恢复到新的原生尝试时随实际案例切换，旧结果仅保留为历史。摘要比较只排除明确的诊断字段，包括工作引用，不掩盖正式资源或完成结果差异；原生边界不足时记录失败，不退回假定耗时继续独立结构验收。冻结同时记录推理、控制和建模镜像；控制代码及运行时也属于预测依据。

下一轮冻结前先收口评价工具的实际开销。沿既有example链路按所有权交接观察图和各后端预测，合并逐rank、逐批、局部及窗口检查中的重复解析、扫描和依赖查询；同一输入、固定资产与后端的既有预测和内部检查由同一案例所有者交接，删除跨验证阶段的重复运行，不将复用计作新的独立证据；必要索引由同一图的消费者共享，不增加通用缓存或任务平台。复用本轮已采的多rank大图、长序列/缓存压力及partial/differences材料，经正式评价入口记录结果、耗时和峰值；相同评价含义下结果应保持一致，若评价本身存在缺陷，则逐项说明修复依据与结论变化，不通过删检查或排除未知工作加速。这些材料转为开发回归，原冻结报告保留；不为评价提速另起整轮serving采集。下一轮矩阵额度须结合这些实测开销重新估算。

相同目标仅生成原生控制后端的正式预测、默认/明细比较和结构报告，已有预测及内部检查由案例所有者交接，按实际依赖复用原生观察；不安排轻量后端运行或双后端比较。观察尚未完成时保持依赖待处理。资源使用范围按实际模型子图及KV传输识别，页表维护不因位于同一动作就成为KV消费者；模型内部的异步设备尾部和实际传输仍须有完成及必要路径证据。

原生组批记录回放仅用于固定成员、token范围和lane核对模板，不作为S9原生控制交付或S11独立预测的替代。原生后端须由模拟反馈自行推进，包括必要无模型清理及跨实例协调；记录不提供这些完整历史。旧记录、同来源建库及目标条件展开只作诊断/开发证据，不能借其消除未验证范围，也不为此扩充workload组批字段。

批次相同不代表输入状态相同：回放沿用轻量控制器的资源容量和跨实例推进，原生接收池的预分配槽位、当时空闲页及先前批次视图须分别核对。记录转换按实际观察的token区间还原接收长度；局部模型比较必须注明这些条件。独立模型入口需要的输入端口由正式准备流程交接；局部诊断与serving使用同一输入绑定和候选发布，区分所有者初始化的状态与调用方必须提供的数据，不依赖标量参数或phase排序猜测实际API。诊断不复制目标图或扩建第二套资源回放。

共享可变张量分别表达视图描述符、存储内容版本和实际返回值，先审查这三者在观察、投影、模板及评价中的完整合同，再决定整段替换或保留。整表版本不能直接充当每个读取区域的生产者；追加的存储别名也不能充当函数返回数量。视图对应须定位同名输出端口或同一结果位置，不任选同形输出。评价由框架语义交出实际参与请求及槽位范围，共同数据流算法追溯读取行的最近写入；只有范围完整、同一逻辑请求的写入已对应时，才消除其他行更新引入的版本冲突和保守别名约束。范围、别名或部分Mixed成员不明确时保留原检查，不按操作名、配置或观察结果豁免。原始图及目标依赖保持原样，CPU提交/等待和跨rank完成仍独立核对；必要证据缺失时保留未知，不以继续增加配对分支代替合同整理。

准备过程须允许资源动作在原生实际调用点介入。先完成“输入构造与提交→必要逐出/分配→其余准备与提交”的端口和完成交接，再整理装配；不能在资源工作全部完成后才一次展开整段准备。来源阶段以已观察的原生调用和数据流为依据，区分来自核心的状态与由框架提供的阶段语义，两个控制实现共用工作/完成接口。该修复覆盖同类准备中的资源交互，删除原子准备的错误假设，不按已见等待编号补边，也不预建通用代码解释器。先复用现有事实确认拆分端口；确有缺失再记录所需事实和有限采集，不逐请求补模板。

核心资源语义、原生控制接管以及会改变预测决定的桥接逻辑也纳入冻结；不能因文件位于adapter目录就将这类修改视作允许的来源适配更新。

以`frozen_revision`核对共同代码、静态合同和评价，以`adapter_revision`核对已审查适配，镜像ID须与登记一致。受影响域使用新来源任务路径，结果的`source_task`绑定该路径，旧结果不自动继承。设备占用或归属未知记为可恢复的`resource_blocked`；依赖缺失继续待执行，A收尾须核对真实冻结检查和新留出输入。

**4. A阶段结束条件。** R1–R9逐项处置：原生链路及共同机制的必修问题闭合或有证据地明确重归因，纯轻量专属项记录后置；不把静态确认写成运行通过，必要原生限制已界定。完成相关全业务链路审查及必要Docker构建/原生公开入口运行，尤其检查抽象与下沉实现的层次、空行/注释、生命周期、可合并删除的跨文件职责。核心与适配各自可核对，原生整链开发回归成立；验证工具可处理失败并继续，代表性大图的评价含义及开销已核对，单原生后端的新清单、输入、判据和额度准备就绪。整理代码、文档和数据，分层提交推送修复基线后再进入S11-B；该提交仅证明开发收尾，不表示独立验证通过。

A收尾按确认缺陷、已查明的观察/历史边界、B的独立泛化义务分开处理。每项未关闭事项只保留其责任、所缺证据和下一步决定；同类局部差异沿同一合同合并，不能不断增加修复子阶段。已有事实不能支持内部逐事件等价时保留该范围，先核对公开工作、参数、状态及必要完成边界；缺少这些必要事实仍是待修复/补证项。开发回归不预先消费B留出，B的未知也不因改为范围说明而获得通过资格。

模型主体的局部评价须覆盖Prefill、Decode和Mixed及其子调用，不能漏掉混合计算后仍以空清单宣布一致。实际出现的批次类型由记录确认，启用某个配置开关不授予对应覆盖。

**独立调查暴露问题后返回A的工作安排。** 保留完整冻结报告与全部失败，先按共享机制收口，再统一回归，不逐case修补或不断增加修复子阶段：

1. 评价先取得可靠的证据所有权与可承担的开销。同一案例交接既有观察、预测和内部检查，减少逐rank/逐批重复生产、解析、扫描和路径查询；用保留大图经公开入口作有界函数级测量，检查结果含义、耗时及峰值后重新估算新轮额度。覆盖降级、部分rank结果及预期拒绝分别判定，不依赖交换律表达式的打印顺序，也不删检查提速。

   同一配置、请求和控制后端已安排独立原生案例时，由该案例承担预测及内部检查，不再另列同输入的纯预测条件。下一轮清单明确合并后的数量与归属，保留全部机制和真实原生目标；原生案例受阻或内部检查未执行仍是未覆盖，不能因合并宣布通过。冻结旧清单、失败和报告不改写。
2. 沿公共输入、表达式作用域和端口统一追溯TP×PP等待缺参及page1局部符号逃逸；另查MoE PD筛选分支与PP×PD Decode的实际输入和条件，不能仅因表现相似就合并根因。事实不足的来源按机制补齐，禁止读取目标图、按长度补模板或按变量名补默认值。模型配置由适配边界规范化交接，避免原始词表字段泄漏。来源准入与目标准入分开：前缀压力只收紧P池，原生D侧在启动worker前按框架自身的预留规则拒绝无法单独准入的请求，不因实验配方错误扩张来源或核心检查。大成员Prefill的输入预算按实际页粒度配置，并保留真实成员数门槛，不能以提高并发上限或Decode人数代替覆盖。
3. 在共同动作/完成接口收口逐请求retain/release顺序，以及有工作但没有模型批次的协调动作；保留其实际时机、参与组和完成责任，不固定追加一次尾图。准备、真实协调和Schedule结束通过原生共享边界交接，删除各选择器的重复转发；来源解释统一维护语义声明，rank装配独占Schedule父调用。请求工作完成与控制调用排空分别核对，末轮筛选与清理也沿共同动作提交，workflow只推进已提交工作及到达，不根据保留视图另造idle工作；空协调不能持续撤销原生idle或阻止参与者静止，清理不能提前关闭已有父调用。核对普通、PP、PD及缓存上下文的必要因果，补足独立跨rank端点与完成事实；不同调用/资源历史先对应条件，不以逐行相同代替正确性。对未确认的行视图生命周期风险先审查证据再决定修法。
4. 功能改动后统一做关联层次与所有权审查，清除重复状态、替代路径和无消费者输出；大范围修改后集中进行必要Docker构建与有限开发回归。完成代码、文档、数据检查及分层提交推送后，重新冻结同一核心/评价基线并按预定顺序启用未使用留出，重新执行完整B。旧目标转为开发用途，旧报告不覆盖，不用只重跑失败项替代完整独立验证；多机探索及性能建设继续后置。

#### S11-B：重新全量独立验证——核心固定、适配按范围更新

**启动前提。** A阶段已完成已知问题的根因定位、机制修复及相关整合回归，并完成维护交付；完整独立矩阵用于验收已收口机制及发现未知风险。已知必修反例仍根因未定、状态所有权不清或同类特例持续增长时，继续A阶段，不用全量矩阵代替尚未完成的接口和机制分析。B中发现新问题仍按冻结规则完整收集、分类和报告，不现场改核心或评价后沿用原验收标签。

**验收对象。** B在未用于修复的真实案例上联合检查两项结果：旁路条件下的调度/资源变化边界，以及已有结构对照覆盖的子图内部工作与必要依赖；两者分别出结论，不互相代替。独立性来自案例未参与规则修正、模板来源与目标用途分离以及核心/评价冻结；允许通过既定接口消费目标案例的真实性能依据，不允许消费真实控制决定、资源分配或目标图作为预测答案。旁路提供者、事件对应及性能数据解释也纳入冻结。这里验收执行结构，不要求先关闭旁路或实现cost model。

**全量的含义。** 重新执行经原生资格筛选、具名固定的完整正式清单，预测后端统一为原生控制，并保留与首轮各覆盖机制的映射；来源、预测、真实原生目标、条件与生命周期案例分别统计。不只重跑失败项，也不只检查修复diff；原生不支持组合保留历史原因，不算核心失败、不靠改框架维持原数量。OLMoE仅覆盖TP1/EP1，多卡EP及PP组合由其他具备原生资格的模型承担。独立目标使用未用于修正规则的请求/种子或几何，旧触发案例另作开发回归。

冻结前在现有example编排中重新列出原生后端清单并计算次数、时间和存储额度，不沿用旧双后端矩阵的案例总数或通过率分母。逐项保留七模型及A–L组的配置、请求、子图与状态机制；原来仅由轻量案例覆盖的通用机制改由合法原生案例承担。轻量专属策略、拒绝条件及双后端比较明确记为后置，不伪装成通过、阻断或原生缺陷。历史415项调查和各后端原结果保持原口径，新报告单列范围变更及覆盖映射。

错峰到达须同时具备真实目标对照，不能只列在给定耗时的配置×workload预测中。分别在单worker、普通PP及带chunk/缓存的PD选一份已纳入请求集的错峰输入，覆盖输入投递、控制推进及跨实例接续；各增加一次真实目标及有限后处理额度，不扩大成全部拓扑的笛卡尔积。发送分组、工作身份对应及内部结构分别报告，声明的到达分组不冒充实际批次；未取得接收事实或比较失败时保留限制和第一处分歧，不修改到达时刻来配合观察。

主种子与备用种子使用同一输入配方，固定人数、页/prompt边界和单步结束，变化其余输出长度；32/64步输出保持原值，通过种子生成prompt组合。路由覆盖随最终请求长度生成，不沿用变更前的token范围。冻结前核对各套实际输入不同且保留全部机制要求，历史几何重合检查只作有限筛查，不代替完整来源审阅或独立运行。Decode预算优先仅归启用mixed的共同实例；非mixed EP及P/D分离不借用该标签，仍保留各自chunk、缓存和交接覆盖。

模型清单为Qwen3-8B、Mistral-7B-v0.3、Qwen1.5-MoE-A2.7B、Qwen3-30B-A3B、Meta Llama-3.1-8B-Instruct、AllenAI OLMoE-1B-7B-0924及智谱GLM-4-9B-Chat，覆盖Alibaba、Mistral AI、Meta、AllenAI及智谱/Z.ai。Llama从公开NousResearch镜像取得原始配置，厂商归属仍为Meta；GLM采用官方zai-org/glm-4-9b-chat的原版Chat模型。所有模型固定revision并保留完整官方结构，使用原生dummy权重，不裁层/专家，不推导真实文本或自然路由；原生资格仅限实际验证的加载方式与配置。独立性以冻结核心及未用于修正规则的运行/目标判定，不将参与过开发的模型描述为全新。换模型通过同一流程取得新来源并自动建库，不要求跨模型复用同一原始图；实际适配改动和维护成本分别报告。

**2. 适配更新按受影响范围处理，避免在矩阵中逐项拟合。**

1. 保存触发失败、当前来源/模板、输入、日志、费用及Git/image依据；先判为核心、适配、工具、原生、资源或未知，无法判定时不放宽冻结。发现核心/评价问题时先记录，继续收齐同一冻结基线下可执行的无依赖案例，不现场修核心；形成该轮结论后返回S11-A，修复后重新完整S11-B。确实使某些检查无法执行的错误列出阻断范围，不能悄悄跳过。
2. 确认为适配缺口后，从原生机制证明所缺事实，确定共享消费者和受影响来源域，暂停这些域的目标检查；其他无依赖域可继续。一次机制修改统一覆盖同类消费者，不按触发案例单独加分支。

### S12：多机初步探索

前提是 S11 已完成单机整合、承接的全量独立验证及维护交付。本阶段只探索多机；原生控制后端已是 S9 的正式交付，不在此再作可选探索。目标是确定扩为多机的真实修改边界，不将完整多机平台纳入本窗口。

复用已取得的本地模板，将一个通信组或stage连接绑定到两个逻辑主机，在单一模拟进程内检查逻辑rank/host/device映射、跨机消息、数据/完成依赖及链路资源归属。明确哪些只需placement/资源绑定，哪些因transport或协议改变必须取得新来源；原生控制通过既有统一接口消费反馈，不因跨机重新设计一套控制通道。

给定通信耗时仅为条件假设，不赋予真实网络资格。若现成硬件、网络和原生环境允许，可在同一案例预算内补一个最小跨机协议观察；资源不可用时明确缺证据，不安装或开发分布式运行平台。跨机因果依消息及完成关系确定，不能直接拼接不同主机的墙钟排序。

最多一个最小案例及一次有新依据的调整，执行前登记累计时间、会话和存储额度。编排和对照放在example，transport差异归adapter；仅发现共同合同的具体缺陷时才修改核心。临时尝试没有后续消费者则删除，保留结论和必要证据即可。

交付说明已尝试的边界、实际结果、需修改的模块、复杂性和未解决问题。结论可以是可接入、需要局部调整、代价过大或条件不足；后两者不自动扩大任务或阻止单机进入S13。若发现单机共同逻辑存在缺陷，则先修正并通过必要开发核对，再冻结验收；探索成功也不宣称正式支持多机。

### S13：独立验证和正式交接

完成选定功能、静态审查和必要开发运行后，冻结源码规则、来源资产、预热约定、控制策略和条件输入，再执行下一节的独立验证。发生结构缺陷时返回对应阶段修正，原对照转为开发证据；重新固定受影响部分并更换或重新声明留出，不沿原冻结标签继续通过。

收口审查同时覆盖采集 → 归一化 → 变换 → 连接 → 控制 → 执行 → 输出。清除被新合同替代的单批次/固定 rank 路径、临时双格式、无消费者字段和实验适配；保留 TP1 的简洁路径。记录业务与示例代码净增减，跨源文件合并重复算法，不靠压行或搬目录减少统计。

输出一份易读的单机拓扑与调度支持结果：正式已验证组合、条件组合、未验证/缺来源组合，以及实际来源与费用。精简结果包含必要的实际计算 token、缓存复用/驻留/淘汰摘要，完整逐页记录仍由明细开关控制。多机、多级存储及本轮原生后端范围外的策略另列后续边界；性能建设继续后置，本窗口不计算 MAPE，也不提交成本模型。

## 6. 验证怎样有界而有说服力

验证编排放在 `example`，复用已有公开入口；核心只保留正式输入边界和运行不变量，不增加窗口专用检查、配置黑名单或第二套状态算法。以下维度在S11/S13独立验证前分别收成有界案例，覆盖已实现主机制及重要交互；S11承接原生后端下的广泛输入泛化、图内容/因果深查及全业务分层审查，S13保持最终固定资产验收和正式交接职责，核对调度/缓存及受影响部分，不生成全组合扫描。

| 机制 | 最小覆盖方向 | 重点观察 |
| --- | --- | --- |
| 模型泛化 | 固定清单中不同厂商的Dense与MoE完整来源及独立目标，仅纳入原生可运行组合 | 相同流程自动发现/归一化/展开，新增适配范围明确，不逐模型复制核心或逐目标补采 |
| 原基线 | TP1/2/4/8、现有 PP 与最小 PD，必要请求/容量变化 | 既有结果、接收/发布职责、组成员和状态所有权保持 |
| 采集前代表复用 | TP peer、可等价的 PP 中间角色及 EP worker；留出未观察角色/运行 | 真实工作与独立绑定正确；区分会话、启动参与者、观察角色和导出开销 |
| 并行与 PD 组合 | TP×PP、TP/PP 与 EP、PD 两侧的多 rank，以及合法高阶/非对称候选 | 组交叠、层/expert 分片、KV 片段映射、通信配对及各自完成/释放 |
| PP | 当前原生合法的首/中/尾 stage、多个微批次；一个合法 TP×PP | P2P 配对、跨 stage 输入、输出回传和资源释放；PP2 在当前 Ascend 环境无原生资格 |
| PD | P/D 各侧的已选拓扑；多请求、短输出、目的容量压力及传输延迟变化 | 所需分片全部可见后才接入，背压、首 token、页释放和交接归属正确 |
| EP 条件结构 | 至少两个合法 EP 部署；同份workload的token/padding路由注入原生并驱动仿真；零接收、非均匀/多目标分发及缺项 | 部署映射、通信及跨 batch/chunk 定位正确，缓存假设一致；输入缺口不隐式补齐 |
| chunk 与 Decode 优先 | 短于一块、整块、多块尾块；新请求与 Decode 同时就绪、token 预算边界 | prompt/KV 进度正确，中间块不输出，Decode 先获预算，有限请求最终完成 |
| 混合组批 | 纯两阶段退化、同批混合、不同 context/成员退出 | 成员阶段与输出不串线，实际 mixed 来源匹配，无重复完整模型工作 |
| 设备前缀缓存 | 冷启动、重复/部分/全可共享前缀、页尾、并发引用、容量驱逐后再访问 | 实际命中及剩余计算量正确，无提前可见/重复分配/错误释放；缓存驻留占用真实容量 |
| 调度与拓扑交互 | 先 TP 下四项联动，再选择合法 PP、P/D、EP 交互；关闭新增开关的基线 | 分片就绪和作用域正确，P/D 不暗中共用缓存，不自动授予全部组合 |
| 必要完成反馈 | 固定原生策略，以具名真实案例覆盖设备/通信交错、不同请求到达及同刻反馈 | 旁路经共同执行器交付性能依据，stage推进、PD背压及资源释放与真实事件对应，不串任务或提前消费 |
| 单机整体闭环 | 一组合法的联合机制场景及本机设备组绑定变化 | 同一入口完整完成，跨组数据/事件不串线，任务与 KV 释放正确 |

采用三种互补证据：

1. **全业务实现、因果与所有权审查。** 沿源码目录、类、接口及跨语言交接检查抽象分层和统一/特化边界，覆盖未改动但关联的代码；每个数据消费有来源，必要通信有匹配端口，状态预约/提交/释放唯一，图无错误环、全局屏障或历史资源串接。核对对外声明与实现，清理冗余职责；源码审查不能替代独立运行。
2. **真实性能依据下的动态结构运行。** 旁路提供已记录的性能依据，共同业务链自行完成任务交错、同刻事件、无输出动作、活跃图回收及默认/明细输出。核对动作、资源和依赖，保留第一次轨迹分歧；不以任意耗时造成的调度差异作为反复修补对象。
3. **有界的扩大独立单机多卡原生对照。** 在未用于修复的真实案例上使用同一旁路和比较规则，比较局部工作、参数、数据/通信关系及关键状态转移，不只比节点总数。单卡分片继续用于取得可隔离的本地模板；各已选通信机制还须有本机真实多rank代表观察，不能用顺序角色模拟代替协议证据。独立观察只交付性能依据，不回填冻结模板或提供目标调度答案；设备不足或原生组合无法运行时保留未验证项，不降低闭环完成条件。

当前结构验收统一输入、初态及真实性能依据，预期控制与资源轨迹对齐，差异按第一处违反共同合同的位置分析。固定批次记录会替代控制决定，不等于性能旁路；它只作局部诊断，不能替代完整结构验证。旁路通过后不要求再用任意给定耗时重现原生轨迹；后续cost model接入同一执行链后再进行自主性能预测及精度验证。

局部变换按同一调用输入条件核对。空闲池等公共状态不同的回调，可用冻结模板在已记录的原生输入条件下独立展开，检查操作、端口及内部依赖；原生条件仅用于这项诊断，不能回填正式预测的控制决定、模板或目标图。已声明的派生输出继续由模板计算。局部范围外的完成关系保留partial，由调用者及整窗口证据闭合。

控制正确性还需按各自轨迹核对请求/token进度、槽位与页的唯一归属及容量守恒、输出/释放的完成条件和跨实例交接。共享池的逐值差异只有在调用输入与比较时点可对应时才用于判错；局部模板通过不能代替这项检查或重新冻结后的完整独立验证。相关编排和检查继续放在example，不为此复制控制器或增加业务验证路径。

## 7. 代码、采集和产物边界

| 职责 | 落点与约束 |
| --- | --- |
| 角色发现、等价依据、分片执行、原生接口、KV布局、专家部署/补齐及受控路由行映射 | Python/C++框架adapter；环境/设备机制留在runtime adapter，依据来自实际对象/代码条件；路由注入不接管原生调度/KV状态 |
| 请求/层/逻辑 token 到全局专家的给定分配 | workload 与公共路由合同；可按拓扑组织输入，专家 ID 的逻辑含义和部署映射仍分开 |
| 值关系、共享定义、代表到 worker 的绑定、通信/数据连接算法 | 共同 contracts、graph、templates；不按模型名、框架私有函数或特定 rank 加分支 |
| 动态决策、资源与执行反馈 | 原生代码经adapter或轻量controller交出同一合同；控制后端维护逻辑进度，核心服务维护资源，execution维护时间与在途任务 |
| 单任务启动、部署、预算、资产发布和恢复 | 正式 workflow；不吸收验证矩阵 |
| 案例构造、受控路由对照编排、跨组合运行、独立比较和汇总 | example；不反向导入业务，不复制原生请求/KV生命周期或待验shape/通信推导规则 |

框架差异集中在有来源的角色、接口和规则，模型差异优先从真实模块/配置取得；只补无法自动获取的最小声明。SGLang 的 profiler 启停继续是采集 adapter 的局部实现，不为这件事另建一套框架层。新结构能力有实际消费者才增加接口或字段，C++ 头源同目录，保持必要空行和关键注释。

采集在启动前按“实现域 → 非等价角色/局部机制 → 有限观察点”规划；正式 workflow 消费原生参与者、观察代表及目标绑定，不按每个逻辑 rank 或请求集合逐次完整启动。统一预热后观察，加载/编译/预热计采集开销而不计模拟服务；新路径需明确是否预热。可隔离的本地事实优先单卡；真实协议所需 peer 仍按原生要求运行，代表观察与独立多 rank 验证分别安排。

首次原生运行前，在同一个运行输入中固定会话上限、原生/处理秒数、临时/保留字节和停止条件；实施阶段日志记录具体数值与累计消耗。不凭未核实的模型/设备估算额度或承诺可运行范围。失败和重启继续计入原任务，遇到同类缺口无新依据就返回机制分析；已有自主采集授权继续有效，不逐次请求确认。

沿用一个时间运行根的 `inputs`、`captures`、`assets`、`results`、`diagnostics`、`logs`、`state.json`、`work` 职责。默认给人看简明组合结果、共享计数、来源/条件和缺口；完整图及原始明细在生产前由现有明细开关控制。共享资产保存定义和绑定，不为每 rank 或每目标复制整库；必需机器资产不因追求短 JSON 而被裁掉。不新建窗口专属产物平台，不清空已有 data。

## 8. 完成、停止与风险处理

**完成要求：** S6取得真实MoE/EP证据，S7完成所选TP/PP/EP/PD组合及采集前代表复用；S8因计划调整结束，其结构覆盖义务不得消失。S9直接运行原生控制代码，经统一接口操作核心资源、模板及执行器；随后完成全项目代码整理、行为核对及独立维护交付；S10完成四项调度/缓存能力及合法交互。S11在原生控制后端下完成单机整合及完整独立验证，覆盖经原生资格筛选的七模型、请求/容量变化、并行组合与未观察worker复用，分别证明核心和适配资格。S12仅形成多机探索结论，S13保持原生后端的最终独立验收与交接；轻量建设及验收留待后续计划。每项区分待做、实施中、源码已改待验证、限定范围验证、待交付和完成；功能、代码/文档/数据检查及提交推送全部完成后才交付。

原生控制闭环是本窗口的正式能力，不能用固定组批回放、真实设备跑一次或仅一个最小案例替代。若必选路径因原生后端/环境/输入或接管机制无法完成，保留具体阻碍及未完成状态；可以交付已完成子集，不自动将整个窗口记为完成。真实多机完整支持仍留未来，S12以有界探索和明确结论结束，不遗留占位实现。

| 主要风险 | 处置与停止边界 |
| --- | --- |
| 并行机制互相组合导致规模失控 | EP 后专门实现组合装配，以有限合法机制组合和非对称候选形成覆盖，不生成笛卡尔积或逐组合子类 |
| 等价归并误删角色、CPU 路径或布局差异 | 区分叶子/布局/完整角色复用，保留条件与绑定；缺依据就不合并 |
| 采后去重被当作采集节省 | 启动前确定代表与绑定，留出 worker 对照；分别报告原生会话、实际参与者及观察角色，不能将派生绑定记作实测 |
| 为单机或当前控制器写死共同流程 | 用原生单worker及TP/EP/PP/PD消费者验证同一接口，审查后续轻量接入与多机的修改落点；请求逻辑归控制后端，资源归共同核心，不提前建设后置后端 |
| 原生接入膨胀成框架重写 | S9先收口实际工作/完成接管点，复用原生生命周期；禁止复制调度算法、维护两份资源状态、批量伪造私有对象或静默回退；共同资源语义须有原生依据，阻碍公开保留 |
| 原生代码运行被误当成正确性证明 | S9基础闭环、S10优化闭环后由S11完整独立验证；真实时间、清理/等待及必要状态交接分别核对，不能跳过S8遗留 |
| 缓存复用导致容量和状态错误 | 实际分配唯一，区分请求引用、缓存驻留与就绪；同内容不自动跨实例/布局共享 |
| 多级存储抽象变成另一套平台 | 首期仅设备层，明确位置/就绪/迁移边界，未来介质后端不预建空实现 |
| 为可扩展性增加无用接口与继承树 | 使用必要的抽象、组合和 C++ 模板；每个实现有本轮消费者，删除旧链路和空占位 |
| 初步探索扩张成第二条开发主线 | 单机整合后再开展，固定案例与额度；给出阻碍和改动范围即可收口 |
| 路由输入或补齐处理扩张成复杂系统 | 按EP拓扑维护token/padding给定路由，adapter解释实际部署及补齐数量；不增加自动路由、双合同或无界补采 |
| 给定路由与原生dummy自然选择不同 | 统一注入workload token/padding条件，核对原生行映射和真实dispatch结果；不回填目标图或注入预测split，不宣称自然路由正确 |
| 工作差异与必要因果未查清 | S9及S11-A收口共同合同和已知缺陷；S11-B核心/评价冻结，适配按原生依据和受影响域更新、重建及复验，暴露目标转开发并启用预定留出；需改核心则汇总后返回S11-A，修复后重新完整S11-B |
| PD异构布局缺依据 | KV按head/层/页片段及真实协议映射，不用平均或补偿规则掩盖缺口 |
| 验证规模扩大却只检查完成或计数 | 预定机制/交互覆盖及深度判据，结合真实留出和全业务分层审查；不以大批量条件展开代替独立证据 |
| 固定耗时通过但资源竞争仍不可信 | 只报告条件结构资格，通信拓扑、成本采样与争用模型明确后置 |
| 开发被无界补采和诊断扩张拖住 | 采集前冻结问题/额度，开发与独立验收分开；只保留正式消费者所需代码 |

阶段内每五个实质代码批次审查层次、所有权、代码表达和冗余，同类补丁反复时提前；阶段收尾还须完成独立的 Git 对比、关联代码审查、整理检查和提交推送。提交集中在阶段边界，阶段内的开发批次和小修复累计在工作区，避免随每次检查零碎提交。阶段任务与验收条件在本计划维护，当前状态统一写入status.md，实际改动、证据及费用变化按批次写入log.md；不增加平行的审查正文和历史备份。
