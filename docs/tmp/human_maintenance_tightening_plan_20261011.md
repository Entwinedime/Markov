# Markov 人工维护与逻辑精简计划

这轮要把项目收紧到开发者能够理解、修改和扩展的规模。重点是减少主流程需要理解的状态和调用关系，删除没有作用的功能与重复实现，而不是换目录、增加抽象层或压缩代码行数。

起点为已提交的 `1f5c341`。自有源码、Shell 入口、CMake 和 Docker 构建文件共 81,229 行，含空行；同范围连同配置等文件为 83,255 行。行数继续作为观察指标，争取明显减少，不作为替代逻辑验收的硬门槛。

## 必须保留的主线

```text
采集 → profile_manifest.json
源 trace → 原始 DAG
原始 DAG + target 配置 + workload → 目标工作与依赖
目标工作 + 未变工作的源成本 + 独立成本包 → 完整 HTTP E2E
```

成本数据库负责独立测量的去重、训练和适用范围。预测只消费已经训练好的成本包。只有实际缺少数据且用户显式开启时，才进入整组共享补采；评分不参与补采或训练。

保留 SGLang、KTransformers、默认关闭的 NodeScale、现行规则的静态 oracle-cost 回放，以及实验时的三阶段报告。保留原子图变换、资源依赖、源与目标数据隔离、正常 HTTP 评分和累计补采预算。不得用删除合法操作、填零、删 gap 或放宽门槛换取精简。

## 已确认的复杂性

- 组配置有只校验而没有消费的 `fixed_calibration_manifests`，也有未被使用的 `control_sources` 汇总和旧校准计划函数。
- 普通预测准备会提前恢复物理与控制校准状态，尽管实际预测只需要成本包。这使默认路径依赖不相关的历史采集文件。
- `prepare.py` 同时组织源准备、命令生成、补采选择、数据库导入和训练；补采分支又通过可变报告字典传递结果。
- 源观测、目标工作、成本绑定和报告之间有大量字段转写及重复分派。需要沿实际调用链确认哪些是必要语义，哪些只是重复包装，不能按文件大小直接删除。
- 主文档夹杂多轮修复记录，用户需要从大量历史段落里辨认现行规则。

## A 收紧用户工作流与组配置

联合处理 `prepare.py`、`group.py`、`control_acquisition.py`、`fixed_calibration.py`、`physical_capture.py` 及独立成本导入。

普通路径只做源输入准备和预测；缺成本后才进入补采恢复。组配置只保存实际使用的输入，删除无调用方的函数及无消费方的字段。物理与控制测量在真正使用时准入，不在普通预测入口重复解析。保持补采与预测的职责独立，避免把全部状态塞入一个报告字典。

默认预测、显式补采和 dry-run 的行为要清楚：dry-run 不启动采集；缺成本时给出具体需求；历史预算不清零；现有成本足够时不额外读校准或启动训练。

## B 精简独立成本与校准逻辑

联合处理 `modeling/cost/`、校准导出和需求选择。保留操作、实现、计时口径、变量、响应形式与适用范围这些必要概念，减少为同一事实维护的派生状态和重复解析。

训练、预测和缺口分析共用必要的模型定义与选择规则。修正一个模型的定义不应要求同步修改多份匹配表。保留数据来源和留出隔离，不新增摘要、内部版本号或冻结机制。本轮优先保持公式与参数不变，不以误差驱动重新拟合。

## C 收紧 C++ 三阶段职责

按操作族联合阅读和修改 `source_dag/`、`structure/`、`cost/`、HiCache runtime、DAG mutation 和报告调用方。

工作描述只回答执行什么，成本接口只回答需要多久，运行时负责依赖与状态推进。统一真正重复的工作描述、成本分派和序列化；不要把不同执行分支硬塞进一个通用模板。删除没有调用方的接口和重复存储，保留真实的安全检查与图不变量。

新算子或新配置的扩展应有明确位置：trace 适配补观测，结构模块补执行规则，成本模块补响应模型。共享核心不按模型名称、配置标签或实验格子分支。详细诊断不成为正常预测的前置条件。

## D 整理采集与实验外围

联合检查 Python probe、profiling 编排、Shell 入口和配置。删除死路径和重复转写，统一已经重复的调用边界；保留有实际用途的框架差异及受控 token 回放。探针保持 snapshot-free，不为可读性新增张量读回或同步。

公开入口仍为四个 Shell 脚本；不会再加一组需要用户串联的内部命令。不新增独立测试文件，不触碰上游源码和运行数据，也不把被删功能换个名字留下。

## E 收紧主文档

README 只解释用途、最短流程和主要限制。采集说明、建模说明和成本说明分别讲自己的合同。工作进展只保留当前结果、未解决事项和资产位置；历史过程由已有 Git 记录与已保留日志承载，不在多份主文档重复维护。

开发者应能从主文档回答：从哪里进入，三个阶段各修改哪里，新增一个操作需要哪些输入，缺数据时发生什么，哪些报告只用于实验。同步删除本轮移除的配置字段和过时入口说明。

## F 统一验证与收口

按此前要求，完整重构后再统一运行 lint、格式检查、clean Release/validation 构建和业务验证。实施阶段以源码、调用关系和 diff 审查为主，不逐文件跑测试或反复扩大矩阵。

使用原共享成本包、原源 profile/CPU 配对和原正常真值，重新完成原 60 格。另选少量覆盖 ShareGPT、page32、短 timeout 与换 base 的真实输入，检查新增泛化能力没有因收紧而丢失。核对现行静态回放、KTransformers 共用构图和 NodeScale 可选入口。

旧成本包上的预测不能验证本轮改过的导出、入库和训练路径。统一验收时另用已有独立测量和原训练请求，在独立输出与临时数据库中导出、导入代表性的 phase、allocator 和共享控制观测，并重训成本包；核对样本准入、所选模型、系数及配对来源。不得覆盖原数据库、成本包或对照结果，不为这项验证新增采集或独立测试脚本。正式 `trace_graph` 构建已依赖 `hicache_calibration_export`，同时覆盖其编译。

可选恢复还需通过 `prepare-hicache` 使用已有控制配对，覆盖 query 重新导出、分组入库与训练，并核对零预算时缺口明确停止、不启动新采集。直接使用齐备成本包的 60 格或单独 `cost-db import/train` 不覆盖这条路径。

如果是纯逻辑整理，预测时间与工作量应保持；发现差异先定位代码行为，不补采调参掩盖。完整 HTTP 不排除 gap、未归属成本或 Prefill/Decode。执行成功、精度门槛和结构覆盖分别报告，不把历史 186 格当作本轮验证。

## 完成标准

1. 正常预测、独立成本维护、共享补采和独立评分各有清晰入口与单向数据流，默认路径不加载未使用的校准状态。
2. 已确认的死代码、无效配置、重复状态和重复接口被实际删除；没有以新包装层代替旧包装层。
3. 三阶段核心及采集外围完成整条职责链的检查和整理，不只修改 Python 主入口。
4. 不新增逐配置、逐 workload 或逐格参数；保留全部明确要求的能力和数据边界。
5. 主文档能独立指导人工使用与扩展，不依赖阅读临时过程日志。
6. 当前代码的构建、公开入口和最终矩阵验证齐备，任何未验证或不支持范围明确列出。

实现按职责链分成较大的工作批次，同时修改耦合文件，不以单文件为一轮。不为频繁记日志切碎工作；仅阶段收口、重大取舍或实际阻塞时在同名 log 中追加简短记录。收口后稳定说明合并回主文档。
