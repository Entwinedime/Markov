# Markov 人工维护与逻辑精简计划

状态：10-12 已收口。正式使用说明已归入主文档，验证结果及尚未完成的能力见 `docs/work_progress.md`。
本计划不再作为下一阶段的任务清单。

这轮要把项目收紧到开发者能够理解、修改和扩展的规模。重点是减少主流程需要理解的状态和调用关系，删除没有作用的功能与重复实现，而不是换目录、增加抽象层或压缩代码行数。

起点为已提交的 `1f5c341`。自有源码、Shell 入口、CMake 和 Docker 构建文件共 81,229 行，含空行；同范围连同配置等文件为 83,255 行。沿用大幅减少、争取接近减半的方向，但按最新取舍，行数不作为替代逻辑验收的硬门槛，不牺牲空行、可读性或必要能力。

## 必须保留的主线

```text
用户：平台、框架、model、base config、workload、一组 target config
  │
  ├─ base 采集 → manifest → 原始 DAG → 目标工作与依赖规则 ─┐
  │                                                      ├─ 成本填充与仿真 → E2E
  └─ 独立性能采集 → 持久数据库 → 各类成本模型 ────────────┘
```

base 为结构主线提供真实请求、执行语义、原始 DAG，以及明确未变工作的迁移成本。
性能数据库是另一条长期维护的主线，不是某次 base 或 target 的附属目录；保存独立测量、来源及测量条件，
不同成本模型使用适合自己的工作变量与响应形式。预测消费从数据库准备好的适用模型，不直接扫描训练 trace。
两条主线是职责上的独立，不意味着同时占用设备采集；设备采集仍严格串行。

已有数据库与模型应跨预测组复用。新平台没有适用数据时，需要先完成独立性能准备；不足时报告具体缺口，
显式开启后才安排小规模、整组共享的补采。不得默认通过逐 target 采集补齐，评分不参与补采或训练。
用户不需要手工构建 base DAG 或目标 DAG，也不需要为每个 target 指定成本模型。

应用输入与性能维护输入分开：应用用户描述平台、model、base、workload 和 targets；
平台维护者准备可复用的数据库、模型定义及采样域。目标工作自动选择适用的模型响应，不逐 target 手工配模型。
当前仍需显式引用成本包或数据库/训练声明；仅填平台名自动发现资产、从空库采齐所有成本尚未实现。
这两项不能用现有平台的实验资产证明已完成，也不能靠增加实验矩阵成为应用用户的前置步骤。
新平台的正式起点仍是用户提供的配置、模型和 workload，而不是预先生成的 base DAG；
性能库准备不足属于另一条主线的待办，不能转嫁为逐 target 的人工装配。

## 抽象层次与职责边界

人工维护的前提是能判断一项修改属于哪里。按职责区分以下层次，不再为每种操作建立一套平行流程。

| 层次 | 输入与输出 | 责任边界 |
| --- | --- | --- |
| 用户工作流 | 用户配置 → 准备结果与预测结果 | 调度采集、离线准备和执行，不包含缓存规则、图算法或回归公式 |
| 原始 DAG 与源观测 | source manifest → 源节点、依赖、调用归属及请求信息 | 解释采集事实，不推测 target 分支；trace 适配差异留在此处 |
| 目标结构 | 源语义、target 配置、workload → 操作、工作量、资源角色与条件规则 | 决定做什么，不查询成本，不以样本缺失删掉合法工作 |
| 成本 | 工作描述或明确的迁移对应 → 耗时、来源和适用范围 | 回答需要多久，不决定操作数、依赖或缓存策略 |
| 仿真执行 | 已描述的工作、资源和成本 → 实际展开的 DAG 与 HTTP 时间 | 沿同一时钟处理排队、完成及条件触发；不重新解释 trace 或拟合参数 |
| 实验评价 | 已完成预测 + 独立 target 实测 → 源回放、结构比较、性能报告 | 只评价，不参与应用预测、补采或训练 |

成本库是成本层的离线数据来源，不是运行时需要反复访问的服务。二、三阶段通过 `OperationWork`
传递必要的工作变量，通过 `CostMigration` 声明确实未变化的源对应；不传数据库路径、回归系数或目标实测。
图槽位和资源编号只用于执行绑定，不成为模型变量。超时等分支保留条件规则，由执行时钟触发，
不能为了三阶段看起来整齐而复制一套离线时间推算。

依赖来自执行规则，耗时来自成本模型；耗时可以通过完成时间影响条件分支，但成本缺失不能决定分支不存在。
因此第二阶段的产物包括可静态确定的工作与条件执行规则，不强求在填成本前生成已经知道全部超时结果的最终 DAG。
新增框架适配负责把该框架的事实与规则接入共享合同，不能把框架函数名的硬对应扩散到工作流和成本层。

## 仿真粒度的取舍

按是否改变因果关系选择粒度，不按 trace 记录条数或可用成本样本数量决定。

| 内容 | 保留的粒度 | 理由 |
| --- | --- | --- |
| 请求准入、页分配/释放、缓存命中与发布 | 足以区分状态变化的请求、页范围和批次 | 容量及可见性会改变后续工作；传输完成不等于缓存已发布 |
| CPU 提交、worker FIFO、设备完成、同步与通信到齐 | 实际跨资源边界和必要完成点 | 合并会丢失等待或重叠，不能用总耗时替代依赖 |
| 计算与传输的服务成本 | 一个有明确工作量的张量调用、传输批次或逻辑通信服务 | 不逐指令模拟；独立子启动会改变 worker/device 重叠时才继续展开，且不再叠加父成本 |
| 固定控制路径的服务 | 已确认分支的典型响应 | 没有规模变化的机制依据时不增加细分回归；CPU 服务与 residual 口径仍分开 |
| residual gap | 保留对应的源等待近似并说明限制 | 本轮不编造精细调度模型，也不将其吸收到计算或 I/O 系数 |
| 报告 | 默认工作量、对应覆盖、设备数量、资源及完成点可达性 | 删除非必要的内核名称清单、内部拓扑统计和串行标签顺序诊断，不影响正式图或成本测量准入 |

降低粒度前必须说明被合并区域是否有外部消费者、资源切换、状态更新或可变执行分支。
存在这些情况时保留边界；没有充分依据时暂不合并。统一表达相同规则，不把语义不同的操作硬合成一种。

## 用户输入合同

普通用户只描述要预测什么和允许使用哪些成本依据，不手工排列内部阶段。

- 首次使用由用户选择平台/框架，提供 model、base config、workload 和 target config 集合。
  当前以 `profile_suite` 引用普通采集配置，模型和 base 执行参数由该配置的 `server` 声明，workload 由 `bench` 声明，
  不再在组配置重复声明一份模型路径或启动参数。只有一个 base 时可从配置直接确定 base 和所声明的 workloads；
  多 base 实验必须明确选择，不默认取矩阵第一行。该引用不要求包含 target 采集。
- 流程负责采集 base、接收 manifest、构建原始 DAG 并生成目标工作。已有 base 用 `base_manifests` 复用；
  trace 和成本包不是用户第一次使用项目时必须预先制作的输入。
- `target_configs` 接受策略/容量对象或文件，不接收 target trace、实测耗时和拟合参数。
- 平台的 `cost_database` 和模型定义属于可复用的性能准备输入。已有 `cost_model` 可直接消费；
  提供数据库与 `cost_training` 时，由同一入口先离线生成适用成本包，再预测全部 target。
  同时提供成本包和数据库时优先使用成本包，不能悄悄重训。数据库方式仍须有明确的部署、模型形式和独立 I/O 依据，不能自动发明这些定义。
- 部署资源优先来自真实 manifest；旧采集缺记录时用 `resource_environment` 显式补充，不硬编码本机环境。
- 源 CPU 修正可声明已有文件/配对；新采集与缺数据恢复均须显式开启并受累计预算约束。不开启就报告缺口。
- 结果在 `group_summary.json` 中直接包含逐目标预测时间、覆盖限制和停止原因，细节及复现输入用路径引用。
  失败时间为 null，不要求用户翻多个内部报告才能知道是否得到了结果。

准备、预测、性能维护和评价仍由现有 Shell 入口组织，不新增需要用户串联的内部命令、版本号、冻结副本或文件摘要。
恢复生成的成本包写入组输出，不覆盖用户提供的共享输入包；同一包供整组 target 使用。

保留 SGLang、KTransformers、默认关闭的 NodeScale、现行规则的静态 oracle-cost 回放，以及实验时的三阶段报告。保留原子图变换、资源依赖、源与目标数据隔离、正常 HTTP 评分和累计补采预算。不得用删除合法操作、填零、删 gap 或放宽门槛换取精简。

## 起点确认的问题（已处理）

- 组配置有只校验而没有消费的 `fixed_calibration_manifests`，也有未被使用的 `control_sources` 汇总和旧校准计划函数。

- 主文档夹杂多轮修复记录，用户需要从大量历史段落里辨认现行规则。

## A 收紧用户工作流与组配置

联合处理 `prepare.py`、`group.py`、`control_acquisition.py`、`fixed_calibration.py`、`physical_capture.py` 及独立成本导入。

普通路径组织源输入准备、必要的离线成本准备和预测；缺成本后才进入显式开启的补采恢复。
已有 base 与成本包时，默认路径不导入训练或采集规划模块；共享预算工具和配置解析仍正常使用。
预测尝试返回自己的结果，不修改源准备状态；组入口负责最终汇总。
组配置只保存实际使用的输入，删除无调用方的函数及无消费方的字段。物理与控制测量在真正使用时准入，
不在普通预测入口重复解析。保持补采与预测的职责独立，避免把全部状态塞入一个报告字典。

默认预测、显式补采和 dry-run 的行为要清楚：dry-run 不启动采集；缺成本时给出具体需求；历史预算不清零；现有成本足够时不额外读校准或启动训练。

首次使用和复用走同一入口：普通采集配置已经声明 model、base 和 workload 时，不要求用户再写一份矩阵或
手工准备 manifest；显式已有 manifest 是复用方式，而不是唯一正式起点。需要筛选多 base 实验时才补充选择字段。
普通模板命令由准备入口转换为记录与回放，不要求预先写 replay 参数；只在声明状态配置时读取 config specs，
运行输出保持 run-local，不覆盖用户的原报告。固定输出与串行请求的支持边界不因此扩大。

## B 精简独立成本与校准逻辑

联合处理 `modeling/cost/`、校准导出和需求选择。保留操作、实现、计时口径、变量、响应形式与适用范围这些必要概念，减少为同一事实维护的派生状态和重复解析。

训练、预测和缺口分析共用必要的模型定义与选择规则。修正一个模型的定义不应要求同步修改多份匹配表。保留数据来源和留出隔离，不新增摘要、内部版本号或冻结机制。本轮优先保持公式与参数不变，不以误差驱动重新拟合。

预测成本包的响应、部署及来源由一个明确的输入对象共同持有，不拆成工作流中的多份平行状态。
离线训练和目标投影共用纯曲线数学，不互相依赖对方的编排。I/O 聚合只保留实际用于参数与来源的分组，
查询在已准入模型上建立一次工作点，避免重复解释相同变量。

独立性能维护支持已有 runtime trace 的显式导入和有目的的独立采集，按操作、实现、计时口径及环境准入与去重。
数据库可以保存不同平台与模型的数据，但训练只使用已建立适用关系的测量，不能因同名操作或相同元素数直接混用。
数据库内容变化不修改已有成本包；重训是性能准备动作，不是预测某个 target 时的隐式副作用。
控制补采的实验选择与所需导出项形成一份计划，执行不另建匹配规则；共享等待、query 复用及未知实现的停止边界保留。
只请求算子训练时不读取 I/O 证据；删除无人消费的自证标志和运行时诊断属性，不以常量字段证明隔离。

需要特别补齐空库/新平台的冷启动说明：现行入口能从已有数据库训练，却还不能保证仅给一个空库就自动获得
全部 HiCache I/O、计算与控制模型。先明确必要的模型定义、采样域、环境和已有测量，再由支持的采样器补缺口。
不支持的采样或结构必须直接说明，不能用人工逐格资产把这一限制藏掉。本轮不新增通用采集框架或假想模型算法。

## C 收紧 C++ 三阶段职责

按操作族联合阅读和修改 `source_dag/`、`structure/`、`cost/`、HiCache runtime、DAG mutation 和报告调用方。

工作描述只回答执行什么，成本接口只回答需要多久，运行时负责依赖与状态推进。统一真正重复的工作描述、成本分派和序列化；不要把不同执行分支硬塞进一个通用模板。删除没有调用方的接口和重复存储，保留真实的安全检查与图不变量。

新算子或新配置的扩展应有明确位置：trace 适配补观测，结构模块补执行规则，成本模块补响应模型。共享核心不按模型名称、配置标签或实验格子分支。详细诊断不成为正常预测的前置条件。

释放和 page-first 提交已改为由生成器给出实际工作描述与绑定位置，统一成本接口只估计这些请求；
删除两套专用 cost helper、头文件和操作枚举，不在两层分别维护命名表和字段映射。
重复拷贝/记录共用响应，执行节点不合并。CPU/worker/device 重叠、同步服务与依赖等待仍分开；
统一验证的实际范围见 F 和工作进展，不把源码整理当作语义已通过。

计算、allocator 与写确认继续归入同一绑定合同，删除张量专用槽位、请求投影与确认成本绑定接口。
生成器声明数值请求，不在下游重新翻译字段；多启动、阻塞返回、CPU-only worker 和普通异步任务仍按各自实际口径估计。

源写入/淘汰只保留已准入的资源身份，不重复保存整份源展开图、策略和无消费方的 lane 状态。
目标容量步骤与源观测使用不同的数据形态；释放片段可以只证明 compute 流，不能因缺少保留的 main 节点而丢掉这一依据。
源观测计数只解释证据，不混称为目标模板数；报告字段随实际职责归一化。

目前回载索引先序列化局部 DAG，Python 又按节点名称拆出操作成本；写入与释放还输出不参与训练的图模板。
这让性能维护多出一套图解释规则，也让测量文件携带没有消费方的结构。

将索引测量归入现有 C++ source_dag 观测层，共用主机、worker、设备与残余间隔的测量输出合同。
Python 不再解释导出的节点、边和内核名，只负责窗口/配对输入、容器执行、来源及原子发布。
删去无消费方的局部图序列化、专用 Python 拆图文件和重复 scope 输出；保留真实缺测、作用域和工作量。
现有数据库、测量、系数包和预测规则不改写，不恢复通过校准模板决定目标结构的旧路径。

实现收口后统一检查、构建，并用保留的独立 full/light 输入重新导出。
逐项比较操作身份、变量、timing scope 与原测量值，再通过公开 cost-db 入口检查入库、重复导入和离线训练。
这轮不改变公式；发现数值或样本准入差异时先解释并修正，不用重训后的 target 分数掩盖变化。
日志只在本阶段收口或重大取舍时追加一次。

## H 性能库只保存一份测量事实

本阶段沿独立性能主线联合梳理数据库、测量准入、训练选择和来源报告，不改 base 构图或目标执行规则。
应用主线仍从用户选择的平台、模型、base、workload 与 targets 开始，不能为了库维护又要求用户手工串联阶段。
目前数据库既在操作表保存测量行，
又在控制证据中保存成套导出文档；同一部署描述也随每条操作重复写入。
这既增加数据体积，也让不影响测量的诊断字段变化引发重导入冲突。
当前共享库约 141 GiB；只读抽查的五条操作，每条部署 JSON 都为 1,405 字节，
而操作索引又包含整份部署字符串。这证明存在表示上的重复，但不足以估计最终压缩比例。

把操作测量与部署、采集及配对来源明确分开，成本训练只读取需要的操作和口径。
去重比较真实测量，不比较整份报告的布局；来源留出仍覆盖别名及完整/轻量依赖，不能因此放宽数据隔离。
先核对全部实际消费方，再决定库内表示。已有共享库和成本包不直接覆盖，迁移须有显式入口和独立输出，
不引入 schema 版本、摘要或冻结副本，也不为旧实现长期保留平行读取流程。

库内只保留有消费方的事实：部署与来源单独保存，逐操作表持有测量身份、工作变量、计时口径与耗时；
I/O 聚合保留拟合实际需要的服务测量和物理依据。控制导出、CPU 原语中的操作行不再重复塞入证据 JSON，
无训练消费方的图模板、审计布局与诊断字段不进入去重比较。模型参数仍是离线训练的输出，不作为原始测量存回库。
旧库通过显式转换写入新路径，原库不变；日常导入、训练和覆盖查看只维护当前表示。
训练按声明的操作族读取，不为一个小模型集合加载整个部署的测量；不同操作族共用现有拟合逻辑，
保留同采集同工作点的中位数、缺口分类、来源留出及模型输出次序。

验收关注同一批独立测量的准入、去重、来源留出、训练参数和内存/磁盘开销，
不拿 target 分数作为数据库正确性的证明。缺成本仍明确停止；空库全自动采齐不由这项整理冒充完成。

本阶段已收口。证据见工作进展：完整转换保留 16,665,007 条操作和 65 项来源关系；
小范围准入、旧文档去重、完整替换、轻量来源留出及原 1,687 项声明的训练已核对。
不将试验训练包替代现行 1,689 项共享包；完整矩阵、任意平台和空库准备不在本阶段验证范围。

## I 删除观测与报告中的重复解释

沿 C++ 源观测、通信准入、结构报告、CLI 输出及 Python 入库调用链联合处理。
性能训练消费逐操作的工作变量与测量，不再生成无人使用的几何清单；结构报告消费实际工作和独立观测，
不再为诊断重新推导一份 Attention/allocator 程序。通信准入直接形成有类型的调用与参与者关系，
删除先拼报告 JSON、再从 JSON 还原调用的路径，以及不参与准入或结构比较的通信内部边诊断。
评分所需的目标结构中间文件默认只在本次比较期间存在；显式详细诊断才保留，失败也清理本次临时文件。

保留实际 shape、跨 rank 参与者对应、提交归属、共享设备冲突、完成点及非阻塞依据；
未知分支和缺失观测仍报告限制。三阶段报告、性能库、成本公式、迁移规则和正式执行粒度不变。
收口后统一检查与构建，以现有独立输入比较测量身份/口径/数值，并核对代表预测的时间、图规模及结构比较。
不重新采设备或用 target 分数调整公式；日志只在本阶段收口时追加。

## J 物理采集不再提前拟合

联合整理物理采集、报告发布、组准入、数据库导入、I/O 离线训练和显式转换。
本阶段起点是采集报告持有一份拟合参数，数据库又将这份参数作为测量保存；补采以参数是否存在或有没有变化判断采集结果。
这把“有没有完成测量”与“测量能否支持某个模型”混在了一起，也让采集报告承担成本模型的维护。

物理采集只发布工作量、计时、执行条件及来源；报告引用原始测量，不携带服务参数。
独立导入读取明确声明的原始文件，数据库保存训练实际需要的测量。历史报告中已有的参数不进入新库，
缺原始文件时明确失败，不能从参数反造测量。日常训练只读取库内事实，由成本层统一构造物理服务响应。
物理参数和运行时倍率仍各有含义，不将不同计时口径或拟合方法硬合并。
已有库的物理证据通过显式重导入更新；不在普通读取中增加旧表示分支，不覆盖原库或现用成本包。

I/O 库维护允许只训练 I/O，不要求为此声明一个无关算子。合法部分测量仍报告缺口，采集成功不等于模型已就绪。
实现收口后统一检查，以保留的真实物理输入和相同运行时测量核对参数、来源、重复导入与缺数据行为。
不读 target 真值、不重采设备、不以逐格误差调整物理公式；本阶段日志只在收口时追加。

本阶段已收口。真实输入的 12 个存储工作点、72 条 DMA 和 26 组预取阶段测量已入库，
四类 I/O 的参数及来源保持，重复导入正确去重。只有 DMA 数据时保留有效响应并明确其余缺口。
完整库转换保留原操作和来源关系；原声明的 1,687 项响应及代表组的完整 HTTP 时间保持。
具体范围见工作进展；采样器实采、另两项生产声明、完整矩阵及新平台冷启动没有在 J 重新验证。

## K 成本声明按共同规则维护

联合处理离线训练、补采需求匹配和训练输入说明。当前独立训练请求有 1,687 项声明，
大量重复同一公式、变量、范围与外推条件；维护者需要逐项修改等价规则，训练和补采又分别解析声明。

一条模型声明允许用明确的操作列表和计时口径列表描述共同规则，单个名字仍是简写。
在输入边界一次展开为现有 `ModelSpec`，训练和补采共用展开结果；不引入通配操作名、继承、覆盖层或模型定义注册框架。
每个操作、实现和口径仍分别选样本与训练，列表不授权混合测量或共享系数；实现通配仍只选择已有观测。
旧单项声明仍属于同一输入合同，不以版本号、迁移握手或冻结副本管理格式。

本阶段不改变量、公式、范围、外推和独立来源。用已有真实训练请求整理共同声明，
核对展开后的具体规则一项不增不减；再从 J 的事实库训练，按模型身份核对所有响应和来源，
并验证补采需求解析使用同一声明、I/O-only 请求不要求无关算子。不给现用包或历史输入回写新表示。
实现收口后统一检查；不重采设备、不扩大矩阵，日志仅在阶段收口时追加。

本阶段已收口。281 条声明展开后与原 1,687 项具体规则完全相同；模型按身份排序后，
离线整包和来源与 J 相同。公开组预测及完整运行摘要保持。合并声明正确识别缺失 query，
零预算停止；I/O-only 恢复完成库重训后报告采样域缺口，没有采设备或填零。
减少的是维护声明，不是独立响应数或主体源码；具体限制及证据见工作进展。

## L 同次源准备与目标执行分开

当前 Python 按 source/target 启动一个 C++ 进程，C++ `run_workflow` 每次重新加载同一 manifest 并构建源图。
一组 target 并没有共享第一次构图；原始源准备和目标执行仍绑在单格进程的生命周期上。
联合检查模型执行器、runner 配置、backend、C++ CLI/workflow/module pipeline 和报告消费方，
将同次调用内不变的源输入准备与逐 target 的私有执行分开，不增加第二套公开预测工作流。

先核对源图、源观测、索引、CPU 校正及成本提供者的可变状态和引用生命周期。
可共享部分只读；每个 target 有自己的图 mutation、缓存状态、执行时钟及查询统计，失败不能污染其他 target。
客户端和源回放仍在成本绑定之前建立，NodeScale 时机与 component ownership 不改。
批次只在同一 manifest、窗口、CPU 校正和采集通道下复用准备；设备采集仍串行。
不落盘冻结源图、不以摘要判定复用，不引入旧产物兼容模式或目标真值输入。

共享的是同次调用的源准备，而非可跨目标线程修改的 `DagGraph` 对象：
读取和构图线程全部退出后，由 Linux 进程写时复制保留同一原始输入，各目标走原有私有 mutation 与仿真。
Python 不再另维护一个逐格线程调度器；源组顺序进入原生批次，原生批次按 jobs 派生目标并逐格返回结果。
不持久化源图，不引入常驻服务；单格复现仍共用准备与执行函数。

保留默认并发上限、dry-run、继续/停止失败及逐目标复现与评分输入。
整理应实际消除重复准备和等价调度/转写，而不是仅将原函数包入一个批次类。
代码收口后统一检查与 clean Release/validation 构建，用同源的多个真实 target 核对逐目标工作、数值、
目标顺序不污染结果及缺成本的停止范围，并覆盖保留的 KTransformers 构图、NodeScale 和静态回放。
不重训或补采调整误差；完整矩阵只在该职责链固定后验收。若源准备不能安全共享，先说明具体副作用，不能用缓存掩盖它。

## M 补齐新平台的性能准备主线

在 L 收口后，联合检查组输入、独立采集、数据库导入、模型定义和成本准备，不再把已有实验资产当成唯一使用方式。
先沿用户输入核对一次完整调用链：选定平台、model、base、workload 与 targets 后，
哪些信息可直接取得，哪些属于平台性能维护，哪些确实缺少测量。不要为方便内部编排增加用户必填的阶段文件。

已有适用库和模型直接复用；新平台缺数据时，由明确的独立采样计划建立性能库，再离线准备相应模型。
计划说明采哪些操作、覆盖哪些变量和资源条件、预计规模与预算，不运行 target 评分 workload 来补成本。
数据库、模型定义与原始测量独立于某次预测组维护；新增测量去重入库，更新模型是显式的性能维护动作。
计算、I/O 与控制使用各自合适的成本形式，不为统一入口强行合并公式或口径。

优先复用现有采样器和模型定义，不新建通用注册框架或另一套预测引擎。
采样器不能覆盖的合法工作要具体报告，结构不支持、缺变量、缺模型定义与缺测量分别处理；
不承诺凭空自动支持新模型、新后端或任意请求模式。采集仍串行，仍受允许的累计预算约束。

实施完成后，用公开入口分别核对首次平台准备、已有库复用与缺数据停止；
应用输入不包含 target trace，也不要求用户手工构建 DAG 或逐 target 指定参数。
M 已完成独立 `prepare-costs` 入口及真实采集、复用、去重、缺数据停止和既有包核对。
base 与独立采集共用 token/profile 作业和累计预算，CPU 校正共用源输入合同；
物理采样只接收部署与采样域，不再载入 target 组。离线发布与应用准备共用训练路径。
声明采样域与模型形式仍属于性能维护，不承诺自动推断未知变量或采齐任意操作。
证据来自独立性能请求的公开入口，不以 L 的预测代替。新增物理采样只核对 dry-run，未重新实采；
最终完整矩阵仍由 F 验收，不把声明的一项设备模型就绪当成全部成本或新平台 E2E 就绪。

## F 统一验证与收口

按此前要求，完整重构后再统一运行 lint、格式检查、clean Release/validation 构建和业务验证。实施阶段以源码、调用关系和 diff 审查为主，不逐文件跑测试或反复扩大矩阵。

使用原共享成本包、原源 profile/CPU 配对和原正常真值，重新完成原 60 格。另选少量覆盖 ShareGPT、page32、短 timeout 与换 base 的真实输入，检查新增泛化能力没有因收紧而丢失。核对现行静态回放、KTransformers 共用构图和 NodeScale 可选入口。

采集侧先用两个框架的公开 dry-run 核对配置与命令，再用现有 SGLang 受控输入实际回放一次，检查探针安装、字段取值和 manifest 交接。旧 trace 的建模不能验证本轮探针改动；未重新确认的扰动和覆盖范围单列，不把 dry-run 当作实采证明。

旧成本包上的预测不能验证本轮改过的导出、入库和训练路径。统一验收时另用已有独立测量和原训练请求，在独立输出与临时数据库中导出、导入代表性的 phase、allocator 和共享控制观测，并重训成本包；核对样本准入、所选模型、系数及配对来源。不得覆盖原数据库、成本包或对照结果，不为这项验证新增采集或独立测试脚本。正式 `trace_graph` 构建已依赖 `hicache_calibration_export`，同时覆盖其编译。

可选恢复还需通过 `prepare-hicache` 使用已有控制配对，覆盖 query 重新导出、分组入库与训练，并核对零预算时缺口明确停止、不启动新采集。直接使用齐备成本包的 60 格或单独 `cost-db import/train` 不覆盖这条路径。

用户合同还要覆盖三种真实场景：已有成本包直接预测、只声明已有数据库和训练请求的首次准备、
缺成本且未授权新采集时明确停止。核对 dry-run 不训练、不采集，生成包自动排除当前 bases，
输入共享包没有被覆盖，组报告可直接读出逐目标结果。新增操作按上述层次检查扩展位置和粒度，
不能要求维护者同步修改多套等价分派或依赖实验身份。

另用普通单 base 配置核对首次采集入口，不提供预制 base manifest，不要求 target profiling 或矩阵；
检查一个配置中的 model/base/workload 能直接进入准备，复用时仍按 manifest 正式交接。
首次模板不带 replay 参数或 config-id 时也要覆盖；已有显式计划应跳过记录，输出不能覆盖原目录。
空库及环境不适用的模型要给出真实停止原因，不以已有平台的成本包证明新平台冷启动已经实现。

如果是纯逻辑整理，预测时间与工作量应保持；发现差异先定位代码行为，不补采调参掩盖。完整 HTTP 不排除 gap、未归属成本或 Prefill/Decode。执行成功、精度门槛和结构覆盖分别报告，不把历史 186 格当作本轮验证。
成本查询的聚合计数不是执行工作量，允许因复用/批次整理变化；实际操作数、节点绑定值和关键路径仍须核对。

## 完成标准

1. 正常预测、独立成本维护、共享补采和独立评分各有清晰入口与单向数据流，默认路径不加载未使用的校准状态。
2. 已确认的死代码、无效配置、重复状态和重复接口被实际删除；没有以新包装层代替旧包装层。
3. 三阶段核心及采集外围完成整条职责链的检查和整理，不只修改 Python 主入口。
4. 不新增逐配置、逐 workload 或逐格参数；保留全部明确要求的能力和数据边界。
5. 主文档能独立指导人工使用与扩展，不依赖阅读临时过程日志。
6. 当前代码的构建、公开入口和最终矩阵验证齐备，任何未验证或不支持范围明确列出。
