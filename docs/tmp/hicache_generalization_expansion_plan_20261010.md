## 1. 这轮要回答什么

现在的 60 格已经全部低于 10%，但它们来自三个专门设计的高敏感 workload 和五个配置。
下一步不是继续把这张表拟合得更漂亮，而是验证：换成真实对话输入、换成没验证过的 HiCache 参数组合，
同一套结构规则和成本模型还能不能工作，精度是否还能保持。

本计划将用户所说的“SharedGPT”按通常使用的 **ShareGPT** 理解。若指另一份数据，执行前替换数据来源，
其他实验边界不变。候选来源为 [ShareGPT_Vicuna_unfiltered 数据集](https://huggingface.co/datasets/anon8231489123/ShareGPT_Vicuna_unfiltered)。
具体使用哪个文件、其使用条件及清洗情况在准备阶段确认，不把不同清洗文件混成同一个数据来源。

目标分为三层：

1. 新负载：仍用原五个配置，验证真实文本和新的长度分布。
2. 新配置：保持模型与硬件不变，验证新的容量、门槛、等待和策略组合。
3. 换 base：不能只证明 C5 好用，再选两种不同策略的配置作为 base 做交叉核对。

正式预测始终是：**某个配置在某个 workload 上的 base profile → 同一 workload 上其他配置的预测**。
这轮不宣称可以只采 W1，就直接预测没有 source profile 的 ShareGPT workload。

## 2. 起点与边界

10-08 的当前对照：60/60 完成，WAPE 3.351%，P90 7.740%，最大 APE 8.483%，44/60 小于 6%。
完整 HTTP E2E 包含 gap、未归属成本和 Prefill/Decode。资产与已知限制见 [工作进展](../work_progress.md)。
起始成本包为 `data/modeling_runs/e2e_accuracy_20261008/normal_io_cost_package.json`。
它已经纠正预取校准的测量口径，但资源争用、残余调度间隔和成本覆盖仍有限制。
达到旧矩阵的 10% 目标，不等于新场景必然达到同样精度。

首轮固定 Qwen3-32B、TP=2、现有 SGLang/Ascend 实现、file 存储、page-first 布局和资源绑定。
请求串行，单个活跃请求，保持现有 eager、非投机、非量化和非 chunked-prefill 路径。
不在这一轮同时改变模型、TP、推理框架、存储后端、图回放或并发度。
这些变化会引入新的结构规则或部署域，不能靠多采几个成本点就声称支持。
KTransformers 与 NodeScale 保留，但不参与本轮 HiCache 扩展，NodeScale 继续关闭。

## 3. ShareGPT 怎样成为可复现的 workload

### 3.1 三类输入，分别回答不同问题

| 负载 | 构造方式 | 主要检查什么 |
| --- | --- | --- |
| 独立请求混合 | 从不同对话取用户请求，按输入长度分层选样，保留真实文本与 chat template | 没有强缓存复用时，计算和固定开销能否泛化 |
| 多轮上下文 | 从同一对话构造逐轮扩展的历史上下文，再交错少量不同会话 | prefix 命中变化后，Prefill/Decode 和缓存工作是否正确 |
| 会话交错与回访 | 多个真实会话交错推进、间隔后回访；请求内容不变，调度顺序明确声明 | 容量压力、驱逐、回载和预取能否泛化 |

每类先选约 16–24 条正式请求，形成一个规模可控的负载；另列准备请求。
覆盖当前合法容量内的短、中、长输入和不同输出长度，不为了让所有样本都成功而静默裁切文本。
以实际 tokenizer 结果判断长度，具体区间在统计数据与最小目标容量后确定，不凭字符数估算。
样本选择不得参考预测误差。清洗、排除、截断及输出长度控制都要列出数量和原因。

独立请求不必强行制造缓存命中；若它不触发 HiCache I/O，就作为计算泛化对照。
会话回访属于明确构造的缓存压力变体，不把它冒充原始用户请求分布。
若这三类仍未触发存储回载，不按 target 实测结果逐格重排；如实说明覆盖不足，
保留原 W1–W3 的 I/O 压力验证，不额外插入一个 micro-workload 阶段。

### 3.2 请求内容与回放

使用部署模型的 tokenizer/chat template 渲染真实消息，保存原对话 ID、轮次、输入 token、输出上限和请求顺序。
token 数组和正文属于运行资产，不放进版本库；不得执行数据集内容，也不将正文当成工作指令。

数据集中的 assistant 文本可以作为明确给定的历史上下文，但不当成当前模型已经生成过的输出。
需要真实生成结果参与下一轮上下文时，在一次 token 捕获中记录并固定完整会话输入。
按实际 token 的共同前缀核对缓存复用，不假定套上 chat template 就一定共享全部历史 token。

首轮用一次无 profiler 的 token 捕获取得各 workload 的生成序列，全部配置回放同一输入和输出计划。
normal HTTP 真值也使用相同计划，但关闭 profiler、hook、Python probe 和诊断计时。
输出长度按 workload 明确声明；不能用 ShareGPT 原回答的长度当成当前模型实际生成长度。
本轮成绩是受控 token 回放下的完整 E2E 泛化，不冒充随机采样、自然 EOS 或并发用户流量的精度。

### 3.3 尽量复用现有工作流

现有 `workload_template` 已支持 `prompt_token_ids`、正式窗口、token 捕获和回放。
优先增加一个薄的数据转化能力，将选中对话转为现有请求计划，不另造 profiling/modeling 主流程。
新能力放在现有 workload 模块，复用 `scripts/bench/hicache_template_workload.py` 的正式入口。

现有模板还有 anchor/tail、准备 checkpoint 和配置状态断言等高敏感实验合同。
执行前区分哪些是通用要求、哪些只适用于人工 workload：真实对话不能伪造 anchor/tail 或 C1–C5 状态断言来过关。
必要时在同一模块明确“普通真实请求”和“有状态压力实验”两种输入语义，保持核心执行、正式窗口和报告共用。
不简单关闭所有校验，也不增加三套近似相同的 runner、日志和报告。

## 4. 新配置怎么选

先新增 **六个 HiCache 配置**，避免把所有参数做笛卡尔积。具体数值在输入与成本覆盖核对后写入声明配置。
配置选择先于 target 实测；只依据框架合法范围、workload token 统计和已有成本测量范围。

| 新配置方向 | 选取原则 | 要验证的变化 |
| --- | --- | --- |
| 较宽裕的 device 容量 | 选一个与原配置不同、能覆盖最大单请求的合法页数 | 少驱逐时是否正确减少传输和重算 |
| 较紧的 host 容量 | 合法且有明确缓存压力，不制造不可执行请求 | host 驱逐、存储回载及发布顺序 |
| 中间预取门槛 | 与 workload 共同前缀长度分布交叉，统一处理 token→page 单位 | 接受/拒绝边界，而不是只测原端点 |
| 短 timeout | 预先选定短于现有 2 秒的合法等待参数 | 部分执行、取消、可见页与实际 I/O 的区别 |
| 已有页宽的新策略组合 | 在 32/64/128 中选已有合法页宽，组合原来未验证的写策略和预取策略 | 参数分别已见过，但联合执行分支未见过 |
| 合法范围内的成本外推 | 选择一个超出已测工作量范围的容量/请求组合，保持结构路径受支持 | 外推是否可用，以及不确定性有多大 |

如果某项没有独立作用或与其他配置等价，执行前替换，不为凑六个而重复配置。
首轮不新增页大小 ABI、存储后端或禁用整个 HiCache；这些需要单独确认生成规则和运行合同。
launcher 参数与预测中的 resolved 容量必须一致，记录页数、token 容量及对齐规则，
不能照搬原实验的 capacity limit 或用名称推测容量。

所有配置分清两件事：结构规则是否支持；成本变量是否在已测范围内。
变量各自在范围内但组合没测过，属于“未见组合”，不能直接记作“已有覆盖”；
确实超范围的配置另列外推结果，不能混入已测范围成绩掩盖失败。

## 5. 实验面板：扩大覆盖，不先扩大成全量 cross

主 base 暂沿用 C5，以复用现有输入并保持对照；这不是算法里的 base 特殊分支。
另外选择 C1、C2，分别核对不同写策略与容量下的 base 依赖。

| 面板 | 预测选择 | 新预测数量 |
| --- | --- | ---: |
| 新 workload、原配置 | C5 在三个 ShareGPT workload 上预测另外四个原配置 | 12 |
| 新配置 | C5 在原 W1–W3 加三个 ShareGPT workload 上预测六个新配置 | 36 |
| 换 base 核对 | C1、C2 各在三个 ShareGPT workload 上预测四个代表 target，均排除自身 | 24 |
| 合计 | 不含 self，也不重复计入原 60 格 | 72 |

换 base 的四个 target 在评分前选定，覆盖等待/不等待、写回及新容量/timeout，
尽量与主 base 面板重合，以比较同一 target 真值；不从误差表挑对自己有利的 target。
不立即跑 11 配置 × 10 个其他配置 × 6 workload 的 660 格全 cross。
原 60 格保留为对照；若修改公式或执行规则，收口后才重跑它，不能只引用旧成绩证明当前代码没退步。

新增采集规模的上界估计：九份 ShareGPT base 完整 profile，加九份同源轻量回放；
新增正常真值最多 51 个配置/workload 组合，每个先测两次，共 102 次；
另选约 6–8 个 target 完整 profile，只用于实验结构诊断，绝不入库。
51 个组合来自“原五配置 × 三新 workload”加“六新配置 × 六 workload”；实际面板无需的组合不采。
重复 target 真值由多个 base 预测共享，不能每条 source→target 都重测。
token 捕获、准备请求、正常重复、失败和补采分别计入预算；这些数量不是零成本承诺。
启动次数、请求/token、墙钟和磁盘预算在 A 阶段依据真实计划计算，不在本文件凭空定绝对 token 上限。

## 6. 校准与数据隔离

第一轮先用现有成本包，关闭自动成本补采，记录缺口和外推。这回答“现在这套模型能走多远”。
新增 base 只用于自己的 DAG、同源 CPU 校正与可迁移成本，不能自动入库训练。
ShareGPT 的评估对话、target 正常运行和结构 trace 都留出；独立校准与评估对话按完整会话分开，
不能只换请求 ID，仍复用同一会话前缀或完整/轻量配对的另一侧。

只有缺少操作测量或合理外推也不足时，才安排少量独立共享校准：

- 按操作、shape、页工作量和部署条件合并全组需求，不按某格误差生成配置。
- 结构缺口先补执行规则；缺变量先补工作描述；不是所有失败都能靠补采修复。
- 新测量经现有 `cost-db import/train` 离线发布，明确排除本轮所有 base 和评分来源。
- 预取倍率仍只接纳匹配轻量测量，不能重新引入带 profiler 的墙钟放大。
- 同部署适用的证据跨 base/target 共享，不为每格维护成本包或专用系数。

首轮已经暴露的范围缺口不只涉及 I/O：短上下文低于旧测量下限、阻塞检查一次确认更多写回、
以及一次回载多个 radix 节点也需要依据。page64/page32 的小写入采集同时核对短上下文计算覆盖；
另准备一份真实对话的共享容量压力输入，检查批量确认与多节点回载，不按 target 名称另造实验。
只使用预选独立会话，保留正文和 tokenizer 结果，不裁切或伪造前缀。输入预期能触发的分支不等于实测覆盖；
若现有补采后这些缺口已消失，不运行额外压力采集。缺口仍在时先保留原预测终态，再串行执行独立采集。
小写入共享输入另回访五条已选真实请求，在已有 page32/page64 采集中同时测量缓存命中后只剩少量 token 的 Prefill；
不裁切文本、不按 target 耗时选样，也不追加单独的 micro-workload 阶段。实际小计算覆盖仍以测量和查询结果为准。
预期的小写入五阶段为 75 请求、6,730 tokens；额外压力三阶段为 48 请求、24,573 tokens。
这些是新增预算声明，实际启动、失败及重试另按 manifest 累计，不覆盖原首轮预算。

共享压力测量已覆盖两节点回载，但最终执行仍需要三节点回载和更大的 page32 写入。
复用预选的独立会话准备一份共同输入，按 token 捕获、完整采集、轻量配对串行执行：
预计 3 次启动、30 请求、41,034 tokens，实际分支覆盖以提取结果为准。
该输入不读取 target trace 或正常耗时，所获数据由所有 base/target 共用，不增加逐格参数。

实际提取后，上述输入覆盖三节点回载，但最大回载索引仅 61 页、可测写入提交仅 58 页，仍少于预测需要的 62 页。
原 20 条校准候选也没有更长的合法完整输入；因此从原固定种子的 4,096 条扫描中，
按 1,984–2,016 输入 tokens 选择一条尚未使用的真实会话，不改评估或最终确认留出。
与已有独立会话组成“大请求、容量压力、回访”的三条正式请求，输出固定为 8 tokens；
包括预热，token 捕获、完整与轻量配对预计共 3 次启动、12 请求、17,373 tokens。
该校准使用 65 个 device 页和 162 个 host 页：1,986 个输入 token 向上对齐为 2,016，
还需保留一个 32-token 调度页及 8 个输出 token，因此 device 容量声明为 2,080 tokens，
而不是只有 2,048。容量压力仍由另一条独立请求产生；不裁切文本或接受零输出来绕过准入。
这是补操作工作量证据，不按 target 耗时挑输入，也不增加独立 micro-workload 评分阶段；
62 页及通信间隔的实际覆盖仍须提取核对，不能因输入已准备就宣称缺口消失。

重训后的代表查询还需单页 radix 索引复制，以及较长空闲页向量的拼接测量。
复用原独立候选中的真实多轮会话和两个容量压力输入，组成四条正式请求；
按 token 捕获、完整及轻量配对执行，预算为 3 次启动、15 个含预热请求、11,832 tokens。
device 为 62 页、host 为 155 页、输出为 8 tokens，不修改评估或确认留出。
释放准备不访问原空闲页向量，不再用该向量长度限制准备段，实际拼接段仍受长度范围约束。
实际拼接的当前常数近似允许仅空闲页向量长度外推，并保留域外标记；
本轮最大页向量为 112 个 int64 元素（896 字节），仍是两个一维输入。
释放页数、页宽和排序条件继续按实测范围限制；不把此小向量近似推广为任意规模拼接的模型。
固定 BF16 logits all-gather 的独立样本覆盖 17 份采集，完成服务采用常数近似；
只允许 `arrival_span_us` 超出测量范围，并保留外推标记。载荷、行列几何、dtype 和 TP 仍受约束，
这种错峰外推不是新测量，也没有精度保证；等待继续由跨 rank 依赖表达，不能并入通信服务。

最终换 base 预测还暴露了单 token Prefill 的 Q/K reshape 视图分支。它只改张量元数据，
不能沿用多行 clone 的设备成本。已有 page32/page64 共享小写入采集各自包含这条分支，
数据库中 CPU 服务与残余间隔各有 768 条观测；先补充两项常数模型声明，不新增采集、不使用 target 耗时。
行数、头数、头宽和行步长仍限定适用域，不把“一行不复制”的测量推广到需要复制的多行路径。
发布后核对既有模型及 I/O 参数是否变化，保留失败终态，并复验受影响的换 base 面板。
小向量拼接的显式长度外推还须覆盖派发间隔：最终 page32 回访查询暴露该口径遗漏了原规则。
统一 caller、dispatch、worker 与 device 的范围声明，仍不放宽释放页数、页宽或排序路径，也不改已有系数。
主 base 的回访负载也遇到同一缺口；可仅复验实际失败格，独立评分通过显式
`--retry-prediction-dir` 替换未完成格。不得替换已完成格挑选更好结果，原 72 格分母不变；
原失败证据保留，所有选定格补齐后才检查正常重复和打开 target 结构。

分别保留“没有新校准”的首轮成绩和“补充共享独立数据”的成绩，不把后一种说成原模型直接泛化。
如在看过验证误差后修正模型，明确该批变成开发验证数据；另外预选新的留出对话，
用未看过结果的样本作最终复验，避免同一批数据反复修改后仍宣称首次泛化。
不引入内部版本号、checksum、冻结副本或验证握手；记录输入路径、测量来源和实际命令即可。

## 7. 分阶段执行

### A. 输入与支持范围核对

确定数据文件与使用条件，统计长度、对话轮数、共同前缀、容量需求，完成六个新配置及留出选择。
确认模板是否能表达真实请求，列出必须调整的合同与现有成本覆盖。
输出样本选择说明、请求计划、目标声明和采集预算。此时不采全矩阵，不改成本系数。

### B. 打通一个真实负载

先选一个较小的多轮负载和两个语义不同 target，经公开入口完成 token 捕获、base 完整/轻量配对、
DAG 构建、预测及正常 HTTP 评分。检查请求身份、共同前缀、正式窗口和缓存初始化状态。
有需要的代码改动按职责链联合完成，不逐文件反复修补；只用正式入口和真实输入验证，不新增独立测试文件。

### C. 完成主 base 的 48 格

在输入与公式确定后完成两个主面板，先记录不补采的结果，再按实际缺口决定是否共享补充数据。
挑选 6–8 个结构代表格检查回载、部分预取、取消、发布与计算工作；
常规格不导出大 DAG，不对每格运行重型 oracle 诊断。

### D. 完成另外两个 base 的 24 格

使用相同成本包和相同 target 真值，比较换 base 是否造成系统性精度变化。
必要时增加一个尚未作为 base 的新配置作小范围反向验证，但单列追加规模，不默认启动全 cross。

### E. 收束

汇总新 workload、新配置、换 base 和外推四类结果，明确支持范围、失败原因和额外采集开销。
如代码/公式有变化，运行最终原 60 格回归；代码未变化时保留已有对照，不无理由重跑。
稳定结论合并到主文档。实施时仅在阶段收口或重大决策追加简短 log，不逐格记日志。

## 8. 验收标准

本轮目标沿用当前阶段：**支持范围内选定的每格完整 HTTP E2E APE 小于 10%**，争取向 6% 靠近。
按新 workload、新配置、base 和成本外推状态分别报告完成数、APE/WAPE/P90/最大值及偏差方向。
原有 WAPE ≤ 3%、P90 ≤ 5% 的正式门槛不改，不能因为本轮 10% 达标就把 MODEL_LIMITATION 改称全面通过。

所有计划格都有明确终态；失败和缺成本不填零、不从分母删除。支持范围须在评分前确定，
不能因为一个 target 不准，就事后将它改称“不支持”。超范围外推的结果单列，包括失败。
正常重复两次取算术均值并报告范围；预先采用相同规则：若 `(最大值−最小值)/均值 > 3%`，
补测到五次并保留全部有效样本，不挑最接近预测的那次。设备干扰导致无效的判定要有运行证据，不能按误差判无效。

三阶段分别交代证据：source 静态回放；代表格 target 工作量/必要依赖比较；全部已完成格正常 HTTP 性能评分。
结构检查允许报告未知覆盖，但已确认的非法分支、错误页数或丢失依赖必须解决，不能用整体误差小掩盖。
全程不排除 gap、未归属成本、Prefill/Decode；完整 HTTP 不等于图中后台工作全部结束。
