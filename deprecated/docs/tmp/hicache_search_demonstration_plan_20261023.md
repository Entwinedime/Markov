## 1. 这次要拿出什么结果

10 月 15 日汇报的第 16 页，以及 `ppts/Screenshot 2026-10-23 at 2.52.53 PM.png`，约定了两个阶段：

| 时间 | 汇报中约定的工作 | 本计划的对应交付 |
| --- | --- | --- |
| 10/14—10/27 | 确定搜索参数、范围和约束，实现初步搜索，筛选候选配置 | 在有缓存复用、竞争和预取的负载上，完成有实际差异的搜索，拿出候选及第一轮实测对照 |
| 10/28—11/10 | 完善搜索方案，实测验证推荐配置的性能，完成自动寻优方案 | 扩展容量和页大小、确认推荐稳定性，再决定是否需要更复杂的搜索方法 |

当前的八点实验只证明入口、预算、恢复和正常确认能串起来，不能作为搜索有效性的主要证据。
它只有一个暖机、两个正式 ShareGPT 请求，每请求两 token；四个写回配置的预测时间完全相同。
继续在这组输入上比较算法，回答不了用户真正关心的问题。

这次要回答的是：

1. 在资源相同的情况下，不同 HiCache 策略到底有没有值得搜索的性能差别？
2. 从一个 Base 出发，模型能否把值得真实运行的候选挑出来，而不是把所有 target 都采一遍？
3. 推荐配置的实测是否优于原配置，与已测候选中的最好结果差多少？
4. 预测和少量确认要花多少时间，相比真实运行全部候选，实际省了什么？

不预设一定有某个百分比的提升。若当前负载不敏感、推荐不稳定或模型排错，要把原因讲清楚，不能换几组输入直到找到好看的结果。

## 2. 首轮范围：先把问题限定得有意义

### 2.1 固定部署，公平比较资源

沿用当前已经有执行规则和独立成本依据的 SGLang、Qwen3-32B、TP=2、Ascend、eager 和文件存储部署。
设备、CPU/NUMA 条件、后端、模型、请求顺序、输入及实际生成 token 固定。
HiCache 开启；本轮不是模型、TP、并发度或框架搜索，也不改变仿真粒度。

主实验以 `C2_host_cliff_selective_wait` 的资源和策略作为 Base：

- 页大小：64 tokens/page。
- 设备缓存：48 页，即 3,072 tokens。
- 主机缓存：64 页，即 4,096 tokens。
- 原策略：选择性直写、等待预取完成、门槛 4 页。

选择它是因为已有 Base/CPU 输入，而且缓存资源有限，适合研究策略取舍；不是因为它在事后实测中最慢。
所有主实验候选使用相同设备与主机缓存容量，不把增加内存得到的收益归给搜索算法。
Base 本身在候选空间内，self 结果只计算一次。

配置解析合法不等于实际不会 OOM。需要同时报告实际资源条件、运行失败和结构/成本缺口。
旧 recipe 中声明的 CPU 集合不等于进程已经绑定；准备时核对实际运行环境，不用声明替代观测。

### 2.2 负载安排

| 负载 | 首轮用途 | 要观察的变化 |
| --- | --- | --- |
| W3：预取准入与回访手工负载 | 机制主实验，完整搜索 | 门槛与预取策略是否改变实际读回、等待和剩余 Prefill 工作 |
| ShareGPT 开发批回访 | 真实对话主实验，完整搜索及主要实测 | 缓存竞争后的再次访问，写入、读回与重算的取舍 |
| ShareGPT 多轮或另一批回访 | 后续迁移确认，只预测少量已选配置 | 推荐是否只适用于第一组会话 |
| ShareGPT 独立请求 | 可选的低复用对照 | 对不敏感负载是否能给出“不值得调”的结论 |

先复用 `data/reproductions/hicache/base_preparation.json` 登记的 C2 Base、对应 CPU 配对和实际 token 计划，
不为开始搜索重建整套 186 格，也不重新建库。W3 的短输出用于辨认缓存机制，不冒充真实长生成负载。

ShareGPT 要保留真实的多会话、访问间隔中的缓存竞争和回访顺序，不能缩成两个独立短请求。
已有输入只要完整且可在预算内运行，就不改动。确需缩短时，通过 workload 配置明确请求数和每请求输出上限：
以约 8—16 个正式回访请求、每请求 8—16 个输出 token 为起始量级，保留准备和竞争请求，另采对应 Base/CPU。
这不是代码中的固定限制，也不是要求无条件重采；缩短后的输入须先验证仍有预期缓存工作，再声明为一个新实验。

本轮使用过的会话只称开发/展示数据；历史“留出批”已经看过结果，不能再次称为从未见过的数据。
后续若声称未见会话泛化，需另选与训练、开发和旧确认都不重叠的会话，先确定选择方法与种子。

## 3. 搜索参数、范围和约束

### 3.1 主空间：固定资源下的 72 个策略组合

| 参数 | 首轮取值 | 为什么需要搜索 |
| --- | --- | --- |
| 写入策略 | `write_through`、`write_through_selective`、`write_back` | 写入时机与写入工作量不同 |
| 预取策略 | `wait_complete`、`best_effort`、`timeout` | 等待、后台读回与直接重算之间的取舍 |
| 预取门槛 | 2、4、8、16 页，对应 128、256、512、1,024 tokens | 避免只比较两个在当前请求上可能没有区别的门槛 |
| timeout 基础等待 | 0.01、0.1、0.5、2 秒 | 覆盖短等待、中间等待和较充分的等待 |
| timeout 每千 token 增量 | 固定为 0 | 首轮先减少自由度，让等待的作用容易解释 |
| timeout 上限 | 固定为 2 秒 | 不与基础等待独立笛卡尔积，避免无意义重复组合 |

timeout 字段只在 timeout 分支展开。因此实际配置数为：

```text
3 种写入 × 4 个门槛 ×（wait_complete + best_effort + 4 个 timeout）= 72
```

两个主负载各搜索同一组 72 个配置，共 144 次配置×负载预测，其中各有一次 Base self。
这是新搜索面板，不是原来的 60-cross 或扩展 72 格准确性面板。
不要求 72 个配置都产生不同时间；执行相同的点可以并列，但要说明哪些参数没有改变工作，不能硬排第一名。

这些取值写在实验请求中，不写入核心算法。启动参数、实际页容量、预取容量上限和条件参数沿用现有解释器。
主机页数必须大于设备页数；预取容量上限派生，不作为独立自由度。
高门槛可能使部分请求不再准入预取，这是重算对照，不要求每个配置都发生读回；相同预测也不能被当作重复配置删除。

### 3.2 页大小和容量：下一步扩展，不把资源收益混进首轮

首轮先把上面的同资源比较做实，再扩展页大小与容量；它们不是不支持，而是需要另一套公平比较口径。

- 页大小先考虑 32、64、128 tokens/page；比较页大小时保持设备/主机 token 容量相同。
- 容量先考虑设备 3,072/4,096 tokens、主机 4,096/8,192 tokens，剔除主机不大于设备的组合。
- 使用模型 KV 几何换算真实字节及每 rank/整机预算；不按页数相同就认为内存相同。
- 增加容量的结果独立展示“用了多少资源、换来多少时间”，不直接并入同资源的策略优劣排名。

现有 `space` 用页容量，与页大小直接相乘会改变总内存。扩展时按页大小生成独立请求，
由 token/字节预算换算页数，复用现有搜索入口，不为展示添加复杂的空间描述语言。
先在首轮选出的少量策略上做容量切片，不立即把所有参数全排列。

## 4. 实施顺序

### A. 先确认输入和搜索确实有东西可搜

一次完成输入、源工作和成本范围检查，再用不超过六个预先声明的边界候选做一批正式预测。
候选覆盖三种写策略，以及短/长等待、best-effort、高/低门槛，不能只重复最接近 Base 的点。

检查：

- Base manifest、CPU 配对、token 回放及资源部署是否适用。
- 源负载确有缓存复用/竞争，工作规则能展开不同预取、写入或 Prefill 工作，而不只是配置名变了。
- 边界候选是否出现缺成本、未支持分支或不可接受的外推；缺失保持缺失，不能填零。
- 单次源准备和目标执行耗时，据此估计完整 144 次预测的时间及内存占用。

先引用 `data/reproductions/hicache/costs/prediction_cost_model.json`，不为搜索重新训练；
不能把 `partial` 宣称为全面覆盖，逐候选保留外推和保留等待的说明。
发现共享成本缺口时，先在独立性能维护中补齐机制所需数据，再开始一轮新比较；不按 target 的实测误差补参数。

本轮边界运行发现了主机备份被拒绝、加载最终分配失败后返回，以及后续空索引拼接/请求更新这三种局部控制工作。
它们通过独立 CPU/控制原语补充，原有 I/O、Prefill/Decode 等响应不重新拟合；实际来源和累计失败写入任务协议与采集记录。
W3 写回边界的准备阶段分配失败已定位为公共引用归属错误：加载失败已释放的主机命中，又被请求重新保护。
按框架规则，请求只锁设备前缀，主机保护由实际 I/O 生命周期负责。修正后须重新验证并运行原空间，不能沿用旧规则下的成功值。
原 W3 失败格的 Release 与 Debug 已得到相同结果；ShareGPT 空索引返回补充了 42 条独立观测，
原有 1,709 个响应和 I/O 参数保持不变。ShareGPT 完整角点已补验成功，主空间在当前统一依据下重新运行。
继续对原定 72 点逐一尝试并保留其未知状态；有未知点时，只报告当前可预测集合中的候选，不能称为整个空间最优。
12 点正常参照与其他已选实测候选仍须先有完整预测，才能进入独立评分，不用缩小参照集合绕过缺口。

如果工作明明应当改变但预测始终没变，先定位规则/输入问题，不用扩大网格掩盖。
如果执行逻辑表明这些参数在某个负载上本来就不起作用，保留这一结论，并按预声明安排继续另一个主负载。
任何空间、输入或公式调整，都要在正常实测前记录原因，换用新的比较目录，不混用旧成功值。

交付：一份运行协议，写明实际输入、空间、成本依据、预算、正常参照集合选择规则和预计用时。
只使用普通参数与来源引用，不新增文件摘要、内部版本或冻结副本。

### B. 完成 72 点搜索，形成可解释的候选

对两个主负载分别枚举完整空间。首轮先获得模型内参照，不急于证明某种算法高级。
不把 W3 与 ShareGPT 秒数直接加权成一个掩盖差异的总分，先给出各自建议。

结果需要包含：

- 完成/缺成本/结构缺口/未评估的配置数，以及各候选完整参数。
- 完整 HTTP 预测时间、相对 self 的预测变化、并列候选。
- 写策略×预取策略的分布，门槛及 timeout 改变后哪些点发生了明显转折。
- 对少量代表说明“多做/少做了哪些 I/O、等待或 Prefill 工作”，不是列出一长串内部函数。

模型预测只说明值得测谁，不自动升级为推荐已经有效。缺成本或结构失败也可能落在真正的快配置上，
因此不能从成功子集宣称整个空间的最优。

### C. 用受控实测判断“有没有选对”，而不只展示预测条形图

第一轮就纳入有限的正常实测，不把所有有说服力的证据都推迟到 10/28 之后。
所有预测和确认集合先写出，再启动或读取正常 target 测量；确认不更新模型、不重排原预测名次。

**ShareGPT 回访：建立一个 12 点、可以完整实测的参照子空间。**

- 保持主空间的资源条件，固定门槛为 4 页。
- 三种写策略，分别配 wait-complete、best-effort、timeout 0.01 秒、timeout 0.5 秒。
- 共 12 个配置，包含原 Base；每个配置预声明五次有效正常运行。
- 另测完整 72 点搜索的前两名代表；若已在这 12 点内则不重复。并列时按固定空间顺序选代表，不用实测挑代表。

这样能回答两种不同的问题：在 12 点参照空间里是否选对；扩大到 72 点后是否找到比这组参照更值得使用的配置。
12 点均有实测时，才能谈这 12 点的实测最优，仍不能称为整个 72 点的真实全局最优。

**W3：确认推荐与机制对照。**

- 最多四个配置：Base、预测前两名代表、一个预测分数不同的竞争候选。
- 各做五次有效正常运行；重合项合并，所有并列预测继续保留。
- 若没有分数不同的竞争候选，明确写“当前模型未区分”，不捏造慢对照。

主轮正常测量最多为 `(12 + 2 + 4) × 5 = 90` 次成功运行，不是再采一遍 72×2×5。
默认新做同一轮对照；旧五次样本只作背景，避免把几天前的 Base 与新候选直接比较。
重复轮次采用预先固定的轮转顺序，让不同配置分布在各轮中，减少按配置连续采五次带来的时间漂移。
每次运行的缓存目录、初始状态和准备步骤一致，复用同一 token 计划；启动/暖机不混入 HTTP 正式窗口。

正常运行关闭 profiler、Python probe 和内建计时探针。采集严格串行；即使其他任务使用另一对 NPU，
共享 CPU/磁盘的干扰也要记录。不能擅自终止其他项目，资源等待单独计时。
本机已出现其他任务在采集中途重新启动、抢占设备 HCCL 端口的情况。example 在每次新采集前检查 NPU 应用，
有占用先等待，退出后再复核；已完成样本直接复用，等待单独累计。检查不能替代设备预留，竞态造成的失败仍须保留和计费。
保留所有有效慢样本；失败、OOM 和重试都记录，不因只对成功运行计算均值而隐去可用性问题。
五次样本不足以证明尾部延迟或可靠置信区间，不作这种承诺；结果接近或波动明显时报告未分出胜负。

这部分的候选选择比现有 `confirmation` 的默认 Base+top+competitor 更广。
12 点参照由显式公开 profiling suite 加独立 `evaluate` 完成，不绕过预测隔离，也不把自动确认模块当作已经支持任意选择策略。
评分用已有 `--target-config` 明确选择测过的候选，例如：

```bash
scripts/model.sh evaluate \
  --prediction-dir <completed-predictions> \
  --normal-http \
  --target-config <selected-target> \
  --profile-run-dir <normal-measurement-suite> \
  --output-dir <separate-evaluation-output>
```

多个候选重复传入 `--target-config`。不能对完整 72 点请求评分后，悄悄跳过没有实测的其余配置。

### D. 比较搜索效率，准备汇报

完整枚举给出本轮“模型内最好结果”。在同一份枚举结果上，回放现有枚举前缀、均匀随机、分层随机会选到哪些点：

- 总预测预算：6、12、24、36 次，均包含一次 self。
- 随机种子：17、71、2026、2027、2028，比较前确定。
- 比较找到的最好预测、相对完整枚举的差距、策略分支覆盖和种子间波动。

这里复用枚举分数，只评价选点效率，不伪装成重新运行了几十次搜索，也不把离线回放的几毫秒当成实际搜索用时。
另用一个主负载，从公开搜索入口真实执行一轮 24 次总预测预算的分层随机，记录源图准备、目标执行和搜索总墙钟。
它不查枚举结果选点；事后才与枚举比较。若它没有优于均匀随机，照实汇报。

暂不新增贝叶斯优化、遗传算法、常驻预测服务或自动在线调参。
只有出现“空间明显更大、单次预测足够贵、现有方法确实选不出好点”的证据，再讨论引入更复杂算法。

## 5. 怎么评价结果

主指标是推荐质量，不是跑了多少格。统一用完整 HTTP 正式窗口，不删除 gap、未归属成本或计算阶段。

| 问题 | 指标与解释 |
| --- | --- |
| 推荐是否更快 | 实测时间缩短率 `1 − 推荐配置实测均值 / Base 实测均值`；同时给绝对秒数、五次样本和范围 |
| 12 点内是否选对 | 在这 12 点中按预测选出的配置，其实测相对 12 点实测最短均值的差距；仅对这个子空间下结论 |
| 72 点搜索是否有额外价值 | 完整空间推荐与 12 点实测最佳的对照，明确整空间仍有未测配置 |
| 排序是否可信 | 正常测量明显可区分的配置对是否排对；重叠或波动大的点不硬排 |
| 时间预测有多准 | 实测集合的 APE、WAPE、P90、最大误差，以及沿用 Base 正常时间的参照 |
| 计算是否值得 | 当前预测调用数与墙钟、Base/CPU 取得成本、正常确认成本、失败/等待；各项分开记录 |

既有精度标准仍按 `docs/validation/hicache_validation.md`：WAPE ≤ 3%、P90 ≤ 5%，cross 优于沿用 Base 正常时间。
该 gate 只适用于实际测量的那组配置，不用它宣称整个未测空间都通过。
搜索选择好坏和绝对时间准不准分开报告：有可能时间偏了一点但选对，也可能总体误差小却把接近的配置排反。

争取至少在一个真实缓存复用场景里得到可重复、量级约 5% 或以上的实际时间缩短；这只是有展示价值的努力方向，
不是允许删慢样本、换 Base 或改 workload 的通过条件。没有可确认收益时，只交付候选与限制，不声称“有效寻优已完成”。

已有 18.785% 最大误差的根因尚未确认，不能称为已解决。搜索不是借机把这格补成好成绩；
也不要求先把 186 格的每个精度问题解决才能开展首轮搜索。推荐若依赖高外推或保留等待，必须明确提示风险。

## 6. 汇报材料要能直接回答问题

首轮结果整理成一份结论文档及四组可放入 PPT 的图表，不在本阶段重做整份汇报：

1. **搜索什么。** 一张参数/资源/负载表，清楚写出 72 点怎样组成、哪些参数固定。
2. **为什么值得搜。** 两个主负载的性能分布或热力图，配一个机制代表，说明策略改变了哪些实际工作。
3. **是否选对。** ShareGPT 的 12 点预测与正常实测图，叠加完整空间推荐；标出 Base、候选和测量波动。
4. **花多少代价。** 预测次数—最好结果曲线，以及实际准备/预测/确认用时表，不把推算加速比当成实测。

展示顺序是“同资源下存在选择空间 → 模型筛出候选 → 实测检验选择 → 还需扩展什么”，
不是目录调整、成本包管理或搜索接口功能清单。

不拿旧八点结果替代新实验；旧 PPT 的历史分数不改写成本轮成绩。
少量确认只能说明已测条件有效，不说任意模型、平台、并发负载都能自动寻优。

## 7. 时间、预算和实现边界

| 时间 | 优先完成内容 | 收口标志 |
| --- | --- | --- |
| 10/23 | 输入和机制核对、边界候选、运行协议与估时 | 确定两个主负载可以进入搜索，不再围绕小型入口验证打转 |
| 10/24—10/25 | 两个 72 点完整预测、候选确定、启动预声明正常对照 | 有完整预测分布、候选与明确未完成项 |
| 10/26—10/27 | 正常对照收口、选点效率比较、一轮真实预算搜索、图表 | 能展示实际配置选择结果及其证据，不只展示程序完成 |
| 10/28—11/10 | 页大小/容量切片、未见会话、推荐稳定性与自动流程 | 完成后续寻优方案，不在首轮提前声称完成 |

时间是按资源可用安排的工作窗口，不保证设备被其他任务占用时仍按日历结束。
参照历史正常采集合计 502 次约 23.43 小时，90 次粗估约 4.2 小时采集生命周期；
这不是本轮承诺，不含额外输入准备、重试、等待或全部预测用时。A 阶段用实际输入测出的耗时更新估计。

预算初稿：

- 普通预测用 Release，`diagnostics=off`，目标 worker 从 2 开始；内存不足则降低并行度。
- 主面板 144 次，额外真实预算搜索 24 次；边界试运行及失败另记，不混入这些成功数。
- 搜索总墙钟初设 8 小时；先完成主面板，不为了比较算法反复构建同一大图。
- 正常采集初设 8 小时、最多 100 次启动，覆盖至多 90 个成功样本及有限失败余量。
- 请求数与 tokens 预算由选定的 workload/token 计划逐项计算，不能只填启动次数，也不借用其他任务账本。
- 若需重采 Base/CPU 或共享成本，单独列准备预算，不重置已有用量，不默认重采整库。

预算到限时保留已得证据并报告缺项，不通过重置账本继续跑；按实际剩余工作一次性调整下一批预算，不逐次追问上限。

优先复用：

- `applications/search/{request,space,algorithms,workflow,results}.py`：空间、选点、预算与预测结果。
- `modeling/predictor.py`、`preparation/`：原有统一预测和输入准备，不另做搜索专用模型。
- 公开 `profile`、`evaluate`：正常确认与独立评分。

新增内容以本次请求、正常 suite、结果整理为主；若需要一次性编排，放在 `examples/`，只调用公开入口。
不新增独立测试文件、不改成本公式凑收益、不逐候选建模板、不重跑全 186 格作为普通展示检查。
确有公共逻辑缺陷时单独说明修复范围，完成相关静态检查、必要构建和关键真实输入验证后，重开受影响比较。

本轮编排位于 `examples/hicache_search/`，复用本轮协议及已登记输入，不是从空目录准备平台性能库的新入口。
边界预测完成并核对后，依次运行：

```bash
bash examples/hicache_search/run.sh search --root data/search_runs/hicache-demo-20261023/request_ownership
bash examples/hicache_search/run.sh select --root data/search_runs/hicache-demo-20261023/request_ownership
bash examples/hicache_search/run.sh normal --root data/search_runs/hicache-demo-20261023/request_ownership --dry-run
bash examples/hicache_search/run.sh normal --root data/search_runs/hicache-demo-20261023/request_ownership
bash examples/hicache_search/run.sh evaluate --root data/search_runs/hicache-demo-20261023/request_ownership
bash examples/hicache_search/run.sh budget-search --root data/search_runs/hicache-demo-20261023/request_ownership
```

`--dry-run` 仅用于 normal 的采集计划。恢复只沿用本次未变依据，已完成正常样本不重采，累计失败及耗用不重置。
选点比较和预测空间图使用 `PYTHONPATH=scripts/internal python3 examples/hicache_search/report.py --root <任务目录>`，
不依赖 target 正常测量；最终正常结果及推荐收益另在实测结束后整理。
实测与独立评分完成后，为同一命令追加 `--normal`，生成正常样本图和 `results.md`。
热力图保留缺预测的格子；选点曲线遇到不完整空间时，参照仅是已有预测中的最小值，不能给未知点填分数。

## 8. 资产、日志与完成条件

执行资产放在一个新的 `data/search_runs/` 任务目录，保存运行协议、输入引用、正式搜索摘要、正常样本、评分及图表来源。
不覆盖 `data/reproductions/hicache/`、10/22 的分层/搜索结果或最大误差排查证据，不删除原 token、成本及 CPU 配对。

执行开始后使用 `docs/tmp/hicache_search_demonstration_log_20261023.md` 记录阶段收口、重大选择和必要交接，
每阶段至多一条摘要；不为每个 cell、轮询或普通检查写日志。收口后把稳定结论并回主文档，计划与过程记录按项目规则归档。

首轮完成必须具备：

- 明确、资源公平的搜索空间和两个不等同于短请求 smoke 的主负载。
- 两个 72 点搜索的完整状态，以及可解释的候选；有缺口就注明未完成，不把成功子集当全空间。
- 预声明的正常对照完成，能判断推荐相对 Base 及 12 点参照的表现；失败和波动没有被藏掉。
- 有一轮真实预算搜索和同口径的选点比较，能区分模型内参照、正常实测与估算代价。
- 有可直接用于汇报的图表、来源和结论，且对推荐是否有效作出明确回答。

“入口跑通”“新增几百个配置”“所有候选都有预测值”都不能单独作为搜索有效性的验收。
若没有确认收益，流程与实验可以收口，但有效自动寻优仍未验收，后续针对证据定位原因，不能用措辞替代结果。
