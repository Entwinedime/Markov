## 1. 要完成的研究

研究问题是：**在给定资源和有限调优预算下，能否从一次 Base 采集出发，预测 HiCache 策略引起的执行变化，
用明显少于直接试遍配置的真实运行，找到适合当前负载的配置，并在新的会话上保持收益？**

这里的“完整”指有明确输入、搜索、确认和退出结果的完整流程，不指对任意平台、模型、并发条件都适用，
也不指有限预算搜索能够证明全局最优。

首个研究范围仍为 SGLang、Qwen3-32B、TP=2、Ascend eager、kernel_ascend/page_first_direct/file，
串行、单活跃请求；模型、CPU/NUMA、设备及存储放置在一次比较中保持一致。
本阶段优化的是已给定代表请求序列上的完整 HTTP 正式窗口，不把结果扩写成在线任意生成、生产并发或吞吐量寻优。
实际生成 token 在 Base 准备时记录，预测及正常对照回放相同序列；未知 EOS 和未来用户输入不属于已解决的问题。
保留既有 SGLang/KTransformers 同级框架能力及默认关闭的 NodeScale，不借本轮搜索重写共享核心或再次开展全仓重构。

完整流程应当是：

```text
用户提供部署、Base、代表负载、资源约束和调优预算
  → 准备 Base DAG 与适用独立成本依据
  → 在合法策略空间内预测、搜索，给出模型推荐和候选
  → 可选的少量正常试跑选定最终候选
  → 独立的新样本确认收益
  → 输出建议配置，或保留原配置并说明原因
```

应用时用户不需要构造准确性矩阵，也不需要自己挑出 candidate 编号、编辑正常采集 suite，再拼接评分命令。
平台性能数据的维护仍是独立主线；不能把每次应用都重新建立性能库作为自动寻优的隐含前提。

## 3. 研究问题与可被否定的假设

| 问题 | 待验证的假设 | 什么结果会否定或削弱它 |
| --- | --- | --- |
| R1：是否确实需要按场景选配置？ | 复用距离、前缀长度、缓存压力改变时，等待、重算、写入与页粒度之间存在有意义的交互 | 所有场景都由同一固定策略取胜，其他参数影响小于波动 |
| R2：模型是否帮助选对？ | 由目标 DAG 推演得到的推荐，在新会话上接近已测参照最优，并优于开发阶段选出的固定策略 | E2E 误差不大，但推荐持续输给固定策略，或遗漏关键执行分支 |
| R3：是否减少真实调优代价？ | 在相近选择质量下，模型辅助方法需要更少的设备试跑，且在合理重复次数内收回总调优成本 | 少采了 target，但 Base、建库、仿真和确认使总成本更高且难以摊销 |
| R4：结论是否稳定？ | 在新的会话、预声明的资源条件和其他合法 Base 下，推荐质量不会出现明显退步 | 只对旧回访序列、某个 Base 或一个资源点有效 |

本轮不预设发明新的通用搜索算法。研究贡献首先来自对配置变化的可解释预测及其决策价值，
其次才是利用执行机制改进搜索效率。若成熟随机或贝叶斯方法已经足够，应保留它们，而不是为算法命名增加复杂度。

## 4. 三类信息分开：决策变量、场景条件与模型输入

“feature”在这里容易混淆，应区分以下三类：

| 类别 | 例子 | 从哪里来 | 如何使用 |
| --- | --- | --- | --- |
| 可调决策变量 `x` | 页大小、写策略、预取策略、门槛、超时参数 | 合法配置与本轮空间声明 | 搜索实际改变它们 |
| 场景条件 `z` | 资源预算、请求顺序、前缀共享、复用距离、输入/输出长度、I/O 环境 | 用户输入、Base 和独立平台测量 | 用于定义任务、解释推荐为何变化 |
| 成本模型工作变量 | 传输字节、页数、操作 shape、上下文长度、参与者数 | 目标工作与依赖推演 | 由独立成本模型估计各操作时间 |

不能把 workload 名称、cell 编号、target 实测时间或“这个配置曾经快”作为成本模型变量。
预测执行中得到的读回量、重算量和资源占用可以帮助解释候选，但不能倒过来用 target 观测生成预测结构。

### 4.1 容量首先是资源条件

首要实验在**相同设备缓存和相同主机缓存额度**下选策略，不开放“无限加内存”这一条捷径。
同一资源点内，各配置按同一实际 KV 几何比较 token 容量和字节预算，不按页数相同就认为资源相同。

资源实验与策略实验分别回答：

- 给定资源：哪种策略更适合这个负载？
- 给定完成时间要求：至少需要多少资源？
- 资源增加：能减少多少耗时，在哪个位置开始收益递减？

若容量增大始终有利，且资源没有代价或限制，选择上界就是这个问题的自然答案。
这可以作为测量结论，但不能包装成具有复杂决策价值的寻优贡献。
也不能事后添加任意的“内存价格系数”，故意制造一个中间最优点。

设备 HBM、主机 DRAM 和 L3 存储分别记账，它们不是可直接相加的同一种预算。
L2 是主机缓存，L3 是 file 后端存储；增加 L2 额度不等于加快 L3，L3 存储上限也不进入本轮核心决策变量。
没有实际配额或淘汰机制支撑时，不把磁盘空间容量虚构成可预测的性能旋钮。

10/27 按现有启动记录补充资源口径：本轮保持相同的是可用 KV token/载荷容量，未修改原配置。
当前实现还给设备 KV 分配一页 dummy buffer，32/64/128-token 页分别增加 4/8/16 MiB 每 rank，不能声称所有页宽的实际分配总字节严格相同。
权重加载、对齐和可用内存分别记录；严格相同全进程 HBM/RSS 上限属于不同约束，本轮不冒称已完成。
推导与 64/128 页已有正常启动复核见研究目录的 `verification/cache_resource_accounting.json`；32 页正常记录在有限参照完成后核对，不为此额外补采。

### 4.2 核心变量必须有相反方向的作用

下表是待检验的机制解释，不是保证出现某种曲线的实验结论。

| 决策变量 | 可能得到的好处 | 可能付出的代价 | 重点检验的交互 |
| --- | --- | --- | --- |
| 页大小 | 更少的页操作与元数据处理，较大的传输粒度 | 前缀匹配取整、内部碎片与无效搬运可能增加 | 页大小 × 前缀边界 × 门槛 |
| 预取门槛 | 低门槛增加可尝试复用的前缀 | 小量无收益读回、主机页预留和控制工作可能增加；高门槛又会增加重算 | 门槛 × 复用长度 × 缓存压力 |
| 预取停止策略 | 等待可避免重复计算，及早停止可减少阻塞 | 等待延迟请求，停止过早增加 Prefill 工作 | 停止策略 × 读回速度 × 重算代价 |
| 超时长度及随请求增长的增量 | 给值得读回的长前缀更多完成机会 | 等待可能超过重算所需时间，也会影响后续请求的缓存状态 | 超时 × 请求大小 × 异步完成时刻 |
| 写策略 | 提前保留 KV，增加后续命中机会 | 额外写入与容量占用，或把写回工作推迟到淘汰关键路径 | 写策略 × 回访距离 × 淘汰压力 |

参数不必每个都呈 U 形。研究上更重要的是：它们是否改变实际工作，作用是否依赖其他变量，
以及是否让不同场景出现可重复的选择差异。若某个轴不影响执行或被其他配置稳定支配，应报告并缩减它，不能为了数量保留。

SGLang 官方文档说明了预取停止、写入和页粒度的基本机制；这些机制为假设提供依据，但本仓库实际规则仍以本地实现为准。
[HiCache 设计文档](https://docs.sglang.io/docs/advanced_features/hicache_design)。

## 5. 优化目标与公平的参照

### 5.1 主目标

对一个给定负载 `w`、部署 `z` 和资源额度 `b`，寻找合法配置中完整 HTTP 正式窗口最短的一项：

```text
minimize    T_http(x, w, z)
subject to  device_KV_bytes(x) ≤ B_device
            host_pool_bytes(x) ≤ B_host
            当前框架和模型支持该页大小、布局与执行分支
            预测及设备试跑不超过各自预算
```

主实验把两项缓存额度固定在同一个值，而不是让各候选分别把资源加到自己需要的大小。
完整 HTTP 包含 HiCache I/O/control、Prefill、Decode、gap 和未归属成本；准备请求仍影响缓存与异步状态，
但其耗时不混入正式窗口。成本总量、I/O 服务时间和关键路径不能直接相加代替完整仿真。

### 5.2 三个“原配置”不能混用

- **采集 Base**：提供源 DAG 和未变工作的迁移成本，是建模锚点。
- **同资源参照**：在当前资源点上使用预声明的原策略，是比较策略收益的主要对照。
- **现有部署配置**：用户当前实际在用、且满足资源约束的配置，是应用回退时的选择。

当资源额度变化时，同资源参照可能是一个 target，而不是新的采集 Base。
允许复用一个合法 Base 预测多个资源点，但必须在每个资源点测量对应参照；
不能把更大缓存下的推荐和更小缓存下的旧 Base 比较，再把差额全归因于策略寻优。
现行 evaluator 的 Base 墙钟评分保持其原义，同资源收益由上层根据显式参照独立报告，不改写 source 身份。

### 5.3 资源扩展的第二个目标

在固定设备缓存下，对不同主机额度画出“资源—完整窗口耗时”的非支配结果，
并回答用户给定窗口时间上限时，哪一项已验证配置使用的主机资源最少。
没有达到上限的配置就报告无已验证可行解；不同维度资源不随意加权成一个“总成本”。

窗口耗时上限不是线上请求 P99 SLO。当前短串行序列不支持宣称生产尾延迟或 goodput 寻优已经完成。
多负载共用配置作为扩展实验：权重在开发阶段声明，比较相对同资源参照的归一化耗时，逐负载结果同时保留，
不让一项长负载掩盖其他负载的退步。预测中的归一化分母来自模型自身，不读取 target 正常时间。

## 6. 预声明的搜索空间

### 6.1 主策略空间：每个资源点最多 10,152 个配置

| 参数 | 本轮研究取值 | 约束 |
| --- | --- | --- |
| 页大小 `p` | 32、64、128 tokens/page | 支持性和成本域先验证；换页大小时保持 token/字节额度相同 |
| 写策略 | 直写、选择性直写、写回 | 三个真实执行分支 |
| 预取门槛 `q` | 128、256、384、512、768、1,024、1,536、2,048 tokens | 使用 token 口径定义，再换算为 `q / p` 页 |
| 停止策略 | wait-complete、best-effort、timeout | timeout 参数只在该分支生效 |
| timeout 基础等待 `b` | 0.005、0.01、0.025、0.05、0.1、0.25、0.5、1、2 秒 | 从几乎立即推进到较充分等待，使用分散的时间尺度 |
| timeout 每千 token 增量 `a` | 0、0.02、0.05、0.1、0.25、0.5 秒/1,024 tokens | 研究固定等待与随前缀长度增长的等待 |
| timeout 上限 `c` | 0.25、0.5、1、2 秒 | 和 `b/a` 联合解释，先删除完全等价的函数 |

超时函数是 `τ(n) = min(c, b + a × n / 1024)`。按所有非负 `n` 上的语义归一化：

- `a=0` 的常数等待只保留九个 `b` 值，统一用 `c=2` 表示；不因换一个无效上限重复计点。
- `a>0` 时，只保留 `b<c`。四个上限下分别有 5、6、7、8 个基础等待值，各配五个正增量，共 `5×(5+6+7+8)=130` 个函数。
- `b≥c` 的等待退化为已有常数，不重复生成。共 **139 个不同 timeout 函数**。

因此每资源点为 `3 页宽 × 3 写策略 × 8 门槛 × (wait + best-effort + 139 timeout) = 10,152`。
这是函数去重后的声明规模；若部署的合法工作范围还能证明部分参数完全等价，应继续合并并报告实际规模，不能用不可达参数凑足一万点。
这七个配置维度包含类别、粒度、准入、固定等待、长度相关等待和截止上限，不能仅靠“资源越多越快”得到答案。
这些值是实验声明，不是核心算法中的硬编码。空间生成保留超时三元组的关系，
优先将合法分支交给现有索引和预算机制，不为本轮增加庞大的空间描述系统。

阈值以 tokens 固定，避免改页大小时同时偷偷改变预取准入条件。
timeout 上限已经使两组参数对所有请求完全等价时，只执行一次；仅预测相同则继续保留不同配置。
不因在一个负载上碰巧没有读回，就删除该配置在其他负载上的身份。

当前空间还要求主机页数大于设备页数，这是本项目现阶段的支持合同，不把它说成所有缓存系统的物理定律。
页宽相关独立测量已有历史输入，是否覆盖本次实际操作仍须逐域核对；不能把“声明了一万点”写成“一万点已经可预测”。
预取容量上限继续遵循框架派生规则，不把未验证的内部常量加入搜索。
超时密度只是其中一部分；必须同时报告页宽、写入、停止策略和门槛的覆盖，不能只在同一机制分支上密集扫时间。

### 6.2 两个主资源点

| 资源点 | 设备 KV 容量 | 主机 KV 容量 | 用途 |
| --- | ---: | ---: | --- |
| 紧容量 | 3,072 tokens | 4,096 tokens | 承接现有实验，观察竞争和预留压力 |
| 较宽容量 | 4,096 tokens | 8,192 tokens | 检查策略是否仅在很小缓存中有效 |

各页宽按同一 KV 布局换算到实际字节；另外记录模型权重、工作缓冲、主机池对齐等实际资源条件，
不能把 KV token 额度冒称为整个进程的内存预算。HBM 与主机池分别核对每 rank 及实例总量。

资源前沿属于三天外的附加验证，固定设备 4,096 tokens，主机额度取 8,192、12,288、16,384 tokens，
先只在机制代表和已选策略上比较，不再把所有容量与全部轴全乘。
如这些容量缺乏有效对比或超出当前资源域，先明确缺口；不能自动换成更好看的容量点。

存储后端、NUMA 和 I/O 性能不在本轮主空间同时变化。
确需第二种 I/O 条件检验机制时，另声明真实存储放置和独立测量，不给原模型乘一个人为“慢盘倍率”。

## 7. 搜索与自动确认方案

### 7.1 先用简单、可解释的方法完成主线

以现有分层随机为基础对照，主方法采用“分支覆盖的初始点＋有限邻域改进＋重新起点”：

1. 检查资源与执行规则，准备 Base 和适用成本，记录本次搜索依据。
2. 先预测同资源参照；按页宽、写策略和停止策略覆盖初始点，初始数量计入总预算。
3. 从当前最好且机制不同的少量点出发，改变一个变量检查邻域：相邻页宽、相邻 token 门槛、相邻超时档或一个策略分支。
4. 加入预先规定的少量联合改变，如页大小与门槛、写策略与停止策略，避免只做单轴改进错过交互。
5. 连续两轮没有改善则换起点，或在预测次数/墙钟用尽时停止。每轮从尚未执行的邻域平衡抽取至多六点，不能一次展开全部邻域突破预算。
6. 保存原始模型排序、并列项、缺口与选中候选；未知成本和执行失败不赋予极慢分数，也不记零。

建议主运行预算为每任务 **96 次**“配置×负载”预测，比较其 24、48、96 次前缀下的模型内选择质量。
空间是一万点，实际搜索是预算内取点，不能把二者混为必须枚举一万次。
前缀曲线直接使用同一实际搜索记录，不能为画三个预算档重跑三遍；与实际真值的比较遵守第 8 节的范围。
一次 self、同资源参照、失败及重试均按实际发生计数；多负载每项分别计数，不把一个配置的多次预测算作一次。
小空间允许枚举，作为模型内参照。算法参数只在开发批确定，最终会话不用于修改初始点、邻域或停止条件。
预算小于分支数时按预声明规则均衡选取子集，报告实际覆盖，不能把 12 次预测称为覆盖了全部页宽/策略组合。

这种方法的价值必须靠实验判断，不能预先声称比现有随机搜索更好。
若在相同实际预算下没有优势，正式默认方法保留分层随机，仍完成自动确认流程，不继续堆叠优化器。

开发比较具体采用低复用/tight、竞争回访/roomy 两项任务，各运行均匀随机、分层随机、单变量邻域和联合邻域四种方法，
每项每方法最多 96 次预测，共最多 768 次；它们与六项最终任务的预算分开记录。
单变量方法保留相同初始覆盖和随机探索，仅关闭两个变量同时改变的邻域，避免把其他差异混进该对照。
先各用八次预测验证自动确认的完整流程；这两次开发检查不作为最终寻优质量证据。

### 7.2 候选确认和最终验证分开

模型排序结束后，先写出候选清单，再读取任何本任务的 target 正常结果。
清单最多六个不同的空间内配置，包含同资源参照、模型前两名、机制不同的两个近优候选，以及开发阶段选出的最好固定策略；重合项合并。
选择规则不利用 target 真值，不把低覆盖点静默当成差配置。
源 Base 在资源空间外时，另采一次正常源锚点以满足现有评分合同；不参与部署选择，不混入 target 最终均值，单独计费。

应用提供两种明确结果：

- **仅模型推荐**：不试跑，直接给预测首选和适用范围，标注未经实测确认。
- **正常运行确认**：允许预算内试跑；先各运行一次作候选筛选，再选定一个候选，与同资源参照各做五次全新的最终确认。

候选筛选样本不混入最终五次均值，防止“从偶然快的样本里选赢家，再用同一批样本证明它快”。
原始模型首选、试跑后选择及最终确认结果分别保存，不覆盖原预测排名。
试跑后选择不是新的预测精度，必须另外报告纯模型首选的表现。
普通应用的独立确认只要求最终候选与同资源参照；研究实验还确认纯模型首选和强固定策略，额外开销单列，见第 12 节。

正式候选筛选可以比较试跑结果，但不能据此打开新配置、重新拟合成本模型或改 DAG 规则。
最终独立 evaluator 的评分不再返回给搜索器；如果发现真实规则缺陷，先结束本次比较，再单独修正并开启新任务。

最终确认无法区分、未满足用户约束或运行不可靠时，输出“保留原配置/尚不能确认收益”，而不是强制推荐一个新配置。
失败候选单列，停止其剩余试跑并继续其他候选；候选在最终确认失败时，只完成参照的独立样本，不通过重试补成五次成功。参照或源评分基准失败则保留测量未完成，不伪造收益；同阶段历史失败在 resume 后仍保留。
原配置不满足当前资源约束时不能回退到它，应报告尚未找到已验证可行配置。
不自动修改长期服务、部署上线或终止其他项目进程。完整自动寻优在本阶段交付可执行配置及确认报告。

### 7.3 不确定性与失败

成本查询范围、未知分支、源等待近似分别说明。现有测量覆盖标记不是统计置信区间，
总体 WAPE 也不能直接充当任意候选的误差上界；本阶段不虚构 `预测 ± 6%` 之类的保证。
候选间预测差距小、排名不稳定或首选使用成本外推时，候选集合保留不同机制，最终依赖独立确认。

缺成本时停止受影响的预测，给出共享独立测量的工作变量需求；缺执行语义时修规则，不能补一个专用模板或参数。
同一比较过程中不补完成本又沿用旧排名。准备阶段可以按预算补足共享依据，然后重新开始统一依据下的搜索。
未知点保持未知；只有参数合同或真实执行规则确立不可行时才能标记为不可行。

### 7.4 六项结束后的超时预测补全（10/26 追加）

六项原定搜索及独立确认全部结束后，补算其中因三小时预测截止而未完成的原定候选，再继续有限参照及其他对照。
只使用各项原已提交的 target/workload 配对，不扩大到一万点全空间，不新增候选；已成功的结果直接复用。
六项预测已结束，分别有 44、6、0、0、44、43 项符合条件，共 137 项；第六项独立确认恢复后开始补全。

源 DAG、CPU 校正及独立成本依据沿用原输入，补算不能读取 target trace、正常耗时或评分来改参数。
原本已经有明确成本/结构/执行失败的项，不当作超时缺项自动重试；补算中新出现的失败保留原因，不填零或称预测成功。

这次补全是独立的事后完整性工作：原预算下的排名、筛选及五次确认不重写，
补齐后的预测另表汇总，额外启动、预测次数、墙钟和失败全部单独计费，不免费加入原预算方法比较。

新增耗时在六项结束、缺项数确定后更新，不能为保持原排期删掉这一步。

外部入口是 `research.py complete-predictions --root <研究目录>`；`reference` 阶段也会先完成这一步，
六项未全部确认结束时拒绝提前运行；设备启动失败后的独立恢复完成后，再接续后继队列。
各项的原结果与补算结果合并到独立的 `prediction_completion/<任务>/completion_summary.json`，
只合并预测事实，不复制旧确认结论为新排名的验证证据。

## 8. 实验设计：避免在已看过的结果上证明自己

### 8.1 开发、最终确认与机制对照

| 数据 | 规模与用途 | 隔离要求 |
| --- | --- | --- |
| 现有 ShareGPT 回访、W3、85 次样本 | 开发、回归、定位机制 | 全部视为已见数据，不再称留出 |
| 新开发会话 | 两批，配合已有数据确定搜索参数、输入规模和基线 | 与最终会话不重叠；看过结果后不转入最终批 |
| 新最终会话 | 三批，低复用、高复用和竞争回访各一批 | 先确定会话选择、种子和长度条件，再采 Base；不按预测或收益筛会话 |
| 手工机制序列 | 复用 W3 并按明确变量做成对变化 | 解释因果，不冒充自然会话分布 |

从同一来源数据先划分会话身份，再构造访问序列，防止同一对话的不同轮次跨开发和最终集合。
“竞争回访”等标签由访问顺序和复用关系定义，不能由某项策略的实测表现反推。
这些是由真实文本构造的受控负载，不冒称原始线上到达流量。

起始规模建议每批约 16 个正式请求、每请求 8—32 个输出 token，保留准备及竞争请求。
长短输出在批次间预声明，避免结论仅来自单 token 或几乎没有 Decode 的场景。
通过 workload 的请求数量和输出上限控制规模，不在核心实现里限制 DAG 大小或按节点数砍图。
设备可行性和运行成本可在开发批检查；最终会话只按预声明规则处理，不为收益重选或事后缩短。

三批最终会话在两个资源点组成 **六个主要寻优任务**。这些任务共享适用的独立性能依据，
各自的源 DAG 仍只来自自身 Base；不把一个 workload 的执行结构当成另一个 workload 的源。
这是三天内的独立验证范围，不能冒称已有六批独立会话的统计证据；增加会话数留作后续复现，不拖延本轮闭环交付。

### 8.2 必须有完整实测的有限参照空间

只测模型看好的候选会产生选择偏差，不能据此证明没有漏掉好配置。
在预先指定的竞争回访最终批、紧容量资源点上建立一项完整实测参照，不按初次收益选择这个任务：

```text
页宽 {32,64,128}
× 写策略 {选择性直写,写回}
× 门槛 {128,512 tokens}
× 停止策略 {等待完成, best-effort, timeout(base=0.1s, per_ki=0.1s)}
= 36 个配置
另加同资源原策略参照，共 37 个配置/任务
```

该子空间覆盖页粒度、准入、写入、等待及它们的交互。37 点各做三次有效正常运行，共 111 次有效样本。
它用于得到完整的有限参照表，三次的波动范围全部保留，不据此精确区分接近的配置。
同一实验的最终推荐、同资源参照和强固定策略仍各做五次独立确认，不把三次样本直接当五次；合法复用时需补齐其余样本。
参照另需最多 37 次公开预测，单独计费，不给主方法免费提供额外搜索结果；主方法仍只使用自身预算内已查询的预测。
只在这 37 点上报告真实参照最优、选择损失和排序；不把它称为一万点全空间最优。
有限空间的 regret 比较要求各方法都在相同的 37 点内搜索。大空间搜索若选出了子空间外的配置，
只能报告它与参照最佳的时间差，这个差可以为负，不能冒称全空间 regret。
若某点无法完成，保留失败类型和覆盖缺口，参照称为已测可用集合，不能删除后继续称全空间。
参照采集复用外部示例 `run.py normal --keep-failures`：每次预声明重复只尝试一次，恢复执行也不重试已记录的失败。
不能使用该示例默认的补齐成功样本循环来隐藏本轮的失败风险；失败点仍留在参照表及覆盖统计中。

本方法的候选清单及最终选择须先写出，参照表在独立评估侧保管，揭示次序写入普通运行记录。
最终确认五次可以复用预先隔离、未参与选择的同轮参照样本并补齐五次；候选筛选样本绝不复用。
其他五个任务测预声明短名单、最终配置和强固定策略对照，报告确认收益，不发布未知全空间上的选择损失。

### 8.3 必须正面比较的基线

| 方法 | 它回答的问题 | 公平比较方式 |
| --- | --- | --- |
| 原策略，同资源 | 相比不调优能改善多少？ | 相同模型、token、容量和正式窗口 |
| 固定选择性直写/best-effort | 是否只是把显然较好的策略设成默认？ | 参数在开发批选定，最终批不改 |
| 开发批最好固定配置 | 是否需要为每个场景重新选择？ | 从开发批选择一个配置，跨最终批使用 |
| 一次只改一个变量 | 联合搜索是否有必要？ | 相同预测预算，与完整联合方法比较 |
| 模型＋均匀随机、分层随机 | 新搜索方法是否真比现有方法好？ | 预算包含 self、失败，种子一致 |
| 真实试跑的随机搜索、SMAC | 模型是否值得，而不只是多了一层仿真？ | 相同设备试跑次数及实际墙钟分别比较 |
| 有限空间枚举与完整实测参照 | 离可知的最佳结果有多远？ | 严格标明模型内或 37 点实测口径 |

固定策略可以在开发批按两个资源点分别选择，但不能在最终批按 workload 身份重新选一项；
其页宽、门槛等附属参数也须在开发批确定。这样既不故意削弱固定策略，也不把它偷偷变成最终数据上的逐任务最优。

固定参数的选择另外做小型交叉核对，不扩大四方法比较：候选池由八项开发搜索各一个预测优胜代表、
两个开发闭环的选项、选择性直写/best-effort 的三种页宽×两个门槛（128/512 tokens），以及原策略组成，
按执行参数去重后最多 17 套。每套在两类开发负载、两个资源点上预测，共最多 68 次额外预测，单独计费，
不免费提供给主搜索。每个资源点按两类负载相对同资源参照的预测耗时等权平均，分别选择固定 best-effort 和开发固定配置；
缺失预测不填零，也不称已测最优。报告明确这是开发预测选出的有限候选池基线，不是开发实测的全空间最佳。
参数在最终批开始前写出，此后不按最终负载重新选择；额外预测不增加正常采集预算。
选定的开发固定配置通过 `search.initial_indices` 纳入各最终任务，排在 Base、同资源参照之后，
占用该任务的 96 次预算，并进入正常筛选；不能只在最终结果出来后追加有利的固定对照。
这一步由外部实验脚本 `examples/hicache_search/baselines.py` 组织，最多使用三小时预测墙钟；
复用已完成的同源同参数预测，只查询缺项。它不更新性能数据库或成本系数。
额外查询时优先计算各资源的原策略参照，避免墙钟预算结束后已有候选却缺少比较分母；其余缺项仍保留未知。
搜索方法仅在联合邻域于两个开发任务都不增加实际查询数、不恶化模型内最小耗时，且至少一项更好时采用联合邻域，
否则使用分层随机；该规则不等于证明实际收益或总调优时间更好。

SMAC 是现有的通用贝叶斯配置优化方法，应优先用成熟实现作为基线，不重新编写一套优化库。
是否引入它作为实验依赖，要与 modeling 的正式依赖分开说明。
[SMAC3，JMLR 2022](https://www.jmlr.org/papers/v23/21-0888.html)。

真实黑盒基线可以按其定义用自己的搜索试跑结果选择下一点；这些数据只进入该基线的独立搜索状态，
不进入本项目成本数据库、predictor 或主方法，也不能读取最终确认样本。
这与“最终独立评分不得回流模型”并不冲突，不放宽原有数据隔离合同。

基于已测参照表的算法回放只评价选点。每次读取一个三次均值，应在虚拟预算中计三次样本成本，
不得让黑盒基线免费获得重复均值、主方法却按一次试跑计费；也不把回放墙钟当成真实调优用时。
算法波动使用预声明的五个种子，优先在有限参照任务离线比较，不为画曲线重复全部大图预测。
离线比较模型排序后筛选、均匀随机和真实 SMAC ask/tell，每种子最多查询六个配置，均先查询同资源参照。
一次揭示三次均值计三份样本，预算点为 3/6/9/12/15/18；模型排序另外计入 37 次独立预测及实际耗时。
三次中有失败或缺项的配置保留在查询流和覆盖统计中，但不能参与有效均值或推荐；参照不完整时只报告完整可用子集上的选择损失。

另选一个事先指定的最终任务，主方法与真实黑盒基线各用一个预声明种子做实际闭环：
各最多六次筛选运行，随后对最终选定配置及同资源参照各做五次新确认。
预测耗时只计入主方法，黑盒方法自身选点开销也保留；这组最多 32 次有效正常运行，避免只用查表估算实际代价。
主方法若与本轮同输入、同种子的已声明运行重合，可共用同一次实际闭环并计一次账，不拿缓存查表伪装重新运行。
真实黑盒优先 SMAC；若成熟依赖接入在两小时内仍不能工作，先用已有随机搜索完成实际对照，明确 SMAC 未执行。
三天不为安装优化库或重复种子延误主线；单种子实跑不作为随机算法普遍优越的证据。

SMAC 仅作为研究依赖，使用独立的 `build/research/smac` 环境；正式 modeling 环境不增加该依赖。
外部实验入口为 `examples/hicache_search/blackbox.py`，读取本轮声明的 ConfigSpace、搜索请求和正常预算，
复用现有采集、token 回放及正式 HTTP 窗口；不调用预测器或训练成本模型。筛选失败单列，不能填成零耗时；
SMAC 内部的失败惩罚不计作真实观测。最终确认使用新样本，样本范围分离不等同于置信区间。
失败惩罚取预声明的确认采集墙钟预算，保持为有限值；当前 SMAC 对无穷大响应的变换会产生 NaN。
该值仅供优化器处理失败，原始观测仍为缺失，不进入实际耗时、收益、精度或成本模型。
最终候选一次失败后保留该失败并停止其余重复，继续完成参照；不足五次的候选不报告确认均值或收益。
参照自身失败则报告测量不完整，不能给出已确认推荐，也不通过自动重试覆盖失败。
后续实验由外部示例 `research.py complete-predictions|reference|controls --root <研究目录>` 组织，复用已有入口，不进入预测核心。
它在六项主任务确认结束后执行，先补超时预测再做有限参照；按实际 ledger 扣除整轮采集预算，固定对照只复用同任务五次完整最终确认样本，
相同执行参数的对照角色共用采集，筛选样本不复用。

### 8.4 分离的三项诊断与最少消融

实验报告继续区分源 DAG 静态回放、目标结构对照和完整 HTTP 精度。
源回放不替代正常时间；少量目标结构对照不替代整空间结构证明。
从准备阶段的独立开发输入中选页宽、部分发布/取消、淘汰备份拒绝等代表，检查正式语义，不能用 E2E 抵消结构问题。

三天优先完成前两项消融，使用同一任务、输入、成本依据和预算；后两项在有现成接口和余量时追加：

1. 去掉联合变量改动，只做单变量搜索：观察交互是否影响推荐。
2. 模型第一名直接确认，对照机制不同的短名单再筛选：观察额外试跑是否值得。
3. 固定页大小，对照搜索页大小：区分页粒度的贡献与策略贡献。
4. 只看 I/O 工作变化，对照含 Prefill/Decode 的完整模型：仅作为独立的决策诊断，不把残缺模型成绩混进正式精度。

第四项如无自然复用入口，不为它重建一套旧 predictor；在少量有完整操作明细的机制输入上做静态诊断，
标注诊断性质。不能声称把计算冻结后的结果就是完整 target 性能。
Base 敏感性先在一个已有代表负载上替换一个合法策略 Base，满足同 token/资源合同的既有资产可复用。
这只是一项锚点检查，不冒称完成多 Base 的全面验证；扩大 Base 组合不阻塞三天交付。
不引入按 Base 身份分支的修正系数。

## 9. 衡量什么，怎样解释

### 9.1 首要指标是选择质量

| 指标 | 定义或使用方式 |
| --- | --- |
| 同资源收益 | `1 − T_selected / T_reference`，同时给秒数及原始样本 |
| 选择损失 regret | `(T_selected − T_best_reference) / T_best_reference`；仅对相同、完整实测的有限空间计算 |
| 胜过最好固定策略的程度 | 在最终会话上逐任务比较，固定策略只由开发批选定 |
| 固定策略胜出/推荐反转 | 标明哪些场景确实需要不同配置，哪些配置差异无法区分 |
| 无需调优识别 | 不敏感负载或无法确认收益时，是否保留原配置 |
| 失败与未知率 | 参数不支持、缺成本、预测执行失败、真实不可行、资源冲突分别记录 |

已测最优本身也有噪声，最小样本均值不是无噪声真理。对范围重叠且差距很小的配置保留并列或不确定结论。
相反，即使推荐收益很大，也不能省略它与“最好固定策略”的比较。

### 9.2 精度与统计口径

完整 HTTP 预测精度沿用现行规则：总体及逐 Base WAPE ≤ 3%、P90 APE ≤ 5%，cross 优于沿用 Base 正常时间。
逐 workload、逐 target、self 分开，最大 APE ≤ 6% 作为附加努力目标，不替代原有门槛。
只对实际选中且有正常真值的集合发布分数，不把它外推成整个一万点空间的精度。

最终固定五次重复，同一轮中配置采用预声明轮转或随机顺序，新服务、新缓存初态、相同准备及实际 tokens。
保留所有有效慢样本。硬件被其他任务占用的处理规则在采集前确定，不能看见结果慢才删样本；无效尝试仍保留并计费。

研究统计以会话批次/寻优任务为主要单位，不能把三批会话的五次重复当成 15 个独立负载。
同一会话的两个资源点也相关，汇总区间时应按会话批次成组，而不是当成六批独立会话。
给逐任务差值、范围和配对结果；需要区间时按任务/运行块的层级重采样，并说明仅三批会话造成的精度限制。
五次样本范围不是置信区间，小样本结果不承诺可靠尾部延迟。
3% 可作为预声明的实际差异关注量级，但不是模型误差上界，也不能用于事后隐藏更小的负收益。

### 9.3 必须算清楚总调优成本

分别记录：代表请求/token 准备、Base、CPU 校正、独立性能维护、源图准备、预测搜索、筛选试跑、最终确认、失败、资源等待和重配置。
搜索墙钟包含源准备，不能重复求和；试跑的启动、暖机和清理计入调优成本，HTTP 正式窗口单独计性能。
冷启动与已有性能库/已有 Base 的热启动分别给结果，平台库的历史成本不能默认记零。

除设备采样数外，还要给达到同一选择损失所用的墙钟、CPU/设备占用及可复用范围。
只少测了配置但总成本更高时，明确写出“减少设备试跑，但尚未减少总体调优代价”。

用一个完整代表窗口作为复用单位，报告近似收支平衡次数：

```text
N_break_even = ceil(一次调优及切换成本 / (原配置每窗口耗时 − 新配置每窗口耗时))
```

收益非正时不计算有限回本次数。缓存暖机、工作量变化和成本摊销假设都要说明；
不能把离线短序列的节省直接承诺成长期线上收益。

旧四点未知的排查限定在第一天的公共缺口工作内，不作逐格拟合或无限调试；尚未解释的点继续未知，交付须明确不完整性。

不能在三天中同时交付三项完整实测参照、六批新会话和多种子实际闭环，故本轮明确减少这些重复证据。
不削减一万点主空间，也不取消独立最终确认或强固定策略对照；尚未采齐不得写成验收完成。

## 13. 验收标准：流程完成和研究成立分开

### 13.1 自动流程完成

- 用户从一份任务声明进入，不手填候选正常 suite；预测、筛选、确认及输出可完成，支持保留已完成输入和累计预算的恢复。
- 原始模型推荐与正常确认选择分别保留；最终评分不回流模型，正常采集和性能准备的数据隔离明确。
- 明确声明的页宽/策略分支没有已知却未解释的语义缺口；未知点不伪装不可行或极慢。
- 每个正式任务给出已确认建议、保留原配置或缺口原因；没有证据时不伪造一个“成功推荐”。
- 六项结束后逐项执行原定超时预测补全，另列覆盖、真实失败及额外耗用；未完成项不声称成功，不改写原预算下的选择。
- 所有结果均保留完整 HTTP 口径、实际资源、失败、波动和成本来源；三阶段诊断的证据范围清楚。

### 13.2 研究目标

以下是执行前提出的目标，不是允许调整输入或门槛来保证通过的承诺：

1. **非平凡性**：在至少两种预声明场景中观察到可重复的不同选择或参数交互，并解释真实工作变化。
   若同一个固定策略始终足够，应否定“需要复杂按场景搜索”的假设，收缩贡献范围。
2. **选择质量**：有限实测参照任务的选择损失争取 ≤3%，超过 6% 作为需要重点解释的较大损失，保留测量不确定性和原始数据。
   一项参照不足以报告跨负载的普遍 regret 保证；其他任务只报告已测集合结果，不补造全空间 regret。
3. **强基线价值**：新最终会话上与开发批最好固定配置、固定 best-effort、真实黑盒基线比较，SMAC 未执行时明确标注。
   要主张优越性，须有逐任务结果和足以区分的配对证据；只胜过原等待策略还不够。
4. **调优代价**：争取在相近选择质量下减少至少一半真实筛选运行；同时报告全部准备、预测和确认开销。
   没有总体时间优势时，诚实区分设备节省、复用收益与首次使用成本。
5. **预测精度**：沿用 WAPE/P90 门槛，不因搜索收益较大就忽略精度失败，也不因总体 PASS 就声称每个操作都准。
6. **适用范围**：对新会话、两个资源点和 Base 敏感性分别给结论；换模型/平台、生产并发与在线动态策略不提前宣称完成。

流程即使跑通，若没有超过简单固定策略或无法收回调优成本，研究结论仍应写为“完整闭环已实现，但额外寻优价值未证实”。
负结果也是本轮必须交付的结果，不能通过重新命名指标代替。

## 14. 最终交付与汇报叙事

三天交付一套有范围的自动寻优入口、一份独立研究报告和前五组可直接用于汇报的核心图表；第六组资源前沿为附加项：

1. **为什么需要搜索**：同资源下的策略交互、页粒度影响和负载之间的选择变化。
2. **模型是否帮忙**：纯模型首选、试跑选择、强固定策略及有限实测参照的对照。
3. **少试多少次**：设备试跑预算—选择损失曲线，区分离线回放和实际闭环。
4. **换会话是否有效**：三批最终会话、两个资源点的逐任务收益和失败，并明确独立批次数有限。
5. **总成本是否值得**：冷/热启动调优成本、设备占用及回本次数。
6. **资源如何取舍**：同资源策略收益与资源—耗时前沿分开展示，并说明未验证范围。

主叙事是“存在需要选择的真实取舍 → 模型预测这些取舍 → 少量运行完成选择 → 新输入验证 → 代价和边界”。
不以新增文件数、模型条目数、预测格子数或复杂算法名称作为主要贡献。
报告收口后将稳定结论并入主文档，保留可复现输入与必要证据，避免多份文档长期重复维护同一状态。

## 15. 与相关工作的关系

以下文献用于界定研究位置，不能直接当成本项目已有能力或新颖性证明。查阅日期：2026-10-25。

- [Vidur，MLSys 2024](https://proceedings.mlsys.org/paper_files/paper/2024/hash/b74a8de47d2b3c928360e0a011f48351-Abstract-Conference.html)：
  通过性能建模与仿真研究推理配置。它说明“仿真支持配置探索”已有成熟先例；本项目要证明的是 HiCache 引起的结构与计算变化能否支持有价值的选择。
- [Dooly](https://arxiv.org/abs/2605.07985)：从操作输入维度的来源出发，复用延迟数据库并减少重复 profiling。
  可借鉴的是性能依据的共享和来源清楚；本轮不以重写成 Dooly 或学习一个新平台作为前提，也不修改另一仓库。
- [SMAC3，JMLR 2022](https://www.jmlr.org/papers/v23/21-0888.html)：成熟的贝叶斯配置优化基线。
  用它检查“已有预测模型是否比直接黑盒调参更值得”，不把替换搜索器本身当成系统研究贡献。
- [SGLang HiCache 设计](https://docs.sglang.io/docs/advanced_features/hicache_design)：提供分层缓存的机制背景。
  在线文档与本地修改后的实现可能不同，尤其是超时、发布和资源占用；本轮执行语义以实际代码及正式诊断为准，不顺手升级上游。

初步可争取的研究定位是：**在资源约束下，利用执行结构变化预测来减少分层 KV 缓存调优的真实试跑，并说明何时值得调、何时无需调。**
是否形成论文贡献，要由固定策略对照、独立会话、真实预算及机制证据共同决定。
